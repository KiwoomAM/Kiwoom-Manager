# 바로가기 메서드는 표에서 만들어 낸다

`VDBManager` 는 하위 클라이언트의 메서드를 같은 인자로 한 벌 더 갖는다. 이 편의는
지킬 만하다 — 일부만 빼면 "어떤 것은 `handler.` 로 되고 어떤 것은
`handler.collection.` 이어야 한다" 는 외워야 할 경계가 생긴다. **문제는 미러링이 아니라
손으로 미러링하는 것이다.** 시그니처가 두 파일에 살면 한쪽이 뒤처지고, 뒤처진 인자는
예외도 경고도 없이 조용히 기본값으로 떨어진 채 나간다.

그래서 사람이 관리하는 것은 `vdb_manager/_shortcuts.py` 의 표뿐이고, 메서드 본문은
`scripts/generate_shortcuts.py` 가 원본 시그니처에서 만들어 `handler.py` 에 써 넣는다.
테스트가 "다시 생성해도 달라지지 않는다" 를 본다(`ruff format --check` 와 같은 방식).

## 왜 `__getattr__` 이 아닌가

`__getattr__` 로 넘기면 두 벌이 아예 사라지고, 중간 프레임이 없어져 경고의
`stacklevel` 문제까지 풀린다. 그래도 고르지 않았다.

- **정적으로 보이지 않는다.** 에디터 자동완성도 타입 검사도 `dir()` 도 비고, 오타는
  런타임 `AttributeError` 가 된다. 이 SDK 는 외부 에이전트가 GitHub 에서 가져다 쓰는
  것을 전제하므로, 무엇을 부를 수 있는지 알아내는 통로를 막는 대가가 크다
- **두 벌이 완전히 사라지지도 않는다.** 바로가기 28개 중 9개는 이름이 원본과 달라
  (`handler.hybrid_search` → `hybrid.search`) 어느 방식을 골라도 대응표가 필요하다
- **`stacklevel` 이점은 이제 쓸 자리가 없다.** 그 문제를 만들던 deprecated `upsert()`
  를 같은 변경에서 삭제했고, 남은 경고 하나(슬래시 든 필드의 index)는 메시지가 대상을
  이름으로 지목해 줄 번호가 빗나가도 무엇을 고칠지 분명하다

데코레이터에 `ParamSpec` 을 얹는 안도 보았다. pyright 는 시그니처를 보지만 에디터마다
결과가 갈리고, 중간 프레임이 남아 `stacklevel` 은 그대로이며, 읽는 사람이 타입 시스템의
중급 문법을 알아야 한다.

## 빈칸은 이유와 함께 등록한다

미러링하지 않는 것은 `NOT_MIRRORED` 에 이유를 적어야 하고, 등록도 미러링도 없는
메서드가 있으면 테스트가 실패한다. 비대칭을 없애는 것이 아니라 **적어 두는 것**이
목적이다 — 이유 없는 빈칸은 다음 사람이 실수인지 결정인지 구별할 수 없다.

지금 등록된 것은 별칭들과 `is_ready` 다섯이다. `is_ready` 는 하위 클라이언트마다
`/v1/admin/status` 를 따로 치므로 다섯을 열면 소비자가 왕복을 다섯 번 하게 유도된다.
`status()` 가 한 번에 넷을 다 준다.

## 대가

생성된 코드가 레포에 남아 `handler.py` 는 여전히 길다. 줄 수를 줄이는 것이 목적이
아니라 **사람이 손으로 맞추는 일을 없애는 것**이 목적이므로 받아들인다. 대신 생성
구간에 "손으로 고치지 말 것" 을 적어 두고, 손으로 고치면 테스트가 잡는다.
