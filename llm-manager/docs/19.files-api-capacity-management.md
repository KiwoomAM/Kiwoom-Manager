## 1. 배경

Gemini Files API 프로젝트 할당 **저장 한도 20GB**. 현재 llm-manager는 자연 만료(Gemini 48h TTL + Redis 동적 TTL)에만 의존 중이라, 단기간에 대량 업로드가 들어오면 한도를 초과해 새 업로드가 실패한다.

**문제**
- Files API 분기 C(신규 업로드, [resolver.py `_upload_and_cache_file`](../service/app/logic/file_processing/resolver.py#L174))에서 `upload_file` / `upload_pdf_parts` 호출 직전 capacity 체크 없음
- 한도 초과 시 SDK가 raise하지만, 운영자가 능동적으로 정리할 수단 없음 → 48h 대기

**목표**
- llm-manager가 업로드 직전 Redis 기반으로 Gemini 누적 용량을 추정하고, **임계값 초과 예상 시 오래된 것부터 자동 정리** 후 업로드 진행
- 정리 대상: Files API 파일 + 그 파일을 참조하는 context_cache 동시 정리(연쇄 삭제) — stale URI 참조 방지

### 2.2 Redis 동적 TTL — FIFO 해석 변경

Phase A 도입 이후 [`compute_files_api_ttl`](../service/app/logic/file_processing/cache_store.py#L115)이 적용되어, `files_api:{checksum}` 키마다 TTL이 다르다.

- **동적 TTL** = `Gemini expiration_time - now - buffer(1h)` (clamp: floor 1h, ceiling 47h)
- 결과: 모든 키 47h 균일이라는 07.md §8.4의 전제는 무효

**새 해석**: 잔여 TTL이 짧을수록 = Gemini 만료가 임박한 키 = 가장 먼저 사라질 자원. **이걸 먼저 정리하는 것은 실질적으로 FIFO에 근사**하고, 가장 잃을 게 적은 자원부터 정리하는 정책이라 합리적이다.

### 3.1 신설 (`FileCacheStore` 클래스 메서드 + 모듈 위임 함수)

| 함수 | 시그니처 | 역할 |
|---|---|---|
| `scan_files_api_keys` | `() -> Iterator[str]` | `file_cache:files_api:*` SCAN, prefix·suffix 제거 후 checksum yield |

### 3.2 BaseJsonStore protected 헬퍼 — 사용 가능 확정

`cache_store.py`가 이미 의존하는 `_make_key` / `_get_json` / `_set_json` / `_delete` ([cache_store.py:42-74](../service/app/logic/file_processing/cache_store.py#L42-L74)) 외에, 본 모듈에 필요한 다음 2개도 redis-handler `BaseJsonStore`에 노출돼 있다 — 추가 작업 불필요.

## 4. 전체 파이프라인

### 4.1 trigger 위치

[`_upload_and_cache_file`](../service/app/logic/file_processing/resolver.py#L174)에서 `upload_file` / `upload_pdf_parts` 호출 직전 ([resolver.py:197 바로 위](../service/app/logic/file_processing/resolver.py#L197)).

```python

tmp.write(fi.data); tmp.close()
try:
    # ↓ 신설: 업로드 직전 capacity 보장
    await ensure_files_api_capacity(fi.file_size)

    if fi.mime_type == "application/pdf" and fi.file_size > _PDF_SPLIT_LIMIT:
        refs = await upload_pdf_parts(tmp.name)
    else:
```

> **size 인자 근거**: split PDF여도 Redis에 저장되는 `file_size`는 원본 단일 합본 크기 ([resolver.py:225](../service/app/logic/file_processing/resolver.py#L225)). Gemini 실제 저장량과 약간의 오차(분할 페이지 재구성 오버헤드)는 §4.3 안전 마진으로 흡수.

### 4.2 임계값

- **상한**: 19 GB (`CAPACITY_THRESHOLD = 19 * 1024**3`)
- 1GB 안전 마진 사유:
  - 동시 업로드 경쟁 (다른 agent가 동시에 같은 임계값 통과)
  - `file_size` ≠ Gemini 실제 저장 크기 (split PDF 오버헤드, 텍스트 파일 인코딩 차이 등)

### 4.4 context_cache 연쇄 삭제 — 순서와 최적화

**순서**: context_cache **먼저** → files_api **나중에**.

근거: context_cache가 남아있는데 Files API URI를 먼저 지우면 cache 참조가 깨진 URI로 호출돼 런타임 에러. 반대 순서면 cache 참조 시점부터 cache는 무효지만 Files API는 직접 사용 가능.

**최적화 — 1회 SCAN + 메모리 인덱스**:
- 매 checksum마다 `find_context_caches_with_checksum`을 부르면 SCAN O(N²)
- 대신 capacity trigger 시 **1회만 context_cache 전체를 SCAN**하여 `dict[checksum] → [(hash_key, doc), ...]` 인덱스 구축
- 이후 삭제 루프에서 메모리 lookup만 — O(N + M)
- 이 인덱스 함수를 `cache_store`에 별도 헬퍼로 둘지(`build_context_cache_index_by_checksum`) capacity.py 내부에 둘지는 §5에서 결정

### 4.5 split PDF 처리

한 checksum이 복수 URI(`split: True, uris: [u1, u2, ...]`)인 경우:
- `files_api:{checksum}` 키 하나에 파트 URI 모두 묶여있음 ([resolver.py:227](../service/app/logic/file_processing/resolver.py#L227))
- §4.3 ⑤(b)의 `for uri in doc["uris"]` 루프로 자동 처리. 한 키 = 한 번의 삭제로 파트 전체 정리
- 부분 삭제 / 부분 누락 케이스 없음

### 4.6 _uri_to_name 변환

Gemini Files API URI는 `https://generativelanguage.googleapis.com/v1beta/files/abc123` 형식. `delete_file(name)`은 `files/abc123` 형태를 받음.

```python
def _uri_to_name(uri: str) -> str:
    # ".../files/abc123" → "files/abc123"
    idx = uri.find("/files/")
    if idx == -1:
        raise ValueError(f"Files API URI 아님: {uri}")
    return uri[idx + 1:]   # "files/abc123"
```

**보강**: llm-handler가 `name` 추출 유틸을 노출하면 그걸 쓰는 게 안전. 없으면 capacity.py 내부 private 헬퍼.

## 5. 모듈 상세

### 5.1 신설: `service/app/logic/file_processing/capacity.py`

```python
"""Files API 용량 관리 — 19GB 임계 초과 시 오래된 키부터 자동 정리.

trigger: _upload_and_cache_file이 upload_file/upload_pdf_parts 호출 직전 invoke.
"""

from __future__ import annotations
import logging
from collections import defaultdict

from llm_handler import aio as llm_handler_aio

from app.core.errors import FileUploadError
from app.logic.file_processing import cache_store

logger = logging.getLogger(__name__)

CAPACITY_THRESHOLD = 19 * 1024**3   # 19 GB (1GB 안전 마진)


async def ensure_files_api_capacity(required_size: int) -> None:
    """업로드 직전 Files API 누적 용량을 점검하고, 초과 예상 시 정리.

    Args:
        required_size: 새로 업로드할 파일 크기(바이트). split PDF여도 원본 합본 크기.

    Raises:
        FileUploadError: 정리 후에도 임계값 미달 못 함 (need_to_free > freed).
        CacheError: Redis 조회/삭제 실패 (cache_store가 raise).
    """
    entries, total = _collect_files_api_entries()

    if total + required_size <= CAPACITY_THRESHOLD:
        return

    entries.sort(key=lambda e: e[0])  # 잔여 TTL 적은 순
    need_to_free = (total + required_size) - CAPACITY_THRESHOLD
    cc_index = _build_cc_index_by_checksum()

    freed = await _evict_until_freed(entries, cc_index, need_to_free)

    if freed < need_to_free:
        raise FileUploadError(
            f"Files API 용량 확보 실패: required={required_size}, "
            f"freed={freed}, need={need_to_free}"
        )


def _collect_files_api_entries() -> tuple[list[tuple[int, str, dict]], int]:
    """SCAN으로 모든 files_api 키 수집 + 누적 용량 합산."""
    entries: list[tuple[int, str, dict]] = []
    total = 0
    for checksum in cache_store.scan_files_api_keys():
        doc = cache_store.find_files_api(checksum)
        # SCAN-GET 사이 만료 → doc None. get_ttl도 -2(키 없음) 가능. 둘 다 skip.
        if not doc:
            continue
        ttl = cache_store.get_ttl_files_api(checksum)
        total += doc.get("file_size", 0)
        entries.append((ttl, checksum, doc))
    return entries, total


def _build_cc_index_by_checksum() -> dict[str, list[tuple[str, dict]]]:
    """context_cache를 1회 SCAN하여 checksum → [(hash_key, doc)] 인덱스 구축."""
    idx: dict[str, list[tuple[str, dict]]] = defaultdict(list)
    for hash_key, cc_doc in cache_store.scan_context_caches():
        for cs in cc_doc.get("file_checksums", []):
            idx[cs].append((hash_key, cc_doc))
    return idx


async def _evict_until_freed(
    entries: list[tuple[int, str, dict]],
    cc_index: dict[str, list[tuple[str, dict]]],
    need_to_free: int,
) -> int:
    freed = 0
    for ttl, checksum, doc in entries:
        if freed >= need_to_free:
            break
        try:
            await _evict_one(checksum, doc, cc_index.get(checksum, []))
            freed += doc.get("file_size", 0)
        except Exception:
            logger.exception("용량 관리 삭제 실패: %s", checksum[:16])
            continue
    return freed


async def _evict_one(
    checksum: str,
    files_api_doc: dict,
    cc_entries: list[tuple[str, dict]],
) -> None:
    # (a) context_cache 연쇄 삭제 (Gemini → Redis)
    for hash_key, cc_doc in cc_entries:
        name = cc_doc.get("cached_content_name")
        if name:
            try:
                await llm_handler_aio.delete_cache(name)
            except Exception:
                logger.warning(
                    "delete_cache 실패: %s — Files API 삭제는 계속", name,
                )
        cache_store.delete_context_cache(hash_key)

    # (b) Gemini Files API 파트 삭제
    for uri in files_api_doc.get("uris", []):
        name = _uri_to_name(uri)
        try:
            await llm_handler_aio.delete_file(name)
        except Exception:
            logger.warning("delete_file 실패(멱등 가정): %s", name)

    # (c) Redis files_api 키 삭제
    cache_store.delete_files_api(checksum)


def _uri_to_name(uri: str) -> str:
    idx = uri.find("/files/")
    if idx == -1:
        raise ValueError(f"Files API URI 아님: {uri}")
    return uri[idx + 1:]
```

### 5.2 cache_store.py 추가분

`FileCacheStore` 클래스에 추가:

```python
def scan_files_api_keys(self) -> Iterator[str]:
    """file_cache:files_api:* SCAN하여 checksum yield."""
    pattern = self._make_key("files_api", "*")  # "file_cache:files_api:*"
    prefix_len = len(self._make_key("files_api", ""))   # "file_cache:files_api:"
    for key in self._scan_iter(pattern):
        yield key[prefix_len:]

def get_ttl_files_api(self, file_checksum: str) -> int:
    """Redis TTL 조회. -2: 없음, -1: 영구."""
    return self._ttl(self._make_key("files_api", file_checksum))

def scan_context_caches(self) -> Iterator[tuple[str, dict]]:
    """context_cache 전체 SCAN (hash_key, doc) yield. 용량 관리 시 1회 호출."""
    pattern = self._make_key("context_cache", "*")
    prefix_len = len(self._make_key("context_cache", ""))
    for key in self._scan_iter(pattern):
        doc = self._get_json(key)
        if doc is None:
            continue
        yield key[prefix_len:], doc
```

모듈 함수 위임 추가도 동일 패턴 ([cache_store.py:171-206](../service/app/logic/file_processing/cache_store.py#L171-L206)).

> ✅ `_scan_iter` / `_ttl` signature는 redis-handler `BaseJsonStore` 노출분과 일치 확인 완료 (§3.2 참조).

## 6. 에러 처리

| 상황 | 대응 |
|---|---|
| 여러 agent 동시 capacity 체크 → 중복 삭제 시도 | "없다고 가정" 범위. `delete_file` / `delete_cache`는 404 멱등(SDK 정책) — 경고 로그 후 계속 |
| SCAN 중 Redis 연결 실패 | `cache_store`가 `CacheError` raise → 업로드 중단. 용량 관리 실패 상태로 업로드 강행 안 함 |
| `delete_file()` 실패 (404 외) | 경고 로그 + 다음 checksum으로 skip. `freed` 누적 안 됨 → 한도까지 돌다 부족 시 `FileUploadError` |
| `delete_cache()` 실패 | 경고 로그 + Files API 삭제는 계속 진행. stale Gemini context cache는 TTL로 자연 만료 |
| `_uri_to_name` ValueError (URI 형식 비정상) | 로그 + skip. 키 자체는 보존 (수동 조사 가능하도록) |
| 정리 후에도 freed < need_to_free | `FileUploadError(502)` raise — 시스템 운영자 개입 신호 |
| Gemini `list_files` API 사용 안 함 | SCAN 기반이므로 list_files 연동 불필요. SDK에 `list_files` 노출돼있더라도 본 모듈은 사용 안 함 |
| **SCAN duplicate yield** (Redis hash rehash 등) | **dedup 미시행**. 동일 checksum이 두 번 yield되면 `total`이 over-estimate (보수적 방향 — 조기 evict 트리거). 1GB 안전 마진 안에 흡수. 두 번째 evict 시도는 cache_store가 이미 키 삭제 → 무해. 운영 정합성 영향 없음 |
| **Redis 부분 장애 → 메모리 백엔드 SCAN 폴백** ([base_store.py](../../redis-handler/redis_handler/base_store.py)) | **방어 완료** — `_collect_files_api_entries` / `_build_cc_index_by_checksum`에서 `scan_*` 호출 시 `strict=True` 옵트인. Redis 미연결/mid-scan 실패 시 redis-handler가 `RedisHandlerError` raise → `CacheError(502)`로 매핑되어 capacity 체크가 명시적으로 abort. 20GB under-estimate 경로 차단 |

**재시도 정책**: llm-manager 자체에서 재시도 안 함. SDK(handler) 측 책임.

## 8. 사용 예시

### 8.1 정상 — capacity 여유 충분

```
누적 18.0 GB, required 50MB → 18.05 GB ≤ 19 GB → 그대로 업로드
```

### 8.2 임계 초과 — 정리 후 업로드

```
누적 18.95 GB, required 100MB → 19.05 GB > 19 GB
need_to_free = 50MB
정렬 후 첫 entry: TTL 1200초, file_size 80MB
  → context_cache 매칭 1건 발견 → delete_cache → delete_context_cache
  → uris 1개 → delete_file
  → delete_files_api
  → freed=80MB > need_to_free=50MB → break
업로드 진행
```

### 8.3 Split PDF 케이스

```
files_api:{cs} = {file_size: 200MB, uris: [u1, u2, u3], split: True}
정리 시: u1, u2, u3 각각 delete_file → 한 번의 freed 누적 200MB
```

### 8.4 정리 실패 — 한도 미달

```
누적 19.5 GB, required 1 GB → need_to_free = 1.5 GB
이용 가능한 entries 합계가 1 GB만 → freed=1 GB < need=1.5 GB
→ FileUploadError("Files API 용량 확보 실패: required=1GB, freed=1GB, need=1.5GB")
```
