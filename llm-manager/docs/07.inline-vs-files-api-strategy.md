# inline vs Files API 전략 (파일 전달 파이프라인)

> `file_manager` 분리([file-manager-separation.md](09.file-manager-separation.md)) 이후
> **받은 파일을 Gemini에 어떻게 전달할지** 결정하는 문서.
> SDK는 파일 bytes를 보내지 않으며, Service가 file_manager로부터 bytes를 수급한다.

## 1. 배경 / 문제 정의

Phase 3 설계는 **SDK 중심 분기**였다:
- `≤20MB` → SDK가 base64 inline으로 body에 포함
- `>20MB` → SDK가 `/v1/files`로 사전 업로드 후 Service는 Redis에서 URI 조회

이 분기는 다음 전제 위에 있었다:
1. SDK가 **로컬 파일**에 접근 가능
2. SDK가 **크기/타입 판단**을 직접 수행

`file_manager` 분리로 **두 전제 모두 무효화**된다:
- Service는 파일 bytes가 없는 상태로 요청을 받음 (`FileMeta` 리스트만)
- 필요할 때 `file_manager`로부터 bytes를 HTTP로 수급
- SDK는 얇은 HTTP 래퍼로만 기능

따라서 **분기·캐시·업로드 로직 전부 Service 내부로 이전** 및 재설계해야 한다.

이 문서는 분기 규칙, 캐시 활용, 파일 처리 흐름만 다룬다.
인터페이스 변경(DTO, SDK 얇아짐 등)은 문서 ①에서 결정됨.

## 2. 사전 정보

### 2.1 Gemini inline 제한 (모달리티별 — 재확인)

Google 공식 문서를 모달리티별로 확인한 결과:

| 모달리티 | 요청 body **전체** 제한 | 개별 파일 제한 | 출처 |
|---|---|---|---|
| 오디오 | **20 MB** (prompt + system + inline files 합산) | 없음 (9.5시간 길이 한도) | [audio docs](https://ai.google.dev/gemini-api/docs/audio) |
| 이미지 | **20 MB** (prompt + system + inline bytes 합산) | 명시 없음 | [image-understanding docs](https://ai.google.dev/gemini-api/docs/image-understanding) |
| PDF | 명시 없음 (일반 100MB 적용 추정) | **50 MB** per file | [document-processing docs](https://ai.google.dev/gemini-api/docs/document-processing) |
| 비디오 | **20 MB** (≤20MB inline 지원, 초과는 Files API) | 없음 (1~3시간 길이 한도) | [video docs](https://ai.google.dev/gemini-api/docs/video-understanding) |

**중요**: 이미지/오디오 20MB는 **개별 파일 한도가 아닌 요청 body 전체 한도**. 여러 파일 + 프롬프트 + system instruction을 모두 합산한 값이 20MB를 넘으면 Files API 필수.

### 2.2 캐시 TTL

| 캐시 | TTL | 비고 |
|---|---|---|
| Gemini Files API URI | **48시간** | 만료 후 404 발생 → 재업로드 필요 |
| Gemini Context Cache | 사용자 설정 TTL (기본 1h) | 토큰 90% 할인 but 저장비 발생 (시간당 4회 미만이면 손해) |
| Redis `files_api:{checksum}` | 47시간 (안전 마진) | Gemini 48h보다 1h 짧게 |
| Redis `context_cache:{hash}` | 사용자 TTL과 동일 | Gemini Context Cache와 동기화 |

(※ 역인덱스 `files_api_uri:{uri}`는 이전 설계에서 고려됐으나 SCAN+TTL 기반 Phase B 용량 관리로 **채택 안 함**. 개념: `docs/concepts.md` "역인덱스")

### 2.3 base64 오버헤드
원본 × 약 1.33배. 원본 20MB → base64 ~26.6MB. 요청 body 한도 계산 시 주의.

### 2.4 지원 mime 화이트리스트

Gemini API 공식 문서에서 확인한 지원 mime 타입. 이 목록에 없으면 거부(§4.5).

| 모달리티 | 확정도 | mime 목록 |
|---|---|---|
| 이미지 | ✅ 공식 | `image/png`, `image/jpeg`, `image/webp`, `image/heic`, `image/heif` |
| 오디오 | ✅ 공식 | `audio/wav`, `audio/mp3`, `audio/aiff`, `audio/aac`, `audio/ogg`, `audio/flac` |
| 문서 (비전 지원) | ✅ 공식 | `application/pdf` |
| 문서 (텍스트 추출만) | ⚠️ 보수적 | `text/plain`, `text/html`, `text/csv`, `text/markdown`, `text/xml`, `application/json`, `application/xml` |
| 비디오 | ⚠️ 보수적 | `video/mp4`, `video/mpeg`, `video/mov`, `video/avi`, `video/x-flv`, `video/webm`, `video/3gpp`, `video/mpg`, `video/wmv`, `video/x-ms-wmv` |

> "보수적"으로 표시된 항목은 공식 문서에 명시적 목록은 없으나 예시/통상적으로 지원되는 포맷. Gemini가 거부하면 에러가 상위로 전파됨.
> 
> 문서 중 PDF만 **비전 지원**(이미지·표·레이아웃 인식). 나머지 텍스트계는 **텍스트 추출만**되어 시각 요소(차트·포맷)가 손실됨 — 호출자 인지 필요.
> 
> **미확인 (TBD)**: Gemini Files API가 `text/*` / `application/json` 등 텍스트계를 업로드 형태로 받는지 공식 문서에서 확인되지 않음. 현재 설계는 텍스트도 Files API 경로로 흘러갈 수 있으나, 미지원이면 런타임 에러로 전파됨. 향후 확인 후 "텍스트는 inline 전용" 정책 추가 가능.
> 
> **오디오 9.5시간 제한**: 파일 bytes만으론 재생 길이 산출 불가 → **사전 체크 불가**. 업로드 후 Gemini가 거부하면 런타임 에러로 전파.

## 3. 3계층 캐시 구조

llm-manager가 관여하는 캐시 전체 그림.

| # | 저장소 | 키 | 값 | 목적 | 관할 |
|---|---|---|---|---|---|
| 1 | file_manager DB | `(file_name, file_mtime, file_size)` 튜플 | metadata 블록 전체 (file_name, file_mtime, file_size, file_path, mime_type, extension) | 같은 파일 중복 저장 방지 | file_manager |
| 2-A | Redis `files_api:{checksum}` | llm-manager 자체 계산 checksum | Files API URI (+ size, PDF split 정보) | 48h 내 재업로드 방지 | llm-manager |
| 2-B | Redis `context_cache:{hash_key}` | sha256(checksums + model + system) | Gemini Context Cache name (+ file_checksums 리스트) | 같은 파일+모델+system으로 여러 프롬프트 시 토큰 절약 | llm-manager |
| 3 | MDB `agent_llm` | cache_key = sha256(llm_input + checksums) | LLM 응답 결과 | 동일 요청 재호출 방지 | llm-manager |

**Layer 1 주의**: file_manager는 내부적으로 **checksum을 만들지 않는다**. 3필드 인덱스로 관리. llm-manager는 받은 metadata로 **자체 해싱**해서 Layer 2·3의 키를 만든다 (문서 ① §3.2). 두 시스템이 서로 다른 식별 방식을 써도, llm-manager 내부 키 일관성만 유지되면 문제 없음.

**Layer 2 용량 관리 (§8, Phase B)**: Files API 20GB 상한 대응은 **Redis SCAN + TTL 기반 FIFO**로 처리한다. 즉 Redis 키(checksum)를 시작점으로 오래된 것을 골라 Gemini 삭제 + Redis 삭제. Gemini 쪽 파일 목록으로부터 Redis 원본 키를 역추적할 일이 없으므로 **역인덱스는 두지 않는다** (역인덱스 개념: `docs/concepts.md` 참고).

**cache_key 불변 조건 (§3 주의)**: Layer 3의 `cache_key`에는 `files_api_uri`(Gemini URI) 또는 `cached_content` 같은 **volatile 값은 절대 포함되지 않는다**. 캐시 키 재현성을 위해 (file_name, file_mtime, file_size) 기반 checksum만 입력으로 사용. 이미 [keying.py](../service/app/logic/keying.py)의 `build_llm_input_subset` / `canonicalize_llm_input`에서 volatile 제거 로직이 구현되어 있음.

## 4. 핵심 설계 결정

### 4.1 파일별 분류 — 최소 개별 체크 + 합계 조정 (부분 섞기)

**Step 1 — 전부 inline 후보 (비디오 선분리 제거 — 변경 C [28](28.gemini-file-spec-resync.md))**

| 조건 | 결정 |
|---|---|
| 전부 (비디오 포함) | **inline 후보 (일단)** |

> 비디오도 ≤20MB면 inline 지원(공식). 개별 한도(PDF 50MB, image/audio/video/text 20MB)는 **Step 2의 합계 체크에 녹아들어** 별도 체크 불필요 — 대형 비디오·대형 PDF는 합계 초과로 자연히 files_api로 밀린다. PDF 50MB 초과·1000p 초과는 이후 Files API 업로드 단계(§6.2 C 분기)의 `splitter.split_pdf`(크기+페이지 캡)에서 처리 — classify_files는 이 부분 관심 없음.

**Step 2 — 합계 체크 (파일 + 비파일 요청 구성요소)**

요청 body에는 파일 외에도 텍스트·system·tools·schema·history·config 등 "비파일 구성요소"가 포함된다. 이것들도 Gemini 요청 전체 크기 한도에 카운트되므로 합계 계산에 **반드시 포함**.

```python
def _estimate_non_file_bytes(llm_input: dict) -> int:
    """파일 Part를 제외한 llm_input의 JSON 직렬화 byte 수 근사.
    
    classify_files 호출 시점에는 llm_input에 파일 Part가 아직 들어있지 않으므로
    (파일은 file_metas로 별도 전달) 단순 직렬화 크기로 충분.
    """
    try:
        return len(json.dumps(llm_input, default=str).encode("utf-8"))
    except Exception:
        return 0  # 추정 실패 시 0 → inline 판정에 관대한 쪽으로 fallback
```

모달리티 인지 유지:
- `inline_pool`에 image·audio·video 포함 → **합계 20MB** (Gemini 강제 상한)
- PDF/텍스트만 → **합계 20MB** (메모리 정책 — 종전 50MB 에서 인하, [33](33.inline-limit-lowered-to-20mb.md))

> 두 한도는 값이 같아졌지만 **근거가 다르므로 상수·분기를 합치지 않는다** — 위는 못 올리는
> 스펙 상한, 아래는 되돌릴 수 있는 정책([33](33.inline-limit-lowered-to-20mb.md) §2.1).
> 인하 근거: inline 은 요청당 메모리 피크가 원본의 약 4배(base64 +33% + JSON 직렬화 복사)라
> 동시 40건이면 감당이 안 된다([32](32.inline-bytes-release.md) §2 실측).

**Step 3 — 작은 것부터 정렬 후 일괄 결정**

정렬 방향은 **오름차순(작은 것부터)**. 반복 호출 시 Redis HIT으로 재사용되는 이점이 큰 파일일수록 Files API가 유리하므로, 작은 파일을 inline에 우선 남기고 큰 파일을 Files API로 넘긴다.

```python
def classify_files(
    file_metas: list[FileMeta],
    llm_input: dict,
) -> tuple[list[FileMeta], list[FileMeta]]:
    inline_pool: list[FileMeta] = []
    files_api_pool: list[FileMeta] = []
    
    # Step 1: 전부 inline 후보 (비디오 선분리 제거 — greedy가 크기로 라우팅)
    inline_pool = list(file_metas)
    
    # Step 2: 합계 한도 결정 (모달리티 인지 — video 포함)
    has_media = any(
        m.mime_type.startswith(("image/", "audio/", "video/")) for m in inline_pool
    )
    limit = 20 * 1024 * 1024 if has_media else 20 * 1024 * 1024  # 둘 다 20MB (문서 33)
    
    # Step 3: 작은 것부터 정렬 + 한 번 순회 (재평가 없음 — Q2 보수)
    inline_pool.sort(key=lambda m: m.file_size)   # 오름차순
    total = _estimate_non_file_bytes(llm_input)
    kept: list[FileMeta] = []
    for m in inline_pool:
        if total + m.file_size <= limit:
            kept.append(m)
            total += m.file_size
        else:
            files_api_pool.append(m)
    
    return kept, files_api_pool
```

### 4.1.1 자동 분류 원칙

- **호출자는 inline/Files API를 직접 지정할 수 없다**. Service가 자동 분류.
- **inline 우선**: 제한을 넘지 않는 한 inline 사용 (Files API 업로드 비용·지연 회피).
- Files API는 제한으로 어쩔 수 없는 파일에만 사용.
- **반복 호출 최적화 (오름차순 정렬 근거)**: 작은 파일을 inline에 우선 남기고, 큰 파일을 Files API로 넘김 → 자주 쓰이는 큰 파일은 Redis HIT으로 48h 내 재사용되어 매 호출 fetch 비용 절약.

### 4.2 이진 분기 vs 부분 섞기

| 방식 | 규칙 | 장점 | 단점 |
|---|---|---|---|
| 이진 | 조건 만족 → **전부 inline** / 아니면 **전부 Files API** | 구현 단순, 흐름 명확 | 작은 파일도 큰 파일 때문에 Files API 경유 — 비용 낭비 |
| **부분 섞기 (선택)** | 파일별로 타입 한도 체크 → 가능한 것만 inline, 나머지 Files API | inline 비용·속도 이점 최대화, 같은 호출에서 유연 | 구현 복잡, contents에 URI Part/inline Part 혼재 |

**부분 섞기 선택 이유**
- **inline = 업로드·저장비 0** (Files API 업로드·저장비 없음) — 단 **비용 0 은 아니다**:
  요청당 메모리 피크가 원본의 약 4배다(base64 +33% + JSON 직렬화 복사, [32](32.inline-bytes-release.md) §2 실측).
  그래서 "제한 범위 내면 무조건 이득"이 아니라 **한도를 메모리로 정한다**([33](33.inline-limit-lowered-to-20mb.md))
- 큰 파일 하나가 섞였다고 작은 파일까지 Files API로 몰아가면 불필요한 업로드 비용
- Gemini API는 같은 `contents` 배열 안에 inline Part와 URI Part 혼재를 원래부터 허용
- 구현 복잡도는 분류 함수(§4.1) 하나로 집약 → 다른 모듈은 결과만 받아서 처리
- **정렬 방향(작은 것부터)로 반복 호출 이득 극대화**: 작은 파일은 inline로 매번 간단히 전송, 큰 파일은 Files API + Redis HIT으로 48h 내 재사용 → 큰 파일의 반복 fetch 비용 제거

### 4.3 임시 파일 처리 — /tmp (방식 B)

| 방식 | 저장 | 장점 | 단점 |
|---|---|---|---|
| A. 메모리 | Python `bytes` 변수 | I/O 없음 | 대용량 부담, PDF split 불가(PyMuPDF는 path 필요) |
| **B. /tmp (선택)** | `tempfile.NamedTemporaryFile(delete=True)` | 대용량 OK, split 호환, 자동 삭제 | 디스크 I/O 1회 |

**B 선택 이유**
- `splitter.py`(PyMuPDF)가 파일 경로 필요 → split 필요한 PDF는 B 필수
- `uploader.upload_file(path, mime)` 기존 시그니처 유지 가능 → 코드 재사용
- `with NamedTemporaryFile(delete=True)` 블록으로 누수 방지

### 4.4 context_cache와 부분 섞기의 관계

Context Cache는 **inline data Part도 받을 수 있으나** (Gemini API 스펙상 가능), **inline 경로엔 cache 적용 안 함**. 이유:

- **저장 비용 비효율**: inline data를 cache 안에 넣으면 base64 1.33배 데이터가 그대로 cache 토큰으로 저장 → 시간당 저장 비용 ↑
- **손익분기점 어려움**: inline 후보는 작은 파일이라 한 번에 inline 보내도 토큰 비용 작음 → 시간당 4회 이상 호출 손익분기점 도달 가능성 낮음
- **운영 단순성**: inline 파일에 대한 cache 매핑·관리 키 추가 → 복잡도 ↑

→ 부분 섞기 하에선 같은 호출에서 일부 파일만 Files API를 타는 상황이 자연스럽게 발생한다.

**정책** (docs/30 — all-or-nothing)

| 상황 | 처리 |
|---|---|
| `context_cache_ttl` 지정됨 | **inline/Files API 분류와 무관하게 전 파일을 Files API 로 승급** → 전부 context_cache 대상. 크기 혼합이어도 작은 파일이 inline 에 잔류해 캐시 밖으로 새지 않는다. 합계가 too-small이면 §4.4.1 fail-soft 로 전부 Files API URI(= all-or-nothing) |
| `context_cache_ttl` 지정 없음 | §4.1 분류 결과 그대로 사용 (작은 것 inline / 큰 것 Files API — 부분 섞기 유지) |

**승급 경고 문구**
```python
logger.warning(
    "context_cache_ttl=%d 지정 — 크기 분기 없이 전 파일 Files API 경로로 승급",
    context_cache_ttl,
)
```

**왜 all-or-nothing인가**: `context_cache_ttl` 지정 = "이 파일들을 캐시에 올려 재사용하겠다"는 신호이므로 **전 파일이 캐시에 있어야 한다.** inline 분기(§4.1)의 원래 목적은 *캐시를 안 할 때* 불필요한 작은 파일을 Files API로 올리지 않으려는 것이라, 캐시를 켠 경우엔 그 목적이 성립하지 않는다. 또 캐시 모드에서 inline은 캐시가 안 돼 매 호출 재전송되므로 승급이 비용상으로도 유리하다.

**과거 정책과의 차이**: 예전엔 "모든 파일이 inline일 때만" 승급하고 일부가 이미 Files API면 inline 파일을 그대로 뒀다. 이제는 **ttl 지정이면 혼합이든 무조건 전원 승급**한다. 구현: `_resolve_pools` 최상단에 ttl early-return — 크기 분기(classify) 자체를 건너뛰고 `[], list(files)` 반환(docs/30).

### 4.4.1 too-small 선제 게이트 — 캐시 시도 전 모달리티 토큰 어림

**문제**: 위 승급 정책상 `context_cache_ttl` 지정이면 전 파일이 Files API로 올라가 context_cache 생성을 시도한다. 그러나 **합계 토큰이 1024 미만인 콘텐츠**(예: 1~2장 출금요청서 PDF)는 캐시가 절대 생성되지 않고 매 호출 `400 min_total_token_count`(§6.2)를 받는다. fail-soft가 잡아 호출 자체는 성공하지만:
- 매 호출 **무의미한 create 왕복**이 generate 앞에 직렬로 붙어 지연,
- 핸들러 로그에 `POST /v1/caches 400`이 계속 누적(운영 노이즈).

→ **캐시가 불가능할 게 뻔하면 create 시도 자체를 건너뛴다.**

**선제 게이트 vs fail-soft (역할 분리)** — 둘 다 둔다. 게이트는 명백한 소형을 왕복 0으로 거르고, fail-soft는 어림 오차를 받친다.

| | 시점 | 역할 |
|---|---|---|
| **선제 게이트 (이 절)** | create 호출 *전* | 로컬 토큰 어림이 1024 미만이면 create skip |
| **fail-soft (§6.2)** | create 호출 *후* 400 | 어림이 빗나가 시도했는데 too-small이면 흡수 (backstop) |

**측정식 (로컬 계산, API 왕복 0)** — 캐시 대상은 `system_instruction` + 캐시될 파일들이므로:

```
E_total = E(system) + Σ E(file_i)
skip create  ⟺  E_total < 1024
else         →  create 시도 (fail-soft가 backstop)
```

모달리티별 토큰 환산 (Gemini 공식 — [tokens](https://ai.google.dev/gemini-api/docs/tokens), [document-processing](https://ai.google.dev/gemini-api/docs/document-processing)):

| 모달리티 | E (토큰 어림) | 비고 |
|---|---|---|
| PDF | `258 × 페이지수` | 페이지당 258 flat. `fitz`(PyMuPDF, splitter가 이미 쓰는 의존성)로 페이지만 읽음 |
| 텍스트 (system, .txt) | `chars / 3` | 실제 ~4 chars/token, 한글 안전 위해 과대평가 |
| 이미지 | `258 × 타일수` | ≤384px=1타일, 초과는 `ceil(w/768) × ceil(h/768)` |
| 오디오 / 비디오 | (어림 안 함) | 스코프 외 — 항상 create 시도 (아래 스코프) |

**과대평가 방향**: 어림은 실제보다 크게 잡는다(예 텍스트 `/3`). 그래야 **캐시 가능한 콘텐츠를 잘못 skip하지 않는다**. 반대로 어림이 모자라 create를 시도하면 fail-soft가 받으므로 **양방향 모두 에러는 없다**.

**스코프**: PDF·텍스트·**이미지**를 정밀 어림한다(이미지=`fitz.Pixmap` 픽셀→타일, 위 표). 오디오/비디오는 길이 측정 의존성이 커 현 수요 밖이라 "항상 시도"로 둔다 — 그쪽은 fail-soft가 계속 backstop. (이미지도 깨진/미상 bytes면 추정 `None` → 시도.)

**승급·전송 정책과의 결합**: §4.4의 강제 승급은 그대로 둔다. 게이트는 *create만* 막을 뿐, **작은 파일도 Files API URI로 전송**한다(inline로 되돌리지 않음). 근거: `context_cache_ttl` 지정은 **같은 콘텐츠 반복 질문** 신호이고(예: extractor가 같은 PDF로 3병렬 호출), 반복 시 업로드 1회 + URI 참조 N회가 매 호출 inline 재전송보다 가볍다. too-small로 skip된 파일이 Files API URI를 유일 경로로 쓰는 것은 [22.files-api-retention-context-cache-lifecycle.md](22.files-api-retention-context-cache-lifecycle.md) lifecycle과 일치.

**임계 주의**: 1024는 `파일 + system` **합계** 토큰이며 모델별 셈법이 다를 수 있다(예: Gemini 3는 PDF 네이티브 텍스트 비과금, 페이지 이미지를 IMAGE로 계상). 그래서 어림은 보수적으로 + fail-soft를 반드시 유지한다.

**구현 위치**: `create_context_cache` 호출 직전 게이트 한 겹(§7.2 `resolver`). 페이지 수는 업로드 경로가 이미 읽는 바이트에서 계산 — 구현 시 §7.2 갱신.

### 4.5 지원하지 않는 mime 타입 거부

Gemini가 지원하지 않는 파일 타입이 file_manager로부터 전달될 수 있다 (mime 오탐지, 지원 외 포맷 등). **LLM 호출 전에 거부**하여 비용·시간을 낭비하지 않는다.

**정책**: `SUPPORTED_MIME_TYPES` 화이트리스트(§2.4)에 없는 mime이 하나라도 포함되면 **전체 요청 거부**.

**검증 시점**: 요청 수신 직후, `prepare()` (cache_key 계산·MDB 조회) **진입 이전**. 잘못된 입력은 fail-fast — 캐시 조회 비용도 낭비하지 않음.

**에러**: `UnsupportedFileTypeError` (HTTP 422) raise.

**방어적 검증**: file_manager가 잘못된 mime_type을 전달해도 llm-manager 쪽에서 2차 방어.

### 4.6 개별 파일 2GB 초과 거부

Gemini Files API는 **파일당 2GB** 상한. 초과 파일은 inline(20MB/50MB)·Files API 어느 경로로도 처리 불가.

**정책**: `FileMeta.file_size`가 2GB를 초과하는 파일이 하나라도 포함되면 **전체 요청 거부** (비디오/PDF/이미지/오디오/텍스트 타입 무관).

**검증 시점**: mime 화이트리스트 체크 **직후**, `prepare()` 진입 이전. 순서: `validate_mime_types` → `validate_file_sizes` → `prepare()`

**에러**: `FileTooLargeError` (HTTP 422) raise.

**방어적 검증**: file_manager에서도 선제 필터될 가능성 있으나, llm-manager에서 2차 방어.

## 6. 분기 상세

### 6.1 inline 분류 파일 처리 (Redis 우회)

`classify_files()`의 **`inline_pool`** 에 담긴 파일만 대상. Redis 전혀 접근하지 않음.

```python
inline_parts: list[Part] = []
for meta in inline_pool:
    bytes_data = await fetch_file_bytes(meta.file_path)  # file_manager HTTP
    inline_parts.append(
        Part.from_bytes(data=bytes_data, mime_type=meta.mime_type)
    )
```

**특성**
- **Layer 2-A / 2-B 전혀 접근 안 함** — Redis 조회·저장 없음
- 매 호출마다 file_manager에서 bytes 수급 (제한 내 작은 파일이라 부담 낮음)
- Files API 48h TTL 재업로드 이슈 없음
- **tempfile 불필요 (예외: >1000p PDF)** — `Part.from_bytes`는 메모리 bytes를 그대로 수용. **단, 인라인 PDF가 1000p를 넘으면** 분류 전 `_expand_pdfs_over_page_limit`이 메모리→tempfile→`split_pdf`로 페이지 분할한다(변경 C, [28](28.gemini-file-spec-resync.md) §5.4). 분할 파트가 인라인 한도를 넘으면 Files API로 폴백. 크기 분할(50MB)은 종전대로 Files API 경로(§6.2)에만 해당
- context_cache와 무관 (inline 파일은 context cache 참여하지 않음)

### 6.2 Files API 분류 파일 처리 — miss 3단계 분기 (A / B / C)

`classify_files()`의 **`files_api_pool`** 에 담긴 파일만 대상. Redis + Gemini Files API 활용.

**핵심 변경**: `context_cache` hash_key 계산에 사용하는 checksum 리스트는 **`files_api_pool`의 checksum만** 포함한다. inline 파일은 context cache에 참여하지 않음.

```
Files API 분류 진입
  │
  ▼
```

**분기별 비용 특성**

| 분기 | bytes 다운로드 | Files API 업로드 | create_cache | 특성 |
|---|---|---|---|---|
| A | ❌ | ❌ | ❌ | 가장 저렴. 같은 파일+모델+system 재호출 |
| B | ❌ | ❌ | 조건부 | 같은 파일이지만 context cache 만료/첫 생성 |
| C | MISS 파일만 | MISS 파일만 | 조건부 | 신규 파일 또는 48h TTL 만료 |

> **too-small fail-soft (이슈 #646):** Context Cache 합계 토큰이 1024 미만이면
> Gemini 가 `400 min_total_token_count` 로 거절한다. 이때 `create_cache` 단계에서
> 캐시 생성을 skip 하고 (`cached_content=None`) Files API URI 로 호출을 이어간다 —
> 캐시는 비용 최적화일 뿐 정확도와 무관하므로 fail-hard 하지 않는다. too-small 외의
> 에러는 그대로 raise. 상세: [21.context-cache-too-small-failsoft.md](21.context-cache-too-small-failsoft.md)

> **다중 파일 캐시 라벨링 (docs/29):** `create_cache` 로 올라가는 콘텐츠는 파일별 헤더
> (`===== [문서 N] 파일명 =====`, 분할 파일은 `(총 M개 파트로 분할 업로드됨)`)로 라벨링된다 —
> 다중 파일 답변의 출처 귀속용. 반환 계약은 무변경(라벨은 캐시 콘텐츠에만). 상세: [29.context-cache-file-labeling.md](29.context-cache-file-labeling.md)

### 6.3 PDF split (>50MB)

- 기존 `splitter.split_pdf(path, target_mb=50)` 그대로 활용
- C 분기에서 bytes → tempfile 저장 → split 필요 여부 체크
- split된 각 파트는 개별 Files API URI로 업로드 → Redis `files_api:{checksum}`에 `split: True` + `uris: [...]` 저장
- 재호출 시 Redis HIT이면 복수 URI로 복수 Part 구성
- Phase B 용량 관리 시 한 checksum의 복수 URI를 **한 번의 삭제로 일괄 정리** (§8.6)

## 7. 모듈별 상세

### 7.1 `runner.py`

**제거**
- `_apply_inline_files()`, `_apply_cached_files()` (입력 형식 폐기)

**재설계**
- `_build_server_call_input(prep)` — **async 변환** + `resolve_files()` 호출 + `_apply_resolved()`로 call_input 조합.
- `_apply_resolved(llm_input, resolved) -> dict` — 신규. `inline_parts + uri_parts + 텍스트`를 contents에 합치고 `cached_content`는 별도 필드로, `file_checksums`는 제거 (Gemini에 전달 금지).
- `_is_gemini_404(exc) -> bool` — 신규. 예외 메시지 기반 판정 (llm-handler가 예외 타입 세분화하면 개선).

**수정**
- `llm_request_async` / `llm_request_stream_async`: **진입 직후 validation** (prepare 호출 이전 — fail-fast). `aio_call` / `aio_stream` 호출을 try/except로 감싸 Gemini 404 감지 시 `resolve_files_after_404` 호출 후 1회 재시도.
  ```python
  async def llm_request_async(llm_input, *, file_metas=None, ...):
      if file_metas:
          validate_mime_types(file_metas)     # §4.5 화이트리스트
          validate_file_sizes(file_metas)     # §4.6 2GB 상한
      prep = prepare(llm_input, file_metas=file_metas, ...)
      if prep.cached_output:
          return prep.cached_output
      call_input = await _build_server_call_input(prep)
      try:
          res = await aio_call(**call_input)
      except Exception as e:
          if _is_gemini_404(e) and prep.file_metas:
              resolved = await resolve_files_after_404(...)
              call_input = _apply_resolved(prep.llm_input, resolved)
              res = await aio_call(**call_input)   # 1회만
          else:
              raise
      return finalize(prep, res, database=database)
  ```
- `prepare()`: `file_meta` → `file_metas: list[FileMeta]`, 각 FileMeta에 대해 `keying.make_file_checksum()` 호출하여 cache_key 구성.

### 7.2 `resolver.py` (재설계)

Phase 2 라이브러리 버전(`Part.from_file(path)` 로컬 경로 사용)을 **완전히 교체**. 구성:

- `_process_inline(inline_pool)` — inline 파일 처리 (§6.1)
- `_process_files_api(pool, *, checksums, ...)` — Files API A/B/C 분기 (§6.2)
- `ResolvedFiles` dataclass — 반환 구조
- `resolve_files(file_metas, llm_input, *, model, system_instruction, context_cache_ttl)` — 진입점

```python
@dataclass
class ResolvedFiles:
    inline_parts: list[Part]       # §6.1 결과 (inline 분류 파일)
    uri_parts: list[Part]          # §6.2 결과 (Files API 분류 파일)
    cached_content: str | None     # §6.2 분기 A에서만 세팅

async def resolve_files(
    file_metas: list[FileMeta],
    llm_input: dict,                           # 합계 계산용 — classify_files 전달
    *,
    model: str | None,
    system_instruction: str | None,
    context_cache_ttl: int | None,
) -> ResolvedFiles:
    # Step 1: §4.1 분류 (비디오 선제 분리 → 합계 체크 → 작은 것부터 정렬)
    inline_pool, files_api_pool = classify_files(file_metas, llm_input)
    
    # Step 2: §4.4 승급 정책 — 모든 파일이 inline인데 context_cache_ttl 지정됐으면 전원 Files API로
    if context_cache_ttl is not None and not files_api_pool and inline_pool:
        logger.warning(
            "context_cache_ttl=%d 지정 — 모든 파일 Files API 경로로 승급",
            context_cache_ttl,
        )
        files_api_pool = inline_pool
        inline_pool = []
    
    # Step 3: 각 풀 처리
    inline_parts = await _process_inline(inline_pool)           # §6.1
    uri_parts, cached_content = await _process_files_api(       # §6.2
        files_api_pool,
        checksums=[make_file_checksum(m) for m in files_api_pool],
        model=model,
        system_instruction=system_instruction,
        context_cache_ttl=context_cache_ttl,
    )
    return ResolvedFiles(inline_parts, uri_parts, cached_content)
```

**too-small 선제 게이트 결선 (§4.4.1)** — 아래는 *as-implemented* 함수명 기준 (위 코드 블록은 설계 시점 이름이라 실제와 다름):

- **신규 헬퍼** `_estimate_cache_tokens(files_api_pool, system_instruction) -> int | None` (resolver) — 모달리티별 합산(§4.4.1):
  - PDF: `258 × page_count` (`fitz`/PyMuPDF — `_count_pdf_pages`)
  - 텍스트(`text/*`): `file_size // 3` (바이트 기반 보수) / system: `len // 3`
  - 이미지(`image/*`): `image_tokens`(stash) — `fitz.Pixmap` 픽셀 → `타일수×258`(`타일 = ceil(w/768)×ceil(h/768)`, 작은 이미지=1타일=258)
  - **audio/video · PDF page_count 미상 · 이미지 미상(깨진 bytes) → `None` 반환**. `None`은 게이트가 skip하지 않고 create 시도(fail-soft backstop).
- **호출 위치**: `_process_files_api` 의 context cache 분기(④) 직전. 현재 `if ctx_cache_active and file_refs:` 안에서 `_resolve_or_create_context_cache` 호출 *전에* 게이트:
  ```python
  if ctx_cache_active and file_refs:
      if _estimate_cache_tokens(files_api_pool, system_instruction) < _CACHE_MIN_TOKENS:
          logger.info("[route] mode=context_cache source=skipped reason=below_min_token_estimate ...")
          # cached_content 는 None 유지 → 업로드된 file_refs(URI)로 그대로 진행
      else:
          cached_content = await _resolve_or_create_context_cache(...)  # 기존 경로 (fail-soft 포함)
  ```
- **페이지 수 소스 (구현됨)**: `fi.data`(bytes)는 업로드 후 `b""`로 비워지므로, 업로드 시점(`_upload_and_cache_file`, bytes 보유)에 `fitz`로 세어 **`FileInput.page_count`에 stash + Redis `files_api` 엔트리에 `page_count` 저장**. cache HIT/병렬 재호출은 `_reuse_files_api_uris`가 Redis에서 복원 → 게이트가 재fetch 없이 동작.
- **상수**: `_CACHE_MIN_TOKENS = 1024` — 모델별 셈법 차이는 보수적 단일값 + fail-soft로 흡수(§4.4.1 임계 주의).
- **fail-soft(§6.2) 유지**: 게이트 통과(추정 ≥ 1024)했는데 실제 too-small이면 `_create_and_save_context_cache`가 그대로 잡아 `None` 반환.

## 8. Files API 용량 관리 (Phase B — 후속 phase)

> ⚠️ **Phase B 보류 중** — llm-handler SDK에 `delete_file(name)` 미노출 상태. 담당자 요청 중 (`/home/rladustn1227/02.github/llm-handler-requests.md`).
> 제공 받기 전엔 Gemini 48h TTL + Redis 47h TTL 자연 정리에 의존.
> `files_api:{checksum}` value의 `size` 필드는 **Phase A에서 이미 저장 중** ([resolver.py `_process_files_api`](../service/app/logic/file_handler/resolver.py)). Phase B는 이 값을 SCAN 시 용량 합산 기준으로 사용.

### 8.1 목적
Gemini Files API 프로젝트 할당 **20GB 상한**을 넘지 않도록 llm-manager가 자동 정리.

### 8.2 임계값
- **19 GB** (1GB 안전 마진 — 동시 업로드 경쟁, size_bytes 부정확성 대비)

### 8.3 트리거 시점
- `upload_file()` / `upload_pdf_parts()` 호출 **직전**
- Files API 경로의 C 분기(신규 업로드)에서만 실행

### 8.4 흐름 — Redis SCAN + TTL 기반 FIFO

Gemini 쪽 `list_files()`에 의존하지 않고 **Redis를 시작점**으로 한다. Redis TTL이 동일(47h)이므로 남은 TTL이 적을수록 먼저 저장된 것 = FIFO 효과.

```
upload_file(tmp_path, mime, size) 호출 직전:
  │
  ▼
① 현재 Redis 용량 추정
   for checksum in scan_files_api_keys():
       doc = find_files_api(checksum)
       total += doc["size"]  # value에 이미 저장된 필드
  │
  ▼
② 용량 체크
   if total + required_size <= 19GB: return  # 여유 충분
  │  (공간 부족)
  ▼
③ SCAN + TTL 기반 정렬
   entries = []
   for checksum in scan_files_api_keys():
       ttl = get_ttl_files_api(checksum)
       doc = find_files_api(checksum)
       entries.append((ttl, checksum, doc))
   entries.sort(key=lambda e: e[0])   # TTL 적은 순 = 오래된 것부터
   need_to_free = (total + required_size) - 19GB
  │
  ▼
④ 오래된 것부터 삭제 루프
   freed = 0
   for ttl, checksum, doc in entries:
       if freed >= need_to_free: break
       try:
           # (a) 연쇄 삭제: 이 checksum이 포함된 context_cache 먼저 처리 — §8.5
           for hash_key, cc_doc in find_context_caches_with_checksum(checksum):
               llm_handler.delete_cached_content(cc_doc["cached_content_name"])
               delete_context_cache(hash_key)
           
           # (b) Gemini Files API 파트 삭제
           for uri in doc["uris"]:
               name = _uri_to_name(uri)  # URI → Gemini File name
               llm_handler.delete_file(name)
           
           # (c) Redis files_api 키 삭제
           delete_files_api(checksum)
           
           freed += doc["size"]
       except Exception:
           logger.exception("용량 관리 삭제 실패: %s", checksum); continue
  │
  ▼
   upload_file() 실행
```

### 8.5 context_cache 연쇄 삭제

`files_api:{checksum}`이 삭제되면 **그 checksum이 포함된 `context_cache:{hash_key}`도 같이 삭제**해야 한다. 그렇지 않으면 Gemini context cache가 stale URI 기반으로 남아 참조 시 실패.

**연결 방법**
- Redis `context_cache` 값에는 이미 `file_checksums: list[str]` 저장 중 ([cache_store.py](../service/app/logic/file_handler/cache_store.py) `save_context_cache` 호출부)
- `find_context_caches_with_checksum(checksum)` 이 SCAN으로 매칭되는 엔트리 반환 (§7.5)

**순서**
1. 먼저 **context_cache 삭제** (Gemini `delete_cached_content` + Redis 키)
2. 이어서 **files_api 삭제** (Gemini `delete_file` + Redis 키)

**순서 근거**: context_cache가 남아 있는 상태에서 Files API URI를 먼저 지우면 context cache가 깨진 URI를 참조. 반대로 context_cache 먼저 지우면 그 시점부터 cache 참조는 무효지만 Files API는 직접 사용 가능.

**최적화 (구현 시)**: 용량 관리 트리거 시 `find_context_caches_with_checksum`를 매 checksum마다 호출하면 SCAN O(N²). 실무적으로는 **한 번의 SCAN으로 context_cache 전체를 메모리에 올린 뒤**, 각 파일 삭제 루프에서 메모리 매칭으로 연결 — 단순 최적화.

### 8.6 Split PDF 처리

한 checksum이 복수 URI(`split: True`, `uris: [uri1, uri2, ...]`) 가지는 경우:
- `files_api:{checksum}` 키 하나에 파트 URI들이 묶여 있으므로, **한 번의 삭제로 파트 전체 Gemini 삭제 + Redis 키 삭제** (§8.4 `for uri in doc["uris"]` 루프)
- 부분 삭제 문제 없음

### 8.7 동시성 / 에러 처리

| 상황 | 대응 |
|---|---|
| 여러 agent 동시 용량 체크 → 중복 삭제 | "없다고 가정" 범위 (문서 ① §9). `delete_file` 멱등성(이미 삭제된 건 404)으로 방어 |

| 오디오 9.5시간 초과 | **사전 체크 불가** — 파일 bytes로 재생 길이 산출 불가. 업로드 후 Gemini가 거부 → 런타임 에러로 상위 전파 |
| Redis 조회/저장 실패 (find_*, save_*) — 연결 실패 포함 | `CacheError` (HTTP 502) raise. 로그에 어느 연산(find_files_api / save_context_cache 등) + checksum/hash_key 명시. 재시도는 redis-handler 측 책임 (§12 백로그) |
| Files API 업로드 실패 (`upload_file` / `upload_pdf_parts`) | `FileUploadError` (HTTP 502) raise. 로그에 file_name, mime_type, 원본 예외 명시. 재시도는 llm-handler 측 책임 (§12 백로그) |
| `create_context_cache` 실패 | `FileUploadError` (HTTP 502) raise. `context_cache_ttl` 지정 자체가 "캐시가 필요하다"는 명시이므로 silent fallback 안 함 |
| Gemini 404 (URI/cache 부재 — 드문 상황) | **자동 복구 1회**: 해당 checksums의 `files_api:{checksum}` + `context_cache:{hash_key}` Redis 키 삭제 → `_process_files_api` 재호출 (분기 C로 자연 유입) → aio_call 재호출. 두 번째 404는 진짜 오류 → raise. 정상 운영에선 Redis TTL(47h) < Gemini TTL(48h)로 거의 발생 안 함 |
| 그 외 Gemini 5xx / 429 / 인증 오류 | 그대로 raise. llm-handler가 재시도 책임 (§12 백로그) |
| `delete_cached_content` 실패 (§8.5 연쇄 삭제) | 경고 로그 + Files API 삭제는 계속 진행. stale Gemini context cache는 TTL로 자연 만료 |
| file_manager 404 (파일 없음) | 문서 ①에 따라 "발생하지 않는다고 가정". 발생 시 `LLMManagerError(502)` |
| file_manager 타임아웃/연결 실패 | `LLMManagerError(503/504)` raise (① T2에서 구현됨) |
| tempfile 누수 | `try/finally`에서 `os.unlink` (uploader / resolver 모두 동일 패턴) |
| PDF split 후에도 파트가 50MB 초과 | 기존 splitter의 재귀(`_MAX_DEPTH=3`)로 처리. 초과 시 경고 후 그대로 업로드 → Gemini가 거부하면 에러 전파 |

## 10. Phase 3 폐기 항목 정리

| Phase 3 결정 | 폐기 이유 |
|---|---|
| SDK가 `≤20MB` inline base64로 사전 변환 후 body에 포함 | Service가 bytes 소스(file_manager) 결정 → SDK는 FileMeta만 보냄 |
| SDK가 `>20MB` 파일을 `/v1/files`로 사전 업로드 | `/v1/files` 엔드포인트 폐지 (문서 ①) |
| `_apply_inline_files` / `_apply_cached_files` (runner.py) | `resolve_files()` 단일 진입점으로 통합 |
| 개별 파일 크기 20MB 이진 분기 | **부분 섞기** — 파일별 개별 판정 + 합계 조정 (§4.1) |
| `InlineFileDTO(data_base64)` DTO | FileMeta로 통일 (문서 ①) |
| resolver.py의 `Part.from_file(path)` (로컬 경로 가정) | file_manager HTTP bytes 수급 + `Part.from_bytes` |
