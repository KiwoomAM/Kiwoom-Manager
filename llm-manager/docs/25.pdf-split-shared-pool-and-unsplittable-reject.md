## §1. 배경 / 문제 정의

50MB를 초과하는 PDF는 Gemini Files API 한도(아래 §2-0) 때문에 `splitter.split_pdf`가
페이지 단위로 분할한다. 운영(Kiwoom-Parsing profile pipeline)에서 특정 대형 PDF를
처리할 때 **split 단계가 파트당 ~16분간 호출 프로세스의 asyncio 이벤트 루프를 블로킹**했고,
같은 문제가 **두 번 재발**했다.

증상 (이슈 #21):
- split이 파트당 ~16분, 그 사이 I/O 0건 → uvicorn 단일 루프 100% 정지(`/health` 타임아웃).
- 호출자 재시도가 dedup으로 합쳐지지 못해 **같은 문서 3중 실행·중복 적재**.

이 문서는 그 원인을 실측으로 규명하고(§2), 수정 설계를 정의한다(§3~).

**처음 의심(이슈 원인분석)과 실제는 달랐다.** 이슈는 ① split 동기실행 →
`to_thread` 오프로드, ② `deflate` 재압축 과중, ③ dedup TTL을 들었으나, 측정 결과
①②는 무효였다(§2). 따라서 이슈의 처방을 그대로 적용하면 안 된다.

## §2. 측정 / 진단 (재현: 52.9MB·236p, 이슈 문서와 동일)

> 재현 파일: `20260522_..._AI-flation.pdf`. 이슈는 "83MB"로 기록했으나, 페이지 수(236),
> 분할 지점(p.1-212 / p.213-236), garbage=4 파트 크기(41.8MB)가 모두 일치 → **동일 문서**
> (83MB는 측정 착오로 추정). 측정 스크립트는 부록 참조.

### §2-0. Gemini 한도 (공식 문서 확인)
- PDF 입력 한도 = **50MB 또는 1000페이지**, **inline·Files API 동일** 적용.
- 즉 코드의 `_PDF_SPLIT_LIMIT = 50MB`는 **정확**하다. 한도를 올려 회피하는 길은 없다.
- **페이지 한도 대응(변경 C, [28](28.gemini-file-spec-resync.md) §5.2)**: `split_pdf(max_pages=1000)`이
  크기 분할 후 1000p 초과 파트를 `ceil(pages/1000)` 등분한다(각 등분은 `_split_group`이 크기도
  재보장). 50MB(크기)·1000p(페이지)는 독립 제약이라 둘 다 충족시킨다. 인라인 PDF가 1000p를
  넘으면 메모리 분할하고, 파트 합계가 인라인 한도를 넘으면 Files API로 폴백한다(§28 §5.4).
  단일 페이지>50MB 거부(`PdfPageTooLargeError`)는 그대로 유지.

### §2-1. garbage 레벨별 비용 (part1 = p.1-212 save)
| garbage | 시간 | 크기 | 비고 |
|---|---|---|---|
| 1 | 0.49s | 50.5MB | unused 제거 |
| 2 | 0.38s | 50.3MB | + xref 압축 |
| 3 | **>150s (kill)** | — | + 중복 객체 합치기 |
| 4 (현재값) | **17.9min** | 41.8MB | + 스트림 중복 대조 |

- **16분의 원인은 `garbage≥3`의 객체/스트림 중복 대조.** 객체가 14만 개(§2-3)라
  이 dedup이 폭발한다.
- `deflate`는 시간·크기에 **영향 0** (g1 deflate on/off 모두 0.4초, 50.5MB). 이슈 ②는 오진.

### §2-2. 페이지 분할은 이 문서에 무효
target_mb를 낮춰 잘게 쪼개도 파트 크기가 안 줄어든다 (garbage=2 기준):

| target_mb | 파트 수 | 각 파트 크기 |
|---|---|---|
| 50 | 2 | 50.3 / 50.1MB |
| 20 | 3 | 모두 ~50.1MB |
| 3 | 20 | 모두 ~50.1MB |

- **단일 페이지 1장만 저장해도 50.2MB** (`clean=True`도 동일). → 페이지 분할로는
  garbage=1/2 상태에서 **절대 50MB 밑으로 못 만든다.**

### §2-3. 근본 원인 — 모든 페이지가 공유 객체 풀을 참조
- `xref_length = 143,006` (236p에 페이지당 ~600객체 — 벡터 차트를 객체로 토해내는 생성기).
- 큰 스트림은 대부분 `/Subtype/Form`(벡터) — 합계 ~33.7MB. 이미지는 2.7MB뿐.
- 모든 페이지의 `/Resources`가 이 **~50MB 공유 객체 풀 전체를 참조** → `select(부분 페이지)`
  후 `garbage=1`(unused 제거)로도 아무것도 못 버림(전부 reachable) → 매 파트가 50MB.
- 이 풀을 줄이는 유일한 수단이 `garbage≥3`의 중복 객체 제거(50.3→41.8MB)인데, 그게 16분.

### §2-4. `to_thread` 오프로드(이슈 ①)는 무효 — PyMuPDF가 GIL을 안 놓음
- 16분 save 중 Jupyter 커널 인터럽트가 **timeout**(KeyboardInterrupt 미전달) → PyMuPDF가
  save 동안 GIL을 계속 점유한다는 직접 증거.
- 따라서 `await asyncio.to_thread(split_pdf, ...)`로 워커 스레드에 던져도, 그 스레드가
  GIL을 독점해 **이벤트 루프는 그대로 굶는다.** 진짜 오프로드는 별도 프로세스가 필요하나,
  애초에 16분 작업을 없애는 게(§3) 우선이라 불필요해진다.

### §2-5. 결론
- "빠르게(g1/g2) → 50MB 초과", "한도 통과(g4) → 16분" — **garbage 숫자만으론 해결 불가.**
- 이 문서처럼 **단일 페이지가 50MB를 넘는 PDF는 어떤 분할로도 전송 불가** → 거부가 정답.
- 정상 대형 PDF(단일 페이지 < 50MB)는 garbage=2 + 재귀 분할로 빠르게 처리 가능.

### 결정 사항 (확정)
1. `garbage=4` → **`2`** (분할·병합 save 양쪽). 16분 경로 제거.
2. **단일 페이지가 50MB 초과**면 분할 포기하고 **명확한 에러로 사용자에게 거부**.
3. `deflate`는 현 상태 유지(무관). `to_thread`/프로세스 오프로드 도입 안 함(불필요).
4. 범위: `llm-manager`만. dedup ③은 `Kiwoom-Parsing#68`.

### 결정 근거 (왜 garbage=2 / 왜 거부인가)
- **garbage 1 vs 2**: 둘 다 sub-second(0.49 vs 0.38s)로 사실상 동률. 2가 xref까지 압축해
  출력이 약간 작고(50.3 vs 50.5MB) 깔끔 → **2 선택**.
- **garbage 3·4 배제**: 객체/스트림 중복 대조가 14만 객체에서 분 단위로 폭발(§2-1).
  크기 이득(g4 41.8MB)이 있어도 17.9분은 수용 불가.
- **deflate 유지**: 시간·크기 영향이 0이라 굳이 끄지 않고 현행 유지(불필요한 diff 회피).
  이슈가 지목한 "deflate 재압축 과중"은 실측상 원인이 아니었다(§2-1).
- **오프로드 배제**: `to_thread`는 PyMuPDF가 save 동안 GIL을 안 놓아 무효(§2-4). 별도
  프로세스로 떼면 풀리지만, garbage=2로 save가 ~0.4s가 되면 오프로드할 무거운 작업
  자체가 사라지므로 불필요.
- **재증류/토글 배제, 거부 채택**: 외부 도구(qpdf 등) 재증류나 프로세스 풀로 "처리되게"
  만들 수도 있으나, 이런 병리적 PDF는 빈도가 매우 낮아(어쩌다 한 번) 과투자.
  "느린 경로 on/off 토글"은 내부 tradeoff를 호출자에게 떠넘기는 footgun이라 배제.
  **단일 페이지 50MB 초과는 50MB 하드 한도를 넘는 입력 → 거부가 임시방편이 아니라
  올바른 최종 동작.** 거부 WARNING이 잦아지면 그때 재증류를 별도 이슈로(§5).

## §3. 새 분할 알고리즘

핵심: **garbage=2(빠름)로 분할하고, 50MB를 넘는 그룹은 페이지를 더 쪼개 재귀.
단일 페이지인데도 넘으면 분할 불가 → 거부.** garbage=4(16분)·오프로드는 없음.

```
split_pdf(path):
    if file_size <= target:            # 분할 불필요
        return [path]
    groups = group_by_estimate(target)              # 기존 추정 기반 그룹핑 유지
    result = []
    for group in groups:
        part = save(group, garbage=2, deflate=True)  # ~0.4s
        if size(part) <= 50MB:
            result.append(part)
        elif len(group) == 1:
            raise PdfPageTooLargeError(page=group[0], size=size(part))   # ← 분할 최소단위 초과
        else:
            result += split_pages_further(group)     # 페이지 bisect 후 재귀 (garbage=2)
    return merge_adjacent(result, garbage=2)         # 기존 병합, garbage 2로
```

- **재귀 종료 조건이 `_MAX_DEPTH`가 아니라 "단일 페이지"로 바뀐다.** garbage=2가 싸서
  단일 페이지까지 내려가도 비용이 작다. 단일 페이지가 floor이자 거부 지점.
- 기존 `_MAX_DEPTH` "한도 초과해도 그냥 진행" 분기는 **제거** — 오버사이즈 파트를
  업로드로 흘려보내지 않고 거부로 끝낸다.
- 정상 대형 PDF: 단일 페이지<50MB라 항상 분할 성공(파트 수만 늘 수 있음, 무손실).

### 변경 지점
- `splitter.py:128`, `:175` — `garbage=4` → `2` (분할·병합 save).
- `splitter.py:54~` — 재귀/종료 로직을 위 알고리즘으로 교체, `_MAX_DEPTH` 진행분기 제거.

## §4. 에러 처리

- **새 예외 `PdfPageTooLargeError`** (page 인덱스 + 실제 크기 포함). 메시지(사용자용):
  *"이 PDF는 처리할 수 없습니다 — 단일 페이지가 Gemini 한도(50MB)를 초과합니다 (p.N, XMB)."*
- **전파 경로(코드 확인 후 확정)**: resolver(`_resolve_files_api`)의 `except Exception → FileUploadError(502)`
  에 **삼켜지지 않게** 별도 분기로 둘지, 기존 에러 릴레이에 태울지 결정. 사용자에게 "처리 불가"가
  명확히 닿는 게 목표(일반 502로 뭉개지면 안 됨).
- **가시성**: raise 직전 `logger.warning("분할 불가 PDF: page=%d size=%.1fMB", ...)` 한 줄.
  드물게라도 재발하면 흔적이 남는다. (메트릭 파이프라인/트리거 이슈는 빈도가 낮아 과함 → 생략.)
