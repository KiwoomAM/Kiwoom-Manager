# 35. `cache_mode`·`save_mode` 의 의미 바로잡기 — 파일 첨부 직교화 + standby 조건

두 플래그가 **자기 소관이 아닌 것까지 좌우하고 있다.** 둘 다 "플래그의 의미가 코드에서 번진 것" 이라는
같은 뿌리라 한 PR 로 묶는다.

| # | 증상 | 원인 |
|---|---|---|
| **A** | `F/F` 에서 `stored_files` 가 무경고로 사라진다 | 드롭 규칙이 세 곳에 복붙 (§1.1) |
| **B** | `T/F` 에서 standby 가 헛돌며 동시 요청을 직렬화한다 | standby 조건이 `save_mode` 가 아니라 `dc` 존재 여부 (§1.2) |

## 1. 배경 / 문제 정의

### 1.1 (A) `F/F` 에서 `stored_files` 가 조용히 사라진다

`cache_mode` 와 `save_mode` 를 **둘 다 `False`** 로 주면, 소비자가 넘긴 `stored_files` 가
**아무 경고 없이 버려진다.** LLM 은 파일을 못 본 채로 답하고, 소비자는 그 답을 정상 응답으로 받는다.

```python
# 소비자가 기대하는 것: 캐시만 끄고, 파일은 붙여서 매번 새로 호출
resp, meta = await llm_request_async(
    {"contents": "이 문서 요약해줘", "model": "gemini-2.5-flash"},
    stored_files=[sf],
    cache_mode=False, save_mode=False,
)
# 실제로 일어나는 일: stored_files = None → LLM 은 첨부 없이 "이 문서 요약해줘" 만 받는다
```

**왜 심각한가 — 실패가 조용하다(`FAIL-LOUD` 위반).** 예외도 경고 로그도 없고, LLM 은 첨부가 없어도
그럴듯한 문장을 만들어 낸다. 그래서 이 증상은 "매니저가 파일을 버렸다" 가 아니라 **"모델이 환각을
일으켰다"** 로 오진된다.

**가정이 아니다 — 이미 한 번 그렇게 오진했다.** `Kiwoom-ETF/docs/45-market-extraction-redesign-brief.md:11-15`
가 자기 실측을 스스로 무효화하며 남긴 기록이다.

> ⚠️ **정정 (2026-07-28) — §2의 환각 실측은 무효다.**
> 아래 §6에 적힌 재현 조합 `cache_mode=False, save_mode=False`는 **SDK가 첨부를 통째로 버린다**.
> 즉 §2-2의 "원문 10개 → 수치 4/5 환각"은 **파일 없이 프롬프트만 받은 LLM**에게 구체적 수치를 요구한 결과다.

그 오진 위에서 내렸던 설계 결정("수치를 지어내니까 원문 첨부는 보류")까지 되돌려야 했다
(`Kiwoom-ETF/docs/42-market-original-pdf-attach-design.md:3-10`).

**드롭 규칙이 세 곳에 복붙돼 있다(`SSOT` 위반).** 아래 줄 번호는 **수정 전** 기준이다 —
이 PR 이 그 줄들을 지우므로 머지 후에는 링크가 다른 곳을 가리킨다.

| 위치 | 코드 |
|---|---|
| [`prepare()` :105](../llm_manager/_internal/runner.py#L105) | `if not (cache_mode or save_mode): files = None` |
| [`llm_request_async` :532](../llm_manager/_internal/runner.py#L532) | `if not (cache_mode or save_mode): stored_files = None` |
| [`llm_request_stream_async` :668](../llm_manager/_internal/runner.py#L668) | `if not (cache_mode or save_mode): stored_files = None` |

여기에 더해 `prepare()` 분기 ①(수정 전 :124)이 `files=None` 을 한 번 더 박는다.
**바깥 두 줄만 지우면 `prepare()` 가 조용히 다시 버린다** — 이 수정의 진짜 함정이다.

### 1.2 (B) `T/F` 에서 standby 가 헛돈다

`agent_llm` standby(동일 요청이 동시에 몰릴 때의 중복 호출 방지)에 들어가는 조건은 두 진입 함수의
`prep.dc is None` **하나뿐**이다(수정 전 :550·:692 — 이 PR 이 바꾸는 줄이라 앵커를 걸지 않는다). 즉 **"캐시 키가 있으면 건다"** 로 판정한다.

그런데 standby 의 이득 구조는 이렇다 — 리더가 LLM 을 부르고 → **MDB 에 저장하고** → 대기자가 그
저장분을 읽어간다. **대기자가 기다린 대가로 받는 것은 리더의 저장분이다.** 그러니 진짜 조건은 키의
존재가 아니라 `save_mode` 다.

| cache | save | `dc` | standby | 대기자가 보상을 받나 |
|---|---|---|---|---|
| T | T | 있음 | 씀 | ✅ 리더가 저장 → 읽어감 |
| **T** | **F** | 있음 | **씀** | ❌ **리더도 `T/F` 면 아무도 저장하지 않아 못 받음** |
| F | T | 있음 | 씀 | ✅ 리더가 저장 → 읽어감 |
| F | F | 없음 | 안 씀 | — |

`F/T` 가 정상 동작하는 이유가 이 구조를 잘 보여준다. 대기자의 재확인
[`_recheck_agent_llm_cache`](../llm_manager/_internal/runner.py#L457) 는 `cache_get` 으로 MDB 를
**직접** 읽고 `cache_mode` 를 보지 않는다. 그래서 조회를 꺼 놨어도 리더가 저장한 것을 받아간다.

**깨진 칸은 `T/F` 하나다.** `dc` 가 있으니 줄을 세우는데 저장하는 사람이 없으면 받아갈 게 없다.
대기자는 [dedup.py:299-305](../llm_manager/_internal/file_processing/dedup.py#L299) 의 3번 경로
("leader 가 기록 없이 사라짐")를 타고 SETNX 재획득 후 **자기가 LLM 을 다시 부른다.**

```
현재 T/F, 동시 요청 3개 (LLM 30초 가정, 아무도 저장 안 함)
  요청1: [LLM 30s] 저장 안 함
  요청2:  ...대기 30s... → 재획득 → [LLM 30s]      = 60s
  요청3:  ...대기 60s... → 재획득 → [LLM 30s]      = 90s
  → LLM 호출 3회(줄지 않음) + 지연만 N배
```

**성공 경로에서 LLM 호출 횟수는 줄지 않는다.** 대기자도 결국 자기 호출을 한다. 줄어드는 것 없이
지연만 쌓이므로 이 조합에서 standby 는 순손실이다. (실패 경로는 다르다 — §3.3 의 "대가" 참조.)

### 2.2 (A) 계약 문서엔 없고, 소비자는 우회 규칙을 만들어 살고 있다

[README.md:739](../README.md#L739) 의 조합별 흐름 표는 그 조합을 이렇게만 적는다.

| cache_mode | save_mode | 흐름 |
| --- | --- | --- |
| `False` | `False` | 키 생성 없음 → LLM 직접 호출 → 저장 없음 |

`guide-doc/user-guide/caching.md:45-51` 의 조합 표도 그 칸을 "일회성/민감한 요청. 디버깅" 이라고만
적는다. **llm-manager 가 소비자에게 주는 어느 계약 문서에도 첨부가 사라진다는 서술이 없다.**

대신 **소비자가 SDK 소스를 런타임에 뜯어보는 방어 코드를 짜고 있다.**
`Kiwoom-ETF/backend/analysis/calls.py:32-34` 가 경고를 적어 두고,

> ⚠️ 옛 llm-manager(≤0.3.0)는 `cache·save` 둘 다 off 면 **첨부를 조용히 버린다**
> (`_internal/runner.py` 의 `if not (cache_mode or save_mode): stored_files = None`) — 그 버전에서
> 재실행이 돌면 map 이 PDF 없이 불려 **지어낸 답**을 낸다.

`_retry_can_skip_save()`(`calls.py:107-137`)가 그것을 **런타임에 판정한다** —
`inspect.getsource(runner)` 로 llm-manager 소스를 읽어 `"if not (cache_mode or save_mode)"` 문자열이
있으면 옛 버전으로 보고 `save_mode` 를 켠 채로 강등한다(`calls.py:151`
`save_mode=use_cache or not _retry_can_skip_save()`).

**이것이 이 동작을 계약으로 만들지는 않는다** — 계약이라면 매니저 문서에 있어야 하고, 소비자가
SDK 소스 문자열을 grep 해 회피하라고 적지 않는다. 오히려 반대로, **매니저가 소비자에게 내부 구현을
런타임에 감시하게 만들었다**는 증거다. 같은 취지가 `Kiwoom-ETF/docs/42`·`45`·
`48-pipeline-core-plan.md:1802-1813` 에도 남아 있다.

> **주의 — 이 인용은 2026-08-28 16:08 시점(`5f72068`)이다.** 초안은 같은 날 오전 판본을 인용했다가
> 리뷰에서 걸렸다. ETF 는 이 영역을 활발히 고치는 중이니 인용 전에 항상 라이브 파일을 다시 읽어라.

### 2.3 (A) 기술적 의존이 없다 — 파일은 캐시 없이도 흐를 수 있다

파일을 실제로 LLM 호출에 싣는 [`_build_server_call_input`](../llm_manager/_internal/runner.py#L429) 은
`prep.files`·`prep.llm_input`·`prep.context_cache_ttl`·`prep.standby_ttl_seconds` 를 읽는다.
**캐시 키(`prep.dc`) 도 MDB 도 참조하지 않는다.**

파일 처리 계층도 캐시 플래그를 모른다. `resolver.py` 전체에 `cache_mode`/`save_mode` 참조가 **0건**이고,
checksum 도 [resolver.py:928](../llm_manager/_internal/file_processing/resolver.py#L928)·
[:843](../llm_manager/_internal/file_processing/resolver.py#L843) 에서 **자기가 다시 계산**한다
(runner 의 [:110](../llm_manager/_internal/runner.py#L110) 계산과 독립이다 — 전자는 Redis
`files_api:{checksum}`·context_cache 키용, 후자는 MDB 응답 cache_key 용).

**주의 — "그러니 비용도 그대로" 는 아니다.** 파일 업로드 dedup 은 **files_api 경로에만** 있다.
inline 경로는 dedup 대상이 아니고 Redis 도 안 만진다. 이 비용은 §4.2 에서 따로 따진다.

### 2.4 (A) 소비자 조사 — 오늘 회귀는 없지만 잠복 경로가 있다

두 플래그의 사용처를 사내 repo 에서 조사했다. 리터럴 `False` 뿐 아니라 **변수로 넘기는 호출부**까지
봐야 한다.

**(가) 현재 상태 — 회귀 없음.** `F/F` 로 고정된 운영 호출은 **12곳**이고 **전부 텍스트 전용**이다
(전 호출부를 열어 `stored_files` 미전달을 개별 확인).

| repo | 호출부 |
|---|---|
| Kiwoom-ETF | `backend/service/volatility_assemble.py:40`·`:64`(날짜 파싱), `backend/llm/guarded.py:117`(응답 판정기) |
| Kiwoom-Guideline | `case_linking/src/{hybrid_linker.py:186, llm_linker.py:59, judge.py:309}`, `threshold_mining/src/{extract_candidates.py:67, rules_30_extract.py:51, rules_31_extract.py:51, rules_32_extract.py:51, rules_treasury_extract.py:52}` |
| Kiwoom-Crawling | `crawler/diagnostics/diagnose.py:116` |

즉 **이 버그를 지금 밟고 있는 운영 코드는 없다.** 고쳐도 회귀가 없다.

**단, "머지 후에도 없다" 는 아니다 — 오히려 기다리는 소비자가 있다.**
`_retry_can_skip_save()`(§2.2)는 이 PR 이 그 문자열을 지우면 `True` 로 뒤집히도록 만들어져 있고,
그 함수의 docstring 이 그렇게 적고 있다.

> 🔴 **임시 — llm-request 의 첨부 유지 변경이 올라오면 이 함수와 호출부를 지우고
> `save_mode=use_cache` 로 못박아라.** (PR 확인 후 제거) — `calls.py:110-111`

소비자가 `pip install -e` 로 붙어 있으므로(§3.5) **머지 즉시** ETF map 재실행이
`stored_files=[doc["stored_file"]]` + `F/F` 로 나간다. 이는 사고가 아니라 **ETF 가 설계해 둔
목표 상태**다 — 재실행이 저장까지 하면 2차 응답이 1차 캐시 슬롯을 덮어 카드가 조용히 오염되기
때문에, ETF 는 재실행을 `F/F` 로 만들고 싶어 하고 그러려면 첨부가 살아 있어야 한다.

**그래서 §4.1 의 새 예외 표면과 §4.2 의 재호출 비용은 "언젠가" 가 아니라 머지 직후 ETF map
재실행 경로에 떨어진다.** 그 경로는 제안서 PDF 를 첨부하므로 비용도 작지 않다. 이 PR 의
릴리스 노트에 그 사실을 적고, ETF 쪽에 `_retry_can_skip_save()` 제거를 함께 알린다(§7).

**(나) 잠복 경로 — 여기가 이 수정의 진짜 이유다.** 플래그를 변수로 받으면서 **파일을 함께 넘기는**
호출부가 `F/F` 에 한 걸음 거리에 있다.

| 잠복 경로 | 어떻게 `F/F` 가 되나 | 터졌을 때 증상 |
|---|---|---|
| **`Kiwoom-Parsing` PDF 파이프라인** — `call_llm.py:79-81`·`:92-94`, `parse_pages.py:211-213`·`:221-223` 이 `stored_files=[sf]` 와 `cache_mode=config.cache_mode, save_mode=config.save_mode` 를 **나란히** 넘긴다. `DEFAULT_CACHE_MODE = False`(`config.py:13`) 라 **이미 절반이 `False`** 다 | 설정에서 `save_mode=False` 한 번 → `F/F` | 프로필·비전 파이프라인이 **PDF 를 한 번도 못 본 채** 파싱 결과를 만든다. 산출물 전체가 환각이 된다 |
| **`Kiwoom-ETF` `request_guarded` 재호출** — `guarded.py:214` 가 `cache_mode=False, save_mode=save_mode` 로 다시 부른다. 운영 호출부는 `overview_service.py:150` 과 `analysis/calls.py:97`·`:121`(`make_map_call`·`make_classify_call` 의 기본 인자) 셋인데, 전자는 `save_mode` 미전달(기본 `True`), 후자 둘은 `save_mode=True` **명시** 라 지금은 안전하다 | 어떤 호출부든 `save_mode=False` 를 주면 재호출만 `F/F` | **첫 응답이 깨졌을 때 부르는 바로 그 재호출**이 제안서 PDF 없이 답한다. 첫 호출은 파일을 봤고 재호출만 못 봐서 재현·진단이 가장 어렵다 |

`calls.py:111` 이 `save_mode=True` 를 하드코딩한 **이유가 바로 이 버그** 라는 점(§2.2)이 잠복성을 잘
보여준다. 방어선이 사람의 기억과 주석뿐이다. **한 플래그가 관계없는 기능(파일 첨부)을 조용히
무력화하는 구조 자체가 문제다**(`FOCUSED` 위반).

### 2.5 (B) standby 는 리더와 대기자의 플래그를 구분하지 못한다

`save_mode` 는 [keying.py:23-45](../llm_manager/_internal/keying.py#L23-L45) 의 `_LLM_INPUT_FIELDS`
에 **없다.** 그래서 같은 입력이면 `T/T` 호출자와 `T/F` 호출자가 **같은 cache_key, 같은 standby 키**
를 쓴다. 대기자는 `cache_get(cache_key)` 로 MDB 를 눈감고 읽을 뿐, 리더가 누구인지도 어떤 플래그인지도
모른다.

따라서 `prep.save_mode` 는 **대기자 자신의 플래그이지 리더의 플래그가 아니다.** 혼합 상황에서
오늘 무슨 일이 벌어지는지 양방향으로 적는다.

| 오늘, 혼합 `save_mode` | 결과 |
|---|---|
| 리더 `T/T` + 대기자 `T/F` | 대기자가 리더의 저장분을 **우연히** 주워간다 (설계된 이득이 아님) |
| **리더 `T/F` + 대기자 `T/T`** | **저장 안 하는 쪽이 리더 자리를 차지해, 저장하는 쪽에게 헛기다림을 물린다** |

즉 혼합 상황은 양쪽으로 작동하고, **해로운 쪽이 더 크다.** `save_mode` 로 게이트하면 앞의 우연한
이득 하나를 잃는 대신 뒤의 피해가 구조적으로 사라진다 — **비용을 내는 쪽(저장하는 쪽)이 이득을 보고,
안 내는 쪽이 공짜를 못 받는** 방향이다.

덤으로 불변식이 하나 생긴다. `save_mode=False` 가 키를 안 잡으므로 **"standby 키가 있다"
= "저장할 **의사**가 있는 리더가 돌고 있다"** 가 보장된다.

**"항상 보상받는다" 로 과장하지 않는다.** 리더가 저장을 *시도했는데 실패*하는 경로가 남아 있다 —
[`finalize`](../llm_manager/_internal/runner.py#L256) 는 `save_result` 예외를 `logger.exception` 으로
삼키고 정상 반환하므로, MDB 장애 시 대기자는 여전히 빈손으로 깨어나 [dedup.py:299-305](../llm_manager/_internal/file_processing/dedup.py#L299)
의 3번 경로를 탄다. 리더 프로세스가 SIGKILL 당하거나 standby TTL 이 먼저 만료돼도 같다.
바뀌는 것은 **"구조적으로 보상이 없는 경우"(`save_mode=False`)를 걸러낸다**는 것이지, 장애까지
없앤다는 뜻이 아니다.

## 3. 설계 — 변경 지점

`cache_mode`/`save_mode` 를 **MDB 응답 캐시의 읽기/쓰기 스위치**로 한정한다. 파일 첨부는 그와
직교하게 만들고(A), standby 는 그 스위치의 결과에 정직하게 반응하게 만든다(B) — standby 의 보상이
곧 "저장" 이므로 `save_mode` 가 그것을 가르는 것은 소관 확대가 아니라 소관 정정이다.

### 3.1 (A) `prepare()` — 드롭 제거

```python
    # ── ① cache_mode=F, save_mode=F → 캐시/키 불필요 ────────
    # files 는 그대로 넘긴다. 캐시 플래그는 MDB 응답 캐시만 가르며 첨부와 직교한다 (docs/35).
    if not cache_mode and not save_mode:
        return _Prepared(
            ...
            route_reason="cache_off_save_off",
            files=files,          # ← None 에서 변경
            ...
        )
```

바뀌는 것은 둘이다.

1. `if not (cache_mode or save_mode): files = None` **삭제**.
2. 분기 ① 의 `files=None` → `files=files`.

분기 ① 위의 checksum 계산 블록은 **건드리지 않는다.** 분기 ① 이 `keying_input` 을 쓰지 않으므로
계산이 헛일이 되지만, [`make_file_checksum`](../llm_manager/_internal/keying.py#L246) 은 세 필드를
sha256 하는 것이 전부라(bytes 도 I/O 도 없음) 이득이 마이크로초다. 그걸 줄이려고 `prepare()` 의 제어
흐름을 재배치하면 리뷰 범위만 넓어진다(`SURGICAL`).

### 3.2 (A) `llm_request_async` / `llm_request_stream_async` — 드롭 제거

두 함수 진입부의 아래 두 줄을 각각 삭제한다.

```python
    if not (cache_mode or save_mode):
        stored_files = None
```

### 3.3 (B) standby 조건을 `save_mode` 로 바꾼다

조건을 **"키가 있으면"** 에서 **"리더가 저장할 때만"** 으로 바꾼다. 두 함수의 진입 가드를 고친다.

```python
    # standby 는 리더가 MDB 에 저장해야 대기자가 그 결과를 받아간다. save_mode=False 면 아무도
    # 저장하지 않아 대기자가 기다린 뒤 자기가 다시 LLM 을 부른다 — 호출 수는 그대로고 지연만
    # 쌓인다(docs/35 §1.2). F/F(dc 없음)도 save_mode=False 이므로 여기서 함께 걸린다.
    if not prep.save_mode:
        return await _do_llm_call(prep, database)          # 스트림은 _do_llm_stream + _build_live_meta
```

`prep.dc is None` 은 **함께 지운다.** `save_mode=True` 면 분기 ②·③④ 가 반드시 `dc` 를 만들므로
`dc is None ⟹ save_mode=False` 이고, `not prep.save_mode` 가 그 경우를 전부 덮는다. 중복 절을 남기면
`prepare()` 가 나중에 바뀌어 가정이 깨졌을 때 **크래시 대신 dedup 을 조용히 건너뛰는 동작**이 된다 —
로그도 예외도 없이 herd 억제가 사라진다. §1.1 이 (A) 를 고치는 이유로 `FAIL-LOUD` 를 들었으므로
같은 문서에서 그것을 뒤집지 않는다. 지우면 가정이 깨질 때 바로 다음 줄 `prep.dc.cache_key` 에서
시끄럽게 터진다.

**바뀌는 칸은 `T/F` 하나뿐이다.** `T/T`·`F/T` 는 `save_mode=True` 라 그대로 standby 를 타고,
`F/F` 는 이미 `dc is None` 으로 걸러지던 것이 같은 조건에 합쳐질 뿐이다.

**대가 — 리더 실패 시의 herd 억제를 `T/F` 에서 잃는다.** 지금은 리더가 실패하면 대기자들이
[runner.py:568-571](../llm_manager/_internal/runner.py#L568-L571) 에서 자기 호출 없이 같은 예외로
끝난다([:583](../llm_manager/_internal/runner.py#L583) 의 `record_failure` 가 그 근거를 남긴다).
조건을 바꾸면 LLM 이 계속 실패하는 동안 `T/F` 요청 N 개가 각자 한 번씩 부딪힌다.

그럼에도 바꾸는 이유는 **성공이 정상 경로**이기 때문이다. `T/F` 의 standby 는 성공 경로에서 얻는 것이
0 이면서 매번 직렬화 비용을 물린다. 게다가 그 대기는 싸지 않다 — backoff 가 0.5→10초 cap 으로
`standby_ttl_seconds`(기본 600초) × `_MAX_TIMEOUT_ROUNDS` 라운드까지 매달릴 수 있고
([dedup.py:276-341](../llm_manager/_internal/file_processing/dedup.py#L276)), 유일한 `T/F` 소비자는
그 시간 내내 ETF 전역 슬롯(`LLM_SLOTS = 15`) 하나를 쥔다. 실패 경로의 억제 하나를 위해 정상 경로
전부를 줄 세울 수는 없다.

**대가 둘 — `T/F` 동시 요청이 직렬에서 병렬로 바뀐다.** 종전 standby 는 성공 경로에서 의도치
않은 레이트 리미터로도 동작했다. 같은 입력의 `T/F` 요청 N 개가 한 번에 하나씩 나갔는데, 이제
동시에 나간다. **호출 횟수는 그대로고 순간 동시성이 1 → N 으로 바뀐다.** 429·쿼터 한계 근처에서는
"느리지만 성공" 이 "동시 버스트로 전부 실패" 가 될 수 있다. 오늘의 실질 영향은 작다 — 유일한 `T/F`
호출부는 파일명마다 cache_key 가 달라 애초에 잘 겹치지 않는다. 그래도 README 로 계약을 공표하는
이상 잃는 것의 목록에 적어 둔다.

**다만 그 대가가 실제로 어디에 떨어지는지는 정직하게 적어 둔다.** 문서 초안은 "재시도·백오프는
소비자 층에 있다" 고 적었으나, 유일한 `T/F` 운영 호출부
`Kiwoom-ETF/backend/product/overview_dates.py:57-68` 은 ETF `request_with_retry` 를 **거치지 않고**
`llm_request_async` 를 직접 부르며 `except Exception: return None` 으로 전부 삼킨다. 즉 그 호출부에는
재시도도 백오프도 없고, herd 가 생겨도 **관측되지 않는다.** 제동은 위 세마포어 15 하나뿐이다.
그 호출부는 실패해도 "날짜 문구가 안 붙는다" 로 끝나는 부가 기능이라 감수할 만하다고 판단한다.

### 3.5 기각한 대안

- **`ValueError` 로 거부(`FAIL-LOUD`)** — 조용한 오답을 시끄러운 에러로 바꾸는 이점은 있으나,
  §2.3 대로 **기술적으로 불가능한 조합이 아니다.** "캐시는 끄고 파일은 붙인다" 는 정당한 요구를
  영구히 막게 되므로 기각.
- **경고 로그만 남기고 드롭 유지** — 근거 없는 규칙(§2.1)을 그대로 안고 간다. 로그를 안 보는
  소비자에게는 여전히 조용한 실패다. 기각.
- **드롭 규칙을 헬퍼 하나로 모아 `SSOT` 만 해결** — 규칙 자체가 틀렸으므로 한 곳에 모아도 버그다. 기각.
- **`F/F` 에서도 `agent_llm` standby 를 걸기** — 검토했고 **성능이 나빠져서** 기각. `F/F` 는 저장하는
  주체가 없어 대기자가 항상 빈손으로 재획득한다(§1.2). 또 `F/F` 에는 `cache_key` 자체가 없어 standby 를
  걸려면 checksum 계산 + `done_check` 로 키부터 만들어야 하는데, 그건 `F/T`(분기 ②)이지 `F/F` 가 아니다.
  리더가 MDB 대신 **Redis 로 결과를 방송**하면 저장 없이도 대기자가 받을 수 있으나, 새 메커니즘이고
  "아무것도 남기지 않는다" 는 `F/F` 의 의미와 충돌한다 — 별건.
- **(A) 와 (B) 를 별도 PR 로 분리** — 롤백 단위가 작아지는 이점이 있으나(소비자가 `pip install -e`
  로 붙어 있어 머지 즉시 전원에게 적용된다), 두 변경 합쳐 4줄이고 같은 함수의 인접한 줄을 건드려
  리뷰 맥락이 겹친다. 사용자 결정으로 한 PR 유지.

## 4. 안전성 검증

### 4.1 (A) `dc=None` 인데 `files` 가 있는 새 조합

이 조합은 **이 변경으로 처음 생긴다.** 그 조합에서 `prep.files` 나 `prep.dc` 를 만지는 하류를 전수 확인했다.

| 하류 | `dc=None` + `files` 존재일 때 | 안전한가 |
|---|---|---|
| [`_build_server_call_input` :429](../llm_manager/_internal/runner.py#L429) | `prep.files` 로 `resolve_files` 실행 → 업로드·inline 분류 정상 | ✅ `dc` 미참조 |
| [`_build_live_meta` :214](../llm_manager/_internal/runner.py#L214) | `prep.dc.cache_key if prep.dc else None` 가드 존재. `file_meta` 가 meta 에 **새로 실린다** | ✅ (진단에 이득) |
| [`finalize` :252](../llm_manager/_internal/runner.py#L252) | `if prep.save_mode and prep.dc is not None` → `save_mode=False` 라 진입 안 함 | ✅ |
| [`_finalize_stream` :333](../llm_manager/_internal/runner.py#L333) | `if not prep.save_mode or prep.dc is None: return` 가드 존재 | ✅ |
| [404 자동 복구 :498](../llm_manager/_internal/runner.py#L498)·[:629](../llm_manager/_internal/runner.py#L629) | `if is_gemini_404(e) and prep.files` → 이 조합에서도 **이제 복구가 동작한다** | ✅ (개선) |

**새 예외 표면이 생긴다.** 오늘 `F/F` 는 `files=None` 이라 file-manager 를 한 번도 안 만진다. 수정 후
`F/F` + 파일이면 validators(`UnsupportedFileTypeError`·`FileTooLargeError`)와 file-manager fetch
(`FileResolveError`·`FMServiceError`)가 **`F/F` 에서 처음으로 발생 가능**해진다. 이는 조용한 오답이
정상적인 예외로 바뀌는 것이라 의도한 방향이지만, `F/F` 를 "절대 안 터지는 가벼운 경로" 로 쓰던 소비자
관점에서는 변화다. 다만 §2.4(가) 대로 **오늘 `F/F` 에 파일을 넘기는 운영 코드는 없으므로** 지금 깨지는
곳은 없다.

**Redis 의존은 새로 생기지 않는다.** 리뷰에서 "`F/F` 에 Redis 하드 의존이 생긴다" 는 지적이 있었으나
확인 결과 **틀렸다.** [`_config.py:39-50`](../llm_manager/_internal/_config.py#L39)·[:86](../llm_manager/_internal/_config.py#L86)
의 `_ensure_redis_connected()` 가 `ensure_configured` 에서 무조건 불리고 실패 시 `RuntimeError` 를
던진다 — **플래그와 무관하게 모든 호출이 이미 Redis 를 요구한다.**

### 4.2 (A) 새로 생기는 비용 — `F/F` 는 응답 캐시도 dedup 도 없다

파일 처리에는 dedup 이 두 층 있는데, `F/F` 는 **둘 다 없다.**

| 층 | 무엇을 아끼나 | `F/F` 에서 |
|---|---|---|
| 파일 단위 (`files_api` standby) | 리더가 올린 **Gemini URI** 를 Redis 에 저장해 대기자가 재사용 | **inline 경로엔 애초에 없음.** [stored_file_resolver.py:6-8](../llm_manager/_internal/stored_file_resolver.py#L6) 이 "결과(bytes)가 Redis 에 캐시되지 않아 dedup 효익 없음 → N 회 fetch 허용(의도된 trade-off, 작은 파일 한정)" 이라고 명시. [`_process_inline`](../llm_manager/_internal/file_processing/resolver.py#L135) docstring 도 "Redis 전혀 접근 안 함" |
| 응답 단위 (`agent_llm` standby + MDB 캐시) | 동시 요청이면 리더 하나만 파일을 만지고 나머지는 응답을 받아감 | **없음** — `F/F` 는 캐시도 standby 도 없다 |

**inline 판정은 파일별이 아니라 합계 기준이고, 예외가 하나 더 있다.**
[`classify_files`](../llm_manager/_internal/file_processing/resolver.py#L112) 는
`_estimate_non_file_bytes(llm_input)` 에서 시작해 작은 파일부터 채우다 20MB 를 넘기면 나머지를
files_api 로 민다. 그래서 "20MB 이하면 무조건 inline" 이 아니다 — 12MB 짜리 둘이면 하나가 files_api 로
간다. 더 큰 예외는 [`_resolve_pools`](../llm_manager/_internal/file_processing/resolver.py#L794) 다:
**`context_cache_ttl` 이 지정되면 크기 분기 없이 전 파일을 files_api 로 승급한다**(docs/30 — 캐시는
all-or-nothing).

| `F/F` + 파일, 경우 | 결과 |
|---|---|
| 합계가 inline 한도 안 (흔한 경우) | dedup 없음 → **매 호출 file-manager 다운로드 + 전량 입력 토큰** |
| 합계 초과분 / `context_cache_ttl` 지정 | files_api 승급 → **Gemini Files API 업로드(48h)·Redis 키·(ttl 지정 시) 과금되는 Context Cache 생성** |

두 번째 줄이 이 PR 이 새로 여는 것 중 **유일하게 비가역인 부분**이다. 코드를 revert 해도 이미
만들어진 Files API 엔트리·Context Cache·Redis 키는 TTL 만료까지 남는다. `F/F` 를 "아무것도 남기지
않는 일회성 호출" 로 이해하는 소비자에게는 의미 있는 변화이므로 소비자 문서에 함께 적는다(§3.4).

메모리도 같이 든다([docs/32](32.inline-bytes-release.md) 실측: 44MB inline PDF 가 힙 peak 237MB).

inline dedup 이 없는 판단 자체는 옳다 — 재사용할 산출물이 URI 처럼 작지 않고 bytes 그 자체라, 공유하려면
bytes 를 Redis 에 올려야 한다. 그 판단의 전제가 "응답 캐시·응답 standby 가 위에서 막아 준다" 였는데
`F/F` 는 그 전제가 성립하지 않는다.

**(B) 적용 후에는 `T/F` 도 응답 standby 를 안 탄다**(§3.3). 그러니 "dedup 이 없는 유일한 조합" 이라는
말은 맞지 않다 — `F/F` 를 특별하게 만드는 것은 dedup 이 아니라 **응답 캐시 조회까지 없어 순차 반복에서도
아무것도 아껴지지 않는다**는 점이다.

**결론: 막지 않는다. 문서화한다.** `F/F` 는 소비자가 "캐시를 쓰지 않겠다" 고 명시적으로 고른 모드이고,
그 대가는 재호출 비용이다. 파일을 조용히 버려서 비용을 아끼는 것은 대가가 아니라 오답이다. 다만 이
비용을 소비자가 알고 고르도록 §3.4 의 문서에 함께 적는다.

### 4.3 (B) standby 를 건너뛸 때 남는 뒷정리

standby 를 안 타면 `token` 이 없다. 리더 경로의 `finally` 가 `release_standby(..., token)` 을
부르므로, **가드에서 곧장 반환해 그 `try/finally` 블록에 진입하지 않는 것**이 유일하게 맞는 모양이다
(§3.3 의 코드가 그렇게 돼 있다). 조건만 바꾸고 아래로 흘려보내면 `cache_key = prep.dc.cache_key`
부터 터진다.

| 확인 항목 | 결과 |
|---|---|
| `T/F` 에서 Redis 잔여 키가 남나 | 선점 자체를 안 하므로 standby 키가 생기지 않는다 ✅ |
| `record_failure`·`release_standby` 미호출로 다른 요청이 굶나 | 그 키를 아무도 안 만들었으므로 대기자도 없다 ✅ |
| 파일 업로드 dedup(`files_api` standby)에 영향 | **무관** — resolver 는 `save_mode` 를 보지 않는다(참조 0건) ✅ |
| `T/T`·`F/T` 리더/대기자 경로 | `save_mode=True` 라 조건에 안 걸린다 ✅ 변화 없음 |
