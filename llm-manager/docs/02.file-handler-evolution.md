## Phase 1: File Checksum 기반 캐시 키 ✅

### 배경

- `contents` 에 `FileRef` / `Part` 를 넣으면 파일 URI 또는 base64 가 캐시 키에 포함됨
  - 같은 PDF 재업로드 → URI 달라져 **캐시 미스**
  - 파일 내용이 바뀌어도 참조가 같으면 **잘못된 캐시 히트**
  - `cached_content` (Context Cache) 도 매번 새로 생성되면 키 미스

### 핵심 설계

- 파일 자체의 SHA-256 checksum 을 캐시 키 입력에 추가 (`file_checksums`)
- `cached_content` 는 cache key 입력에서 제외 — file_checksums 가 있으면 volatile
- `runner` Public API 에 `file_paths` 파라미터 추가 → checksum 계산 후 `llm_input` 사본에 주입

### 변경 파일

| 파일 | 변경 |
|---|---|
| `checksum.py` (신규) | SHA-256 계산 |
| `keying.py` | `_LLM_INPUT_FIELDS` 에 `file_checksums` 추가, `canonicalize_llm_input` 정규화, `build_llm_input_subset` 의 `cached_content` 제거 |
| `runner.py` | Public API 시그니처 + `_prepare` + `_Prepared.file_meta` + `_finalize/_finalize_stream` |
| `store.py` | doc 에 `file_meta` 키 |
| `pyproject.toml` | 의존성 |
| `tests/test_checksum.py` (신규), `test_keying.py`, `test_store.py`, `test_runner.py` | 회귀 테스트 |

## Phase 2: 파일 업로드/캐싱 자동화 ✅

### 배경

Phase 1 의 한계:
- caller 가 직접 `genai.upload_file()` 호출해야 함 → boilerplate
- 같은 파일 N 회 업로드 → Files API URI 캐시 부재
- Context Cache 수동 관리 → 재사용 어려움

### Phase 2 목표

- 파일 업로드/캐싱을 `file_handler` 모듈이 자동 처리
- caller 는 `file_paths` 만 넘기면 됨

### 파일 처리 방식

| 분기 | 처리 |
|---|---|
| 작은 파일 (< inline 임계) | base64 inline contents 에 임베드 |
| 큰 파일 (≥ inline 임계) | Files API 업로드 + URI 캐시 (Redis) |
| Context Cache (opt-in) | `cached_content` 인자 명시 시 별도 cache 생성/조회 |
| 50MB+ PDF | `splitter` 가 분할 후 multi-cache |

### `file_cache` Redis 저장소 정책

| 항목 | 정책 |
|---|---|
| Key 설계 | `file_cache:{hash_key}` — sha256(file_path + size + mtime) |
| 캐시 키 입력 (`hash_key` 생성) | `file_checksums` 사용 (URI 매번 변함) |
| TTL | Files API URI 와 정합 — 48 시간 |
| 404 Fallback | 캐시 hit URI 로 호출 → 404 시 재업로드 + 캐시 갱신 |

### 모듈 구성

| 모듈 | 책임 |
|---|---|
| `resolver.py` | `file_paths` → inline 또는 Files API URI 변환 (Phase 3 에서 SDK ↔ Service 분리됨) |
| `cache_store.py` | `BaseJsonStore` 상속, `prefix="file_cache"` |
| `uploader.py` | `llm_handler.aio.upload_file` 직접 사용. `create_cache` 재시도 (2회 / 5초, 500/503/429/RESOURCE_EXHAUSTED) |
| `splitter.py` | ESG `split_by_size` 복제 후 llm-request 에 맞게 수정 |

## Phase 3: llm-request 서버화 ✅

### 목표

llm-request 라이브러리를 **SDK + Service 분리**. SDK 는 agent 머신, Service 는 별도 서버. llm-handler 패턴 따름.

### 핵심 설계 결정

| # | 결정 |
|---|---|
| 1 | 파일은 서버로 보내지 않음 — Redis 파일 캐시 miss 시에만 |
| 2 | SDK 가 Redis 파일 캐시 조회 (agent 머신에서 직접) |
| 3 | 단계적 서버화 — SDK 가 checksum 계산 + Redis 조회 + httpx HTTP 클라이언트 |
| 4 | 엔드포인트 분리 (파일 업로드 vs 일반 요청) |

### 변경 파일

| 파일 | 변경 |
|---|---|
| `service/` 디렉토리 신규 | FastAPI 래퍼, `logic/` 으로 비즈니스 로직 이동 |
| `service/app/config.py`, `core/` | settings, errors |
| `service/app/dto/requests.py`, `responses.py` | Service 모델 |
| `service/app/routers/request.py` | `/v1/request`, `/v1/done-check`, `/v1/fetch` 엔드포인트 |
| `sdk/llm_request/` | checksum 계산 + Redis 조회 + httpx 클라이언트 |
| `sdk/llm_request/_client.py` | Public API (sync/async) |
| `runner.py` | `runner.run_request` → 옛 모놀리식 → SDK + Service 분리 |

### Task 결과

| Task | 내용 | 결과 |
|---|---|---|
| 1 | Service 디렉토리 생성 + 로직 이동 | ✅ |
| 2 | Service config + core (settings, errors) | ✅ |
| 3 | Service models (DTO) | ✅ |
| 4 | Service router (`/v1/request` 등 엔드포인트) | ✅ |
| 5 | SDK `_client.py` Public API | ✅ |
| 6 | SDK Redis 파일 캐시 조회 | ✅ |
| 7 | 회귀 + e2e 검증 | ✅ |

> Phase 3 의 일부 (file 업로드 책임) 는 후속으로 **file-manager 외부 패키지 분리** (09) → **bytes passthrough** (10) 로 재구조화됨. 즉 Phase 3 의 SDK ↔ Service 분리 골격은 유지되지만, file-manager 가 별도 패키지로 떨어져나가며 책임 경계가 바뀜.

## Phase 4: orchestrator + 파일 서버 ⏸ 미진행

### 원래 계획

| Part | 내용 |
|---|---|
| A | `orchestrator.run_many` 에 file_handler 연동 (배치 처리 + 공유 파일) |
| B | 파일 서버 구축 + MDB 에서 파일 존재 여부 체크 |

### 사유

Phase 3 완료 후 방향 전환:
- Phase 3 의 SDK 가 file 책임을 너무 많이 가짐 — Redis 조회, checksum 계산, 업로드 분기 등
- Part B (파일 서버) 가 SDK 책임 분리 요구를 더 강하게 만듦
- → **file-manager 외부 패키지 분리** 로 결정 (`09.file-manager-separation.md`)
- 후속 — bytes passthrough (`10.file-manager-bytes-passthrough.md`)
- 더 후속 — file-meta 응답 노출 + stored_files 입력 + Method 1 폐기 (`18.file-meta-stored-files-history.md`)
