# llm-request: 서버 레이어 제거 → 순수 SDK manager 리팩토링 계획

> 상세 설계(스키마·파이프라인·모듈별·에러처리·로드맵·TODO)는 이후 섹션별로 채운다.
> 이 문서엔 우선 **배경**과 **개요**만 기록.

## 1. 배경

### 현재 구조와 문제 제기

llm-request는 지금 **2겹**으로 돼 있다.

```
사용자 → sdk/(얇은 httpx 클라이언트) → service/(FastAPI 서버) → logic/ → handlers
```

`service/app/logic/`이 실제 manager 본체(mdb·redis·llm·file handler를 in-process로 조합)인데,
이걸 FastAPI 서버로 감싸고 다시 httpx SDK로 호출하는 우회 구조다.

여기서 "llm-request가 **서버화될 필요가 있는가**"라는 질문이 나왔다.

### handler / manager taxonomy

- **handler = 서버.** 외부 시스템 하나를 감싼다(Mongo·Redis·Gemini·파일). 서로 못 부름. 외부 사용자는 코드 모르고 URL만.
- **manager = SDK.** handler들을 "우리가 원하는 방식"으로 조합한 wrapper. 외부 사용자가 직접 import해서 씀.

이 정의에서 **llm-request는 handler가 아니다** — 자기 소유의 외부 리소스가 없고, 다른 handler들을 조합(orchestrate)할 뿐이다. 그건 정확히 **manager의 일**이고, manager는 SDK다. (caching agent라는 표현도 file-manager가 SDK인 것과 같은 의미의 SDK manager이지 서버가 아니다.)

### 서버화 근거 검토 — 전부 소멸

| 서버화 근거 | 결론 |
|---|---|
| 자격증명 중앙화 | ✗ cert는 전 agent 공통, handler URL은 하드코딩, Gemini key는 사용자 설정 → 중앙화할 게 없음 |
| Gemini 호출량/레이트리밋 제어 | ✗ llm-handler가 담당 |
| 로직 독립 배포(버전 스큐 방지) | ✗ 이전 버전 fallback 기간 후 폐기 방식으로 흡수 |
| 무거운 의존성 격리 | ✗ 설치 1회뿐, 이후 무관 |
| 캐시 키 결정성(단일 소스) | ✗ keying canonicalize를 **동결 계약**으로 두면 SDK 분산 배포해도 안전. file-manager도 동일 트레이드오프를 이미 수용 |
| byte 경로 / manager↔handler 잡담 | ✗ **아래 토폴로지 참고** — 같은 LAN이라 무손실 |
| 상사 방침: 사용자는 SDK로만 접근 | → 서버로 두면 "감싸는 SDK를 또 만들어야" 함 = 2겹은 불필요한 군더더기 |

### 네트워크 토폴로지 (byte 경로 caveat이 무효인 이유)

- handler들과 agent PC가 **모두 같은 서브넷(`192.7.9.x`, 같은 LAN)** 에 있다.
- manager는 handler와 **수다스럽다**(cold 요청 1건당 done_check·dedup standby·find/save·fetch·upload 등 핸들러 왕복 10~15회).
- manager가 어디서 돌든 이 왕복은 **LAN(sub-ms)** 이라 cold라도 총 몇 ms → 무시 가능.
- warm(캐시 HIT)은 원래부터 양쪽 1 왕복으로 동일.
- 속도 계층 참고: loopback(같은 머신·다른 포트, µs) > LAN(같은 서브넷, sub-ms) > WAN(인터넷, 10~50ms).
  서버화가 byte 경로에서 이득을 보는 경우는 **agent가 WAN 너머 + cold 대용량 파일이 잦을 때**뿐인데, 같은 LAN이므로 해당 없음.

### 결론

서버 레이어를 유지할 근거가 남지 않는다. **llm-request는 순수 SDK manager로 전환한다.**

## 2. 개요

### 목표 형태

```
[현재]  사용자 → sdk/(httpx) → service/(FastAPI) → logic/ → handlers   (2겹)
[목표]  사용자 → llm-request SDK(= 기존 logic/ 본체) → handlers        (1겹)
```

### 작업 윤곽

- **제거**: `service/app/main.py`, `service/app/routers/`, `sdk/`의 httpx 왕복 경로
- **승격**: `service/app/logic/`을 llm-request manager SDK의 본체로
- **유지**: public API 시그니처(`llm_request_async`, `llm_request`, `done_check`, `fetch_by_cache_key`, `delete_cache*` 등)는 그대로. 내부 배선만 "httpx로 서버 호출" → "logic 직접 호출"로 교체

→ 사용자 import(`from llm_request import llm_request_async`)는 **변경 없음**. 외부 영향 0, 내부 한 겹만 걷어내는 작업.

### 의식 사항 (단 하나)

`keying.py`의 canonicalize는 이제 **분산 계약**이다. 변경 시 캐시가 쪼개지므로 → **키 동결 + 변경 시 fallback 기간 필수** 규칙을 지킨다. (file-manager가 이미 같은 규칙으로 운영 중.)
