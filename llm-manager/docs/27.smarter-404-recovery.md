# 27. Smarter Gemini 404 복구 — files_api 보존

> 상태: **설계 (backlog, 미예약)**. docs/26 작업과 별개 feature. 구현 일정 미정.
> 관련: docs/07(inline-vs-files-api §9), docs/26(file_preprocessing + delete/update_context_cache)

---

## 1. 배경 / 문제 정의

Gemini 호출이 404 를 내면 `resolve_files_after_404` 가 복구한다. 그런데 현재 복구는
**shotgun** — 영향 checksum 의 `files_api:{cs}` 키와 `context_cache:{hash_key}` 키를
**무조건 둘 다 삭제**한 뒤 `resolve_files` 를 다시 불러 **파일을 재업로드**한다
([resolver.py:512-533](../llm_manager/_internal/file_processing/resolver.py)).

문제: **context cache 가 404 인 경우에도 Files API URI 까지 버린다.** Gemini 에서
context cache 와 Files API 파일은 **수명이 별개**다(cache=`context_cache_ttl` 예 30분,
URI=48h). context cache 만 만료돼 404 가 나도 URI 는 대개 멀쩡한데, 현재 코드는 그걸
확인 없이 폐기하고 재업로드한다 → **불필요한 업로드 비용·지연**.

대표 트리거: 누군가 Gemini cache id 로 context cache 만 직접 만료시켜(또는 cache TTL 이
URI 보다 먼저 만료돼) Redis 엔 stale context_cache 키가 남은 경우. 다음 사용에서
Redis HIT → Gemini 404 → 현재 복구가 URI까지 재업로드. (docs/26 §"name-direct delete"
논의에서 도출된 비효율.)

## 2. 사전 정보 (코드로 확정)

### 2.1 현재 복구는 origin 을 구분하지 않는다

`resolve_files_after_404` 는 404 가 **어느 자원에서 났는지 모른다**:
- 호출 payload 엔 `cached_content`(있으면) 또는 `uri_parts` 가 들어간다.
- URI 가 404 면 **재업로드 필수**. context cache 만 404 면 **URI 재업로드 불필요**.
- 구분 못 하니 최악을 가정(URI 도 죽었을 수 있다)하고 둘 다 재건 — 안전하지만 과함.

### 2.2 origin 구분은 원리상 가능

404 를 일으킨 호출이 **`cached_content` 를 썼는지**가 핵심 신호다:
- `_apply_resolved` 가 `cached_content` 를 세팅했으면(=context cache 사용) → 404 는
  **context cache 쪽일 가능성이 큼** → URI 보존 + cache 만 재생성으로 시도.
- `cached_content` 없이 `uri_parts` 만 썼으면 → 404 는 **URI 쪽** → 기존대로 재업로드.

runner 의 `_do_llm_call`/`_do_llm_stream` 이 404 를 잡는 지점에서 "이번 호출이
cached_content 를 썼나"를 복구 함수에 넘기면 분기할 수 있다.

### 2.3 비용 차이 (왜 가치 있나)

| | 현재(shotgun) | 제안(URI 보존) |
|---|---|---|
| context cache 404 시 | files_api 삭제 + **재업로드** + cache 재생성 | cache 만 재생성(URI 재사용) |
| URI 404 시 | 재업로드(정상) | 재업로드(동일) |

context cache 404 가 잦은 워크로드(짧은 `context_cache_ttl`, 파일 재사용)일수록 이득.

## 3. 제안 설계 (초안 — 미확정)

> 아래는 방향 스케치다. 세부(시그니처·신호 전달 방식)는 구현 착수 시 docs/26 식으로
> 섹션 승인받아 확정한다.

1. **404 origin 신호 전달**: runner 가 복구 호출 시 `used_cached_content: bool` 를
   `resolve_files_after_404` 에 전달.
2. **분기**:
   - `used_cached_content=True` → **context_cache 키만 삭제**, files_api 키는 보존.
     `resolve_files` 재호출 시 files_api Redis HIT → 재업로드 없이 cache 재생성.
   - `used_cached_content=False`(또는 불명) → **현행 shotgun 유지**(안전 폴백).
3. **재시도 후 또 404**: 그때는 shotgun 으로 격상(URI 도 의심) — 1회 한정.

### 3.1 검증해야 할 가정 (구현 전 확인)

- [ ] context cache 삭제가 Gemini 에서 Files API 파일을 **연쇄 삭제하지 않는다**는 점
      (별개 수명) — Gemini 공식 문서/실측으로 확인. 만약 연쇄 삭제면 이 설계는 무효.
- [ ] `used_cached_content` 신호를 runner→복구로 넘기는 깔끔한 경로(현 함수 시그니처 영향).

## 4. 에러 / 엣지

- cache 만 재생성하다 **다시 404** → 이번엔 URI 도 의심하여 shotgun(재업로드). 무한루프
  방지 위해 복구는 총 1회(기존 정책 유지).
- too-small fail-soft, dedup standby 등 기존 경로와의 상호작용은 구현 시 재점검.
