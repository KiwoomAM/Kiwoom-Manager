# 37. 스트리밍으로 함수 호출 쓰기 — 이벤트 통과(A) + 대화용 함수 신설(B)

관련: [KiwoomAM/Kiwoom-Manager#99](https://github.com/KiwoomAM/Kiwoom-Manager/issues/99) · [KiwoomAM/Kiwoom-Rag#875](https://github.com/KiwoomAM/Kiwoom-Rag/issues/875) · 선결이었던 [docs/35](35.stored-files-orthogonal-to-cache-flags.md) 는 해소됨(§7)

기준: **`6d3675c`** — PR #100 의 head 이자 `origin/main`(머지 커밋 `e0d5b0f`, 2026-09-02)과 트리가 동일하다. #100 이 `_events()` 를 다시 쓰고 sync 스트림을 진짜 증분으로 바꿨으므로 A 는 그 위에 쌓는다. **llm-manager 쪽 줄 번호는 전부 `6d3675c` 기준**이고, 소비자(Kiwoom-Rag) 레포 인용은 §2.8 이 밝히는 별도 SHA 기준이다.

## 1. 배경 / 문제 정의

도구를 스트리밍으로 쓰려는 소비자가 매니저를 못 쓴다. 원인이 둘인데 **서로 독립이고 여는 것이 다르다.**

| | 무엇이 막혀 있나 | 고치면 열리는 것 |
|---|---|---|
| **A** | 스트림 이벤트에서 함수 호출이 버려진다 | **챗봇 밖 영역의 도구 호출 스트리밍** — 단발(1라운드)은 이것만으로 완결된다 |
| **B** | 대화용 입구가 없다 | 챗봇처럼 대화·첨부·도구를 함께 쓰는 경로 |

**A 는 B 의 준비 단계가 아니다.** `tools` 는 이미 매니저를 그대로 통과하고 모델도 함수 호출을 돌려주므로, 마지막 한 겹만 고치면 단발 도구 호출이 스트리밍으로 곧장 된다. 비스트림(`llm_request_async`)은 이미 되고 있다.

**(A) 매니저가 스트림 이벤트에서 함수 호출을 버린다.** [`__init__.py:301-317`](../llm_manager/__init__.py#L301-L317) 의 `_events()` 가 `StreamChunk` 를 이벤트 dict 로 옮기면서 `text`·`finish_reason`·`usage` 셋만 고른다. 나머지 일곱(`function_calls`·`tool_calls`·`tool_responses`·`code_blocks`·`code_results`·`grounding`·`url_context`)이 여기서 사라진다.

**(B) 매니저에 대화용 입구가 없다.** 매니저의 입력 계약은 `contents`(+`history`) 뿐이고, `messages` 를 억지로 끼워 넣으면 캐시 키가 대화를 못 보고 첨부와 같이 쓰면 예외가 난다(§2.7). 다만 이것은 **표현 불가가 아니라 불편**이다 — 도구 루프 자체는 `contents`+`history` 로도 표현된다(§2.6).

그래서 kiwoom-rag 챗봇 오케스트레이터는 매니저를 건너뛰고 [`aio.stream`](../llm_manager/_internal/handler_client/aio.py#L180) 을 직접 부른다.

**소비자가 그 갭을 스스로 메운 흔적이 이미 남아 있다.** Kiwoom-Rag 가 2026-09-01 첨부를 참조로 바꾸면서(머지 커밋 `032da17b`; 아래 인용 줄 번호는 §2.8 이 밝히는 `ca62c2bf` 기준), 공개 API `file_preprocessing_async` 를 **직접** 불러 주소를 받아다 `Part.from_uri` 로 붙인다. 원래 문제였던 "5MB PDF 가 상태 채널에 18.33MB 로 앉는다"(Kiwoom-Rag#875)는 그렇게 닫혔다.

**닫힌 것은 증상이고 갭은 남았다.** `file_preprocessing_async` 는 docstring 이 밝히듯 *"파일 전처리만 실행 — LLM 호출 없음"* 인 **반쪽 경로**다. 소비자가 그 길로 얻지 못하는 것이 넷이다.

- **Gemini 404 자동 복구.** 복구는 `_do_llm_stream`/`_do_llm_call` 안에 있어 매니저가 LLM 호출을 소유해야 돈다. 게다가 소비자가 이미 `Part.from_uri` 로 굳혀 넘기므로 매니저는 그 주소의 출처를 몰라 **원리적으로도** 복구할 수 없다. Files API 주소는 48h 시한부다.
- **응답 캐시 · dedup standby**
- **왕복이 둘** — 전처리 한 번, LLM 호출 한 번.
- **거친 모서리를 소비자가 떠안는다.** 파일을 하나씩 넘기고 있는데, 코드 주석이 이유를 적어 뒀다 — *"모아 넘기면 `file_preprocessing_async` 가 목록 전체를 fail-fast 로 …"*.

즉 B 의 근거는 사라진 것이 아니라 **더 구체적인 증거로 바뀌었다** — 소비자가 갭을 메우려고 실제로 코드를 썼고, 그 우회의 대가가 위 넷이다.

## 2. 사전 정보 — 코드로 확정

### 2.1 밑단은 함수 호출을 온전히 지원한다

[`models.py:191-203`](../llm_manager/_internal/handler_client/models.py#L191-L203) 의 `StreamChunk` 는 열 필드를 갖는다. [`models.py:300-326`](../llm_manager/_internal/handler_client/models.py#L300-L326) 의 `Part` 는 `function_call`·`function_response` 를 포함한 아홉 타입을 갖고, 모든 Part 에 `thought_signature` 가 달려 있다. [`_common.py:148-171`](../llm_manager/_internal/handler_client/_common.py#L148-L171) 의 `is_valid_response` 는 텍스트가 없어도 `function_calls` 만 있으면 유효 턴으로 쳐서 이력에 남긴다 — `thought_signature` 사슬을 끊지 않기 위해서다.

### 2.2 값은 매니저까지 온전히 도달한다

[`runner.py:618-655`](../llm_manager/_internal/runner.py#L618-L655) 의 `_do_llm_stream` 은 `aio_stream` 이 준 청크를 손대지 않고 그대로 `yield` 한다. 즉 유실은 **마지막 한 겹**에서만 일어난다.

### 2.3 의도적 제거가 아니다

같은 파일의 [`_to_stream_chunk`](../llm_manager/_internal/runner.py#L368-L381)(캐시 히트 경로)는 열 필드를 전부 옮긴다. 모델도 밑단도 지원한다는 뜻이다. 필드 선택 블록만 좁혀 `git log -L 307,314:llm-manager/llm_manager/__init__.py` 를 돌리면 커밋이 둘이다 — `37cde32`("LLMManager SDK 변환")에서 지금 모양으로 태어났고, 이후 유일한 변경인 `8623bed`(#100)는 `try` 안으로 들여쓴 것뿐이다. **필드를 뺀 커밋이 없다.**

### 2.4 비스트림은 멀쩡하다

[`runner.py:278`](../llm_manager/_internal/runner.py#L278) 의 `finalize` 가 `LLMResponse` 객체를 손대지 않고 반환한다. 저장·복원도 `model_dump()` / `model_validate()` 전체 왕복이라 보존된다. **유실은 "객체를 통과시키느냐, dict 를 새로 짓느냐"의 차이에서만 나온다.**

### 2.5 도구와 캐시는 충돌하지 않는다

Context Cache 는 opt-in 이다(`context_cache_ttl` 기본 `None`). [`_apply_resolved`](../llm_manager/_internal/runner.py#L386-L426) 가 `tools`·`tool_config` 를 제거하는 분기는 `if resolved.cached_content:` 안쪽뿐이라, 캐시를 안 켜면 도구가 그대로 살아남는다.

### 2.5-1 도구 정의 형식 — 감싸면 핸들러가 500 을 낸다 (실측)

라이브 호출로 확인했다. `tools` 는 **평평한 dict 목록**이다.

```python
tools = [{"name": "get_stock_price", "description": "종목 현재가를 조회한다",
          "parameters": {"type": "object", "properties": {...}, "required": [...]}}]
```

Gemini 원문서 관례대로 `[{"function_declarations": [...]}]` 로 감싸면 **`HandlerInternalError` (500)** 이 난다. 내장 도구는 `[{"google_search": {}}]` 꼴이다(`tests/handler_sdk/test_async.py:284`). README 의 `llm_input` 키 목록에 `tools` 는 있으나 **예시가 없어** 처음 쓰는 사람이 반드시 한 번 밟는다. README 에 이 예시를 넣는 것을 A 의 후속으로 남긴다.

### 2.6 도구 루프에 `messages` 가 필수는 아니다

[`_common.py:304-307`](../llm_manager/_internal/handler_client/_common.py#L304-L307) 의 `build_body` 는 대화 표현 셋을 배타로 강제한다.

| 형태 | 인자 | 마지막 턴의 role |
|---|---|---|
| ① | `contents` | `user` (강제) |
| ② | `contents` + `history` | `user` (강제) |
| ③ | `messages=[Content, …]` | 호출자가 정함 |

①②는 [`_common.py:317-321`](../llm_manager/_internal/handler_client/_common.py#L317-L321) 에서 마지막에 `{"role": "user", …}` 를 무조건 붙인다. 그래서 처음엔 "도구 라운드 2회차부터는 마지막 턴이 도구 응답이라 ③이 아니면 표현이 안 된다"고 봤으나, **코드를 확인해 보니 과장이었다.**

- `history` 는 [`_common.py:317-318`](../llm_manager/_internal/handler_client/_common.py#L317-L318) 에서 `msgs.extend(history)` 로 **그대로 이어붙는다.** 역할 제한이 없어 모델의 함수 호출 턴·도구 응답 턴을 다 담는다. ②와 ③은 결국 같은 `body["messages"]` 를 만든다.
- 소비자의 실제 대화가 **언제나 `user` 턴으로 끝난다.** kiwoom-rag 는 도구 결과를 `role="user"` 턴에 싣고([`execute_workers.py:245`](https://github.com/KiwoomAM/Kiwoom-Rag/blob/ca62c2bf/src/backend/core/graph/nodes/execute_workers.py#L245)), 최종 답변 단계에서는 지시 문장을 담은 `user` 턴을 하나 더 붙인다([`response_generator.py:37-51`](https://github.com/KiwoomAM/Kiwoom-Rag/blob/ca62c2bf/src/backend/core/graph/nodes/response_generator.py#L37-L51) — 그게 없으면 모델이 답 대신 함수 호출을 시도해 빈 응답이 난다고 실측 주석까지 달려 있다).
- 밑단 [`AsyncSession.send_tool_results`](../llm_manager/_internal/handler_client/_async_session.py#L187-L265) 가 ③을 쓰는 이유도 docstring 에 *"**빈** user message append 우회"* 라고 적혀 있다. 넣을 내용이 있으면 우회할 이유가 없다.

**즉 `messages` 가 진짜 필요한 경우는 대화를 `user` 가 아닌 턴으로 끝내려 할 때뿐이다.** ③이 주는 것은 가능/불가능이 아니라 표현의 자연스러움이다. (②로 도구 루프가 실제로 도는지는 미검증 — B 착수 전 실측 대상.)

### 2.6-1 지금 도구를 쓰는 곳은 챗봇뿐이다

사내 전 레포에서 `tools`·함수 선언을 만드는 곳은 **Kiwoom-Rag 하나**다. ETF·ESG·GM·PF·EM·Parsing·STT 어디에도 없다. 그래서 A 가 여는 "챗봇 밖 도구 호출"은 지금 사용자가 0 인 **새 능력**이다 — 회귀 위험이 없고, 반대로 A 없이는 그 영역이 스트리밍에서 계속 막혀 있다.

### 2.7 `messages` 에 대해 매니저가 모르는 네 곳

| # | 위치 | 증상 |
|---|---|---|
| ㄱ | [`_apply_resolved`](../llm_manager/_internal/runner.py#L416-L426) | 두 분기 모두 `call_input["contents"]` 를 반드시 세팅 → `messages` 와 동시에 실려 `build_body` 가 `ValueError` |
| ㄴ | [`keying._LLM_INPUT_FIELDS`](../llm_manager/_internal/keying.py#L23-L43) | `messages` 없음 → 대화 내용이 캐시 키에서 통째로 빠짐 |
| ㄷ | [`__all__`](../llm_manager/__init__.py#L130-L151) · [`aio.__all__`](../llm_manager/aio.py#L40-L60) | `Content`·`FunctionResponse` 공개 export 없음 → 소비자가 `_internal` 을 뚫음 |
| ㄹ | [README `llm_input` 키 목록](../README.md#L338-L359) | `contents` 필수로만 적혀 있음 |

ㄱ은 **첨부가 있을 때만** 터진다. `prep.files` 가 비면 `_apply_resolved` 를 안 타므로 `messages` + `tools` 는 지금도 동작한다. 하필 이 작업이 원하는 조합(도구 + 참조 첨부)에서만 터지는 셈이다.

ㄴ은 조용히 틀린다. `cache_mode=False` 면 읽기는 피하지만 `save_mode` 는 기본 `True` 라, 대화가 안 섞인 키로 기록이 남는다.

### 2.8 소비자가 지금 하는 일 (Kiwoom-Rag `ca62c2bf` — 2026-09-02 시점 main)

| 위치 | 내용 |
|---|---|
| `core/graph/nodes/llm_node.py:51` | `aio.stream(messages=…, tools=…)` 직행 — 매니저 우회 |
| `utils/client.py:15` | `from llm_manager._internal.handler_client import Content` — 공개 export 가 없어 내부를 뚫음 |
| `utils/client.py:102` `_resolve_uris` | `file_preprocessing_async` 를 **파일당 한 번씩** 직접 호출해 주소를 받음 |
| `utils/client.py:237` | `Part.from_bytes(…)` — 이제 **영속화 실패 시 폴백**으로만 남음 |
| `utils/client.py:254` `read_stream_chunk` | `chunk.function_calls` 를 **객체로** 읽어 `thought_signature` 를 꺼냄 |

**줄 번호를 이 커밋으로 못 박아 둔다.** 이 문서 초안은 16 커밋 뒤처진 로컬 브랜치(`fix/ETF_bug`)를 읽고 썼다가 전부 어긋나 있었다 — 소비자 레포는 인용 전에 `origin/main` 을 fetch 해서 대조할 것.

마지막 줄이 A 의 설계에 영향을 준다 — 소비자는 `assistant_message` 가 아니라 `function_calls` + `text` 로 다음 턴을 재조립한다. **따라서 A 는 `assistant_message` 를 이벤트로 노출하지 않아도 된다**(§6). 챗봇 자체의 이관은 A 로 열리지 않는다 — `messages` + 첨부 조합이 §2.7ㄱ 에 걸리므로 B 가 필요하다. 즉 **A 는 착수 시점에 소비자가 0 인 채로 나간다**(§2.6-1).

## 3. 설계 — A: 이벤트 통과

### 3.1 변경 지점

[`__init__.py`](../llm_manager/__init__.py#L301-L317) 의 `_events()` 하나. #100 이 이 함수에 `try/finally` + `chunk_stream.aclose()`(standby 리더 토큰 해제)를 넣었으므로 그 `try` 안에 얹는다. `usage` 와 동일하게 **값이 있을 때만** 넣어 기존 소비자의 이벤트 모양을 바꾸지 않는다.

```python
_LIST_FIELDS = ("function_calls", "tool_calls", "tool_responses", "code_blocks", "code_results")
_OBJ_FIELDS = ("grounding", "url_context")

async def _events() -> AsyncGenerator[dict[str, Any], None]:
    try:                                    # ← #100 이 넣은 정리 계약. 건드리지 않는다
        async for chunk in chunk_stream:
            event: dict[str, Any] = {
                "type": "chunk",
                "text": chunk.text,
                "finish_reason": chunk.finish_reason,
            }
            if chunk.usage:
                event["usage"] = chunk.usage.model_dump()
            for name in _LIST_FIELDS:       # ← 여기부터가 이번 변경
                items = getattr(chunk, name)
                if items:
                    event[name] = [item.model_dump() for item in items]
            for name in _OBJ_FIELDS:       # 리스트가 아닌 필드 (단발성이라는 뜻이 아니다)
                obj = getattr(chunk, name)
                if obj is not None:         # ← truthiness 금지: Grounding() 은 비어도 True
                    event[name] = obj.model_dump()
            yield event
    finally:                                # ← #100 이 넣은 standby 리더 토큰 해제
        await chunk_stream.aclose()
```

두 루프의 조건이 다른 것은 의도다. 리스트 5종은 `if items:` 가 `None` 과 `[]` 를 함께 거르지만, **pydantic 모델은 비어 있어도 truthy** 라(`bool(Grounding())` = `True`, 실행 확인) 컨테이너 2종은 `is not None` 으로 걸러야 한다. 레포의 기존 누적기도 같은 이유로 [`runner.py:313-317`](../llm_manager/_internal/runner.py#L313-L317) 에서 `is not None` 을 쓴다. 즉 §3.1 의 "값이 있을 때만"은 **리스트는 빈 값 제거, 컨테이너는 None 제거**라는 뜻이다.

`model_dump()` 로 내리는 이유는 둘이다. 이벤트 계약이 이미 dict 이고(`usage` 가 그렇게 한다), 소비자가 이 이벤트를 다시 SSE 로 직렬화하는 자리라 JSON 으로 떨어지는 편이 안전하다.

### 3.2 docstring — 누적 규칙을 반드시 적는다

`llm_request_stream_async` 의 이벤트 형태 설명이 지금 `{"type","text","finish_reason","usage"?}` 만 적고 있다. 새 선택 키를 적으면서 **누적 규칙을 같이 적는다.**

[`_common.py:43-55`](../llm_manager/_internal/handler_client/_common.py#L43-L55) 의 `extend_stream_field` 가 계약을 못 박아 뒀다 — *"parallel function call N개가 N개 청크로(1개씩) 흩어져 오므로 덮어쓰면 마지막 청크 것만 남는다."* 리스트 5종은 소비자가 `extend` 로 누적해야 한다. 이 규칙을 모르는 소비자가 덮어쓰기로 구현하면 **병렬 함수 호출이 조용히 하나만 남는다.** docstring 이 유일한 방어선이다.

**`grounding`·`url_context` 는 단정하지 않는다.** 매니저 코드는 "턴당 한 번"을 전제로 [`_StreamMeta.update`](../llm_manager/_internal/runner.py#L313-L317) 가 마지막 non-None 으로 덮어쓰는데, 소비자(`Kiwoom-Rag llm_node.py:120-123`)는 *"다중 검색 포함 여러 번 나눠 올 수 있어 dedup 누적한다 — 마지막 것만 취하면 앞 검색 출처가 유실된다"* 며 반대로 걸어 뒀다. **docstring 에는 리스트 5종의 누적 규칙만 적고, 이 두 필드는 "청크별로 온다"까지만 적는다** — 몇 번 오는지 단정하지 않는다.

**`_StreamMeta` 덮어쓰기가 옳은지는 A 밖 별건이다**(§6). A 에 넣지 않는 근거가 셋이다.

- **이슈 #99 요구사항 4개 어디에도 없다.** A 를 그 범위 안에 둔다.
- **'extend' 가 한 단어로 안 끝난다.** `Grounding` 은 리스트가 아니라 컨테이너이고, 그 안 [`GroundingSupport.chunk_indices`](../llm_manager/_internal/handler_client/models.py#L117-L121) 는 **자기 청크 안에서의 인덱스**다. 두 청크의 `chunks` 를 이어붙이면 뒤 청크의 supports 가 앞 청크의 출처를 가리킨다 — 인용 매핑이 조용히 뒤바뀐 채 저장된다. 필드별 병합 규칙과 재인덱싱을 정해야 하는데 그 순간 #99 범위를 벗어난다.
- **고쳐도 수렴하지 않는다.** 응답 캐시는 기본 TTL 이 없어(`mdb_ttl` 기본 `None` → `expires_at` 자체가 안 붙는다) 이미 저장된 문서가 영구히 남고, 캐시 키는 입력에서만 나오므로 같은 입력은 계속 옛 문서에 히트한다. "고치면 캐시와 라이브가 일치한다"는 **기존 키에서는 참이 되지 않는다.**

**캐시 히트 모양도 한 줄 적는다.** 캐시 히트 스트림은 [`_to_stream_chunk`](../llm_manager/_internal/runner.py#L368-L381) 가 만든 **이벤트 하나**가 전부라, `text`(전문)와 도구 필드가 **같은 이벤트에** 실린다. 라이브에서는 도구 필드가 text 없는 청크로 따로 오는 것이 보통이므로, `if ev.get("text"): 토큰 else: 도구` 로 짠 소비자는 캐시 히트마다 함수 호출을 조용히 버린다 — 기존 소비자 Kiwoom-PF `chat.py:115-125` 가 실제로 그 구조다.

**sync 쪽도 갱신한다.** 이슈 #99 요구사항 2 가 `llm_request_stream_async` **와 `llm_request_stream` 둘 다**를 명시했다. sync([`__init__.py:422`](../llm_manager/__init__.py#L422))는 같은 이벤트 dict 를 주므로 누적 규칙을 모르면 똑같이 병렬 함수 호출을 잃는다. **다만 계약 전문을 복제하지 않는다** — 같은 계약이 두 docstring 에 앉으면 필드가 늘 때 사람이 두 곳을 맞춰야 한다(`SSOT`). `llm_request_stream_async` 의 이벤트 계약을 가리키는 **한 줄만** 넣는다.

### 3.3 기각한 대안

**객체를 그대로 통과** — `event["function_calls"] = chunk.function_calls`(Pydantic 객체 리스트). 소비자가 지금 객체로 읽고 있어 이관 비용이 0 이라는 장점이 있으나, 이벤트가 JSON 직렬화 불가가 되고 `usage` 와 규칙이 갈린다. 이벤트 dict 라는 계약을 지키는 쪽을 택했다.

**필드를 명시적으로 일곱 번 나열** — `_to_stream_chunk` 의 스타일과 맞으나, "값 있을 때만 + 리스트는 각각 dump" 조건이 붙어 7×4줄이 된다. 상수 두 줄 + 루프가 읽기 쉽다고 판단했다.

## 4. 설계 — B: 대화용 함수 신설

> **superseded — 이 절은 [docs/38](38.chat-function.md)로 대체됐다.** 이 절은 첨부가 바이트로 상태 채널에 앉아 있는 상태를 전제로 표찰(§4.3의 ④)과 `stored_files` 인자를 설계했다. 그 뒤 Kiwoom-Rag 챗봇이 첨부를 주소 블록으로 바꿔 두어 전제가 달라졌고, 대화 함수의 입력·반환·캐시·실패 처리 결정이 모두 다시 정해졌다. 아래 내용은 보존 목적이며 새 작업의 근거로 쓰지 않는다.

### 4.1 왜 기존 함수를 고치지 않고 새로 만드나

매니저의 **`llm_request*` 계열은 대화를 다뤄본 적이 없다.** `history` 인자는 있으나 사내 유일 사용처가 ESG `company_matcher` 의 few-shot 예시 상수이고(파일 없음), `stored_files` 사용처(7개 레포 26개 파일 — ETF·ESG·GM·PF·EM·Parsing·Rag)는 전부 단발 호출이다. 즉 `contents`+`history`+`stored_files` 삼박자는 한 번도 밟히지 않은 구석이다.

다만 밑단에는 대화 수단이 이미 있다 — `Session`·`AsyncSession` 이 공개 export 이고 `send_tool_results` 가 도구 루프까지 풀어 뒀다. 없는 것은 **그 대화 수단과 매니저의 파일·캐시·복구를 함께 쓰는 길**이다.

용도가 갈리는 지점이 분명하다.

| | 단발 (기존 `llm_request*`) | 대화 (신설) |
|---|---|---|
| 대화 표현 | `contents`(+`history`) | `messages` |
| 응답 캐시 | 켬 — 핵심 가치 | 꺼야 함 — 매 턴 키가 갈려 히트 0 |
| 도구 | 거의 안 씀 | 핵심 |
| 파일 위치 | 이번 발화 하나 | 여러 발화에 흩어짐 |

한 함수로 합치면 "이 인자를 쓸 때만 적용되는" 조건부 규칙이 쌓인다(`EXPLICIT` 위반). 나누면 대화용 함수의 계약이 **조건 없이** 성립하고, 기존 소비자는 한 글자도 안 건드린다.

기각한 대안 — `llm_input` 에 `messages` 키를 더하기. README 가 `llm_input` 을 "handler `call()` 파라미터 대부분과 동일"로 정의하므로 계층 일관성은 이쪽이 낫다. 다만 위 표의 기본값 충돌을 조건부 규칙으로 떠안게 되어 기각했다. 대신 README 에 "단발용이라 `messages` 는 받지 않는다"를 명시해 구멍이 아니라 의도임을 남긴다.

### 4.2 만들 것

```
llm_chat_async(...)         -> (LLMResponse, ResponseMeta)
llm_chat_stream_async(...)  -> (AsyncIterator[dict], meta)
```

`messages` 만 받는다(`contents`·`history` 는 거부). async 만 만든다 — 소비자가 전부 async 다. 내부는 기존 `runner` 를 그대로 부르는 얇은 층으로 둔다(`llm_request` 가 `llm_request_async` 의 얇은 래퍼인 것과 같은 패턴).

응답 캐시(`cache_mode`·`save_mode`)는 인자로 남기되 **기본값을 `False`** 로 둔다. 재시도 상황의 여지는 남기고, 모르고 켜두어 조용히 낭비하는 일은 막는다.

### 4.3 첨부 위치 — 자리표시자(④) 채택

`stored_files` 는 평평한 목록이라 **"몇 번째 발화의 첨부"라는 정보가 없다.** 단발에서는 붙일 자리가 하나뿐이라 문제가 안 됐으나, 대화에서는 매니저가 추측해야 한다.

네 안을 검토했다.

| 안 | 위치 | 판정 |
|---|---|---|
| ① | 마지막 `user` 발화 앞 | 기각 — 소비자가 도구 결과를 `user` 발화로 실어서, 라운드 2회차부터 도구 결과 옆에 붙는다 |
| ② | 첫 `user` 발화 앞 | 기각 — `messages` 에 대화 전체가 들어와, 오늘 붙인 파일이 어제 첫 발화에 붙는다 |
| ③ | 파일 전용 발화를 맨 앞에 신설 | 기각 — 아래 |
| **④** | **소비자가 남긴 자리표시자를 매니저가 치환** | **채택** |

**④ 채택 근거 넷.**

1. **소비자가 이미 그 구조다.** 챗봇은 파일을 그 발화 안에 넣는다([input_processor.py:97-102](https://github.com/KiwoomAM/Kiwoom-Rag/blob/ca62c2bf/src/backend/core/graph/nodes/input_processor.py#L97-L102)). 위치 정보는 실재하고, `stored_files` 라는 API 모양이 그것을 버릴 뿐이다. ④는 없는 정보를 요구하는 게 아니라 **버리지 않는** 것이다.

> ⚠️ **이 근거는 다시 봐야 한다.** 소비자가 2026-09-01 에 이미 바이트를 참조로 바꿨다(§1). "바이트에서 경로 한 줄로 바꾸는 것뿐"이라던 이관 비용 서술은 그 변경으로 이미 치러졌고, 지금 소비자는 `file_preprocessing_async` 로 **자기가 주소를 받아** `Part.from_uri` 를 붙인다. ④ 가 요구하는 것은 이제 "바이트를 표찰로"가 아니라 "**소비자가 직접 푼 주소를 다시 매니저에 맡기기**"다 — 방향이 반대라 이관 비용도 다르다. B 착수 전 §4.3 전체를 소비자 현황 기준으로 재검토할 것.
2. **Gemini 원본 구조와 같다.** Gemini 에는 "파일 목록" 인자가 없다 — 파일은 언제나 어떤 발화의 조각이다. 매니저가 자리표시자를 실제 조각으로 치환하고 나면 Gemini 가 받는 모양은 원본과 동일하다.
3. **여러 턴 첨부에서 지시어가 산다.** 1턴 A.pdf · 3턴 B.pdf 인 대화에서 "이건 어때?" 가 무엇을 가리키는지 유지된다. ③은 둘을 한 덩어리로 앞에 몰아 이 구분을 잃는다.
4. **암묵 캐시에 유리하다.** Gemini 2.5+ 는 앞부분이 겹치면 자동으로 75% 할인한다(별도 설정 없음, 모델별 최소 토큰 조건 있음 — 2.5 Flash 1,024 / 2.5 Pro 2,048 / 3.x Flash 4,096). ④는 새 파일이 새 발화(맨 뒤)에 붙어 앞부분이 불변이므로 **새 턴만** 재계산된다. ③은 새 파일을 맨 앞에 끼워 넣어 그 지점부터 뒤가 전부 미적중이 된다. 구글 권고("앞부분은 그대로 두고 매번 바뀌는 것은 끝에")와도 ④가 일치한다.

**치환 규약.** 자리표시자는 파일 경로만 담고, 같은 파일을 `stored_files` 로도 넘긴다(메타 6필드가 checksum·dedup 에 필요). 매니저가 경로로 짝지어 치환하며, 밑단(handler)으로 나가기 전에 전부 사라진다. **짝이 안 맞으면(표찰만 있거나 파일만 왔거나) 그 자리에서 실패시킨다** — 조용히 넘기면 모델이 파일을 못 본 채 그럴듯한 답을 만든다(`FAIL-LOUD`).

**검토 중 바로잡은 오해 둘.** 기록으로 남긴다.

- *"Context Cache 를 쓰려면 파일을 앞으로 몰아야 하니 위치 보존과 배타"* — **틀렸다.** Gemini 는 대화 이력을 발화 목록 그대로 캐시할 수 있고, Anthropic 도 캐시는 접두사 경계 표시일 뿐 파일을 옮기지 않는다. 배타로 보인 것은 우리 `create_cache` 가 역할 없는 조각 목록(`ContentsType`)만 받아 대화 구조를 못 담기 때문이다. handler 쪽 별건이며, 열리면 ④가 그대로 얹힌다.
- *"앞에 몰면 모델이 더 정확히 읽는다"(Lost in the Middle)* — 근거로 못 쓴다. 긴 컨텍스트의 U자 곡선은 알려진 현상이나, 최근 측정에서 Gemini 2.5 Flash 는 위치에 따른 열화가 관측되지 않았다. 다만 챗봇 실제 모델은 `gemini-3.7-flash`(`Kiwoom-Rag utils/client.py:14` 기본값)라 그 측정과 같은 모델은 아니다 — 즉 이 논거는 **양쪽 다 근거가 약하다**.

### 4.4 캐시 키 — `messages` 를 넣되 파일은 넣지 않는다 🔴

`_LLM_INPUT_FIELDS` 에 `messages` 가 없어 대화 내용이 캐시 키에서 통째로 빠진다. 추가해야 한다.

다만 그냥 추가하면 안 된다. [`keying.py:159-164`](../llm_manager/_internal/keying.py#L159-L164) 의 `Part` 정규화(base64 `data` 제거)가 **`has_file_checksums` 일 때만** 돌기 때문에, 파일을 인라인한 `messages` 는 base64 통째가 `str(obj)` fallback 으로 키에 들어간다.

④가 이 문제를 자동으로 닫는다 — 파일은 `stored_files` 로만 오고 `messages` 에는 자리표시자(경로 한 줄)만 남으므로, 파일은 기존대로 `file_checksums` 로 키에 들어간다.

**🔴 남은 결정 — 규약을 어겼을 때(`messages` 안에 실제 파일 조각이 있을 때) 거부할 것인가, 경고만 남길 것인가.** `FAIL-LOUD` 로는 거부가 맞으나, 소비자 이관 과도기에 섞여 올 여지가 있다.

### 4.5 공개 export

`Content` 와 `FunctionResponse` 를 [`__init__.py`](../llm_manager/__init__.py#L130-L151) 와 [`aio.py`](../llm_manager/aio.py#L40-L60) 양쪽 `__all__` 에 추가한다. 지금 소비자가 `_internal` 을 뚫고 있고, Kiwoom-Rag 테스트에는 `# 공개 export 없음` 주석까지 달려 있다. 결정 사항이 아니라 누락 보정이다.

### 4.6 인자 모양 🔴

**🔴 남은 결정.** (가) 기존 스타일대로 설정 dict 하나를 받는다 — SDK 전체가 한 스타일로 유지되고 생성 파라미터를 다시 나열하지 않는다. (나) 인자를 펼친다 — 읽기는 명확하나 생성 파라미터 10개를 세 번째로 나열하게 되어(handler `call()`·`stream()` 에 이미 두 벌) 추가 시 세 곳을 고쳐야 한다.

## 5. 테스트 계획 (TDD — 실패하는 테스트 먼저)

### 5.1 A

공개 이벤트 계층 테스트는 **이미 있다** — #100 이 `tests/test_sync_stream.py` 를 추가하면서 공개 `llm_request_stream_async`·`llm_request_stream` 을 부르고 이벤트 dict 를 직접 단정한다(`assert first["text"] == "c0"`). `tests/_internal/test_runner_standby.py` 에도 `runner.aio_stream` 을 갈아끼워 실 사슬로 이벤트를 확인하는 케이스가 들어왔다.

**없는 것은 필드 통과 축이다.** 기존 둘은 정리 계약과 증분성을 붙들 뿐 `function_calls` 같은 필드가 이벤트에 실리는지는 보지 않는다. 축이 다르므로 새 파일 `tests/test_public_stream_events.py` 를 열되, `test_sync_stream.py` 의 `_patch_stream` 헬퍼를 재사용해 패치 방식을 한 곳에 둔다(`SSOT`).

| 테스트 | 붙드는 계약 |
|---|---|
| `test_all_stream_chunk_fields_are_covered` | **불변식** — `_LIST_FIELDS ∪ _OBJ_FIELDS` 가 `StreamChunk.model_fields` 에서 `text`·`finish_reason`·`usage` 를 뺀 집합과 정확히 같다 |

| `test_absent_fields_omitted` | 값 없으면 키 자체가 없음 (기존 소비자 모양 불변) |
| `test_list_fields_are_per_chunk` | 두 청크에 나뉜 `function_calls` 가 각 이벤트에 따로 — **이벤트 층은 누적하지 않는다**(저장·캐시 층의 `_StreamMeta` 누적과 별개) |
| `test_grounding_and_url_context_pass_through` | 리스트가 아닌 두 필드도 **청크별로** 그대로 실린다 (매니저가 병합하지 않음) |
| `test_event_is_json_serializable` | `json.dumps(event)` 가 통과 (3.1 의 dump 결정을 붙듦) |

**첫 줄이 핵심이다.** §3.3 에서 필드를 일곱 번 나열하는 대신 상수 튜플 + 루프를 골랐는데, 그러면 `_LIST_FIELDS` 에서 하나를 빠뜨려도 타입 오류도 테스트 실패도 없이 **그 필드만 조용히 사라진다** — 이 문서가 §1 에서 문제로 지목한 바로 그 증상이다. 케이스를 손으로 나열하는 테스트로는 못 잡으므로 불변식으로 붙든다(팀 공통 함정 "테스트 기대치 매직 넘버 금지 — 계약은 불변식으로"). `StreamChunk` 에 필드가 늘면 이 테스트가 스스로 터진다.

다만 **약속의 범위를 정확히 해 둔다.** 이 불변식은 합집합 동치만 검사하므로 필드 **누락**은 잡지만 리스트/컨테이너 **오배치**(새 리스트 필드를 `_OBJ_FIELDS` 에 넣는 것)는 못 잡는다. 그리고 `_events()` 만 덮는다 — 같은 필드 분류가 [`_StreamMeta.update`](../llm_manager/_internal/runner.py#L306-L317)·[`_to_stream_chunk`](../llm_manager/_internal/runner.py#L368-L381)·[`extend_stream_field` docstring](../llm_manager/_internal/handler_client/_common.py#L43-L55) 에도 손으로 나열돼 있어, 캐시 경로의 조용한 유실은 이 테스트로 닫히지 않는다.

**헬퍼는 옮겨서 공유한다.** `_patch_stream` 은 지금 [`tests/test_sync_stream.py:21`](../tests/test_sync_stream.py#L21) 의 모듈 사설 함수다. 이 저장소는 공유 헬퍼를 `conftest.py` 에 두는 관례이고 테스트 모듈끼리 import 하는 사례가 없으므로, `tests/conftest.py` 로 올리고 양쪽이 거기서 가져다 쓴다. 기존 파일 수정은 import 한 줄이다(`SURGICAL`).

더해 기존 [`test_runner.py:641`](../tests/_internal/test_runner.py#L641) 의 `_to_stream_chunk` 테스트가 `url_context` 만 보고 있어 `function_calls` 케이스를 하나 더한다. 이슈 #99 요구사항 4번("캐시 히트가 함수 호출을 보존하는지 — 확인만")이 이걸로 닫힌다.
