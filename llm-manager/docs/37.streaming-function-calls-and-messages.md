# 37. 스트리밍으로 함수 호출 쓰기 — 이벤트 통과(A) + 대화용 함수 신설(B)

관련: [KiwoomAM/Kiwoom-Manager#99](https://github.com/KiwoomAM/Kiwoom-Manager/issues/99) · [KiwoomAM/Kiwoom-Rag#875](https://github.com/KiwoomAM/Kiwoom-Rag/issues/875) · 선결 `docs/35`(작성 중 — 브랜치 `fix/stored-files-with-cache-off`, 아직 미커밋이라 링크 걸지 않음)

기준: **PR #100 head `4c0672c`**(브랜치 `fix/stored-files-with-cache-off`). A 는 이 위에 쌓는다 — #100 이 `_events()` 를 다시 쓰고 sync 스트림을 진짜 증분으로 바꾸며 docs/35 를 해결하므로, main 기준으로 작업하면 충돌한다. 이 문서의 모든 줄 번호는 `4c0672c` 기준이다.

## 1. 배경 / 문제 정의

도구를 스트리밍으로 쓰려는 소비자가 매니저를 못 쓴다. 원인이 둘인데 **서로 독립이고 여는 것이 다르다.**

| | 무엇이 막혀 있나 | 고치면 열리는 것 |
|---|---|---|
| **A** | 스트림 이벤트에서 함수 호출이 버려진다 | **챗봇 밖 영역의 도구 호출 스트리밍** — 단발(1라운드)은 이것만으로 완결된다 |
| **B** | 대화용 입구가 없다 | 챗봇처럼 대화·첨부·도구를 함께 쓰는 경로 |

**A 는 B 의 준비 단계가 아니다.** `tools` 는 이미 매니저를 그대로 통과하고 모델도 함수 호출을 돌려주므로, 마지막 한 겹만 고치면 단발 도구 호출이 스트리밍으로 곧장 된다. 비스트림(`llm_request_async`)은 이미 되고 있다.

**(A) 매니저가 스트림 이벤트에서 함수 호출을 버린다.** [`__init__.py:300-317`](../llm_manager/__init__.py#L300-L317) 의 `_events()` 가 `StreamChunk` 를 이벤트 dict 로 옮기면서 `text`·`finish_reason`·`usage` 셋만 고른다. 나머지 일곱(`function_calls`·`tool_calls`·`tool_responses`·`code_blocks`·`code_results`·`grounding`·`url_context`)이 여기서 사라진다.

**(B) 매니저에 대화용 입구가 없다.** 매니저의 입력 계약은 `contents`(+`history`) 뿐이고, `messages` 를 억지로 끼워 넣으면 캐시 키가 대화를 못 보고 첨부와 같이 쓰면 예외가 난다(§2.7). 다만 이것은 **표현 불가가 아니라 불편**이다 — 도구 루프 자체는 `contents`+`history` 로도 표현된다(§2.6).

그래서 kiwoom-rag 챗봇 오케스트레이터는 매니저를 건너뛰고 [`aio.stream`](../llm_manager/_internal/handler_client/aio.py#L180) 을 직접 부른다. 대가로 매니저가 주는 것을 통째로 잃는다 — `stored_files` 참조 첨부, inline/Files API 자동 분류, Gemini 404 복구, 응답 캐시, Context Cache.

가장 아픈 것은 첨부다. 소비자가 바이트를 직접 인라인해야 해서(`Kiwoom-Rag/src/backend/utils/client.py` 의 `to_llm_messages` → `Part.from_bytes`), 5MB PDF 하나가 LangGraph 상태 채널에 18.33MB 로 앉는다. 이것이 Kiwoom-Rag#875 가 checkpointer 를 못 켜는 직접 원인이다.

## 2. 사전 정보 — 코드로 확정

### 2.1 밑단은 함수 호출을 온전히 지원한다

[`models.py:191-203`](../llm_manager/_internal/handler_client/models.py#L191-L203) 의 `StreamChunk` 는 열 필드를 갖는다. [`models.py:300-326`](../llm_manager/_internal/handler_client/models.py#L300-L326) 의 `Part` 는 `function_call`·`function_response` 를 포함한 아홉 타입을 갖고, 모든 Part 에 `thought_signature` 가 달려 있다. [`_common.py:148-171`](../llm_manager/_internal/handler_client/_common.py#L148-L171) 의 `is_valid_response` 는 텍스트가 없어도 `function_calls` 만 있으면 유효 턴으로 쳐서 이력에 남긴다 — `thought_signature` 사슬을 끊지 않기 위해서다.

### 2.2 값은 매니저까지 온전히 도달한다

[`runner.py:618-655`](../llm_manager/_internal/runner.py#L618-L655) 의 `_do_llm_stream` 은 `aio_stream` 이 준 청크를 손대지 않고 그대로 `yield` 한다. 즉 유실은 **마지막 한 겹**에서만 일어난다.

### 2.3 의도적 제거가 아니다

같은 파일의 [`_to_stream_chunk`](../llm_manager/_internal/runner.py#L368-L381)(캐시 히트 경로)는 열 필드를 전부 옮긴다. 모델도 밑단도 지원한다는 뜻이다. `git log -L 291,300:llm-manager/llm_manager/__init__.py` 결과도 커밋 `37cde32`("LLMManager SDK 변환") 하나뿐이고, 이후 이 필드를 뺀 커밋이 없다. 처음부터 이 모양으로 태어났다.

### 2.4 비스트림은 멀쩡하다

[`runner.py:278`](../llm_manager/_internal/runner.py#L278) 의 `finalize` 가 `LLMResponse` 객체를 손대지 않고 반환한다. 저장·복원도 `model_dump()` / `model_validate()` 전체 왕복이라 보존된다. **유실은 "객체를 통과시키느냐, dict 를 새로 짓느냐"의 차이에서만 나온다.**

### 2.5 도구와 캐시는 충돌하지 않는다

Context Cache 는 opt-in 이다(`context_cache_ttl` 기본 `None`). [`_apply_resolved`](../llm_manager/_internal/runner.py#L386-L426) 가 `tools`·`tool_config` 를 제거하는 분기는 `if resolved.cached_content:` 안쪽뿐이라, 캐시를 안 켜면 도구가 그대로 살아남는다.

### 2.6 도구 루프에 `messages` 가 필수는 아니다

[`_common.py:304-307`](../llm_manager/_internal/handler_client/_common.py#L304-L307) 의 `build_body` 는 대화 표현 셋을 배타로 강제한다.

| 형태 | 인자 | 마지막 턴의 role |
|---|---|---|
| ① | `contents` | `user` (강제) |
| ② | `contents` + `history` | `user` (강제) |
| ③ | `messages=[Content, …]` | 호출자가 정함 |

①②는 [`_common.py:317-321`](../llm_manager/_internal/handler_client/_common.py#L317-L321) 에서 마지막에 `{"role": "user", …}` 를 무조건 붙인다. 그래서 처음엔 "도구 라운드 2회차부터는 마지막 턴이 도구 응답이라 ③이 아니면 표현이 안 된다"고 봤으나, **코드를 확인해 보니 과장이었다.**

- `history` 는 [`_common.py:317-318`](../llm_manager/_internal/handler_client/_common.py#L317-L318) 에서 `msgs.extend(history)` 로 **그대로 이어붙는다.** 역할 제한이 없어 모델의 함수 호출 턴·도구 응답 턴을 다 담는다. ②와 ③은 결국 같은 `body["messages"]` 를 만든다.
- 소비자의 실제 대화가 **언제나 `user` 턴으로 끝난다.** kiwoom-rag 는 도구 결과를 `role="user"` 턴에 싣고([`execute_workers.py:225-227`](https://github.com/KiwoomAM/Kiwoom-Rag/blob/main/src/backend/core/graph/nodes/execute_workers.py#L225-L227)), 최종 답변 단계에서는 지시 문장을 담은 `user` 턴을 하나 더 붙인다([`response_generator.py:37-51`](https://github.com/KiwoomAM/Kiwoom-Rag/blob/main/src/backend/core/graph/nodes/response_generator.py#L37-L51) — 그게 없으면 모델이 답 대신 함수 호출을 시도해 빈 응답이 난다고 실측 주석까지 달려 있다).
- 밑단 [`AsyncSession.send_tool_results`](../llm_manager/_internal/handler_client/_async_session.py#L187-L265) 가 ③을 쓰는 이유도 docstring 에 *"**빈** user message append 우회"* 라고 적혀 있다. 넣을 내용이 있으면 우회할 이유가 없다.

**즉 `messages` 가 진짜 필요한 경우는 대화를 `user` 가 아닌 턴으로 끝내려 할 때뿐이다.** ③이 주는 것은 가능/불가능이 아니라 표현의 자연스러움이다. (②로 도구 루프가 실제로 도는지는 미검증 — B 착수 전 실측 대상.)

### 2.6-1 지금 도구를 쓰는 곳은 챗봇뿐이다

사내 전 레포에서 `tools`·함수 선언을 만드는 곳은 **Kiwoom-Rag 하나**다. ETF·ESG·GM·PF·EM·Parsing·STT 어디에도 없다. 그래서 A 가 여는 "챗봇 밖 도구 호출"은 지금 사용자가 0 인 **새 능력**이다 — 회귀 위험이 없고, 반대로 A 없이는 그 영역이 스트리밍에서 계속 막혀 있다.

### 2.7 `messages` 에 대해 매니저가 모르는 네 곳

| # | 위치 | 증상 |
|---|---|---|
| ㄱ | [`_apply_resolved`](../llm_manager/_internal/runner.py#L416-L426) | 두 분기 모두 `call_input["contents"]` 를 반드시 세팅 → `messages` 와 동시에 실려 `build_body` 가 `ValueError` |
| ㄴ | [`keying._LLM_INPUT_FIELDS`](../llm_manager/_internal/keying.py#L23-L43) | `messages` 없음 → 대화 내용이 캐시 키에서 통째로 빠짐 |
| ㄷ | [`__all__`](../llm_manager/__init__.py#L130-L151) · [`aio.__all__`](../llm_manager/aio.py#L40-L60) | `Content`·`FunctionResponse` 공개 export 없음 → 소비자가 `_internal` 을 뚫음 |

ㄱ은 **첨부가 있을 때만** 터진다. `prep.files` 가 비면 `_apply_resolved` 를 안 타므로 `messages` + `tools` 는 지금도 동작한다. 하필 이 작업이 원하는 조합(도구 + 참조 첨부)에서만 터지는 셈이다.

ㄴ은 조용히 틀린다. `cache_mode=False` 면 읽기는 피하지만 `save_mode` 는 기본 `True` 라, 대화가 안 섞인 키로 기록이 남는다.

### 2.8 소비자가 지금 하는 일 (Kiwoom-Rag)

| 위치 | 내용 |
|---|---|
| `core/graph/nodes/llm_node.py:51-57` | `aio.stream(messages=…, tools=…)` 직행 |
| `utils/client.py:10` | `from llm_manager._internal.handler_client import Content` — 내부 뚫기 |
| `utils/client.py:54` | `Part.from_bytes(data=raw, …)` — **첨부 바이트 직접 인라인** |
| `utils/client.py:71-84` | `chunk.function_calls` 를 **객체로** 읽어 `thought_signature` 를 꺼냄 |

마지막 줄이 A 의 설계에 영향을 준다 — 소비자는 `assistant_message` 가 아니라 `function_calls` + `text` 로 다음 턴을 재조립한다. 따라서 A 는 일곱 필드만 통과시켜도 소비자가 이관 가능하다.

## 3. 설계 — A: 이벤트 통과

### 3.1 변경 지점

[`__init__.py`](../llm_manager/__init__.py#L300-L317) 의 `_events()` 하나. #100 이 이 함수에 `try/finally` + `chunk_stream.aclose()`(standby 리더 토큰 해제)를 넣었으므로 그 `try` 안에 얹는다. `usage` 와 동일하게 **값이 있을 때만** 넣어 기존 소비자의 이벤트 모양을 바꾸지 않는다.

```python
_LIST_FIELDS = ("function_calls", "tool_calls", "tool_responses", "code_blocks", "code_results")
_OBJ_FIELDS = ("grounding", "url_context")

async def _events() -> AsyncGenerator[dict[str, Any], None]:
    try:                                    # ← #100 이 넣은 정리 계약. 건드리지 않는다
        async for chunk in chunk_stream:
            event: dict[str, Any] = {
                "type": "chunk",
                "text": chunk.text,
                "finish_reason": chunk.finish_reason,
            }
            if chunk.usage:
                event["usage"] = chunk.usage.model_dump()
            for name in _LIST_FIELDS:       # ← 여기부터가 이번 변경
                items = getattr(chunk, name)
                if items:
                    event[name] = [item.model_dump() for item in items]
            for name in _OBJ_FIELDS:
                obj = getattr(chunk, name)
                if obj:
                    event[name] = obj.model_dump()
            yield event
    finally:                                # ← #100 이 넣은 standby 리더 토큰 해제
        await chunk_stream.aclose()
```

`model_dump()` 로 내리는 이유는 둘이다. 이벤트 계약이 이미 dict 이고(`usage` 가 그렇게 한다), 소비자가 이 이벤트를 다시 SSE 로 직렬화하는 자리라 JSON 으로 떨어지는 편이 안전하다.

### 3.2 docstring — 누적 규칙을 반드시 적는다

`llm_request_stream_async` 의 이벤트 형태 설명이 지금 `{"type","text","finish_reason","usage"?}` 만 적고 있다. 새 선택 키를 적으면서 **누적 규칙을 같이 적는다.**

[`_common.py:43-55`](../llm_manager/_internal/handler_client/_common.py#L43-L55) 의 `extend_stream_field` 가 계약을 못 박아 뒀다 — *"parallel function call N개가 N개 청크로(1개씩) 흩어져 오므로 덮어쓰면 마지막 청크 것만 남는다."* 리스트 5종은 소비자가 `extend` 로 누적해야 하고, `grounding`·`url_context` 는 턴당 한 번 온다. 이 규칙을 모르는 소비자가 덮어쓰기로 구현하면 **병렬 함수 호출이 조용히 하나만 남는다.** docstring 이 유일한 방어선이다.

### 3.3 기각한 대안

**객체를 그대로 통과** — `event["function_calls"] = chunk.function_calls`(Pydantic 객체 리스트). 소비자가 지금 객체로 읽고 있어 이관 비용이 0 이라는 장점이 있으나, 이벤트가 JSON 직렬화 불가가 되고 `usage` 와 규칙이 갈린다. 이벤트 dict 라는 계약을 지키는 쪽을 택했다.

**필드를 명시적으로 일곱 번 나열** — `_to_stream_chunk` 의 스타일과 맞으나, "값 있을 때만 + 리스트는 각각 dump" 조건이 붙어 7×4줄이 된다. 상수 두 줄 + 루프가 읽기 쉽다고 판단했다.

## 4. 설계 — B: 대화용 함수 신설

### 4.1 왜 기존 함수를 고치지 않고 새로 만드나

매니저의 **`llm_request*` 계열은 대화를 다뤄본 적이 없다.** `history` 인자는 있으나 사내 유일 사용처가 ESG `company_matcher` 의 few-shot 예시 상수이고(파일 없음), `stored_files` 사용처(7개 레포 26개 파일 — ETF·ESG·GM·PF·EM·Parsing·Rag)는 전부 단발 호출이다. 즉 `contents`+`history`+`stored_files` 삼박자는 한 번도 밟히지 않은 구석이다.

다만 밑단에는 대화 수단이 이미 있다 — `Session`·`AsyncSession` 이 공개 export 이고 `send_tool_results` 가 도구 루프까지 풀어 뒀다. 없는 것은 **그 대화 수단과 매니저의 파일·캐시·복구를 함께 쓰는 길**이다.

용도가 갈리는 지점이 분명하다.

| | 단발 (기존 `llm_request*`) | 대화 (신설) |
|---|---|---|
| 대화 표현 | `contents`(+`history`) | `messages` |
| 응답 캐시 | 켬 — 핵심 가치 | 꺼야 함 — 매 턴 키가 갈려 히트 0 |
| 도구 | 거의 안 씀 | 핵심 |
| 파일 위치 | 이번 발화 하나 | 여러 발화에 흩어짐 |

한 함수로 합치면 "이 인자를 쓸 때만 적용되는" 조건부 규칙이 쌓인다(`EXPLICIT` 위반). 나누면 대화용 함수의 계약이 **조건 없이** 성립하고, 기존 소비자는 한 글자도 안 건드린다.

기각한 대안 — `llm_input` 에 `messages` 키를 더하기. README 가 `llm_input` 을 "handler `call()` 파라미터 대부분과 동일"로 정의하므로 계층 일관성은 이쪽이 낫다. 다만 위 표의 기본값 충돌을 조건부 규칙으로 떠안게 되어 기각했다. 대신 README 에 "단발용이라 `messages` 는 받지 않는다"를 명시해 구멍이 아니라 의도임을 남긴다.

### 4.2 만들 것

```
llm_chat_async(...)         -> (LLMResponse, ResponseMeta)
llm_chat_stream_async(...)  -> (AsyncIterator[dict], meta)
```

`messages` 만 받는다(`contents`·`history` 는 거부). async 만 만든다 — 소비자가 전부 async 다. 내부는 기존 `runner` 를 그대로 부르는 얇은 층으로 둔다(`llm_request` 가 `llm_request_async` 의 얇은 래퍼인 것과 같은 패턴).

응답 캐시(`cache_mode`·`save_mode`)는 인자로 남기되 **기본값을 `False`** 로 둔다. 재시도 상황의 여지는 남기고, 모르고 켜두어 조용히 낭비하는 일은 막는다.

### 4.3 첨부 위치 — 자리표시자(④) 채택

`stored_files` 는 평평한 목록이라 **"몇 번째 발화의 첨부"라는 정보가 없다.** 단발에서는 붙일 자리가 하나뿐이라 문제가 안 됐으나, 대화에서는 매니저가 추측해야 한다.

네 안을 검토했다.

| 안 | 위치 | 판정 |
|---|---|---|
| ① | 마지막 `user` 발화 앞 | 기각 — 소비자가 도구 결과를 `user` 발화로 실어서, 라운드 2회차부터 도구 결과 옆에 붙는다 |
| ② | 첫 `user` 발화 앞 | 기각 — `messages` 에 대화 전체가 들어와, 오늘 붙인 파일이 어제 첫 발화에 붙는다 |
| ③ | 파일 전용 발화를 맨 앞에 신설 | 기각 — 아래 |
| **④** | **소비자가 남긴 자리표시자를 매니저가 치환** | **채택** |

**④ 채택 근거 넷.**

1. **소비자가 이미 그 구조다.** 챗봇은 파일을 그 발화 안에 넣는다([input_processor.py:91-101](https://github.com/KiwoomAM/Kiwoom-Rag/blob/main/src/backend/core/graph/nodes/input_processor.py#L91-L101)). 위치 정보는 실재하고, `stored_files` 라는 API 모양이 그것을 버릴 뿐이다. ④는 없는 정보를 요구하는 게 아니라 **버리지 않는** 것이다. 소비자가 고칠 것은 그 자리에 든 것을 바이트에서 경로 한 줄로 바꾸는 것뿐이다.
2. **Gemini 원본 구조와 같다.** Gemini 에는 "파일 목록" 인자가 없다 — 파일은 언제나 어떤 발화의 조각이다. 매니저가 자리표시자를 실제 조각으로 치환하고 나면 Gemini 가 받는 모양은 원본과 동일하다.
3. **여러 턴 첨부에서 지시어가 산다.** 1턴 A.pdf · 3턴 B.pdf 인 대화에서 "이건 어때?" 가 무엇을 가리키는지 유지된다. ③은 둘을 한 덩어리로 앞에 몰아 이 구분을 잃는다.
4. **암묵 캐시에 유리하다.** Gemini 2.5+ 는 앞부분이 겹치면 자동으로 75% 할인한다(별도 설정 없음, 모델별 최소 토큰 조건 있음 — 2.5 Flash 1,024 / 2.5 Pro 2,048 / 3.x Flash 4,096). ④는 새 파일이 새 발화(맨 뒤)에 붙어 앞부분이 불변이므로 **새 턴만** 재계산된다. ③은 새 파일을 맨 앞에 끼워 넣어 그 지점부터 뒤가 전부 미적중이 된다. 구글 권고("앞부분은 그대로 두고 매번 바뀌는 것은 끝에")와도 ④가 일치한다.

**치환 규약.** 자리표시자는 파일 경로만 담고, 같은 파일을 `stored_files` 로도 넘긴다(메타 6필드가 checksum·dedup 에 필요). 매니저가 경로로 짝지어 치환하며, 밑단(handler)으로 나가기 전에 전부 사라진다. **짝이 안 맞으면(표찰만 있거나 파일만 왔거나) 그 자리에서 실패시킨다** — 조용히 넘기면 모델이 파일을 못 본 채 그럴듯한 답을 만든다(`FAIL-LOUD`).

**검토 중 바로잡은 오해 둘.** 기록으로 남긴다.

- *"Context Cache 를 쓰려면 파일을 앞으로 몰아야 하니 위치 보존과 배타"* — **틀렸다.** Gemini 는 대화 이력을 발화 목록 그대로 캐시할 수 있고, Anthropic 도 캐시는 접두사 경계 표시일 뿐 파일을 옮기지 않는다. 배타로 보인 것은 우리 `create_cache` 가 역할 없는 조각 목록(`ContentsType`)만 받아 대화 구조를 못 담기 때문이다. handler 쪽 별건이며, 열리면 ④가 그대로 얹힌다.
- *"앞에 몰면 모델이 더 정확히 읽는다"(Lost in the Middle)* — 근거로 못 쓴다. 긴 컨텍스트의 U자 곡선은 알려진 현상이나, 최근 측정에서 Gemini 2.5 Flash 는 위치에 따른 열화가 관측되지 않았다. 다만 챗봇 실제 모델은 `gemini-3.7-flash`(`Kiwoom-Rag utils/client.py:14` 기본값)라 그 측정과 같은 모델은 아니다 — 즉 이 논거는 **양쪽 다 근거가 약하다**.

### 4.4 캐시 키 — `messages` 를 넣되 파일은 넣지 않는다 🔴

`_LLM_INPUT_FIELDS` 에 `messages` 가 없어 대화 내용이 캐시 키에서 통째로 빠진다. 추가해야 한다.

다만 그냥 추가하면 안 된다. [`keying.py:159-164`](../llm_manager/_internal/keying.py#L159-L164) 의 `Part` 정규화(base64 `data` 제거)가 **`has_file_checksums` 일 때만** 돌기 때문에, 파일을 인라인한 `messages` 는 base64 통째가 `str(obj)` fallback 으로 키에 들어간다.

④가 이 문제를 자동으로 닫는다 — 파일은 `stored_files` 로만 오고 `messages` 에는 자리표시자(경로 한 줄)만 남으므로, 파일은 기존대로 `file_checksums` 로 키에 들어간다.

**🔴 남은 결정 — 규약을 어겼을 때(`messages` 안에 실제 파일 조각이 있을 때) 거부할 것인가, 경고만 남길 것인가.** `FAIL-LOUD` 로는 거부가 맞으나, 소비자 이관 과도기에 섞여 올 여지가 있다.

### 4.5 공개 export

`Content` 와 `FunctionResponse` 를 [`__init__.py`](../llm_manager/__init__.py#L130-L151) 와 [`aio.py`](../llm_manager/aio.py#L40-L60) 양쪽 `__all__` 에 추가한다. 지금 소비자가 `_internal` 을 뚫고 있고, Kiwoom-Rag 테스트에는 `# 공개 export 없음` 주석까지 달려 있다. 결정 사항이 아니라 누락 보정이다.

### 4.6 인자 모양 🔴

**🔴 남은 결정.** (가) 기존 스타일대로 설정 dict 하나를 받는다 — SDK 전체가 한 스타일로 유지되고 생성 파라미터를 다시 나열하지 않는다. (나) 인자를 펼친다 — 읽기는 명확하나 생성 파라미터 10개를 세 번째로 나열하게 되어(handler `call()`·`stream()` 에 이미 두 벌) 추가 시 세 곳을 고쳐야 한다.
