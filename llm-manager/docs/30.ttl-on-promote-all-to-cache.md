# 30. ttl-on 시 전 파일 Context Cache 승급 (all-or-nothing 라우팅)

> 관련: [07.inline-vs-files-api-strategy.md](07.inline-vs-files-api-strategy.md) §4.4(승급 정책),
> [21.context-cache-too-small-failsoft.md](21.context-cache-too-small-failsoft.md)(too-small fail-soft)

---

## 요약 (TL;DR)

- **문제**: `context_cache_ttl`을 켜면 첨부 파일이 **전부 캐시에 들어가는 게 맞는 시맨틱**인데,
  지금은 파일 크기가 섞이면(작은 것 + 큰 것) 작은 파일이 inline에 잔류해 캐시에서 빠진다. 승급
  조건이 `not files_api_pool`(= 전원 inline일 때만)이라 그렇다. 애초에 inline 분기를 앞에 둔 건
  **캐시를 안 할 때** 불필요한 작은 파일을 Files API로 올리지 않으려는 것인데, 캐시를 켠 경우엔
  그 이유가 성립하지 않는다(어차피 전부 캐시에 넣어야 하므로). 게다가 캐시 모드에서 inline은
  캐시가 안 돼 **매 콜 재전송**된다.
- **해결**: `_resolve_pools`에서 **ttl 켜지면 크기 분기(classify) 없이 전 파일을 files-api로** 보낸다
  (최상단 early return). 결과: ttl-on이면 전 파일 캐시(합계가 too-small이면 기존 fail-soft가 전부
  **Files API URI로 전송·uncached**) → **깔끔한 all-or-nothing.**
- **범위**: `_resolve_pools` 최상단에 ttl early-return 추가(작은 변경). 캐시 키·dedup·too-small 게이트 로직 무변경.

---

## 1. 배경 / 문제 정의

### 1.1 증상

`context_cache_ttl`을 지정했는데도, 한 요청에 파일이 여럿이고 크기가 섞이면 작은 파일이
**inline으로 남고** 큰 파일만 files-api(→ 캐시)로 간다.

- 예: 30MB + 60MB PDF. `classify_files` 합계 한도(PDF-only 50MB)를 30MB가 먼저 채우고 60MB가
  넘쳐 files-api로 → **30MB inline, 60MB files-api.** ttl을 켰어도 이 갈림이 유지된다.

### 1.2 왜 문제인가

**(1) 시맨틱 — 캐시는 all-or-nothing 이 맞다.** `context_cache_ttl`을 켰다는 건 "첨부 파일을 캐시에
올려 재사용하겠다"는 뜻이다. 그렇다면 **첨부 파일 전부가 캐시에 들어가는 게 맞다.** 크기 때문에
일부가 캐시 밖 inline으로 남는 건 캐시 의도와 어긋난다. inline 분기(§2.1 ①)의 원래 목적은
**캐시를 안 할 때** 불필요한 작은 파일을 Files API로 올리지 않으려는 것이라, 캐시를 켠 경우엔
그 목적이 적용되지 않는다.

**(2) 재전송 비용.** 캐시 모드에서 `_apply_resolved`는 `contents = inline_parts + text_contents`로
inline을 **매 콜 다시 싣는다**(inline은 캐시가 안 됨). 같은 캐시를 여러 번 참조하는 소비자에서
작은 파일 바이트가 매 콜 재전송된다.

### 1.3 원인 — 승급 조건이 "전원 inline"에 한정

`_resolve_pools` Step 2 승급 정책이 `not files_api_pool`(files-api 풀이 비었을 때 = 전원 inline)일
때만 전원 승급한다. 큰 파일이 하나라도 있어 풀이 이미 차 있으면 승급이 안 걸려 작은 파일이 inline에 남는다.

## 2. 사전 정보

### 2.1 두 게이트 (독립)

- **① `classify_files` (바이트)** — 작은 것부터 합계 한도(미디어 20MB / PDF·텍스트 50MB)까지
  inline, 넘치면 files-api. **부분 섞기** 가능.
- **② context cache too-small (토큰)** — files-api 풀을 캐시 시도하다 합계 토큰이 너무 적으면(~1024 미만)
  fail-soft로 **캐시 생성만 skip하고 그 풀을 Files API URI로 전송(uncached, docs/21)** — inline로 되돌리지 않음.

### 2.2 현재 승급 정책 (`_resolve_pools` Step 2)

```python
inline_pool, files_api_pool = classify_files(files, llm_input)

if context_cache_ttl is not None and not files_api_pool and inline_pool:
    files_api_pool = inline_pool          # 전원 inline일 때만 승급
    inline_pool = []
```

### 2.3 cached 경로의 inline 재전송

```python
# _apply_resolved
if resolved.cached_content:
    call_input["contents"] = resolved.inline_parts + text_contents   # inline은 매 콜 재전송
```

## 3. 설계 (변경)

`_resolve_pools` 최상단에서 **ttl이 켜져 있으면 크기 분기(classify)를 건너뛰고 전 파일을
files-api로** 보낸다(early return). inline 분기의 목적은 '캐시 안 할 때' 작은 파일을 굳이 Files API로
안 올리려는 것이라, 캐시를 켜면 나눌 이유가 없다. → "나눴다 다시 합치기"보다 의도가 명료.

```python
# before — 항상 classify 후, 전원 inline일 때만 승급
inline_pool, files_api_pool = classify_files(files, llm_input)
if context_cache_ttl is not None and not files_api_pool and inline_pool:
    files_api_pool = inline_pool
    inline_pool = []
# ... Step 2.5(>1000p inline 전개) ...

# after — ttl이면 크기 분기 없이 early return; ttl 없을 때만 classify + 전개
if context_cache_ttl is not None:
    return [], list(files)
inline_pool, files_api_pool = classify_files(files, llm_input)
if inline_pool:                       # ttl-off 전용: >1000p inline PDF 전개·재분류
    expanded = await _expand_pdfs_over_page_limit(inline_pool)
    inline_pool, spilled = classify_files(expanded, llm_input)
    files_api_pool = spilled + files_api_pool
```

- 승급 후 `checksums = [make_file_checksum(fi) for fi in files_api_pool]`는 기존 호출부 그대로
  `files_api_pool`(= ttl이면 전 파일) 기준 계산.
- **Step 2.5(>1000p inline PDF 전개)는 ttl-off 전용**이 된다(ttl-on은 애초에 inline 없음).
  큰/긴 PDF의 분할은 files-api 경로의 `split_pdf`(50MB·1000p)가 처리하므로 손실 없음.
- **404 복구 정합**: `_resolve_pools`는 `resolve_files_after_404`와 공유 — ttl-on이면 두 호출 모두
  `[], list(files)`로 결정적이라 무효화 대상 checksum 일치(회귀 없음).
- 결과: **ttl-on = 전 파일 files-api → 캐시.** 합계가 too-small이면 기존 fail-soft가 전부 Files API
  URI로 전송(uncached) → all-or-nothing.

## 4. 불변식 / 영향

| 항목 | 영향 | 근거 |
|---|---|---|
| too-small fail-soft | 유지 | 전 파일 tiny면 캐시 거부 → 캐시만 skip, 전부 **Files API URI로 전송(uncached)**. 균일하므로 여전히 all-or-nothing |
| 캐시 키 / dedup | 없음 | 이 변경은 **라우팅**(어느 풀로 가나). hash_key 재료(checksum·model·system·tools) 무관 |
| 전 소비자 정책 변경 | 있음(인지 필요) | ttl 켜는 **모든** 소비자의 작은 파일이 inline→캐시. 방향 일치(캐싱 의도)+효율 이득이라 순이득이나, 공용 SDK 동작 변경임 |
| 첫 콜 업로드 | 작은 파일도 Files API 업로드 발생 | 다중콜이면 상쇄, 단발+ttl(드문 조합)이면 순오버헤드 |
| 병리적: 단일 페이지>50MB | **기존과 동일**(신규 아님) | too-small은 Files API URI 폴백이라 크기 무관 안전. 진짜 거부는 '한 페이지가 50MB 초과라 분할 불가' → `PdfPageTooLargeError`(docs/25), 이 변경과 무관 |
