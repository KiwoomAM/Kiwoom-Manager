# 32. inline 경로 bytes 회수 (`fi.data = b""`)

## 1. 배경 / 문제 정의

`_process_inline`이 `Part.from_bytes(data=fi.data)`로 base64 `Part`를 만든 **뒤에도 원본 bytes(`fi.data`)를 계속 들고 있다.** 이미 base64 문자열로 변환돼 전송에 쓰이므로 원본 bytes는 더 이상 필요 없는데, 요청이 끝날 때까지 메모리에 상주한다.

같은 파일의 **Files API 경로에는 이 회수가 이미 있다** ([resolver.py:297](../llm_manager/_internal/file_processing/resolver.py#L297), [resolver.py:388](../llm_manager/_internal/file_processing/resolver.py#L388)):

```python
fi.data = b""  # Files API 경로 — bytes 가 디스크/URI 로 옮겨졌으니 메모리 회수 (docs/16 §3.2)
```

즉 회수 정책([docs/16](16.*) §3.2)은 이미 있고, **inline 경로에만 적용이 빠졌다.** 설계 결함이 아니라 누락이다.

## 2. 사전 정보 — 실측 (2026-07-14)

실제 코드 경로(`classify_files` → `_process_inline` → `build_body` → `json.dumps`)를 그대로 태우고 `tracemalloc`(파이썬 힙) + `ru_maxrss`(RSS)로 측정. 도커(python:3.12-slim, PYTHONPATH로 모노레포 소스 연결).

대상: `2022_CJ제일제당_지속가능보고서.pdf` — **46,681,609 bytes (44.52 MiB), 115p** → inline 분류(`inline=1, files_api=0`).

| 단계 | 힙 current | 힙 peak | RSS 최대 |
|---|---:|---:|---:|
| 0. 시작 (import 직후) | 0.0MB | 0.0MB | 70.5MB |
| 1. 원본 bytes 로드 | 44.5MB | 44.5MB | 115.1MB |
| 2. FileInput 생성 | 44.5MB | 44.5MB | 115.1MB |
| 3. classify_files | 44.5MB | 44.5MB | 115.1MB |
| **4. _process_inline (base64)** | **103.9MB** | **163.3MB** | 234.0MB |
| 5. build_body (model_dump) | 103.9MB | 163.3MB | 234.0MB |
| **6. json.dumps + encode** | **163.3MB** | **237.5MB** | **293.2MB** |

`_process_inline` 직후 동시 상주:

```
fi.data (원본 bytes)     46,681,609 bytes (44.52 MiB)   ← 불필요
Part.data (base64)       62,242,148 chars (59.36 MiB)   ← 전송에 필요
                                    합계 103.88 MiB
```

**낭비분은 `fi.data` 44.52 MiB.** 나머지 증폭은 inline 방식의 원가라 이 문서의 범위가 아니다(§7).

### 2.1 실측으로 기각된 가설

| 가설 | 실측 결과 |
|---|---|
| pydantic `FileInput(data=...)`이 bytes를 복사할 것 | **복사 안 함** (2단계 힙 44.5MB 불변) |
| `model_dump()`가 base64 문자열을 복사할 것 | **복사 안 함** (5단계 변화 0) |

파이썬 bytes/str이 불변이라 참조만 넘어간다. 따라서 **줄일 수 있는 건 `fi.data` 하나뿐**이다.

## 3. 설계 — 변경 지점

[`_process_inline`](../llm_manager/_internal/file_processing/resolver.py#L129) 루프에서 `Part` 생성 직후 회수한다.

```python
    for fi in inline_pool:
        if not fi.data:
            fi.data = await fetch_with_fallback(fm, fi)
            if fi.resolved_via is None:
                fi.resolved_via = "primary"
        inline_parts.append(
            Part.from_bytes(data=fi.data, mime_type=fi.mime_type)
        )
        fi.data = b""  # ← 추가: base64 Part 로 옮겨졌으니 원본 bytes 회수 (docs/16 §3.2)
        logger.info("[route] file=%s mode=inline", fi.file_name)
```

Files API 경로와 **동일한 주석·동일한 패턴**을 쓴다(`SSOT`·일관성).

### 3.1 기각한 대안

- **`Part.from_bytes` 안에서 회수** — `Part`는 `FileInput`을 모르고, 호출자의 변수를 건드리는 건 숨은 부작용이다(`EXPLICIT` 위반). 기각.
- **`_process_inline` 종료 후 일괄 회수** — 파일 N개면 마지막 파일 전까지 전부 상주해 피크가 안 줄어든다. 루프 내 즉시 회수가 맞다.
- **base64 팽창까지 함께 손보기** — 별건(§7). 이 변경의 범위를 넘는다(`SURGICAL`).

## 4. 안전성 검증

`fi.data`를 비운 뒤 그 bytes를 다시 읽는 곳이 있으면 조용히 깨진다(`FAIL-LOUD` 위반). 전수 확인했다.

| 확인 항목 | 결과 |
|---|---|
| `resolver.py` 밖에서 `FileInput.data` 소비 | **없음** (grep 전수) |
| `classify_files` | `fi.file_size`(메타)만 사용 — bytes 무관 |
| `make_file_checksum` ([keying.py:246](../llm_manager/_internal/keying.py#L246)) | `(file_name, file_mtime, file_size)`만 사용 — bytes 무관 |
| 404 복구([resolver.py:860](../llm_manager/_internal/file_processing/resolver.py#L860))가 **같은 `files` 객체 재사용** | `_process_inline` 진입부의 `if not fi.data:` **재fetch 가드가 이미 존재** → 비워져 있으면 file-manager에서 다시 받아온다 |

Files API 경로가 안전하게 비울 수 있는 근거와 정확히 같다.

**비용**: 404 복구 시 inline 파일을 file-manager에서 1회 재fetch한다(네트워크). 단, inline 파일은 Gemini URI를 갖지 않아 404의 원인이 될 수 없고, 404 복구 자체가 드물다(Redis TTL 47h < Gemini TTL 48h, [docs/27](27.smarter-404-recovery.md)). 정합성 손실은 없다.

## 5. 테스트 계획 (TDD — 실패하는 테스트 먼저)

대상: `tests/_internal/file_processing/test_resolver.py`

1. **회수 확인** — `_process_inline([fi])` 호출 후 `fi.data == b""`, 그리고 반환된 `Part.data`(base64)는 원본을 온전히 담고 있다(`b64decode(part.data) == 원본`). → **현재는 실패해야 한다.**
2. **재fetch 가드 회귀** — `data=b""`인 `FileInput`으로 `_process_inline`을 부르면 `fetch_with_fallback`이 호출되고 `Part`가 정상 생성된다(404 복구 경로 보호). → 현재도 통과해야 하며, 변경 후에도 통과해야 한다.

4단계 자체의 peak(163.3MB)는 변하지 않는다. `b64encode(data).decode()`가 base64 bytes와 str을
순간적으로 둘 다 들고 있는 구간이 **회수 시점보다 앞서** 일어나기 때문이다. 회수의 이득은
그 뒤(6단계 `json.dumps`)부터 나타난다 — 원본 44.5MB가 빠진 만큼 이후 모든 단계의 피크가 내려간다.

## 7. 범위 밖 (별건으로 분리)

- **base64 +33% 팽창 / `json.dumps` 복사** — inline 방식의 구조적 원가. 줄이려면 전송 방식 자체를 바꿔야 한다.
- **한도 체크가 raw bytes 기준인데 실제 전송은 base64 1.33배** — `classify_files`는 `fi.file_size`(raw)로 50MB 한도를 재지만 실제 wire는 59.4MB. Gemini가 실제로 거절하는지 **미검증**. ([docs/07](07.inline-vs-files-api-strategy.md) 54행이 "요청 body 한도 계산 시 주의"라고 이미 경고 중.)
- **`_split_pdf_bytes`(>1000p inline PDF)가 전 파트를 메모리에 적재** — 발동 조건(1000p 초과 + inline 한도 이하 = 텍스트 위주 얇은 PDF)이 좁아 미검증. 샘플 확보 시 측정.
