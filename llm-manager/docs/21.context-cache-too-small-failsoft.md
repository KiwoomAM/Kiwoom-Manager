# 21. Context Cache too-small fail-soft

> 대상 브랜치: `fix/646` (이슈 #646)
> 관련 문서: [07.inline-vs-files-api-strategy.md](07.inline-vs-files-api-strategy.md) §6, [20.context-cache-expire.md](20.context-cache-expire.md)

## 1. 배경 / 문제 정의

Gemini Context Cache 는 **합계 토큰이 1024 미만이면 캐시 생성을 거절**한다
(`400 INVALID_ARGUMENT`, `min_total_token_count`). 현재 llm-manager 는 caller 가
`context_cache_ttl > 0` 을 넘기면 무조건 캐시 생성을 시도하므로, 짧은 컨텍스트
(예: 1페이지 표만 있는 PDF, 추정 561토큰) 호출이 **통째로 실패**한다.

```
ServiceError: [provider] Gemini 캐시 생성 에러: 400 INVALID_ARGUMENT.
{'error': {'code': 400, 'message': 'Cached content is too small.
  total_token_count=561, min_total_token_count=1024'}}
```

영향: 짧은 PDF·짧은 프롬프트 호출이 전부 막힌다 (추출·리뷰·gather_missing 등).
현재 Kiwoom-PF 는 caller 측에서 `try/except → context_cache_ttl=0 재호출` 로
워크어라운드 중 (`features/withdrawal/core/_llm_call.py` 3곳: extractor, reviewer,
agent/graph._gather_missing).

**캐시는 비용 최적화이고 정확도와 무관하므로 fail-hard 가 아니라 fail-soft 가 옳다.**
provider 에 fail-soft 를 두면 caller 모두가 자동으로 이득을 본다.

### 범위 (scope) — 명시적 비목표

- inline 사이즈 파일을 Files API 업로드 없이 직접 캐시하는 "inline-direct" 최적화는
  **이번 범위에서 제외**한다. 이득(첫 호출 업로드 RTT 1회 절약)이 변경 폭 대비 작고,
  Files API 저장은 무료(48h 자동 삭제)라 비용 절감도 미미하기 때문. 추후 Files API
  용량이 실제 문제가 될 때 별도로 검토한다.
- 따라서 `resolve_files` 의 승급 정책(§4.4)·`resolve_files_after_404`·uploader
  시그니처는 **건드리지 않는다.**

## 2. 사전 정보

### 2.1 캐시 생성 경로

`context_cache_ttl > 0` 일 때, 파일은 Files API 업로드 후
[`_create_and_save_context_cache`](../service/app/logic/file_processing/resolver.py)
가 `create_context_cache(file_refs, ...)` 로 캐시를 생성하고 Redis 에 저장한다.
이 함수는 `_process_files_api` 의 두 지점(standby 선점 경로 / standby timeout 경로)
에서 호출되며, 현재 실패 시 예외를 raise 한다.

### 2.2 too-small 에러 형태

Gemini `400 INVALID_ARGUMENT` → llm-handler 가 `HandlerError`(`error_type="provider"`,
`status_code=400`) 로 relay, 메시지에 `min_total_token_count` 포함.
[`gemini_errors.py`](../service/app/logic/gemini_errors.py) 의 `is_gemini_404` 와
동일한 판정 패턴을 쓸 수 있다.

### 2.3 runner 계약 (`_apply_resolved`)

[runner.py `_apply_resolved`](../service/app/logic/runner.py): `cached_content` 가
`None` 이면 `uri_parts` 가 contents 에 포함되어 전송된다. 즉 **캐시 생성을 skip 하고
`cached_content=None` 으로 두면, runner 가 그대로 Files API URI(또는 inline)로 호출**
한다 — 호출 측 추가 처리 불필요.

## 3. 설계

### 3.1 감지 헬퍼 (`gemini_errors.py`)

```python
def is_cache_too_small(exc: Exception) -> bool:
    """Gemini Context Cache 'min_total_token_count' 미달(400) 신호인지 판정.

    캐시 생성에 필요한 최소 토큰(현재 1024) 미달 시 Gemini 가 반환하는
    400 INVALID_ARGUMENT 를 식별. caller 는 이 경우 캐시를 skip(fail-soft)한다.
    """
    if (isinstance(exc, HandlerError) and exc.status_code == 400
            and "min_total_token_count" in str(exc).lower()):
        return True
    # llm-handler 가 wrap 못한 경로 fallback (메시지 substring)
    return "min_total_token_count" in str(exc).lower()
```

`min_total_token_count` 는 매우 특정한 토큰이라 **다른 400을 잘못 삼킬 위험이 없다.**

### 3.2 fail-soft 지점 (`_create_and_save_context_cache`)

반환형을 `str → str | None` 로 바꾼다. `None` 은 "캐시 skip(too-small)" 을 의미.

```python
async def _create_and_save_context_cache(...) -> str | None:
    try:
        cache_ref = await create_context_cache(file_refs, ...)
    except (HandlerError, HandlerConnectionError) as e:
        if is_cache_too_small(e):
            logger.info(
                "[route] mode=context_cache source=skipped reason=below_min_token "
                "hash_key=%s", hash_key[:16],
            )
            return None
        raise  # 그 외 provider/connection 에러는 그대로 전파
    except Exception as e:
        if is_cache_too_small(e):   # wrap 안 된 raw 예외 방어
            logger.info("[route] mode=context_cache source=skipped reason=below_min_token")
            return None
        logger.exception("Context cache 생성 실패")
        raise FileUploadError(f"Context cache 생성 실패: {e}") from e

    # 성공 시에만 Redis 저장 (기존과 동일)
    cache_store.save_context_cache(hash_key, {...}, ttl=ttl)
    return cache_ref.name
```

- too-small → `None` 반환, **Redis 저장 안 함** (다음 호출도 동일하게 재시도 — 매번
  재시도 정책, negative-cache 마커는 YAGNI 로 미도입).
- 그 외 에러는 **기존 동작 그대로 유지** (500/503 등 진짜 장애는 raise → relay).

### 3.3 호출부

`_process_files_api` 의 두 호출 지점은 이미 `cached_content: str | None` 에 결과를
대입한다. `None` 이 와도 그대로 `cached_content = None` → runner 가 `uri_parts`(Files
API URI)를 전송. **호출부 코드 변경 불필요.**

### 3.4 context_cache_id 게이팅

`resolve_files` 는 `context_cache_id` 를 **실제 캐시가 있을 때(`cached_content` not
None)만** 노출한다 — `context_cache_id = hash_key if cached_content else None`.
too-small fail-soft 로 캐시를 skip 했거나 `context_cache_ttl` 미지정이면 캐시가
없으므로 `None`. 이는 `ResolvedFiles` docstring·README 가 이미 명시한 "생성/HIT 시
노출" 의미와 일치시키는 것이다(기존엔 캐시 없어도 hash_key 가 노출되던 불일치 수정).

> caller 관점: `context_cache_ttl` 을 지정했는데 응답에 `context_cache_id` 가 없으면
> = 콘텐츠가 작아(<1024 토큰) 캐시가 skip되고 Files API 로 처리된 것 → 삭제할 캐시 없음.

## 4. 에러 처리 요약

| 시나리오 | 처리 |
|---|---|
| 캐시 too-small (`min_total_token_count`) | `cached_content=None` → Files API URI 로 전송, 크래시 없음 |
| 그 외 캐시 생성 에러 (provider 500/503, connection 등) | 기존대로 raise (relay) |
| too-small 아닌 다른 400 | `is_cache_too_small=False` → 기존대로 raise |

## 5. 테스트

`service/tests/logic/file_processing/` (또는 기존 resolver 테스트 위치 따름).

- **fail-soft 동작**: `create_context_cache` 가 too-small `HandlerError(400, "...min_total_token_count...")`
  를 raise 하도록 mock → `_create_and_save_context_cache` 가 `None` 반환, `save_context_cache`
  **호출 안 됨** 검증.
- **end-to-end**: `_process_files_api` 가 too-small 시 `cached_content=None` 반환,
  `uri_parts` 는 그대로(전송 가능), 예외 전파 안 됨.
- **다른 400 은 raise**: `HandlerError(400, "some other invalid argument")` → `None` 아니라
  **raise** 검증 (too-small 만 삼킴).
- **다른 에러 raise**: `HandlerError(503, ...)` → 기존대로 raise.
- **감지 헬퍼 단위**: `is_cache_too_small` 가 too-small 메시지 True, 그 외 400/503 False.
