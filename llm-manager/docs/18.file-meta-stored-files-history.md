## Part A — Phase 1: `file_meta` 응답 노출

### 배경

- file-manager 가 부여한 `file_path` 가 응답에 노출되지 않아 caller 가 알 수 없음
- caller (ESG 등) 가 `file_path` 를 자기 DB 에 보관해야 재호출 / multi-doc 패턴 가능
- `metadata` 는 free-form 이라 키 추가 안전 (Pydantic v2 `extra="ignore"`)

### 핵심 결정

| # | 결정 |
|---|---|
| 1 | `file_meta` 6 필드 — `file_path, file_name, file_size, file_mtime, mime_type, extension` |

| 4 | MongoDB doc 의 `file_meta` 키와 1:1 거울 매칭 |
| 5 | helper 함수화 X — 인라인 유지 (3 곳 모두 한 줄짜리 dict 머지) |

## Part B — Phase 2: `stored_files` 입력 지원

### 배경

- Phase 1 으로 caller 가 `file_meta` 6 필드를 응답으로 받음
- 다음 호출에 그대로 보내서 bytes 재전송 회피 — 같은 파일 N 회 호출 시 네트워크 비용 0

### ⚠️ 진행 중 모델 변경 (4 → 6 필드)

초기 plan 은 `StoredFile` 을 4 필드 (`file_path` + hashing 3) 로 잡고 mime/extension 은 file-manager 의 `get_file` metadata 에서 추출하는 구조. Task 1, 2, 4 적용 도중 **caller mental model 일관성 (FileInput 과 대칭)** 이 더 가치 있다고 판단해서 6 필드로 변경. Phase 1 응답이 6 필드를 주므로 그대로 다시 넘기는 게 자연스러움.

### 핵심 결정

| # | 결정 |
|---|---|
| 1 | `StoredFile` = `FileInput` 의 bytes 만 `file_path` 로 대체된 형태 (5 메타 + file_path = **6 필드**) |
| 2 | 신규 인자 `stored_files: list[StoredFile]` (기존 `files=[FileInput]` 와 sibling) |
| 3 | `file_resolver.py` 신규 모듈 — file-manager 에서 bytes fetch |
| 4 | 진입점 4 함수가 `resolve_stored_files` → 6 필드 그대로 `FileInput` 으로 변환 → 기존 파이프라인 |
| 5 | 1차 `get_file(file_path)` 실패 시 hashing 3 필드로 `check_cache` fallback. 둘 다 miss 면 `FileResolveError` raise |
| 6 | 응답 `resolved_via` 추가 — `"primary"` / `"fallback"` / `"upload"` |
| 7 | `bytes` 직렬화는 base64 (Pydantic v2 JSON 모드) — SDK + Service 양쪽 동일 정의 (의도된 중복) |

### `resolved_via` 의미

| 값 | 의미 |
|---|---|
| `primary` | `file_path` 1차 fetch 성공 |
| `fallback` | 1차 stale → `check_cache` 로 새 path 찾아 성공 → caller 가 새 `file_path` 로 갱신해야 함 |
| `upload` | bytes 모드 새 업로드 (Phase 2 시점 — Method 1 공존. Phase 3 에서 사라짐) |

## Part C — Phase 3: Method 1 폐기 + Lazy Fetch

### 배경 — Phase 1+2 의 한계

- Phase 1+2 후 Method 1 (data-mode `files=[FileInput(bytes)]`) + Method 2 (path-mode `stored_files`) 가 공존
- agent 첫 평가 시 여전히 bytes 보내야 함 → 메모리 부담 (ESG: 70 DP 평가 동안 PDF bytes 메모리 점유)
- 첫 평가 / 재평가 흐름이 비대칭 — agent 가 file_path 를 자기 DB 에 저장 후 재호출이라 첫 코드 경로와 재호출 코드 경로가 다름
- 같은 PDF N 동시 호출 시 N 번 fetch (dedup 가 fetch 단계 안 흡수)

### 핵심 결정

| # | 결정 |
|---|---|
| 1 | agent 가 file-manager 직접 등록 (`register_or_get` 헬퍼) → `file_path + 5 메타` 만 llm-request 에 전달 |
| 2 | Method 1 폐기 — `LLMRequestBody.files` 인자 제거 + `LLMRequestBody.extra="forbid"` (silent drop 방지) |
| 3 | llm-request lazy fetch — 실제 bytes 는 4·5단계 standby leader 만 가져옴 |
| 4 | 기존 dedup 메커니즘 (`try_acquire_standby`) 이 leader 분기에 추가된 fetch 까지 자동 흡수 — 70 동시 요청도 fetch 1 회 |
| 5 | inline 경로 (`_process_inline`) + Files API 경로 (`_upload_and_cache_file`) 양쪽 모두 lazy 화 |
| 6 | 404 자동 복구 — `resolve_files_after_404` → `resolve_files` 재호출. `if not fi.data:` 가드로 두 번째 호출의 재 fetch 방지 |
| 7 | `FileInput.data` default 값 `b""` 로 둠 — file_resolver 가 placeholder 만 만들고 실제 bytes 는 leader 만 |

### 70 동시 요청 시나리오 (같은 PDF, Files API 분류)

```
follower 69                                 leader 1
      │                                          │
      ├─ try_acquire_standby → DEFER             ├─ try_acquire_standby → ACQUIRED
      │                                          ├─ fm.get_file(file_path) ← 1 회만 fetch
      │                                          ├─ Files API upload + Redis 저장
      │                                          ├─ release_standby
      └─ wait_for_result ────────────────────→  ✓ Files URI 공유
```

→ N=70 → fetch 1 회 / Files API upload 1 회 / Redis URI 1 개 공유.

| | 옛 SDK (`files=[FileInput]`) | 새 SDK (`stored_files=[StoredFile]`) |

### PR 리뷰 반영 (계획 외 추가)

PR 머지 전 리뷰어 지적에 따라 추가 정정한 내역. 22번 plan 에는 없던 항목들.

#### Critical (5건)

| 항목 | 정정 |
|---|---|
| **dedup 범위 정정** | "70 동시 요청 fetch 1 회" 는 **files_api 경로 한정**. inline 경로는 결과 (bytes) 가 Redis 에 캐시되지 않아 dedup 효익 없음 → N 회 fetch 허용 (의도된 trade-off, 작은 파일 한정). docstring / README / debugging-guide 모두 이 표현으로 통일 |
| **`resolved_via` 초기값** | placeholder 의 초기값 `"primary"` → `None`. 실제 fetch 한 분기 (`_process_inline` / `_upload_and_cache_file` 의 `fetch_with_fallback` 직후) 에서만 `"primary"` 로 갱신. cache HIT (`_reuse_files_api_uris`) / standby waiter 분기는 `None` 유지 — 검증 안 된 `"primary"` 박제 안 됨 |
| **`FileResolveError` docstring** | 폐기된 복구 경로 (data-mode `files=[..]`) 안내 제거. `register_or_get` 기반 복구 안내로 갱신 |
| **fallback race 보호** | 두 번째 `get_file(new_path)` 도 `try/except FMServiceError` 로 감싸 `FileResolveError` 로 wrap. miss 와 race 동일하게 `error_type='file_resolve'` 로 통일 |
| **SDK 모듈 docstring** | 옛 `files=[FileInput]` 예시 → `FileManagerHandler.register_or_get` + `StoredFile` 예시로 갱신 |

#### Important / 정정 (7건)

- **호환성 매트릭스 3단계로 분리** (위 표) — "옛 SDK silent drop" 은 pre-Phase-2 한정 케이스. Phase 3 는 fail-fast 422
- 비-404 raise 전 `logger.exception(...)` 진단 로그 추가 (file-manager 다운/네트워크 단절 식별)
- `("upload", "primary", "fallback")` enum 테스트 → `("primary", "fallback")` 만 — Method 1 폐기 정합 (회귀 보호 복원)
- `[Phase3]` 로그 prefix 제거 (네이밍 위생) — debugging-guide 의 `[Phase2]` 안내와 충돌 해소
- `StoredFile` 응답 dict 재사용 시 422 — README 에 6 필드 픽킹 one-liner 안내 (`StoredFile(**{k: saved[k] for k in StoredFile.model_fields})`)
- `_estimate_non_file_bytes` 의 broad `except Exception` → **별도 PR 머지** — `except (TypeError, ValueError, RecursionError)` 로 좁힘 + 테스트 케이스 circular reference 로 교체 (`json.dumps(default=str)` 가 실제 발생시킬 수 있는 예외만)
- cache hit dump 의 옛 doc `resolved_via` 키 누락 — README 호환 안내 (caller 가 `fm.get("resolved_via")` 안전 접근)

#### Suggestions (4건)

- README 디렉터리 트리 갱신 — 삭제된 `file_register.py` 제거, 신규 `file_resolver.py` 추가
- `file_resolver.py` vs `file_processing/resolver.py` 이름 충돌 → **별도 PR 머지** — `service/app/logic/file_resolver.py` → `stored_file_resolver.py` 개명. import / 테스트 파일명 / monkeypatch 경로 / docstring / README 디렉터리 트리 / debugging-guide 동반 갱신

## 사용 예시 (Phase 3 최종 형태)

```python
# Agent 측 (ESG 등)

# 1. file-manager 에 등록 (이미 있으면 skip, 없으면 upload)
from file_manager import FileManagerHandler
fm = FileManagerHandler()
metadata = fm.build_metadata(file_name, file_mtime, file_size)
file_meta = await fm.register_or_get(bytes_data, metadata)
del bytes_data  # 메모리 즉시 회수

# 2. llm-request 호출 (file_path + 5 메타만 전송, bytes 0)
from llm_request import StoredFile, llm_request_async
stored = StoredFile(**file_meta)
response, meta = await llm_request_async(
    llm_input,
    stored_files=[stored],
    cache_mode=True,
)

# 3. 응답 meta.file_meta[0].resolved_via 확인
# - "primary": file_path 1차 fetch 성공
# - "fallback": 1차 stale → check_cache 로 새 path → caller 가 자기 DB 갱신해야 함
```
