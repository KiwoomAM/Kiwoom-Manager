## §1. `fetch_by_cache_key` ✅ 완료 (13)

### 의도

caller 가 이미 `done_check` 으로 받은 `cache_key` 를 보유. 다시 `llm_input` → canonicalize → hash 과정 없이 **cache_key 만으로** MongoDB 에서 결과 조회 + LLMResponse / StreamChunk 형식으로 반환.

### 변경 파일

| 파일 | 변경 |
|---|---|
| `service/app/logic/store.py` | `fetch_by_cache_key` 함수 신규 |
| `sdk/llm_manager/__init__.py` | export 추가 |
| `sdk/llm_manager/_client.py` | SDK 진입점 |

### 사용 예시

```python
from llm_manager import fetch_by_cache_key
result, meta = await fetch_by_cache_key("abc123...", database="default")
```

→ Phase 1 (`18.file-meta-stored-files-history.md` Part A) 의 `file_meta` 노출도 이 경로에 포함됨.

## §2. LLM 호출 실패 결과 MongoDB 저장 — ⚠️ 구현 후 폐기 (12)

### 원래 의도

LLM 호출 실패 시 에러 정보를 MongoDB 에 저장. 단, 캐시 조회에서는 제외 (같은 입력으로 재호출 시 에러 캐시 반환 방지).

### 폐기 결정 사유

- 에러 saving 은 캐시 조회 비대칭 (조회 제외 + 저장만) 으로 운영 복잡도 증가
- 디버깅 가치는 logging / observability 로 충분히 커버
- 실제 사용처 부재 — 도입 후 활용 시나리오 안 만들어짐
- → 구현 완료했으나 코드에서 제거

### 잔재

코드 제거 완료. 본 결정은 미래 재도입 시 같은 곳을 다시 파지 않도록 기록.

## §3. Files API URI 복구 — sha256_hash 기반 ⏸ Backlog (11)

### 아이디어

Gemini Files API 가 반환하는 `sha256_hash` (content hash) 와 `list_files()` 를 활용. Redis files_api 캐시가 유실/만료됐을 때 재업로드 없이 URI 복구.

### 동작 시나리오

1. Redis cache miss
2. `list_files()` 호출하여 Gemini 측 파일 목록 조회
3. `sha256_hash` 매칭으로 URI 발견 → Redis 캐시 갱신 후 사용
4. 매칭 실패 시 일반 업로드 경로

### 보류 사유

- 현 운영상 Redis 만료 빈도 낮음
- `list_files()` API 비용 / rate limit 영향 미측정
- 필요 시 재검토 — 트리거: Redis 만료/장애 빈발 또는 운영 측 요청

## §4. Observability Backlog ⏸ (14)

### 의도

llm-manager 가 요청 하나를 처리할 때 내부 분기 / 캐시 상태 / 동시성 역할을 **서비스 로그 (uvicorn stdout)** 만 보고 파악할 수 있도록 로그 추가.

### 방침

- `meta` 응답 스키마는 건드리지 않음 (프로덕션 스키마 고정)
- SDK / 클라이언트 호출 코드 변경 없음
- Service 측 stdout 로그만 추가

### 추가 후보

| 영역 | 로그 |
|---|---|
| 요청 진입 | request_id, file_count, mode (path/data) |
| 캐시 조회 | hit/miss, source (redis/mongo), key prefix |
| dedup | leader/follower, standby_key, wait_duration |
| Files API | upload/cache, URI 출처 |
| Context Cache | create/reuse, ttl 잔여 |
| LLM 호출 | model, input_tokens, output_tokens, elapsed |
| 응답 | resolved_via, cache_hit, error_type |

→ 우선순위 결정 후 진행. 현재 미진행.

## §5. Memory Cleanup — `fi.data` 라이프사이클 단축 (16)

### 배경

Kiwoom-ESG 다중 파일 일괄 처리 시 `docker stats` 로 호스트 메모리 점유 1 순위가 **llm-manager Service 컨테이너**. 같은 bytes 가 한 요청 동안 여러 사본으로 메모리에 머무는 문제.

### 정리 후보 4 가지

| # | 후보 | 후속 처리 |
|---|---|---|
| 1 | FastAPI raw body + Pydantic bytes 사본 | ⏸ Backlog — body parsing 단계 메모리 (FastAPI 한계) |
| **2** | **`_Prepared.files` / `fi.data` 잔존** | **✅ Phase 3 (`18.md` Part C) 의 lazy fetch 로 자연 해소** — `FileInput.data` default `b""`, leader 만 fetch, leader 도 fetch 후 즉시 비우기 |
| 3 | `splitter.py` 임시 파일 disk leak | ⏸ Backlog — splitter 종료 시 임시 디렉토리 정리 |
| 4 | stream `accumulated` 청크 누적 | ⏸ Backlog — stream 종료 후 즉시 release |

### #2 의 Phase 3 흡수 흐름

```
요청 진입 (path-mode)
  └─ FileInput.data = b""           ✅ 처음부터 비어있음
       │
       ├─ follower: 그대로 대기      ✅ fetch 안 함
       │
       └─ leader 분기에서 lazy fetch
            ├─ fi.data = await fm.get_file(file_path)
            ├─ Files API upload OR inline 처리
            └─ fi.data = b""        ✅ 즉시 회수
```

→ #2 는 Phase 3 로 자연 해소. #1, #3, #4 는 별개 backlog.

### 측정값

- Phase 3 적용 전: ESG 다중 파일 처리 중 llm-manager 컨테이너 RSS 1 순위
- Phase 3 적용 후: 70 동시 요청 시 fetch 1 회 + bytes 즉시 회수 → 메모리 stable (정량 수치는 별도 측정)
