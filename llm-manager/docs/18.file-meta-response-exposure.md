> file-manager `file_path` 라운드트립 — 서버가 부여한 `file_path` 를 응답으로 노출(Phase 1) + 사용자가 그 `file_path` 로 다시 호출하여 bytes 재전송 회피(Phase 2).

# Phase 1 — `file_meta` 응답 노출

## 1. 배경 / 문제 정의

### 외부 요청

Kiwoom-ESG 가 평가 결과를 MDB 에 저장할 때 file-manager 가 부여한 `file_path` 를 함께 저장해야 한다. 같은 PDF 로 재평가 시 file-manager 에서 bytes 를 다시 받아오기 위함.

### 현재 동작

- 파일 등록은 llm-request 의 [`register_files`](../service/app/logic/file_register.py#L22) 가 담당.
- file-manager 가 부여한 `file_path` 는 [`FileInput.file_path`](../service/app/models/requests.py#L37) 에 심어진 뒤, [`_dump_files_meta`](../service/app/logic/runner.py#L195) 가 dump 하여 MDB `agent_llm` 컬렉션의 `doc["file_meta"]` 키로 저장된다 ([store.py:90-91](../service/app/logic/store.py#L90-L91)).
- 그러나 응답 (`/v1/request`) 의 `meta` dict 에는 노출되지 않아 → ESG 가 호출 시점에 `file_path` 를 알 길이 없음.

### 추가 발견 — SDK 모델 호환성

[`RequestMeta`](../sdk/llm_request/models.py#L59) 는 SDK 가 실제로 `model_validate` 한다 ([__init__.py:242, 360](../sdk/llm_request/__init__.py#L242)). `model_config` 가 없어 Pydantic v2 기본 `extra="ignore"` 가 적용 → 서버가 `file_meta` 를 응답에 추가해도 SDK 객체에는 누락됨. ESG 가 `meta.file_meta` 로 접근하면 `AttributeError`. **SDK 모델에도 필드 추가가 필수.**

## 2. 사전 정보

### 2.1 meta dict 가 만들어지는 자리 — 3 곳

| # | 위치 | 진입점 영향 |
|---|------|------------|
| ① live | [`_build_live_meta`](../service/app/logic/runner.py#L181) | non-stream / stream live / stream standby 모두 사용 |
| ② cache hit | [`prepare` cached_meta](../service/app/logic/runner.py#L142-L148) | non-stream / stream cache hit / standby waiter 모두 사용 |
| ③ fetch | [`fetch_by_cache_key`](../service/app/logic/store.py#L141-L147) | done_check 후 직접 조회용 별도 진입점 |

→ ①/②/③ 셋만 손대면 SDK 공개 함수 5 개 (`llm_request_async`, `llm_request`, `llm_request_stream_async`, `llm_request_stream`, `fetch_by_cache_key`) 가 한 번에 영향 받음.

### 2.2 MongoDB doc vs 응답 meta — 구조 비교

| 키 | MongoDB doc | 응답 meta (현재) | 응답 meta (변경 후) |
|----|-------------|-----------------|--------------------|
| `_id` (= cache_key) | ✅ | — (`cache_key` 키로 노출) | 동일 |
| `cache_key` | — | ✅ | 동일 |
| `canonical_json` | ✅ | ❌ | ❌ |
| `result` | ✅ | — (튜플 첫 원소로 별도) | 동일 |
| `metadata` | ✅ | ✅ | ✅ |
| `created_at` | ✅ | ❌ | ❌ |
| `requested_at` | ✅ (조건부) | ❌ | ❌ |
| `expires_at` | ✅ (조건부) | ❌ | ❌ |
| `file_meta` | ✅ (조건부) | ❌ | ✅ (조건부) ← **추가** |
| `source` / `cache_hit` / `collection` | ❌ | ✅ (응답 컨텍스트) | 동일 |

→ 응답 meta 는 doc 의 부분집합이 아니라 별개 모양. 다만 `metadata` ↔ `metadata`, `file_meta` ↔ `file_meta` 두 키가 **doc 과 1:1 거울** 관계로 정렬됨.

### 2.3 `metadata` 가 자유입력이 아니라는 점

[`build_meta`](../service/app/logic/meta.py#L6) 가 만드는 `prep.meta` 는 **고정 2 필드** (`service_name`, `model`). 사용자 자유입력 dict 가 아니므로, `file_meta` 를 `metadata` 안에 nest 하지 않고 형제 top-level 키로 두는 것이 의미상 더 명확.

## 3. 저장소/스키마 설계

### 3.1 응답 shape — Before / After

```jsonc
// Before — files 유무 무관
{
  "result": {...},
  "meta": {
    "source": "live", "cache_hit": false, "cache_key": "...",
    "metadata": {"service_name": "...", "model": "..."},
    "collection": "agent_llm"
  }
}

// After — files 있는 호출
{
  "result": {...},
  "meta": {
    "source": "live", "cache_hit": false, "cache_key": "...",
    "metadata": {"service_name": "...", "model": "..."},
    "collection": "agent_llm",
    "file_meta": [
      {"file_name": "report.pdf", "file_size": 12345, "file_mtime": 1700000000,
       "mime_type": "application/pdf", "extension": ".pdf",
       "file_path": "<file-manager 가 부여한 path>"}
    ]
  }
}

// After — files=None 호출
{
  "result": {...},
  "meta": {
    "source": "live", "cache_hit": false, "cache_key": "...",
    "metadata": {"service_name": "...", "model": "..."},
    "collection": "agent_llm"
    // file_meta 키 없음 — MongoDB doc 동작과 거울 매칭
  }
}
```

### 3.2 결정 사항

| # | 결정 | 결과 | 근거 |
|---|------|------|------|
| Position | meta 안에서의 위치 | **형제 top-level** (nest 아님) | MongoDB doc 의 `metadata`/`file_meta` 형제 구조와 거울 매칭. `metadata` 는 system-derived 고정 2필드 vs `file_meta` 는 등록된 파일 아티팩트 — 카테고리 분리 |
| D1 | 키 이름 단/복수 | **`file_meta` 단수** | MDB 저장 키 (`doc["file_meta"]`) 와 동일하게 통일 |
| D2 | `fetch_by_cache_key` 포함 | **포함** | 5 개 진입점이 같은 모양 유지 — ESG 가 진입점마다 분기 안 해도 됨 |
| D3 | SDK `RequestMeta` 모델 | **추가 필수** | `extra="ignore"` 기본값으로 누락 위험 (§1 추가 발견) |
| D4 | `files=None` 시 | **(a) 키 자체 생략** | doc 의 `if file_metas: doc["file_meta"] = ...` 동작과 정확히 일치 |
| D5 | 옛날 doc 호환 | `dc.cached.get("file_meta")` → `None` | 자연 호환 — 별도 작업 없음 |

## 4. 전체 파이프라인

```
SDK (llm_request_async)
  └─ POST /v1/request
       └─ runner.llm_request_async
            ├─ register_files(files)           ← fi.file_path 채워짐 (file-manager 등록)
            ├─ prepare(...)                    ← meta dict 조립
            │    ├─ live 경로 → _build_live_meta(prep)
            │    │                                └─ _dump_files_meta(prep.files) → file_meta 키 추가
            │    └─ cache hit 경로 → cached_meta (prepare 내부)
            │                          └─ dc.cached.get("file_meta") → file_meta 키 추가
            ├─ _do_llm_call → finalize → save_result(file_metas=...)  ← MDB 에 doc["file_meta"] 저장
            └─ return (response, meta)         ← meta 에 file_meta 포함

SDK (fetch_by_cache_key)
  └─ POST /v1/fetch
       └─ store.fetch_by_cache_key
            └─ doc = cache_get(cache_key)
                  └─ doc.get("file_meta") → meta 에 file_meta 키 추가
            └─ return (response, meta)

SDK 수신
  └─ RequestMeta(**result["meta"])             ← file_meta 필드 정의돼 있어야 통과
```

**변경** (`+3 줄`)
```python
def _build_live_meta(prep: _Prepared) -> dict[str, Any]:
    meta: dict[str, Any] = {
        "source": "live",
        "cache_hit": False,
        "cache_key": prep.dc.cache_key if prep.dc else None,
        "metadata": prep.meta,
        "collection": prep.dc.collection if prep.dc else None,
    }
    file_metas = _dump_files_meta(prep.files)
    if file_metas is not None:                          # D4 (a): 조건부 키
        meta["file_meta"] = file_metas
    if prep.debug and prep.route_reason:
        meta["route_reason"] = prep.route_reason
    return meta
```

### 5.5 헬퍼 함수화 검토 — 인라인 유지

①/② 가 동일 패턴(`if not None: dict[k] = v`) 이라 헬퍼화 가능하지만:
- 동작 3 줄짜리 — 함수화 시 호출 인덱싱 한 단계 더 늘어남
- ① 은 `prep.files` → `_dump_files_meta` 호출, ② 는 doc dict 에서 `.get` — 입력 형태가 다름
- ③ 은 store.py 라 import 가 또 필요

→ **인라인 유지**. YAGNI.

## 6. 에러 처리

### 6.1 `_dump_files_meta` 가 raise 할 수 있는가

[`_dump_files_meta`](../service/app/logic/runner.py#L195) 는 `model_dump(exclude={"data"})` — Pydantic 모델 dump 라 정상 입력에선 raise 없음. `files=None` / `[]` 도 None 반환으로 처리. **에러 처리 불필요.**

### 6.2 cache hit 경로에서 doc 손상

`dc.cached.get("file_meta")` — 키 없거나 `None` 이면 자연스럽게 `None` 처리. doc 의 `file_meta` 가 list 가 아닌 다른 타입으로 손상돼 있어도 (운영자가 mongo shell 로 직접 수정 / 다른 코드와 컬렉션 혼용 / 마이그레이션 실수 등 이상 시나리오) 응답에는 **그대로 통과**시킴 — consumer 측 책임.

**별도 검증 안 함 — silent passthrough.** 손상은 doc 작성 쪽 책임이고, defensive 검사 추가 비용 대비 발생 가능성이 낮음. 만약 검사를 넣으려면 `if not isinstance(file_metas, list): log warning + drop` 같은 loud failure 방향으로 갈 수 있지만, 현재는 채택 안 함.

### 6.3 SDK ↔ Service 버전 매트릭스 — 자연 호환

SDK 와 Service 는 독립 배포라 "한쪽만 새 거 깔린 상태" 가 잠깐 존재할 수 있다. 4 칸 매트릭스로 정리:

| | 옛 서버 (응답에 `file_meta` 키 **없음**) | 새 서버 (응답에 `file_meta` 키 **포함**) |
|---|---|---|
| **옛 SDK** (`RequestMeta` 에 필드 **없음**) | ✅ 정상 (변경 전 상태) | ⓐ |
| **새 SDK** (`RequestMeta` 에 필드 **있음**) | ⓑ | ✅ 정상 (의도한 동작) |

**ⓐ 옛 SDK + 새 서버** — 새 서버가 `"file_meta": [...]` 를 응답에 넣어 보내지만, 옛 SDK 의 `RequestMeta` 에는 필드가 없음. **Pydantic v2 기본 `extra="ignore"`** 로 모르는 키는 조용히 버려짐 → 에러 없이 `RequestMeta` 객체 생성. 옛 SDK 사용자는 `meta.file_meta` 접근 불가(새 기능 못 씀) — 다만 깨지지는 않음.

**ⓑ 새 SDK + 옛 서버** — 옛 서버는 `file_meta` 키 자체를 안 보냄. 새 SDK 의 `RequestMeta.file_meta: list[dict] | None = None` 의 default 값으로 채워짐 → `meta.file_meta is None` 으로 객체 생성. 에러 없음.

→ **"자연 호환"** = 추가 코드/분기 없이 **배포 순서가 어떻든 깨지지 않는다**. §9 의 "SDK 선행 배포" 결정의 근거 — ⓑ 가 안전하므로 SDK 를 먼저 깔아도 무방.

# Phase 2 — `stored_files` 입력 지원

> Phase 1 으로 응답에 노출된 `file_meta` 의 `file_path` 를 호출자가 다시 입력으로 넘기면, llm-request 가 file-manager 에서 직접 fetch 해 bytes 재전송 비용(네트워크 + CPU + 메모리)을 없앤다.

---

## 1. 배경 / 문제 정의

### 외부 요청

같은 PDF 로 재호출 시 호출자(ESG 등)가 bytes 를 다시 base64 로 인코딩해 보내는 비용이 매번 발생한다. Phase 1 으로 응답의 `meta.file_meta[i].file_path` 를 받았으니, 이 path 를 그대로 다시 넘기면 llm-request 가 file-manager 에서 직접 가져올 수 있어야 한다.

### 핵심 흐름

1. `stored_files` 의 각 ref 에 대해 `file-manager.get_file(file_path)` 1차 시도 → bytes + 메타 6 필드 확보
2. 1차 실패 (file_path stale, 404) 시 hashing 3 필드로 `file-manager.check_cache` → 새 file_path 발견 시 재시도 + 호출자에게 경고 신호
3. 둘 다 miss 면 `FileResolveError` raise (호출자가 catch 후 data-mode 로 재업로드 결정)

### 옵션 A vs B 검토 결과

기존 `FileInput` 의 `data` 를 Optional 로 만들고 같은 list 에 두 모드 섞기(A) vs 새 인자 `stored_files` 추가(B) 검토 결과 **B 채택**. 핵심 근거:

- **Phase 1 응답 ↔ Phase 2 입력 모델 호환** — Phase 1 이 노출한 `file_meta` dict 의 4 필드(`file_path`, `file_name`, `file_size`, `file_mtime`)를 그대로 `StoredFile` 로 만듦
- **`FileInput` 의미 보존** — `data: Base64Field` 필수 계약 유지, `file_path` 가 "server-fill 결과" 의미 그대로
- **기존 호출자 무영향** — 신규 인자 default `None`, 기존 코드 경로 그대로

## 2. 사전 정보

### 2.1 file-manager SDK API

[`FileManagerHandler`](../../file-manager/sdk/file_manager/handler.py) 가 제공하는 메서드 중 Phase 2 가 사용하는 2 개:

| 메서드 | 입력 | 반환 | Phase 2 활용 |
|--------|------|------|------------|
| [`get_file(file_path)`](../../file-manager/sdk/file_manager/handler.py#L151) | UUID.확장자 | `(bytes, metadata 6 필드)` | **1차 fetch** — file_path 가 유효하면 bytes + 메타 한 번에 |
| [`check_cache(metadata)`](../../file-manager/sdk/file_manager/handler.py#L102) | `{file_name, file_size, file_mtime}` | `{hit: bool, file_path: str \| None}` | **2차 fallback** — 1차 path 가 stale 일 때 hashing 으로 새 path 찾기 |

→ 호출자가 보낼 정보는 **`file_path` + hashing 3 필드** 로 충분. mime_type / extension 은 `get_file` 의 metadata 응답에 포함되어 자동 채워짐.

### 2.2 진입점 영향 범위

SDK 공개 함수 4 개 (`llm_request_async` / `llm_request` / `llm_request_stream_async` / `llm_request_stream`) 시그니처에 `stored_files: list[StoredFile] | None = None` 추가. `fetch_by_cache_key` 는 cache_key 직접 조회라 Phase 2 영향 없음.

### 2.3 Phase 1 ↔ Phase 2 모델 호환

| 측 | dict / 모델 | 필드 |
|---|------------|------|
| Phase 1 응답 `meta.file_meta[i]` | dict (6 필드) | file_name, file_size, file_mtime, mime_type, extension, file_path |
| Phase 2 입력 `StoredFile` | Pydantic model (4 필드) | file_path, file_name, file_size, file_mtime |

호환 — 호출자가 dict 에서 4 필드만 추출해 넘김. `extra="forbid"` (§3.2 P2-4) 결정으로 키 오타 즉시 잡힘.

## 3. 저장소/스키마 설계

### 3.1 응답 shape

```jsonc
// Phase 2 — stored_files 호출
{
  "result": {...},
  "meta": {
    "source": "live", "cache_hit": false, "cache_key": "...",
    "metadata": {"service_name": "...", "model": "..."},
    "collection": "agent_llm",
    "file_meta": [
      {"file_name": "x.pdf", "file_size": 100, "file_mtime": 1700000000,
       "mime_type": "application/pdf", "extension": ".pdf",
       "file_path": "abc.pdf",
       "resolved_via": "primary"},      // ← file_path 1차 fetch 성공
      {"file_name": "y.pdf", ...,
       "file_path": "new_path.pdf",
       "resolved_via": "fallback"}      // ← 1차 stale → check_cache 로 새 path 찾아 2차 fetch 성공
    ]
  }
}

// data-mode (files=...) 호출 — Phase 2 적용 후
// file_meta[i].resolved_via == "upload" (호출자가 보낸 bytes 를 file-manager 에 신규 업로드)
//
// ⚠️ resolved_via 값은 "성공한 경로"만 표현 — 완전 실패 시 FileResolveError raise 로
//    응답 자체가 만들어지지 않으므로 "fail" 같은 값은 없음
```

### 3.2 결정 사항

| # | 결정 | 결과 | 근거 |
|---|------|------|------|
| Q2 | 새 인자 vs FileInput 확장 | **(B) 새 인자 `stored_files`** | Phase 1 ↔ Phase 2 모델 호환 / FileInput 의미 보존 / 기존 호출자 무영향 |
| P2-1 | mixed 호출 (`files` + `stored_files` 동시) | **(a) 허용** | 내부에서 합쳐 이후 파이프라인 진입. 한 호출에 신규 + 재사용 자연스럽게 |
| P2-2 | 1차 실패 → fallback 발생 알림 | **(c) server log + meta flag** | server log: 운영자 가시 / `meta.file_meta[i].resolved_via` flag: 호출자가 stale 감지 후 자기 DB 갱신 |
| P2-3 | get_file + check_cache 둘 다 miss | **(a) `FileResolveError` raise** | 부분 성공 응답보다 fail-fast — 호출자가 catch 후 재업로드 결정 |
| P2-4 | `StoredFile` Pydantic `extra` | **(c) `forbid`** | llm-request 가 ESG 외 다수 사용자 보유 — 키 오타/잘못된 입력 즉시 잡아야 함 |
| P2-5 | data-mode `resolved_via` 기본값 | **`"upload"` 항상 채움** (3 enum: `upload` / `primary` / `fallback`) | 응답 shape 에 키가 항상 존재 → consumer 처리 단순. None default 시 dump 동작 추가 분기 필요 |

### 3.3 호환성 / 파일 순서

#### SDK ↔ Service 매트릭스

| | 옛 SDK (`stored_files` 안 보냄) | 새 SDK (`stored_files` 보낼 수 있음) |
|---|---|---|
| **옛 Service** (`LLMRequestBody.stored_files` 없음) | ✅ 정상 | ⚠️ silent drop — atomic 동시 배포로 회피 |
| **새 Service** (`LLMRequestBody.stored_files` 있음) | ✅ 정상 | ✅ 의도한 동작 |

→ SDK 와 Service 는 **atomic 동시 배포** (한 PR + 같은 CI/CD pipeline). 시간 gap 자체가 없으면 silent drop 시나리오 미발생.

→ 호출자 (ESG 등) 는 자기 코드에서 `stored_files` 사용 시작하기 전에 SDK 만 업데이트하면 됨 — 새 Service 가 이미 처리 가능 상태.

> `LLMRequestBody.model_config` 는 기본 `extra="ignore"` 유지. forbid 로 바꾸지 않는 이유 — 옛 SDK 가 새 서버에 무해하게 호출 가능 (호환성 보존).

- 기존 호출자: 신규 인자 default `None` → 기존 코드 무영향
- service router DTO `LLMRequestBody.stored_files: list[StoredFile] | None = None` 추가

#### 파일 순서 — 결정적 (deterministic)

내부에서 항상 **`files` 먼저, `stored_files` 나중** 으로 합침: `combined = (files or []) + resolved`.

- 같은 파일을 한 번은 `files=[A]`, 다음엔 `stored_files=[A]` 로 호출 → 같은 cache_key (hashing 3 필드 동일)
- mixed 호출 시 결정적 순서 보장 → cache_key 일관 + Gemini contents 순서 예측 가능

## 4. 전체 파이프라인

```
SDK (llm_request_async)
  └─ POST /v1/request {llm_input, files, stored_files}
       └─ runner.llm_request_async
            ├── if stored_files:                                   ← Phase 2 신규 단계
            │     ├─ resolve_stored_files(stored_files)
            │     │     for ref in stored_files:
            │     │       try:
            │     │         bytes, fm_meta = await fm.get_file(ref.file_path)
            │     │         → FileInput(data=bytes, file_path=ref.file_path,
            │     │                     **fm_meta_5fields, resolved_via="primary")
            │     │       except FMServiceError(404):            ← 1차 실패
            │     │         cache = await fm.check_cache({name,size,mtime})
            │     │         if cache.hit:
            │     │           bytes, fm_meta = await fm.get_file(cache.file_path)
            │     │           logger.warning("stale file_path: ...")
            │     │           → FileInput(..., file_path=cache.file_path,
            │     │                       resolved_via="fallback")
            │     │         else:
            │     │           raise FileResolveError              ← 2차 실패
            │     ├─ validate_mime_types(resolved)               ← G2: file-manager 가 우리 화이트리스트 모름
            │     └─ validate_file_sizes(resolved)
            │
            ├── if files:                                        ← 기존 data-mode
            │     ├─ validate_mime_types(files)                   ← 기존 fail-fast
            │     ├─ validate_file_sizes(files)
            │     ├─ register_files(files)
            │     └─ files[*].resolved_via = "upload"            ← P2-5
            │
            ├── combined = (files or []) + resolved              ← 합치기 (P2-1 a, G4 결정적 순서)
            ├── combined = combined or None                      ← 빈 리스트 정규화
            ├── prepare(..., files=combined)
            └── ... 이하 기존 파이프라인 (resolver / aio_call / finalize)
                  └─ _dump_files_meta(combined)
                       → meta["file_meta"][i] 에 resolved_via 자동 노출
```

> 순서 결정 — `stored_files` resolve 를 `files` register_files 보다 먼저. fail-fast (stored_files 가 실패 가능성 높음) + register_files 의 file-manager 업로드를 헛수고로 만들지 않음.

값 enum:

| 값 | 의미 |
|----|------|
| `"upload"` | data-mode (`files=...`) — file-manager 에 신규 업로드된 파일 |
| `"primary"` | path-mode (`stored_files=...`) — file_path 1차 fetch 성공 |
| `"fallback"` | path-mode — file_path stale → check_cache fallback 으로 새 path 발견 후 fetch |

P2-5 결정으로 모든 경로에서 채워짐 → `_dump_files_meta` 의 `model_dump(exclude={"data"})` 가 자동으로 응답·doc 에 포함.

### 5.3 신규 모듈 — `service/app/logic/file_resolver.py`

```python
"""Phase 2 — stored_files 를 file-manager 에서 fetch 하여 FileInput 으로 변환."""

from __future__ import annotations

import logging

from file_manager import FileManagerHandler
from file_manager.exceptions import FMServiceError    # V1 검증: status_code 속성 보유

from app.core.errors import FileResolveError
from app.models.requests import FileInput, StoredFile

logger = logging.getLogger(__name__)


async def resolve_stored_files(refs: list[StoredFile]) -> list[FileInput]:
    """각 StoredFile 를 file-manager 에서 fetch → bytes 로딩된 FileInput 반환.

    1. fm.get_file(ref.file_path) 1차 시도 → 성공 시 resolved_via="primary"
    2. 404 시 fm.check_cache(hash 3 필드) → 새 path → 재 fetch + resolved_via="fallback"
    3. 둘 다 miss → FileResolveError raise
    """
    fm = FileManagerHandler()
    return [await _resolve_one(fm, ref) for ref in refs]


async def _resolve_one(fm: FileManagerHandler, ref: StoredFile) -> FileInput:
    try:
        data, fm_meta = await fm.get_file(ref.file_path)
        return _build_file_input(data, fm_meta, resolved_via="primary")
    except FMServiceError as e:                # 404 외 에러는 그대로 전파
        if e.status_code != 404:
            raise
        cache = await fm.check_cache({
            "file_name": ref.file_name,
            "file_size": ref.file_size,
            "file_mtime": ref.file_mtime,
        })
        if not cache["hit"]:
            raise FileResolveError(
                f"file_path '{ref.file_path}' 404 + check_cache miss "
                f"(file_name={ref.file_name})"
            ) from e
        new_path = cache["file_path"]
        logger.warning(
            "[Phase2] stale file_path: input=%s, resolved=%s, file_name=%s",
            ref.file_path, new_path, ref.file_name,
        )
        data, fm_meta = await fm.get_file(new_path)
        return _build_file_input(data, fm_meta, resolved_via="fallback")


def _build_file_input(data: bytes, fm_meta: dict, *, resolved_via: str) -> FileInput:
    return FileInput(
        data=data,
        file_path=fm_meta["file_path"],
        file_name=fm_meta["file_name"],
        file_size=fm_meta["file_size"],
        file_mtime=fm_meta["file_mtime"],
        mime_type=fm_meta["mime_type"],
        extension=fm_meta["extension"],
        resolved_via=resolved_via,
    )
```

> 검증 완료 (V1) — import path: `from file_manager.exceptions import FMServiceError`. `FMServiceError(message, status_code)` 가 `status_code` 속성 보유 → `e.status_code == 404` 패턴으로 404 판정.

### 5.5 진입점 4 함수 + service router 변경

```python
# service/app/logic/runner.py
from app.logic.file_resolver import resolve_stored_files

async def llm_request_async(
    llm_input: dict,
    *,
    files: list[FileInput] | None = None,
    stored_files: list[StoredFile] | None = None,         # ← 추가
    cache_mode: bool = True, save_mode: bool = True,
    ttl_seconds: int | None = None,
    database: str | None = None,
    context_cache_ttl: int | None = None,
    standby_ttl_seconds: int = 600,
    debug: bool = False,
) -> tuple[LLMResponse, dict[str, Any]]:
    if not (cache_mode or save_mode):
        files = stored_files = None

    # Phase 2 — stored_files 먼저 resolve (실패 가능성 높음 → fail-fast)
    resolved: list[FileInput] = []
    if stored_files:
        resolved = await resolve_stored_files(stored_files)
        # G2: file-manager 는 우리 SUPPORTED_MIME_TYPES 화이트리스트 모름 → 재검증
        validate_mime_types(resolved)
        validate_file_sizes(resolved)

    # 기존 data-mode
    if files:
        validate_mime_types(files)                    # 기존 fail-fast (user 입력)
        validate_file_sizes(files)
        await register_files(files)
        for fi in files:
            fi.resolved_via = "upload"               # P2-5

    combined = (files or []) + resolved              # G4: 결정적 순서 (files 먼저)
    combined = combined or None                       # 빈 리스트면 None 으로 정규화

    prep = prepare(llm_input, files=combined, ...)
    # ... 이하 기존 코드 그대로
```

## 6. 에러 처리

### 6.1 1차 실패 → fallback 정상 흐름

- `get_file(file_path)` 가 file-manager `FMServiceError(status_code=404)` 로 raise
- `check_cache(hashing 3)` → `{hit: true, file_path: new_path}`
- `get_file(new_path)` 재호출 → 성공 시 `resolved_via="fallback"`
- server log `WARN` + 응답 `meta.file_meta[i].resolved_via="fallback"` (P2-2 c 양쪽)
- 호출자 액션: 자기 DB 의 file_path 를 새 값으로 갱신 권장

### 6.2 둘 다 miss → `FileResolveError`

- get_file 404 + check_cache `{hit: false}` → file-manager 에 정말로 없음
- `FileResolveError` raise — caller 가 catch 후 data-mode 로 재업로드 결정 (P2-3 a)
- 부분 성공 (일부 stored_files 만 resolve, 나머지 error) 같은 복잡 처리는 안 함 — fail-fast

### 6.3 file-manager 자체 장애 (network / 5xx)

- `get_file` 비-404 에러 → 그대로 전파 (`FMServiceError(status_code=5xx)` 또는 `httpx.HTTPError`)
- `check_cache` 도 동일

### 6.4 mixed 호출 시 부분 실패 순서

- stored_files resolve 단계가 raise → files 의 `register_files` 는 시작 전에 끝
- 순서: **stored_files 먼저** (실패 가능성 더 높음 → fail-fast)
- 반대 순서로 갔을 때 우려: data-mode 업로드 성공 후 stored_files resolve 실패 시 file-manager 에 고아 파일 잔존 가능. 다만 file-manager 의 dedup 로직이 있어 다음 호출에서 같은 메타로 재업로드해도 동일 file_path 반환 → 실질 문제 아님. fail-fast 가 더 깔끔.

### 6.5 옛 Phase 1 doc 의 `resolved_via` 부재

Phase 1 만 배포된 시기에 저장된 MDB doc 의 `file_meta[i]` 에는 `resolved_via` 키가 없다. Phase 2 배포 후 이 doc 을 cache hit 으로 응답에 노출 시 — `resolved_via` 키 누락된 채 응답 (G5).

→ 자연 호환이지만 consumer 측 안전 접근 권장:

```python
# 직접 인덱싱은 KeyError 가능
resolved = fm["resolved_via"]    # ❌

# .get() 사용
resolved = fm.get("resolved_via")  # ✅ None 또는 "upload"/"primary"/"fallback"
```

→ ESG 등 consumer 의 fallback 감지 코드 (§7.2) 도 `.get()` 사용하면 옛/새 doc 모두 안전.

### 6.6 `stored_files` 의 mime/size 검증 — 재실행 (G2)

`stored_files` 가 file-manager 에서 fetch 한 파일은 file-manager 측에선 검증됐지만, **llm-request 의 `SUPPORTED_MIME_TYPES` 화이트리스트는 file-manager 가 모름** → resolve 직후 `validate_mime_types(resolved)` / `validate_file_sizes(resolved)` 재실행 (§4 / §5.5 참고).

- 검증 실패 시: `UnsupportedFileTypeError` / `FileTooLargeError` raise (data-mode 와 동일 동작)
- 호출자: 해당 파일을 stored_files 에서 제외하거나 다른 파일 보내야 함

## 7. 사용 예시

### 7.1 기본 — Phase 1 응답을 받아 Phase 2 로 재호출

```python
from llm_request import llm_request_async, FileInput, StoredFile

# 첫 호출 — Phase 1 응답으로 file_meta 받음
response, meta = await llm_request_async(llm_input, files=[FileInput(...)])
# meta.file_meta[0] = {... file_path: "abc.pdf", resolved_via: "upload"}

# 호출자 (ESG) 가 자기 DB 에 저장
db.evaluations.insert_one({"result": response.text, "file_meta": meta.file_meta})

# 재호출 — 4 필드만 추출 (P2-4 forbid)
saved = db.evaluations.find_one({...})["file_meta"]
STORED_KEYS = {"file_path", "file_name", "file_size", "file_mtime"}
refs = [StoredFile(**{k: d[k] for k in STORED_KEYS}) for d in saved]

response2, meta2 = await llm_request_async(llm_input, stored_files=refs)
# meta2.file_meta[0].resolved_via == "primary" (또는 stale 시 "fallback")
```

### 7.2 fallback 감지 후 자기 DB path 갱신

```python
for i, fm in enumerate(meta2.file_meta):
    if fm["resolved_via"] == "fallback":
        db.evaluations.update_one(
            {"_id": eval_id},
            {"$set": {f"file_meta.{i}.file_path": fm["file_path"]}}
        )
        logger.info("file_path 갱신: %s → %s", refs[i].file_path, fm["file_path"])
```

### 7.3 mixed — 신규 + 재사용 한 호출에

```python
response, meta = await llm_request_async(
    llm_input,
    files=[FileInput(data=new_bytes, ...)],     # 신규 업로드
    stored_files=[StoredFile(file_path="...", ...)],  # 기존 파일 재사용
)
# meta.file_meta = [
#   {... resolved_via: "upload"},     # files 에서 옴
#   {... resolved_via: "primary"},    # stored_files 에서 옴
# ]
```

### 7.4 둘 다 miss 처리

```python
try:
    response, meta = await llm_request_async(llm_input, stored_files=refs)
except FileResolveError as e:
    logger.warning("stored_files 실패 — data-mode 로 재시도: %s", e)
    files = [FileInput(data=fetch_from_local(...), ...) for ...]
    response, meta = await llm_request_async(llm_input, files=files)
```
