# 16. Memory Cleanup Plan — `fi.data` 라이프사이클 단축

> 큰 파일 요청 시 같은 bytes가 한 요청 동안 여러 사본으로 메모리에 머무는 문제를 해소한다.
> inline 경로는 그대로 두고, **Files API 경로를 1차 타겟**으로 한다.

---

## 1. 배경 / 문제 정의

### 관찰된 증상

- Kiwoom-ESG 코드에서 **다중 파일 일괄 처리** 시나리오를 돌리던 중 발견.
- 동일 호스트(서버 컴퓨터)에 여러 Docker 컨테이너가 함께 동작.
- ESG 컨테이너에서 작업이 진행되는 동안 **모니터링 화면이 정상적으로 뜨지 않음**.
- `docker stats` 로 호스트 메모리 점유율 확인 결과, **`llm-request` 서비스 컨테이너가 가장 큰 지분**을 차지.

### 진단 결론

- 메모리 발 컨테이너 = **llm-request 서비스 컨테이너 (FastAPI 측)**.
- ESG(SDK 호출 측) 자체의 메모리 부풀음은 1차 타겟에서 제외 — `read_bytes()` 의 영향이 있다 해도 본 plan 범위 밖.
- 따라서 본 plan 은 §2 의 **service 측 `fi.data` 라이프사이클** 분석을 그대로 타겟으로 한다.

### 측정값

- 측정 도구: `docker stats <container>` 로 호스트의 컨테이너별 메모리 점유율 모니터링
- 정성적 관찰: ESG 다중 파일 처리 중 `llm-request` 컨테이너가 호스트 메모리 1 순위 점유
- 정량 수치: Phase 1 적용 전후 RSS 비교 측정 예정 (§8 검증 방법 참조)

## 2. 사전 정보 — 현재 `fi.data` 라이프사이클

### 2.1 `fi.data` read 지점 (3곳)

| # | 위치 | 코드 | 역할 |
|---|------|------|------|
| ① | [file_register.py:59](../service/app/logic/file_register.py#L59) | `fm.upload_file(fi.data, upload_meta)` | 파일 등록 — file-manager에 업로드 |
| ② | [resolver.py:141](../service/app/logic/file_processing/resolver.py#L141) | `Part.from_bytes(data=fi.data, mime_type=fi.mime_type)` | **inline 경로** — Part로 감싸 LLM payload에 삽입 |
| ③ | [resolver.py:188](../service/app/logic/file_processing/resolver.py#L188) | `tmp.write(fi.data)` | **Files API 경로** — 임시 파일로 쓴 뒤 `upload_file` |

### 2.2 `prep.files`의 라이프사이클

`runner.llm_request_async`는 다음 순서로 진행되며, `prep.files`는 함수 끝까지 살아있다:

```
files 수신
 └─ register_files(files)             ← ① fi.data read
 └─ prep = prepare(..., files=files)  ← prep.files 에 매달림
 └─ _do_llm_call(prep)
      └─ _build_server_call_input(prep)
           └─ resolve_files(prep.files, ...)
                ├─ _process_inline        ← ② fi.data read (inline)
                └─ _upload_and_cache_file ← ③ fi.data read (Files API)
      └─ aio_call(**call_input)  ⏱️ LLM API 호출 (수~수십 초)
      └─ finalize(prep, ...)
           └─ _dump_files_meta(prep.files)  ← model_dump(exclude={"data"})
                                             bytes 불필요
```

**핵심 관찰** — ②/③ 이후로 `fi.data` 는 직접 read 되지 않는다. 다만:

- **inline(②)** 경로는 `Part.from_bytes` 가 bytes 를 (참조든 복사든) 잡고 있어, 비우면 LLM payload 가 깨질 수 있음.
- **Files API(③)** 경로는 `tmp.write` 후 더 이상 `fi.data` 를 사용하지 않는다 → **즉시 비울 수 있다.**

`finalize` / `_dump_files_meta` 는 `model_dump(exclude={"data"})` 로 bytes 를 의도적으로 제외한다 → MDB 저장에는 필요 없음.

### 2.3 inline vs Files API 경로 — 분기 핵심

| 경로 | 분류 기준 | bytes 마지막 사용 시점 | 회수 가능 시점 |
|------|----------|----------------------|---------------|
| inline | image/audio 합 ≤20MB 또는 PDF/text 합 ≤50MB | `Part.from_bytes` 호출 | Part 폐기 시 (LLM 응답 이후) |
| Files API | 위 한도 초과 또는 video | `tmp.write(fi.data)` 직후 | **`_upload_and_cache_file` 종료 시점** |

→ 큰 파일은 정확히 Files API 경로로 가므로, **이 경로만 정리해도 메모리 효과의 대부분을 가져온다.**

### 2.4 404 자동 복구 경로 (예외 흐름)

`_do_llm_call` 은 Gemini 404 발생 시 `resolve_files_after_404(prep.files, ...)` 로 재처리 → **이때 `fi.data` 가 다시 필요**할 수 있음. 비우는 시점을 정할 때 이 흐름과의 호환성을 §6 에서 다룬다.

### 3.2 #2 — `_Prepared.files` / `fi.data` 잔존

**현재**
`prep = prepare(..., files=files)` 로 `_Prepared.files` 에 매달리고, `_do_llm_call(prep)` → `_build_server_call_input` → `resolve_files` → `aio_call(...)` → `finalize` 까지 함수 스코프 끝날 때까지 살아있다. Files API 경로는 [resolver.py:188](../service/app/logic/file_processing/resolver.py#L188) `tmp.write(fi.data)` 직후로 사용처가 없고, inline 경로는 `aio_call` 종료까지 `Part` 가 참조 유지.

**문제**
Files API 경로 bytes 가 LLM API 응답 대기(수~수십 초) 동안 메모리에 잡혀 있음. 큰 파일일수록 큼. `finalize` / `_dump_files_meta` 는 `model_dump(exclude={"data"})` 로 의도적으로 bytes 를 제외하면서, 정작 메모리에선 안 비운다.

**수정** (`1~3줄 + α`)

- Files API 경로 — [`_upload_and_cache_file`](../service/app/logic/file_processing/resolver.py#L168) 끝에:
  ```python
  fi.data = b""  # Files API 경로 — 이후 더 이상 안 씀
  ```
- inline 경로 (선택) — `aio_call` 종료 후 inline 풀의 `fi.data` 비우기. 효과는 작지만 일관성 위해 검토.
- 404 자동 복구는 비운 후 raise (옵션 나) — 1회 재시도 정책 유지.

**효과**
LLM API 응답 대기 동안 큰 파일 bytes 즉시 회수. 50MB 파일 5개 = 250MB 가 응답 시간(예: 30초) 동안 free.

### 3.3 #3 — `splitter.py` 임시 파일 disk leak

**현재**
[`split_pdf`](../service/app/logic/file_processing/splitter.py#L54) 가 분할하면서 `NamedTemporaryFile` 을 여러 개 만들어 `result` 에 누적, 호출자(uploader)가 `try/finally` 로 정리. 정상 흐름엔 leak 없음. 그러나 **`split_pdf` 자체가 중간에 raise**(예: line 124 `part_doc.save()`, line 164 `doc_m.save()`) 하면 이미 만들어진 임시 파일이 함수 밖으로 나오지 못해 호출자가 정리 못 한다.

**문제**
50MB PDF 분할 중 5개째 save 실패 시 → 앞 4개 임시 파일이 디스크에 leak. 반복 발생하면 디스크 누적 → tmpfs 점유 → 호스트 메모리 압박 (`/tmp` 가 tmpfs 면 직접 메모리).

**수정** (`10~20줄`)
`split_pdf` 에 `created_temps` 추적 + `except` 정리:
```python
created_temps: list[str] = []
try:
    # 기존 로직, tmp 만들 때마다 created_temps.append(tmp.name)
    return result
except Exception:
    for t in created_temps:
        if t not in result:  # 호출자에게 안 넘긴 것만
            try: os.unlink(t)
            except OSError: pass
    raise
```

**효과**
분할 실패 시 디스크 leak 0. 정상 흐름엔 무영향.

**관련 잠재 버그 (같이 수정)**

- **Bug A** — `_estimate_page_sizes` 호출 시 fitz Document leak ([line 84-88](../service/app/logic/file_processing/splitter.py#L84))
  - `doc = fitz.open(path); _estimate_page_sizes(doc, ...); doc.close()` 사이에 raise 시 close 누락
  - 수정: `try/finally` 로 doc.close 보장

- **Bug B** — `_MAX_DEPTH` 초과 재귀 후 unlink 결과 leak ([line 139-143](../service/app/logic/file_processing/splitter.py#L139))
  - 재귀가 `[tmp.name]` 그대로 반환하면 unlink 후 `result` 에 없는 파일 추가 → 호출자 `FileNotFoundError`
  - 수정: `if sub_paths == [tmp.name]: result.append(tmp.name)` else 분기로 unlink/extend

- **시나리오 ③ 보강** — 재귀 후 `os.unlink(tmp.name)` 실패 시 `sub_paths` leak
  - 수정: `created_temps.extend(sub_paths)` 를 unlink 전에 호출

### 3.4 #1 — FastAPI raw body + Pydantic bytes 사본

**현재**
SDK 가 파일을 base64 인코딩한 string 을 JSON 본문에 실어 POST. 서버는 raw body(string) 를 받고, Pydantic 의 `BeforeValidator` 가 `b64decode` → `FileInput.data`(bytes). [models/requests.py:19](../service/app/models/requests.py#L19)

**문제**
같은 파일이 **(a) raw body 의 base64 string ≈ 원본 ×1.33 + (b) decoded bytes**, 두 사본이 동시 메모리 점유. 100MB 파일 → 233MB. Starlette `Request` 객체가 raw body 를 핸들러 종료 시점까지 보유 → 우리 코드에서 직접 비울 수 없음.

**수정** (`50~100줄`)
JSON+base64 → `multipart/form-data` 로 전환.

- `models/requests.py`: `FileInput.data` 제거, 메타만 유지
- `routers/request.py`: `LLMRequestBody` → `UploadFile` + Form 분리
- `sdk/_client.py`: httpx `data=` → `files=`
- SDK ↔ 서버 동시 변경, 호환성 깨짐

**효과**
파일당 사본 1개로 축소. 100MB 파일 → 100MB. 이론상 **-57% 메모리**. multipart 는 streaming 처리도 가능 → 추가 절약 여지.

> 비고 — 사용자 의견 "llm_handler.call 에 간 후엔 제거하자" 는 (a) decoded bytes (`fi.data`) 부분으로 해석 가능 → #2 inline 경로 처리와 동일한 메커니즘 → **#2 안에서 함께 다룬다**. raw body 사본 자체는 multipart 전환이 필수.

### 3.5 #4 — stream `accumulated` 청크 누적

**현재**
[`_do_llm_stream`](../service/app/logic/runner.py#L532) 이 `async for` 로 받은 모든 `StreamChunk` 객체를 `list` 에 누적 → `_finalize_stream` 이 통째로 받아 `full_text` 조립 + 마지막 청크의 usage/finish_reason 추출.

**문제**
정작 필요한 건 텍스트 합본 + 마지막 청크 메타 + function_calls 뿐. 청크 객체 전체를 보관하는 건 낭비. 긴 응답 + function calling 폭주 시 수 MB 단위 누적 가능. 일반적으론 수십 KB 라 큰 부담은 아님.

**수정** (`20~30줄`)
텍스트는 `list[str]` 로만, 마지막 청크와 function_calls 만 따로 보관:
```python
text_parts: list[str] = []
last: StreamChunk | None = None
function_calls = None
async for chunk in aio_stream(**call_input):
    text_parts.append(chunk.text or "")
    last = chunk
    if chunk.function_calls is not None:
        function_calls = chunk.function_calls
    yield chunk
_finalize_stream_lite(prep, text_parts, last, function_calls, ...)
```
`_finalize_stream` 시그니처 변경.

**효과**
청크 수에 무관하게 일정 메모리. 보통은 차이가 작음(수십 KB), 긴 응답에서만 의미.

> 비고 — 사용자 우려 "다 모일 때까지 갖고 있어야 한다" 는 텍스트 합본 측면에선 맞다. 차이는 **청크 객체 전체 N개 vs 텍스트 list[str] + 마지막 객체 1개** — 의미상 동일한 정보를 더 가벼운 형태로 보관.

### 3.6 FAQ — 자주 헷갈리는 지점

#### Q1. #3 splitter cleanup 이 정상 흐름을 늦추지 않나?

정상 흐름엔 영향 없음. 추가되는 건 `created_temps.append(tmp.name)` 호출 N 번뿐 (마이크로초). cleanup 루프는 **예외 발생 시에만** 실행되며, 그때는 이미 raise 경로라 추가 시간(밀리초) 무관.

#### Q2. #4 stream — yield 와 누적이 동시에 어떻게 가능한가?

"stream 으로 사용자에게 yield" 와 "메모리에서 삭제" 는 별개 개념.

- (a) 청크는 yield 즉시 사용자(SSE) 에게 흘러감 — 사용자 측 처리는 우리와 무관.
- (b) 우리는 **MDB 저장용으로 전체 응답을 따로 모아둬야** 함 — finalize 시점에 필요.

차이는 **모아두는 형태**다.

| | 현재 | 제안 |
|---|------|------|
| 누적 컨테이너 | `list[StreamChunk]` (객체 N 개) | `list[str]` (텍스트 N 개) + 마지막 객체 1 개 |
| 메모리 | 객체×N | 문자열×N + 객체×1 |

→ 텍스트는 그대로 N 개 모임. 차이는 **청크 객체 자체** 를 들고 있느냐 여부. 정상 응답에선 차이 작아 후순위.

## 4. 파이프라인 — 현재 vs 개선 후

### 4.1 현재 (Files API 경로)

```
SDK → Server (요청 수신)
  ↓
prepare(..., files=files)              ← prep.files 매달림
  ↓
_build_server_call_input(prep)
  └─ resolve_files
       └─ _process_files_api
            ├─ _reuse_files_api_uris (cache HIT)
            │    └─ uri_parts/file_refs append
            │                                 ⚠️ fi.data 살아있음
            └─ _upload_and_cache_file (cache MISS)
                 ├─ tmp.write(fi.data)
                 ├─ upload_file(tmp.name)
                 ├─ os.unlink(tmp.name)
                 ├─ cache_store.save_files_api(...)
                 └─ uri_parts/file_refs append
                                            ⚠️ fi.data 살아있음
  ↓
aio_call(**call_input)                 ⏱️ LLM 응답 대기 (수~수십 초)
                                            ⚠️ fi.data 여전히 살아있음
  ↓
finalize(prep, llm_result)
  └─ _dump_files_meta(prep.files)      ← model_dump(exclude={"data"})
                                            ⚠️ fi.data 마지막까지 살아있다 함수 종료 시 GC
```

### 4.2 개선 후

```
SDK → Server (요청 수신)
  ↓
prepare(..., files=files)
  ↓
_build_server_call_input(prep)
  └─ resolve_files
       └─ _process_files_api
            ├─ _reuse_files_api_uris (cache HIT)
            │    ├─ uri_parts/file_refs append
            │    └─ fi.data = b""             ✅ 즉시 회수
            └─ _upload_and_cache_file (cache MISS)
                 ├─ tmp.write(fi.data)
                 ├─ upload_file(tmp.name)
                 ├─ os.unlink(tmp.name)
                 ├─ cache_store.save_files_api(...)
                 ├─ uri_parts/file_refs append
                 └─ fi.data = b""             ✅ 즉시 회수
  ↓
aio_call(**call_input)                 ⏱️ LLM 응답 대기
                                            ✅ fi.data 이미 비어있음 → 메모리 free
  ↓
finalize(prep, llm_result)
  └─ _dump_files_meta(prep.files)      ← exclude={"data"} 동작 그대로
```

**핵심 차이**: `aio_call` 진입 시점에 Files API 경로 파일의 `fi.data` 가 모두 비어있음 → LLM 응답 대기 시간(수~수십 초) 동안의 메모리 점유 제거.

## 6. 에러 처리 — 404 자동 복구 호환성

### 6.1 배경

`_do_llm_call` / `_do_llm_stream` 은 Gemini 404 (Files API URI 만료) 발생 시 [`resolve_files_after_404(prep.files, ...)`](../service/app/logic/file_processing/resolver.py#L440) 로 자동 재처리. 이 흐름은 **`prep.files` 의 `fi.data` 가 살아있다고 가정**한다.

#2 적용 후 `fi.data` 가 비워지면 404 복구 시 `tmp.write(b"")` → 빈 파일 업로드 → 또 raise.

### 6.2 옵션 비교

| 옵션 | 설명 | 장점 | 단점 |
|------|------|------|------|
| 가 | 비우기 전에 tmp path 를 prep 에 보관 → 404 시 path 에서 다시 read | 404 복구 완전 작동 | `_Prepared` 스키마 추가, 코드 복잡 |
| **나** | **비운 후 404 나면 그대로 raise** | **코드 단순, 자동 복구 폐지 (사용자 재시도)** | 404 복구 실패 → 사용자 재시도 필요 |
| 다 | Files API 경로 fi.data 안 비움 (현재 유지) | 404 복구 작동 | 메모리 절약 효과 없음 (Phase 1 의미 없음) |

### 6.3 채택 — 옵션 나

**근거**:
- [resolver.py:457](../service/app/logic/file_processing/resolver.py#L457) 코멘트: "정상 운영에선 Redis TTL(47h) < Gemini TTL(48h) 로 거의 발생 안 함"
- 404 발생 자체가 드물고, 발생 시 자동 복구 대신 진입 가드로 명확한 `FileUploadError` raise → 사용자가 새 요청으로 재시도
- 코드 변경 최소 (#2 의 fi.data 비우기 + `_upload_and_cache_file` 진입 가드)

### 6.4 영향 범위

- 정상 흐름: 영향 없음
- 404 발생 시: 진입 가드(`if not fi.data: raise FileUploadError`)로 즉시 raise — 자동 복구는 더 이상 시도하지 않음
- 사용자 측: 재시도 시 새 fi.data 로 요청 가능
