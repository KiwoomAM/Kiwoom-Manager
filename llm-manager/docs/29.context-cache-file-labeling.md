# 29. Context Cache 파일 라벨링 (다중 파일 구분자)

> 관련 문서: [07.inline-vs-files-api-strategy.md](07.inline-vs-files-api-strategy.md) §6,
> [25.pdf-split-shared-pool-and-unsplittable-reject.md](25.pdf-split-shared-pool-and-unsplittable-reject.md),

## 1. 배경 / 문제 정의

한 번의 `generateContent` 요청에는 **`cachedContent` 를 하나만** 참조할 수 있다
(Gemini 공식 제약). 그래서 llm-manager 는 같이 쓰는 Files API 파일들을 **하나의
Context Cache 로 묶는다** — `_process_files_api` 가 파일별 `FileRef` 를 평평한
`file_refs: list[FileRef]` 로 모아 `create_context_cache(file_refs, ...)` 로 넘긴다.

현재 캐시에 들어가는 콘텐츠는 **file part 의 단순 나열**이다. `_normalize_contents`
가 각 `FileRef` 를 `{"type":"file","file_uri":...,"mime_type":...}` 로 바꿔
`contents=[{"role":"user","content":[file1, file2, file3, ...]}]` 형태가 된다.

```
# 현재 — 캐시 안 콘텐츠 (라벨 없음)
[ file(uri1), file(uri2), file(uri3), file(uri4) ]
```

여기엔 두 가지 정보가 **누락**된다:

1. **문서 경계** — uri1~4 중 어디까지가 A 문서이고 어디부터 B 문서인지 표시가 없다.
   파일 이름(`file_name`)은 Redis 저장 doc 에만 있고 **캐시 콘텐츠엔 안 들어간다.**
2. **분할 사실** — PDF 가 50MB / 1000페이지 초과로 여러 파트로 쪼개져 업로드되면
   (docs/25) 한 문서가 여러 `FileRef` 가 된다. LLM 입장에선 이게 서로 다른 문서인지,
   한 문서가 이어지는 파트인지 구분할 근거가 없다.

**영향:** 여러 문서를 한 캐시에 넣고 "문서 A 의 매출은?", "B 와 C 를 비교" 같은
문서 지시형 질의를 할 때 LLM 이 어느 URI 가 어느 문서인지 안정적으로 구분하지 못한다.

### 범위 (scope) — 명시적 비목표

- **캐시 미스(non-cache) 경로는 제외.** too-small fail-soft(docs/21) 나
  `context_cache_ttl` 미지정으로 캐시를 skip 하면 파일은 `uri_parts` 로 인라인
  전송된다(runner `_apply_resolved`). 그 경로의 라벨링은 별도 작업으로 남긴다 —
  이번 변경은 **캐시 생성 콘텐츠에만** 라벨을 넣는다.
- **핸들러/HTTP/서버 스키마 변경 없음** (§2.1 참조).
- **캐시 키·dedup·too-small 게이트 로직 변경 없음** (§4).

## 2. 사전 정보

### 2.1 하부 배관은 이미 존재 (핵심)

핸들러 클라이언트의 콘텐츠 타입은 이미 텍스트+파일 혼합을 받는다:

```python
# handler_client/_common.py
ContentsType = str | list[str | FileRef | Part]

def _normalize_contents(contents):
    ...
    for item in contents:
        if isinstance(item, str):
            parts.append({"type": "text", "text": item})     # ← str 지원 이미 있음
        elif isinstance(item, FileRef):
            parts.append({"type": "file", "file_uri": item.uri, "mime_type": item.mime_type})
        ...
```

즉 **구분자 텍스트는 `str` 아이템으로 그냥 끼워넣으면 된다.** `build_cache_body` /
`_client.create_cache` / handler 서버 어느 쪽도 수정할 필요가 없다.

### 2.2 그룹 정보가 사라지는 지점

[`_process_files_api`](../llm_manager/_internal/file_processing/resolver.py) 의 파일 루프:

```python
for fi, checksum in zip(files_api_pool, checksums):
    parts, refs = await _resolve_one_files_api(fi, checksum, ...)  # refs = 이 파일 1개의 FileRef들
    uri_parts.extend(parts)
    file_refs.extend(refs)   # ← 여기서 파일별 그룹이 평평해짐 (정보 소실)
```

`_resolve_one_files_api` 는 **파일 1개** 단위로 `(parts, refs)` 를 돌려준다
(HIT 재사용/MISS 업로드 양쪽 동일). `len(refs) > 1` 이면 그 파일이 분할된 것이다.
그룹 정보는 바로 이 루프에 있으며, `file_refs.extend()` 로 버려질 뿐이다.

### 2.3 캐시 생성 호출 사슬

```
_process_files_api
  → _resolve_or_create_context_cache(hash_key, checksums, file_refs, ...)
     → _create_and_save_context_cache(hash_key, checksums, file_refs, ...)
        → create_context_cache(file_refs, ...)          # uploader.py
           → handler create_cache(contents=file_refs)   # 이미 ContentsType
```

`file_refs` 는 캐시 생성 외에 **Redis `files_api_uris` 필드**
(`[r.uri for r in file_refs]`) 에도 쓰인다 — 이 용도는 유지해야 한다.

## 3. 설계

### 3.1 라벨 정책 — 파일 단위 (URI 단위 아님)

분할은 **의미 단위가 아니라 50MB/1000p 한도 때문의 기계적 분할**이다. 한 문서의
연속 파트 사이에 라벨을 꽂으면(예: `--- 파트 2/3 ---`) 경계에 걸친 표·문장의
연속성을 오히려 끊는다. 따라서:

- **문서(파일)마다 헤더 1개**를 붙이고, 그 아래 `FileRef` 들을 **라벨 없이 연속** 배치.
- 분할 파일은 헤더에 **"총 N개 파트로 분할됨"** 메타만 표기 — 파트 사이엔 넣지 않는다.
- 문서 경계는 다음 파일 헤더가 표시하므로 파트별 번호는 불필요(중복).

```
# 목표 — 캐시 안 콘텐츠 (파일 3개, 문서1이 3파트 분할)
[
  "===== [문서 1] 2024_사업보고서.pdf (총 3개 파트로 분할 업로드됨) =====",
  file(uri1), file(uri2), file(uri3),
  "===== [문서 2] 재무제표.csv =====",
  file(uri4),
  "===== [문서 3] 감사의견.pdf =====",
  file(uri5),
]
```

> 대안(URI 단위 라벨: 파트마다 `--- 파트 k/n ---`)은 **채택 안 함.** 문서 경계
> 구분은 동일하게 되지만 분할 파트 연속성을 해치고 노이즈만 늘린다.

> ⚠️ **헤더의 `file_name`은 다운스트림 소비자 계약이다(빼지 말 것).** 이 라벨은
> llm-manager 내부의 "파일 구분"만을 위한 게 아니다. 파일명 기반 출처 귀속 소비자
> (예: ESG 다중 보고서 평가)가 **프롬프트로 "근거가 어느 파일인지 답하라"** 지시하고
> **모델이 헤더의 파일명을 읽어 출력**하면, 소비자가 그 파일명을 자기 파일 목록과 매칭한다.
> 즉 모델이 파일명을 알 수 있는 **유일한 출처가 이 헤더**다(§29 개념: 파일명은 모델
> content에 달리 노출되지 않음). 따라서 헤더를 "인덱스만"으로 단순화해 `file_name`을
> 떼면 그런 소비자가 깨진다. `[문서 N]` 인덱스는 부가정보라 바꿔도 무방하나 **파일명은 유지.**

### 3.2 그룹 보존 (`_process_files_api`)

루프에서 파일별 그룹을 함께 수집한다. `file_refs` 는 기존 용도(Redis uris)로 유지.

```python
uri_parts: list[Part] = []
file_refs: list[FileRef] = []                        # Redis files_api_uris용 (유지)
groups: list[tuple[FileInput, list[FileRef]]] = []   # ← 추가: 파일별 그룹

for fi, checksum in zip(files_api_pool, checksums):
    parts, refs = await _resolve_one_files_api(fi, checksum, standby_ttl_seconds=...)
    uri_parts.extend(parts)
    file_refs.extend(refs)
    groups.append((fi, refs))                         # ← 추가 한 줄
```

### 3.3 라벨 빌더 (신규 헬퍼)

```python
def _build_labeled_cache_contents(
    groups: list[tuple[FileInput, list[FileRef]]],
) -> list[str | FileRef]:
    """파일별 구분자 헤더 + FileRef 를 섞은 cache contents 를 구성한다.

    분할 파일(len(refs)>1)은 한 헤더 아래 파트들을 라벨 없이 연속 배치해
    '한 문서가 용량 때문에 쪼개진 것'임을 LLM 이 인지하되 연속성은 유지한다(§3.1).

    주의(라벨을 출처 귀속에 쓰는 소비자용 — §3.6):
    1. 라벨은 **context cache 콘텐츠에만** 붙는다. classify_files 는 '부분 섞기'라
       작은 파일이 inline 으로 빠지면 라벨이 없다. too-small/TTL 미지정으로 캐시를
       skip 하면 uri_parts 인라인이라 역시 라벨 없음. → 파일명 기반 출처 귀속 소비자는
       'files-api + 캐시 경로'가 전제다(docs/30 의 ttl-on 전원 승급으로 이 전제 강화).
    2. 분할 파일: 헤더 + '총 N파트'로 '한 문서'임은 전달되나, 각 파트는 새 PDF 로
       저장돼 페이지가 1 부터 재시작한다(원문 오프셋 미적용). 파트2 의 'p.100' 은
       절대페이지가 아니다. 절대페이지가 필요한 소비자는 스스로 보정 불가(분할은
       llm-manager 내부 사실).
    """
    contents: list[str | FileRef] = []
    for idx, (fi, refs) in enumerate(groups, start=1):
        n = len(refs)
        header = f"===== [문서 {idx}] {fi.file_name}"
        if n > 1:
            header += f" (총 {n}개 파트로 분할 업로드됨)"
        header += " ====="
        contents.append(header)
        contents.extend(refs)   # 파트 사이 라벨 없이 연속
    return contents
```

### 3.4 생성 호출부 (contents 주입)

`_create_and_save_context_cache` / `_resolve_or_create_context_cache` 에
`cache_contents: list[str | FileRef]` 인자를 추가해 통과시킨다. 캐시 생성은
`cache_contents` 로 하되, Redis `files_api_uris` 는 그대로 `file_refs` 로 계산.

```python
# _create_and_save_context_cache
cache_ref = await create_context_cache(
    cache_contents,          # 기존: file_refs
    model=model, system_instruction=system_instruction,
    ttl=ttl, tools=tools, tool_config=tool_config,
)
...
"files_api_uris": [r.uri for r in file_refs],   # ← file_refs 로 유지 (변경 없음)
```

호출 지점(선점 경로 / timeout 경로 양쪽)에서:

```python
cache_contents = _build_labeled_cache_contents(groups)
cached_content = await _resolve_or_create_context_cache(
    hash_key, checksums, file_refs, cache_contents,   # ← cache_contents 추가
    model=model, ...,
)
```

**실제 `cache_contents` 예시 (파일 2개, 문서1이 2파트 분할):**

```python
groups = [
    (FileInput(file_name="2024_사업보고서.pdf", ...),
     [FileRef(name="files/a1", uri="gs://.../a1", mime_type="application/pdf"),
      FileRef(name="files/a2", uri="gs://.../a2", mime_type="application/pdf")]),
    (FileInput(file_name="감사의견.pdf", ...),
     [FileRef(name="files/b1", uri="gs://.../b1", mime_type="application/pdf")]),
]

# _build_labeled_cache_contents(groups) → create_context_cache 로 넘어가는 list[str | FileRef]
cache_contents = [
    "===== [문서 1] 2024_사업보고서.pdf (총 2개 파트로 분할 업로드됨) =====",
    FileRef(uri="gs://.../a1", mime_type="application/pdf"),
    FileRef(uri="gs://.../a2", mime_type="application/pdf"),
    "===== [문서 2] 감사의견.pdf =====",
    FileRef(uri="gs://.../b1", mime_type="application/pdf"),
]
```

`create_context_cache → _aio_create_cache → 핸들러 _normalize_contents` 가 이걸 변환해
**캐시에 실제 저장되는 parts** (str → text part, FileRef → file part):

```python
[
    {"type": "text", "text": "===== [문서 1] 2024_사업보고서.pdf (총 2개 파트로 분할 업로드됨) ====="},
    {"type": "file", "file_uri": "gs://.../a1", "mime_type": "application/pdf"},
    {"type": "file", "file_uri": "gs://.../a2", "mime_type": "application/pdf"},
    {"type": "text", "text": "===== [문서 2] 감사의견.pdf ====="},
    {"type": "file", "file_uri": "gs://.../b1", "mime_type": "application/pdf"},
]
```

즉 헤더 텍스트가 각 파일 앞에 하나씩, 분할 파트는 한 헤더 아래 연속으로 캐시에 얹힌다.

### 3.5 uploader 시그니처 확장

```python
# uploader.py
async def create_context_cache(
    contents: list[str | FileRef],   # 기존: file_refs: list[FileRef]
    *, model, system_instruction=None, ttl=3600, tools=None, tool_config=None,
) -> CacheRef:
    ...
    return await _aio_create_cache(contents, model=model, ...)   # 내부 로직 무변경
```

이미 `ContentsType` 가 혼합을 받으므로 재시도 래퍼·전달 로직은 그대로다.

### 3.6 분할 파일의 페이지 — 실측 결과: 오프셋 이번엔 보류

원리상 라벨링은 분할 파일의 **문서 구분**은 해결하지만 **물리 페이지 번호**는 못 고친다: splitter 는
PyMuPDF `select`→`save` 로 각 파트를 **새 PDF** 로 저장하므로 파트2 는 1쪽부터 다시 세는 별도 문서다.

**실측(실제 GS건설 통합보고서 · Pro `gemini-3.1-pro-preview`)**: 보고서를 물리 반으로 분할해
헤더 라벨만(오프셋 없는 A 표현) 캐시에 올리고 part2 쪽 본문의 출처를 물었더니 **정답 8/8(100%)**
— part2 끝쪽(분할 경계에서 20쪽 떨어진 p40)까지. 이유 = 실제 ESG 보고서엔 **인쇄 쪽번호가 페이지에
박혀 있어 분할해도 살아남고**, 모델이 그걸 읽는다. 즉 **실무상 오프셋 보정 없이도 출처가 맞는다.**

- **오프셋(splitter 반환값 변경·절대페이지 보정)은 이번 라벨링에서 하지 않는다(보류).** 실제 보고서
  인쇄 쪽번호가 분할 문제를 흡수하므로 현재 불필요 — 라벨 헤더/조립만 구현(SURGICAL).
- **재검토 트리거**: 인쇄 쪽번호가 **없는** 보고서에서 분할 경계 너머 출처가 실제로 틀리는 게 관찰되면
  그때 착수. (소비자(ESG) 프롬프트가 "인쇄 쪽번호 vs 첨부 파일의 문서 페이지" 중 무엇을 요구하는지도 함께 관찰.)
- **정식 해법(착수 시)**: 모델 산수 금지(병합 문제 재발) → 파트별 마커로 `(파트, 로컬페이지)` 출력 +
  코드가 `시작페이지+로컬-1` 계산. §3.1 "파트 사이 라벨 없음"을 뒤집는 트레이드(경계 연속성 vs 해석성).

## 4. 불변식 — 영향 없음 확인

| 항목 | 영향 | 근거 |
|---|---|---|
| 캐시 키 / dedup | 없음 | `make_context_cache_key` 는 checksum·model·system·tools·tool_config 로만 계산. 라벨은 키 재료 아님 → 동일 입력 = 동일 hash_key = dedup 그대로 |
| too-small 게이트 | 없음(무시 가능) | `_estimate_cache_tokens` 는 파일 기준 추정. 라벨 몇 토큰은 실제값을 추정보다 크게만 만들어 min(1024) 판정에 안전 방향 |
| cache HIT 재사용 | 정상 동작 | `_resolve_one_files_api` 가 HIT/MISS 양쪽에서 refs 반환 → groups 두 경로 다 채워짐. `fi.file_name` 은 FileInput 에 상존 |
| Redis 저장 doc | 없음 | `files_api_uris` 는 `file_refs` 로 계산(유지). 라벨은 캐시 콘텐츠에만 존재, Redis 미저장 |
| 핸들러/서버 | 없음 | `str` 콘텐츠 이미 지원 (§2.1) |
| 분할 파일 절대페이지 | **라벨링 범위 밖(기존 한계)** | 파트는 1쪽부터 재시작하는 새 PDF — 라벨은 문서 구분만, 페이지 오프셋 미보정 (§3.6) |
| 파일명 헤더 형식 | **다운스트림 계약** | 소비자가 헤더 `file_name`을 매칭에 사용 → 형식 변경 시 소비자 영향 (§3.1) |

## 6. 테스트

`tests/_internal/file_processing/` (기존 resolver 테스트 위치 따름).

- **라벨 빌더 단위** (`_build_labeled_cache_contents`):
  - 단일 파일(refs 1개) → `["===== [문서 1] a.pdf =====", FileRef]`.
  - 분할 파일(refs 3개) → 헤더에 `(총 3개 파트로 분할 업로드됨)` 포함, 파트 사이 라벨 없음.
  - 다중 파일 → 문서 인덱스 1,2,3 순차 + 각 헤더 뒤 해당 refs 만.
- **그룹 보존**: `_process_files_api` 가 파일 2개(하나는 분할)일 때 `create_context_cache`
  에 넘어간 contents 가 `[헤더, refs..., 헤더, refs...]` 순서인지 (mock 으로 인자 캡처).
- **불변식 회귀**:
  - `hash_key` 가 라벨 유무와 무관하게 동일 (dedup 회귀 방지).
  - Redis `files_api_uris` 가 여전히 순수 uri 리스트 (라벨 문자열 미포함).
- **HIT 재사용 경로**: files_api HIT(reuse) 파일도 groups 에 들어가 헤더가 붙는지.
