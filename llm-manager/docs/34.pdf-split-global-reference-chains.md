# 34. PDF split — 문서 전역 참조 사슬(구조트리·주석 동작) 차단

> 상태: **구현 완료 (TDD)** — 전체 스위트 531 passed, 실물 8개 재검증 완료(§8-1).
> 남은 것: 소비처(Kiwoom-ESG) BNK 업로드 재현.
> 변경: `splitter.py`(`_target_bytes`·`_needs_split`·`_annot_xrefs`·`_strip_chains_copy` 신설,
> `split_pdf` 재구성, 임시 파일 회수 수정), `tests/_internal/test_splitter.py`(신규 7·개정 2),
> [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §6-3에 반증 표시.
> 독립 리뷰 3렌즈(grounding·consistency·adversarial) 반영 완료 — 사실·인용 오류 14건은 본문에,
> 설계 판단 7건은 §10에 처리 기록.
> 범위: `llm-manager`(SDK)의 `_internal/file_processing/splitter.py`.
> 선행 문서: [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) — 공유 객체 풀·분할불가 거부, 주석 사슬 1차 대응.
> 측정 환경: PyMuPDF 1.27.2.2 / MuPDF 1.27.2, Python 3.12.

## §1. 배경 / 문제 정의

`splitter.split_pdf`가 **2025 BNK금융그룹 지속가능경영보고서(84.1MB·196p)** 를 분할하지 못하고
`PdfPageTooLargeError`로 거부한다. [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §6에서
도입한 주석 제거 재시도(`_strip_annots_copy`)를 태워도 결과가 같다.

증상 로그 — 페이지를 반씩 줄여도 크기가 꿈쩍하지 않는다.

```
분할: p.1-61 (87.2MB) → 이등분
분할: p.1-30 (86.8MB) → 이등분
분할: p.1-15 (86.7MB) → 이등분
분할: p.1-7  (86.7MB) → 이등분
분할: p.1-3  (86.7MB) → 이등분
분할: p.1-1  (86.7MB) → 분할 불가
단일 페이지 한도 초과 — 주석 제거 후 재분할 시도
분할: p.1-1 (85.5MB) → PdfPageTooLargeError(p.1, 85.5MB)
```

원인은 주석이 아니었다. **문서 카탈로그의 구조트리(`/StructTreeRoot`)** 가 전 페이지를 붙잡고
있어서, 페이지를 아무리 줄여도 `select()`가 문서 전체를 끌고 온다(§2-2).

[25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §6은 `select()`를 무력화하는 사슬로
**주석**을 지목하고 그것만 끊었다. 실측 결과 이 계열의 사슬은 **최소 두 종류**이고 진입점이
서로 반대다(§2-3).

```
현대글로비스 — 페이지가 옆 페이지를 붙잡는다 (아래에서 위로)
   page 3 ──/Annots──▶ Widget ──/AA──▶ GoTo ──▶ page 57 ──▶ 그 페이지의 이미지

BNK — 문서 루트가 전 페이지를 붙잡는다 (위에서 아래로)
   Root ──/StructTreeRoot──▶ StructElem ──/Pg──▶ page 1 … page 196 (195개)
```

주석 사슬은 페이지 쪽을 청소하면 끊기지만, 구조트리는 페이지를 아무리 청소해도 끊기지 않는다.
반대편 끝인 카탈로그가 계속 붙잡고 있기 때문이다.

부수적으로, 기존 주석 제거 처방이 **원본에 없던 손실을 만들고 있다는 사실**도 이번 측정에서
드러났다(§2-5). 이 문서는 두 문제를 함께 다룬다.

## §2. 측정 / 진단

재현 파일은 `bug_report/버그확인파일/`의 실물 보고서들이며, 측정 스크립트는 부록에 둔다.

### §2-1. 재현 — 무엇이 실패하는가

| 파일 | 크기 | 페이지 | xref 길이 | 생성기 | 현재 결과 |
|---|---|---|---|---|---|
| BNK금융그룹 | 84.1MB | 196p | 67,431 | Adobe InDesign 21.4 (Macintosh) | ❌ `PdfPageTooLargeError` (4.5초) |
| 현대글로비스 | 96.6MB | 153p | 6,142 | — | ✅ 3파트 (주석 제거 재시도로) |
| GS건설 | 88.4MB | 133p | — | — | ✅ 2파트 |
| 기업은행 | 64.2MB | 172p | — | — | ✅ 2파트 |
| 파라다이스 | 69.0MB | 97p | — | — | ✅ 2파트 |

50MB를 넘는 파일 5개 중 실패는 BNK 하나뿐이며, **이 코퍼스에서는 추가 실패 모드가 관찰되지
않았다.** (부재 증명은 아니다 — 표본은 코퍼스 19개, 그중 50MB 초과 5개뿐이다. 특히
[25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §2의 원인 파일인 공유 객체 풀 병리
PDF는 이 목록에 없다.)

### §2-2. 근본 원인 — `/StructTreeRoot`

BNK는 InDesign이 태그드 PDF(`/MarkInfo <</Marked true>>`)로 내보낸 파일이다.
구조트리 노드가 `/Pg`로 **196페이지 중 195페이지**를 직접 지목한다.

p.1 한 장만 `select()`해서 저장한 크기:

| 처리 | p.1 크기 |
|---|---|
| 원본 그대로 | 86.74MB |
| 주석 제거만 (현행 처방) | 85.48MB ← 1.26MB만 감소 |
| **`/StructTreeRoot` 제거만** | **0.27MB** ← 원본 대비 321배 감소 |
| 둘 다 제거 | 0.27MB |

`/StructTreeRoot`만 떼고 주석은 그대로 둔 채 분할하면 **2파트(48.7MB/64p + 33.3MB/132p),
196페이지 전부 보존**으로 성공한다.

### §2-3. 두 사슬은 서로 배타적이다

| | 현대글로비스 96.6MB/153p | BNK 84.1MB/196p |
|---|---|---|
| `/StructTreeRoot` | **없음** | 있음 (195/196 페이지 참조) |
| 문제 페이지 원본 | p.3 = 97.11MB | p.1 = 86.74MB |
| 주석 제거 후 | **0.24MB ✅** | 85.48MB ❌ |
| 구조트리 제거 후 | (해당 없음) | **0.27MB ✅** |

이 두 파일은 각각 한 가지 병만 앓았다(병이 겹치지 않는다는 일반 법칙은 아니다 — §3-1의 처방이
세 곳을 동시에 조작하는 것은 겹칠 수 있다는 전제 위에 있다). BNK도 주석은 있지만
(`_has_annots` = True) 그 사슬이 붙잡는 것은 1.26MB뿐이라, 현행 재시도는 한 바퀴를 헛돌고
같은 예외로 끝난다.

### §2-4. `select()`가 실제로 살려두는 것 — 닫힌 목록

위험 목록을 추측으로 늘리지 않기 위해, `select([0])` 이후 카탈로그에 무엇이 남는지 직접 확인했다.

```
select 전 (BNK) : AcroForm, Lang, MarkInfo, Metadata, Names, Outlines, Pages,
                  StructTreeRoot, Type, ViewerPreferences
select 후       : Names, Pages, StructTreeRoot, Type
```

세 파일(BNK·현대글로비스·포스코) 모두 생존 키가 같았다. **관찰한 이 세 파일에서는
`Type`·`Pages`·`Names`·`StructTreeRoot` 넷만 남았고, 그 밖의 카탈로그 기능은 mupdf가 버렸다.**
(mupdf 소스로 확인한 것이 아니라 표본 3개·mupdf 1버전에서 얻은 귀납이다. §3-2의 화이트리스트는
이 귀납이 틀려도 사슬 차단에는 영향이 없지만, "지워도 잃는 게 없다"는 무해성 주장은 여기에
기댄다.)

| 생존 키 | 페이지를 붙잡나 | 판정 |
|---|---|---|
| `/Type`, `/Pages` | 페이지 트리 자체, mupdf가 재작성 | 안전 |
| `/Names` | 키는 남지만 **내용은 가지치기됨** | 안전 |
| `/StructTreeRoot` | **가지치기 안 함 — `/Pg` 195개 그대로 생존** | 🔴 위험 |

`/Names`가 안전한 근거: 참조 그래프상 `/Names`는 BNK에서 47페이지·56.6MB에 도달하지만,
`/StructTreeRoot`만 제거하면 `/Names`가 남아 있는데도 결과가 0.27MB다. 결과물의 `/Pg` 참조
개수도 BNK는 195개인 반면 현대글로비스·포스코는 0개였다.

**함정 — "그래프상 사슬"과 "실제 사슬"은 다르다.** 참조 그래프만 그리면 `/AcroForm`이 가장
위험해 보인다(BNK 194/196p·81.5MB, 현대글로비스 150/153p·96.0MB, 포스코 166/168p·19.0MB).
폼 필드가 위젯을 가리키고 위젯이 `/P`로 자기 페이지를 지목하니 이론상 전역 사슬이 맞지만,
mupdf가 `/AcroForm`을 버려서 실현되지 않는다. **판단 기준은 "이 키가 페이지를 참조하는가"가
아니라 "select 후에도 살아남는가"여야 한다.**

### §2-5. 기존 주석 제거 처방의 부작용 — 손실이 실재한다

`_strip_annots_copy`는 사슬을 끊지만 **원본에 없던 손실**을 만든다. 공백을 제외한 글자 수 기준:

| 파일 | 현 상태 | 카탈로그 비우기 | 주석 통째 제거 (현행) |
|---|---|---|---|
| BNK | 실패 중 | ±0자 | ±0자 |
| 현대글로비스 | 주석 제거 대상 | ±0자 | **−491자 (0.32%)** |
| GS건설 | **정상** | ±0자 | **−388자 (0.22%)** |
| 기업은행 | 정상 | ±0자 | ±0자 |
| 파라다이스 | 정상 | ±0자 | ±0자 |

사라지는 글자의 정체를 추적했다. 현대글로비스 p.4에는 주석이 13개 있고, 사라진 문자열
("CEO Message", "Company Overview")은 **페이지 콘텐츠 스트림에 존재하지 않는다.**

```
p.4 콘텐츠 스트림에 'CEO' 존재     = False
p.4 콘텐츠 스트림에 'Message' 존재 = False
p.4 콘텐츠 스트림에 'Company' 존재 = False
```

그 글자는 **위젯 주석 자신의 외관 스트림(`/AP`)** 안에 그려져 있는 것으로 보인다 — 콘텐츠
스트림에 없고(위), 주석을 남긴 채 동작만 끊으면 글자가 그대로 남는다(§2-6)는 두 관찰에서
나온 추론이며, `/AP` 객체를 열어 텍스트 연산자를 직접 확인하지는 않았다. InDesign이 만든
인터랙티브 네비게이션 버튼이라 버튼 그림과 라벨이 주석에 딸려 있는 형태로 추정된다.
주석을 통째로 지우면 외관도 함께 사라진다.

렌더링 픽셀로도 확인했다(표본 12페이지, dpi=50).

| 파일 | 주석 통째 제거 (현행) |
|---|---|
| 현대글로비스 | **1/12만 동일** — 11페이지가 시각적으로 달라짐 |
| GS건설 | 11/12 동일 |
| BNK | 12/12 동일 |

즉 현행 처방은 **로컬 렌더(PyMuPDF) 기준으로 페이지 그림을 이미 바꾸고 있다.** Gemini가 PDF를
렌더할 때 주석 외관(`/AP`)을 합성해 보는지는 이 측정으로 알 수 없다 — 그건 미검증이다.
차이의 *크기*도 재지 않았다(달라진 페이지 수만 셌다).

### §2-6. 무손실 처방 — 주석은 남기고 '동작'만 끊는다

코퍼스 7개 파일에서는 사슬이 주석의 `/A`·`/AA`·`/Dest`(동작·목적지)에만 있었고, `/AP`(외관)를
남겨도 페이지가 딸려오지 않았다. 따라서 주석 객체를 남긴 채 동작 키만 비우면 사슬이 끊긴다.

**단, 이것은 명세적 보장이 아니라 표본 관찰이며, 반례가 실재한다.** `/AP`는 Form XObject라 자기
`/Resources`로 임의 객체를 참조할 수 있다. 그것이 문서 공용 풀이면
[25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §2-3의 공유 풀 병과 같은 형태가 되어,
페이지를 참조하지 않고도 바이트가 딸려온다.

**합성 PDF로 확인했다**(테스트 `test_shared_pool_via_appearance_stream`). 모든 페이지의 위젯
`/AP`가 같은 무거운 Form XObject를 참조하게 만들면 단일 페이지가 문서 전체 크기가 되고,
**동작 키만 끊는 1단계로는 끊기지 않는다.** 2단계(주석 통째 제거)에서야 해결된다.
즉 `/AP` 존치의 안전성은 코퍼스 7개 파일에 대해서만 성립하며, §3-3의 안전망은 죽은 경로가
아니라 **실제로 필요한 경로**다.

```
주석 객체
 ├─ /AA · /A · /Dest  → GoTo → 다른 페이지   ← 이것만 null 로
 └─ /AP               → 버튼 그림 + 라벨 글자  ← 보존
```

| 처방 | 현대글로비스 p.3 select | 공백 제외 글자수 |
|---|---|---|
| 원본 | 97.11MB | 155,744 |
| 카탈로그만 비우기 | 97.11MB (사슬 생존) | ±0 |
| **카탈로그 + 주석 동작만 끊기** | **0.25MB** | **±0** |
| 카탈로그 + 주석 통째 제거 (현행) | 0.24MB | −491 |

사슬 차단 효과는 사실상 동일한데(0.25 vs 0.24MB) 손실이 없다.

**전수 검증** — 7개 파일 모두 분할 성공, 페이지 보존, 글자 손실 0. **렌더링 픽셀은 7개 전부가
아니라 3개 파일(현대글로비스·BNK·GS건설)에서만 확인했고, 그 3개는 표본 12페이지가 모두
동일했다.** 나머지 4개는 글자 수만 비교했다.

| 파일 | 결과 | 페이지 | 글자 증감 |
|---|---|---|---|
| BNK 84.1MB/196p | 2파트 ✅ | 196/196 | ±0 |
| 현대글로비스 96.6MB/153p | 3파트 ✅ | 153/153 | ±0 |
| GS건설 88.4MB/133p | 2파트 ✅ | 133/133 | ±0 |
| 기업은행 64.2MB/172p | 2파트 ✅ | 172/172 | ±0 |
| 파라다이스 69.0MB/97p | 2파트 ✅ | 97/97 | ±0 |
| SK텔레콤 39.3MB/235p | 1파트 ✅ | 235/235 | ±0 |
| 포스코 20.4MB/168p | 1파트 ✅ | 168/168 | ±0 |

> **각주 — 카탈로그 정리가 텍스트 추출값을 바꾸는 경우가 있다(내용 손실은 아니다).**
> 구현 후 [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §2의 원인 파일(52.9MB·236p)로
> 재검증하다 발견했다. 그 파일 p.114에서 `/StructTreeRoot` 를 떼면 PyMuPDF `get_text()` 글자
> 수가 25자 줄어든다(문서 전체 227,420자의 0.011%). 주석과 무관하다 — 그 페이지 주석은 0개이고,
> 조작을 분리해보면 구조트리 제거만으로 재현된다.
>
> **그러나 같은 페이지의 렌더링 픽셀은 완전히 동일하다**(dpi 150). 글리프는 그대로 그려지며,
> PyMuPDF 가 그 25자를 세지 않을 뿐이다. §2-10 의 Gemini A/B 에서 구조트리 제거가 판정·근거
> 페이지에 영향을 주지 않은 것과 같은 방향의 결과다. 대조적으로 주석 통째 제거는 같은 방식으로
> 재보면 **픽셀이 달라진다**(§2-5). 이것이 §3-1 이 "무손실"의 기준을 추출값이 아니라 렌더링으로
> 잡는 이유다. (한계 — 픽셀 비교는 문제된 페이지 한 장을 dpi 150 에서 본 것이라, 그 해상도에서
> 안 잡히는 차이는 배제하지 못한다.)

### §2-7. 비용 — 진단해도 아낄 것이 없다

진단(무엇을 떼야 하는지 먼저 따져보기)이 제거보다 **싸긴 하다.** 그런데 진단이 "있다"고 답하면
어차피 떼야 하므로 절약되는 것이 없고, 카탈로그는 통째로 비우는 비용이 구조트리 하나를 골라
떼는 것과 사실상 같다.

| 대상 | 진단 비용 | 제거 비용 |
|---|---|---|
| 구조트리 유무 | 0.02~0.04ms | **0.28ms** (키 1개) |
| 카탈로그 전체 비우기 | — | **0.15~0.28ms** (선별 제거와 같은 수준) |
| 주석 (`_has_annots`) | 3.5~26.1ms | 32~77ms (전 페이지 루프) |

정확한 진단("이 사슬이 실제로 무는가")은 `select()`를 해보는 것뿐이고, 그게 §2-1의 실패 경로
(BNK 4.45초)다 — 싼 진단은 부정확하고(§2-4의 `/AcroForm` 사례) 정확한 진단은 비싸다.

무손실 처방 전체(카탈로그 비우기 + 주석 동작 끊기)의 실측 비용:

| 파일 | 떼기 | 사본 저장 | 분할 총시간 | 현재 |
|---|---|---|---|---|
| BNK 84.1MB | 165ms | 262ms | **0.83초** | 4.45초 ❌ |
| 현대글로비스 96.6MB | 111ms | 127ms | **0.55초** | 1.29초 |
| GS건설 88.4MB | 172ms | 93ms | 0.50초 | 0.28초 |
| 기업은행 64.2MB | 214ms | 92ms | 0.65초 | 0.51초 |
| 파라다이스 69.0MB | 175ms | 101ms | 0.54초 | 0.28초 |
| **합계** | | | **3.07초 · 전건 성공** | **6.81초 · 1건 실패** |

실패 경로가 비싼 이유는 87MB 파일을 이등분하며 여섯 번 저장하고, 주석 제거 후 그것을 한 번 더
반복하기 때문이다. 선제로 끊으면 그 헛수고가 통째로 사라진다.

### §2-8. 코퍼스 현황 — 얼마나 흔한가

보유 PDF 19개 전수 조사.

- **태그드(`/StructTreeRoot`) 3개**: BNK 84.1MB/196p(실패 중), SK텔레콤 39.3MB/235p, 한국항공우주 16.7MB/65p
  - 뒤의 둘은 50MB 이하라 분할이 걸리지 않는다 — **잠복 상태**
- 50MB 초과 5개 (§2-1)
- 아직 겪지 않은 사슬 후보: 페이지 `/AA` **0건**, `/B` 아티클 비드 **0건**,
  `/Threads`·`/DPartRoot`·`/AF`·`/Collection` **0건**, `/OCProperties` 1건(POSCO factbook)
  - 실물이 없어 mupdf가 이들을 살려두는지 **미검증**
- 순수 군살(사슬 아님): `/Thumb`·`/PieceInfo` — 참조 그래프 조사에서 페이지를 붙잡지 않는 것으로
  나왔다. 바이트 규모는 따로 기록하지 않았다.

덤으로 발견한 것 — 한국항공우주 파일은 열 때 xref 오류가, BNK는 렌더링 시
`No common ancestor in structure tree` 경고가 mupdf 로그로 나온다. 둘 다 원본 자체의 문제이며
이번 처리와 무관하다. **다만 "무관하다"의 근거는 두 파일이 현재 임계 아래라는 것뿐이다** —
같은 손상을 가진 50MB 초과 파일이 오면 이 처방이 어떻게 동작하는지는 미검증이다(§9 범위 밖 참고).

### §2-9. 기각한 대안 — `insert_pdf`

`select()` 대신 `insert_pdf()`로 파트를 만드는 방법도 측정했다. BNK p.1은 0.26MB로 잘 되지만,
**현대글로비스 p.3·p.101과 정상 파일인 포스코 p.3·p.101에서 `FzErrorLimit: exception stack
overflow`로 죽는다**(위젯 graft 경로 `_do_widgets` → `pdf_graft_mapped_object`).
지금 정상 동작하는 파일을 깨뜨리므로 채택하지 않는다.

### §2-10. 소비처(Gemini) 수준 검증 — 구조트리를 떼면 분석이 달라지는가

§2-5·§2-6의 "무손실"은 `get_text()`·`get_pixmap()`으로 잰 것인데, **둘 다 PyMuPDF이고 PyMuPDF는
`/StructTreeRoot`를 읽지 않는다.** 즉 그 측정은 구조트리 제거에 대해 원리적으로 아무 정보도 주지
못한다(독립 리뷰 지적). 실제 소비자는 Gemini이므로 소비처 수준에서 다시 쟀다.

**설계** — SK텔레콤 지속가능경영보고서(39.3MB·235p, 태그드, 코퍼스에서 유일하게 태그드이면서
현재 정상 처리되는 파일)를 두 벌로 만들었다. **A**는 원본(`/StructTreeRoot 7620 0 R`, `/Pg` 참조
235개), **B**는 구조트리만 `null`로 만든 사본(`/Pg` 참조 0개). 페이지 235p·공백 제외 314,174자로
동일하고 파일명도 같게 맞춰 프롬프트 차이를 없앴다. 프롬프트·모델은 실제 ESG 평가 경로 그대로다
(`SYSTEM_PROMPT` + `build_single_prompt`, DP 프롬프트는 MongoDB `agent_data`,
`gemini-3.1-pro-preview`, thinking=medium, `DPEvidence` 스키마, context cache TTL 1800).
DP 8개는 기후 거버넌스 2개 + 감축목표 4개 + 대기오염 2개로, **표에서 근거를 찾아야 하는 것**을
골랐다.

**대조군이 핵심이다.** A를 캐시 우회로 한 번 더 돌린 A2를 두어, A-B 차이가 구조트리 탓인지 LLM
자체 변동인지 가른다.

| 지표 | A vs B (구조트리 제거) | A vs A2 (같은 파일 재실행) |
|---|---|---|
| Y/N 판정 일치 | **8/8** | **8/8** |
| 근거 페이지 일치 | **7/8** | **7/8** |
| 근거 문장 겹침(Jaccard 평균) | **0.47** | **0.52** |

**결론 — 구조트리 제거의 영향이 LLM 자체 변동과 구분되지 않는다.** 어긋난 DP가 서로 다른 것이
결정적이다. A-B는 A0000006에서, A-A2는 A0000004에서 갈렸다. 구조트리 탓이라면 같은 자리가
흔들려야 한다. 문장 단위로는 **같은 파일을 두 번 돌린 A-A2의 겹침이 0.00인 DP도 있었다**
(A0000002). A-B에서 관찰된 "공통 문장 0건"(A0000007)은 구조트리와 무관한 현상이다.
A-B에서 유일하게 갈린 페이지도 B가 근거를 하나 **더** 찾은 경우라 품질 저하가 아니다.

**한계** — 파일 1개·DP 8개·각 1회 표본이고 판정이 Y 6 / N 2로 쏠려 있어, 판정이 뒤집히는 것을
잡아낼 검정력은 낮다. 다단 조판·복잡한 표를 표적으로 고르지도 않았다. 따라서 결론은 "Gemini가
태그를 쓰지 않는다"가 아니라 **"이 조건에서 차이가 노이즈와 구분되지 않는다"** 까지다.

**부수 관찰(범위 밖)** — ESG 평가는 같은 입력에도 근거 인용 문장이 절반가량 바뀐다. 판정은
안정적이나 인용은 재실행마다 달라진다.

## §3. 처방 설계 — 무엇을 떼는가

`select()` 이전에 **문서 전역 참조 사슬을 끊되, 보이는 것은 하나도 건드리지 않는다.**

> **"무손실"의 기준은 렌더링 불변이다.** 페이지를 렌더한 픽셀이 같으면 무손실로 본다. 소비자
> (Gemini)가 보는 것이 그것이고, 텍스트 추출값은 파서마다 다르기 때문이다. 실제로 카탈로그
> 정리는 렌더링이 동일한데도 PyMuPDF `get_text()` 결과가 파일에 따라 미세하게 달라진다
> (§2-6 각주 — 실측 1개 파일에서 0.011%). 반대로 주석 통째 제거는 **렌더링 자체가 바뀐다**
> (§2-5) — 그래서 그건 무손실이 아니고 2단계 안전망으로만 쓴다.

### §3-1. 세 가지 조작

| 대상 | 조작 | 근거 |
|---|---|---|
| 문서 카탈로그 | `Type`·`Pages`를 뺀 **모든 키를 `null`** | §2-4 — 생존 키는 4개뿐이고 그중 `/StructTreeRoot`가 사슬 |
| 페이지 객체 | `/AA`(페이지 열기 동작)를 `null` | 다른 페이지로 가는 GoTo를 담을 수 있는 자리 (코퍼스엔 0건, 예방) |
| 주석 객체 | `/A`·`/AA`·`/Dest`를 `null` | §2-6 — 사슬은 여기에만 있고 `/AP`(외관)는 페이지를 참조하지 않음 |

**주석 객체 자체와 `/AP`는 남긴다.** 이것이 [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §6의
처방과 다른 점이며, 글자·픽셀 손실이 사라지는 이유다(§2-5, §2-6).

### §3-2. 왜 화이트리스트인가

카탈로그를 "위험한 키만 골라 뗀다"(블랙리스트)로 가면 아픈 파일을 만날 때마다 목록이 자란다.
실제로 [25](25.pdf-split-shared-pool-and-unsplittable-reject.md)는 주석 하나를 등록했고, 이 문서는
구조트리를 추가하려는 참이다. 다음은 페이지 `/AA`나 `/B` 차례일 것이다.

반면 §2-4가 알려준 사실 — **`select()` 후 살아남는 카탈로그 키는 4개뿐이고, 분할 파트에 필요한
것은 `/Type`과 `/Pages`뿐** — 을 쓰면 목록이 닫힌다. 아직 못 본 기능이 나와도 자동으로 막히고,
`/Names`처럼 무해한 것을 지워도 잃는 게 없다(§2-5, 5개 파일 전부 ±0자).

한계도 명시한다. 화이트리스트는 **카탈로그 쪽만** 닫는다. 페이지·주석 쪽은 여전히 열거식이다.

두 갈래를 실제로 재봤다. **위젯의 `/Parent` → 폼 필드 → `/Kids` → 다른 페이지의 위젯** 경로는
합성해봤을 때 페이지를 끌고 오지 않았다 — 단일 페이지가 원본의 1/3에 그쳤다. PyMuPDF 1.27.2가
이 경로를 가지치기한다는 뜻이라, 이론상의 구멍이 이 버전에서는 발현되지 않는다(버전이 바뀌면
달라질 수 있다). 반면 **`/AP` → `/Resources` → 공유 풀** 경로는 실재한다(§2-6). 그래서 §3-3의
안전망을 둔다.

### §3-3. 안전망 — 손실 있는 조치는 마지막에만

무손실 정리로도 단일 페이지가 한도를 넘으면, 그때만 기존 처방(`_strip_annots_copy` — 주석
통째 제거)을 태운다. 손실(§2-5)은 정말 필요한 파일에만 발생한다.

```
1단계  무손실 정리 → 분할            ← 대부분 여기서 끝 (코퍼스 7/7)
2단계  + 주석 통째 제거 → 재분할      ← 손실 있음, 여기서만
3단계  PdfPageTooLargeError          ← 진짜 분할 불가
```

**2단계 진입 게이트(`_has_annots`)는 유지하되, 무엇을 거르는지 정확히 적는다.**

이 게이트가 거르는 것은 **"뗄 주석이 하나라도 있는가"** 뿐이다. 1단계가 주석 객체는 남기고 동작
키만 비우므로 `_has_annots(cleaned)`는 `_has_annots(path)`와 같다. 따라서 **주석은 있는데 그
사슬이 무의미한 파일(BNK가 그렇다 — §2-3)은 게이트를 통과해 2단계를 헛돈다.** 게이트는 그걸
막지 못한다.

그럼에도 유지하는 이유는 **주석이 아예 없는 파일**을 걸러주기 때문이다. 대표적인 것이
[25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §2의 공유 객체 풀 파일이다 — 페이지들이
공용 풀을 참조해 큰 것이지 주석 때문이 아니라 뗄 주석이 없다. 게이트를 빼면 그 파일이 거부되는
길에 원본 크기 사본을 한 번 더 뜨고 재분할까지 돌린다. 비용도 게이트가 싸다 — `_has_annots`
3.5~26ms 대 사본 저장 92~262ms(§2-7).

## §4. 적용 시점 — 선제 단일 경로

**분할이 걸릴 때만 무조건 선제로 정리한다.**

임계는 50MB가 아니다. 현행 코드의 분할 개시 조건은
`file_size > target_mb × 1024² × _SAFETY_MARGIN`이고 `_SAFETY_MARGIN = 0.95`이므로,
기본값 `target_mb=50`에서 **실제 분기점은 47.5MB**다(`splitter.py:26`, `:346`, `:349`).
아래 흐름과 `_needs_split`은 이 값을 상수에서 유도해야 하며, 문면의 "50MB"를 그대로 구현하면
47.5~50MB 구간의 안전 마진이 조용히 사라진다.

```
split_pdf(path)
 ├─ 47.5MB·1000p 이하 → [path] 즉시 반환      ← 사본을 만들지 않는다 (현행과 동일)
 └─ 초과 →
     1. 무손실 정리 사본 생성 (§3-1)
     2. 분할
     3. 단일 페이지 초과면 → 주석 통째 제거 후 재분할 (§3-3)
     4. 그래도 초과면 → PdfPageTooLargeError
```

**왜 선제인가.** 현행은 "원본으로 시도 → 실패하면 정리 후 재시도"라 아픈 파일이 반드시 두 번
일한다. BNK는 실패를 확인하는 데만 4.45초를 쓴다(87MB 파일을 이등분하며 여섯 번 저장하고,
주석 제거 후 그것을 한 번 더 반복). 선제로 끊으면 그 헛수고가 사라진다.

**단, "무조건 더 빠르다"는 아니다.** 실측(§2-7)에서 정리 비용은 떼기 111~214ms + 사본 저장
92~262ms이고, 아래 표대로 **정상 대형 파일 3건은 오히려 0.2~0.3초 느려진다.** 합계가 줄어드는
것은 BNK 실패 경로 4.45초가 사라지기 때문이다. 즉 "실패 파일에서 크게 이득, 정상 대형 파일은
0.2~0.3초 손해"가 정확한 서술이다.

**왜 임계 이하는 건드리지 않는가.** 코퍼스 19개 중 14개가 여기 해당하며 사본을 만들 이유가
없다. (`_needs_split`도 페이지 수를 세려면 파일을 한 번 열어야 하므로 비용이 0은 아니다 —
현행 `_split_once`가 이미 하는 일과 같은 수준이고, 달라지는 것은 "사본을 만들지 않는다"는
점이다.) 분할하지 않는 파일이 원본 그대로 업로드된다는 현행 동작도 유지된다.

| | 현재 | 이 설계 |
|---|---|---|
| 임계 이하 (14개) | 사본 없음 | **사본 없음 (동일)** |
| BNK | 4.45초 ❌ | **0.83초 ✅** |
| 현대글로비스 | 1.29초 (−491자) | **0.55초 (±0자)** |
| GS건설·기업은행·파라다이스 | 0.28~0.51초 | 0.50~0.65초 (느려짐) |
| 큰 파일 5개 합계 | 6.81초 · 1건 실패 | **3.07초 · 전건 성공** |

## §5. 모듈별 상세

대상 파일: `llm_manager/_internal/file_processing/splitter.py`.

### §5-1. 새 상수

```python
_CATALOG_KEEP = ("Type", "Pages")     # 카탈로그 화이트리스트 (§3-2)
_ACTION_KEYS = ("A", "AA", "Dest")    # 주석의 동작·목적지 — 코퍼스에서 사슬이 있던 곳 (§2-6)
```

### §5-2. 새 함수

```python
def _needs_split(path: str, target_mb: int, max_pages: int) -> bool:
    """사본을 만들기 전에 분할이 필요한지 판정한다.

    크기 임계는 _SAFETY_MARGIN 을 곱한 값이다 (target_mb=50 → 47.5MB, §4).
    _split_once 와 같은 상수에서 유도해 판정이 어긋나지 않게 한다 (SSOT).
    """

def _annot_xrefs(doc: fitz.Document, page_xref: int) -> list[int]:
    """페이지 /Annots 가 가리키는 주석 객체 xref 목록.

    /Annots 는 직접 배열("array")로도 간접 참조("xref")로도 온다 —
    간접이면 배열 실물을 열어야 한다(_has_annots 와 같은 이유).
    """

def _strip_chains_copy(path: str, created_temps: list[str]) -> str:
    """문서 전역 참조 사슬만 끊은 사본을 만들어 경로를 반환한다 (무손실).

    카탈로그는 _CATALOG_KEEP 만 남기고, 페이지 /AA 와 주석 _ACTION_KEYS 를 null 로 만든다.
    주석 객체와 그 외관(/AP)은 건드리지 않아 보이는 내용이 그대로 보존된다 (docs/34 §3-1).

    xref_set_key(x, k, "null") 은 키를 삭제하지 않고 `/k null` 을 남기며, 없던 키에 쓰면
    그 키를 새로 만든다 — 값이 null 이면 명세상 부재와 등가라 사슬 차단에는 문제가 없으나,
    "무손실"이 바이트 수준 무변경을 뜻하지는 않는다 (§3-1). 기존 키가 있을 때만 지정해
    손대는 객체 수를 줄인다.

    tempfile 은 save 이전에 created_temps 에 등록해, save 가 도중 실패해도 호출자의
    정리 루프가 회수하게 한다 (leak 방지 — _save_pages·_split_once 와 같은 패턴).
    """
```

### §5-3. 기존 함수의 운명

| 함수 | 처리 | 이유 |
|---|---|---|
| `_strip_annots_copy` | **존치** | §3-3 안전망(2단계)에서 그대로 쓴다 |
| `_has_annots` | **존치** | 2단계 진입 게이트. 거르는 것은 "뗄 주석이 하나라도 있는가"뿐이며, 주석이 있으나 사슬이 무의미한 파일은 못 거른다(§3-3) |
| `_split_once` | 변경 없음 | 사슬 차단은 호출 전에 끝나 있다 |
| `_save_pages` | 변경 없음 | **`select()`가 실제로 일어나는 유일한 지점.** 이 설계는 그 앞에서 사슬을 끊을 뿐 이 함수는 손대지 않는다 |
| `_estimate_page_sizes`·`_group_pages`·`_split_group`·`_merge_adjacent`·`_cap_pages`·`_cleanup` | 변경 없음 | |

### §5-4. `split_pdf` 재구성

```python
def split_pdf(path, target_mb=50, max_pages=1000):
    if not _needs_split(path, target_mb, max_pages):
        return [path]                       # 사본을 만들지 않는다 (§4)

    temps: list[str] = []
    try:
        cleaned = _strip_chains_copy(path, temps)          # 1단계 — 무손실
        try:
            parts = _split_once(cleaned, target_mb, max_pages)
        except PdfPageTooLargeError:
            if not _has_annots(cleaned):
                raise                                      # 뗄 주석이 없다 — 2단계가 무의미 (§3-3)
            logger.warning("무손실 정리로도 한도 초과 — 주석 제거 후 재분할: %s", path)
            cleaned = _strip_annots_copy(cleaned, temps)   # 2단계 — 손실 있음
            parts = _split_once(cleaned, target_mb, max_pages)
    except Exception:
        _cleanup(temps, keep=path)
        raise

    # 파트로 반환된 사본만 남기고 나머지 임시 파일을 회수한다.
    _cleanup([t for t in temps if t not in parts], keep=path)
    return parts
```

**왜 `cleaned not in parts` 단일 가드가 아니라 파일 단위 필터인가.** 정리 후 사본이 한도 아래로
내려가면 `_split_once`가 `[cleaned]`(사본 경로 자체)를 반환한다. 이때 그 사본을 지우면 호출자
(uploader)가 업로드할 파일이 사라지므로 남겨야 한다 — 여기까지는 현행과 같다.

그런데 이 설계는 사본을 **최대 두 개** 만든다(1단계 `_strip_chains_copy`, 2단계
`_strip_annots_copy`). `_cleanup`은 전부 아니면 전무라, 2단계까지 간 뒤 `_split_once`가
`[2단계 사본]`을 반환하면 `cleaned in parts`가 참이 되어 **정리가 통째로 건너뛰어지고 1단계 사본
(원본 크기급)이 디스크에 영구히 남는다.** 상위 `upload_pdf_parts`의 `finally`도 `parts` 안의
경로만 지우므로 회수하지 못한다. 그래서 "파트에 없는 임시 파일만 지운다"로 바꾼다 — 사본이 몇
개든 성립한다.

파트 삭제 책임은 호출자에게 있다는 기존 계약은 그대로다.

| 실패 지점 | 처리 |
|---|---|

## §7. 결정성과 캐시 영향

**결정성은 유지된다.** 무작위·시간 의존이 없고, 정리 조작(키를 `null`로)은 페이지 순서·내용을
바꾸지 않는다. 같은 PDF 바이트 + 같은 PyMuPDF 버전이면 항상 같은 경계에서 분할된다.

**기존 Redis 캐시와의 정합성은 깨지지 않는다.** `pdf_part_ranges`는 파트 URI와 **같은
files_api 레코드에 함께 저장**되며(`resolver.py:380`), HIT 시 그 레코드에서 복원될 뿐
재계산되지 않는다(`resolver.py:283`~`:284`). 따라서 이미 캐시된 문서는 옛 파트와 옛 범위가
짝을 이룬 채 그대로 유효하고, 새로 올라가는 문서만 새 경계를 쓴다. **마이그레이션 불필요.**

캐시 키는 원본 파일의 체크섬(`file_name`+`file_mtime`+`file_size`)이라 이번 변경의 영향을
받지 않는다 — 우리가 손대는 것은 업로드용 임시 사본뿐이다.

다만 **분할 경계 자체는 이번 변경으로 달라질 수 있다**(정리로 사본 크기가 바뀌므로). 위 이유로
기존 레코드가 깨지진 않지만, 같은 파일을 새로 올리면 이전과 다른 파트 구성이 나올 수 있다.

## §10. 독립 리뷰 결과와 처리

grounding·consistency·adversarial 3렌즈를 각각 읽기 전용 서브에이전트로 돌려 나온 지적 중,
**문서 수정으로 끝나지 않던 7건**의 처리 결과다. 사실·인용 오류 14건은 본문에 직접 반영했다.

| # | 쟁점 | 처리 |
|---|---|---|
| 1 | "무손실"의 근거가 계측기 맹점 위에 있다 | **실측으로 해소** — §2-10. 소비처(Gemini) 수준 A/B + 대조군에서 영향이 관측되지 않았다 |
| 2 | 정리 사본이 임계 아래로 내려가는 경로 | **코드 변경 없음** — 아래 근거 |
| 3 | `/AP`와 공유 객체 풀 | **확인 완료 — 실재한다.** 합성 PDF로 재현했고 1단계로는 안 끊긴다(§2-6). 안전망(§3-3)이 필요한 경로임이 증명됐다 |
| 4 | [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §2의 원인 파일 미검증 | **측정으로 이관** — §8 실물 검증에 포함 |
| 5 | 이벤트 루프 기아 | **기록으로 갈음** — 아래 근거 |
| 6 | 롤백 절차 부재 | **하지 않음** (결정) |
| 7 | `_has_annots` 게이트 무의미 | **게이트 유지 + 서술 정정** — 아래 근거 |

**쟁점 2 — 왜 고치지 않는가.** 정리 사본이 단일 파트로 반환되면 `upload_pdf_parts`의 비분할 판정
(`parts[0] == path`, `uploader.py:50`)이 어긋나 `pdf_part_ranges`가 `None` 대신 `[(1, N)]`이 된다.
그러나 소비처를 확인해보니 **이미 길이로 거르고 있다** — Kiwoom-ESG는 재평가 라우팅
(`evaluator.py:289`)과 분할 보고서 조인(`evaluator.py:315`) 두 곳 모두
`len(pdf_part_ranges) >= 2`를 요구하므로 1개짜리는 비분할과 동일하게 취급된다. 설령 통과하더라도
페이지 오프셋이 `start - 1 = 0`이라(`source_verify.py:36`) 환산 결과가 바뀌지 않는다.
남는 영향은 통계 dict 한 곳(`evaluator.py:137`, `>= 2` 가드 없음)에 무의미한 항목이 하나 끼는
것뿐이며 동작에는 영향이 없다. 리뷰가 "깨진다"고 지목한 `test_hit_non_split_file_keeps_none`도
확인 결과 Redis 복원 시 예외가 안 나는지를 보는 테스트이지 `split_pdf`의 반환을 박아둔 것이
아니다. `select()`가 돌지 않는다는 점도 실질 위험이 아니다 — §2-10이 "카탈로그를 비운 파일을 통째로
올려도 Gemini 응답이 같다"를 실측했고, 그때 쓴 SK텔레콤이 바로 분할되지 않는 파일이었다.

> **정정 — "도달 범위가 좁다"는 처음 판단은 틀렸다.** 초안은 "정리 절감량이 2~3MB이므로 원본
> 50~50.5MB 구간에서만 걸린다"고 적었다. 구현 후 실물 검증에서
> [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §2의 원인 파일이 **52.9MB → 37.6MB로
> 15.3MB(29%)** 줄어 임계 아래로 떨어졌다. 구조트리가 거대한 파일에서는 절감이 훨씬 크므로
> 이 경로는 흔히 도달한다. 코드 변경을 하지 않는 근거는 "좁아서"가 아니라 **소비처가 길이로
> 이미 거르기 때문**이다(위). 실제로 그 파일이 이 경로를 타서 236페이지가 온전히 나왔다(§8).

**쟁점 5 — 왜 기록으로 갈음하는가.** [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §1의
원인 사건은 파트당 ~16분 블로킹이었고, 이 설계가 더하는 것은 0.2~0.3초다(§4 표). 세 자릿수 차이라
같은 급의 위험으로 다루지 않는다. "정상 대형 파일의 GIL 점유가 약 2배가 된다"는 사실 자체는 §4에
적었다. 운영에서 문제가 되면 답은 이 설계를 되돌리는 것이 아니라 `split_pdf`를 스레드로 오프로드하는
것이다(범위 밖).

**쟁점 7 — 왜 제거가 아니라 유지인가.** 리뷰 지적("게이트가 무의미해졌다")은 절반만 맞다. 주석이
*있는데* 사슬이 무의미한 파일은 못 거르는 게 사실이나(BNK), **주석이 아예 없는 파일은 제대로
거른다.** 그리고 그게 [25](25.pdf-split-shared-pool-and-unsplittable-reject.md) §2의 공유 객체 풀
파일이다 — 빼면 그 파일이 거부되는 길에 원본 크기 사본을 한 번 더 뜨게 되어, 같은 리뷰가 쟁점 4에서
경고한 "사본 저장이 한 번 더 는다"가 현실이 된다. 기존 테스트
`test_empty_annots_array_skips_retry`(`test_splitter.py:236`)가 이 동작을 이미 박아두고 있다.
그래서 처방은 제거가 아니라 **§3-3에 게이트의 한계를 명시하는 것**으로 한다.

**페이지 `/AA` — 두기로 결정.** 코퍼스 0건이라 발현을 재현할 실물이 없고, 그래서 §8에 전용
테스트를 만들지 못한다는 점을 알고도 처방에 남긴다. §3-2가 블랙리스트 증식의 예로 든 항목을
§3-1이 스스로 추가한 모순은 남지만, 페이지에서 다른 페이지로 새는 형태가 `/Annots`와 동일해
실물이 오면 같은 병이 될 것이 구조적으로 명백하고 조작 비용이 0에 가깝기 때문이다.
**검증되지 않은 채로 들어간다는 사실을 여기 남긴다** — 나중에 이 줄이 도는지 확인하려면
페이지 `/AA`를 가진 실물이나 합성 PDF가 필요하다.

**임시 파일 누수 — 고친다.** 2단계까지 가고 2단계 사본이 파트로 반환되면 1단계 사본이 회수되지
않는 문제를 consistency·adversarial 두 렌즈가 함께 지적했고 실재한다. 쟁점 2와 달리 이건
**원본 크기급 파일이 디스크에 조용히 쌓이는** 실패이고 수정이 한 줄이라, 발생 창이 좁아도 넣는다
(§5-4 반영, §8 테스트 #9).

## 부록. 측정 방법

이 문서의 수치는 llm-manager `.venv`(PyMuPDF 1.27.2.2)와 `Kiwoom-ESG/bug_report/`의 실물
보고서 19개로 일회성 스크립트를 돌려 얻었다. **스크립트는 보관하지 않는다** — 재현이 필요하면
아래 방법으로 다시 짠다.

| 측정 | 방법 |
|---|---|
| 재현 (§2-1) | `split_pdf`를 DEBUG 로깅으로 호출해 이등분 재귀 로그와 예외를 관찰 |
| 사슬 지목 (§2-2) | 카탈로그 키를 하나씩 `null`로 만든 뒤 `select([0])` → `save` 하여 p.1 크기 비교 |
| 참조 그래프 | 전 객체의 `N 0 R` 참조로 그래프를 만들고(`/Parent`는 페이지트리 역방향이라 제외) 기능별 도달 페이지 수·스트림 바이트 합계를 계산 |
| 생존 키 (§2-4) | `select([0])` → `save` 후 결과물의 Root 키 목록과 `/Pg` 참조 개수 확인 |
| 손실 (§2-5) | 전 페이지 `get_text()`에서 공백을 제거한 글자 수 비교 + `get_pixmap(dpi=50, annots=True)` PNG 바이트 동일성 비교 |
| 비용 (§2-7) | `perf_counter`로 열기·떼기·저장·분할을 구간별 3회 측정, 중앙값 |

**주의.** 위 "참조 그래프"는 *잠재적* 사슬만 보여준다. 실제로 무는지는 §2-4처럼 `select()`
결과로 확인해야 한다(`/AcroForm` 사례 — 그래프상 전 페이지 도달, 실제로는 무해).
