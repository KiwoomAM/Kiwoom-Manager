# 36. sync `llm_request_stream` 을 진짜 증분 스트리밍으로

## 1. 배경 / 문제 정의

`llm_request_stream`(sync)은 **이름과 달리 스트리밍이 아니다.** 모든 이벤트를 리스트에 다 모은
뒤에야 이터레이터를 돌려준다 ([__init__.py:305-332](../llm_manager/__init__.py#L305)).

```python
def llm_request_stream(...) -> tuple[Iterator[dict], dict]:
    async def _collect():
        event_stream, meta = await llm_request_stream_async(...)
        events = []
        async for event in event_stream:
            events.append(event)          # ← 끝까지 다 모은다
        return events, meta

    events, meta = asyncio.run(_collect())
    return iter(events), meta             # ← 그제서야 이터레이터
```

**결과: 첫 글자까지의 지연이 논스트림과 같다.** 스트리밍을 쓰는 이유가 그 지연을 줄이는 것인데,
sync 소비자는 그 이득을 하나도 못 받으면서 스트림 API 를 쓰고 있다고 믿는다(`EXPLICIT` 위반).

**async 쪽은 진짜다.** [`_client.py:181`](../llm_manager/_internal/handler_client/_client.py#L181) 이
`httpx` 로 `POST /v1/stream` 을 열고 `aiter_lines()` 로 SSE 를 한 줄씩 파싱해 chunk 마다 yield 한다.
중간에 모으는 곳이 없다. **sync 래퍼만 혼자 다르게 동작한다.**

## 2. 사전 정보 — 실측 (2026-08-29)

### 2.1 소비자가 0이다

사내 전 repo 에서 `llm_request_stream`(sync)을 부르는 코드가 **한 줄도 없다.** 쓰이는 것은 전부
`llm_request_stream_async` 다 (`Kiwoom-ETF/backend/llm/streaming.py:65`,
`Kiwoom-PF/src/features/withdrawal/core/chat.py:105`).

**이것은 양날이다.** 고쳐도 아무도 안 깨진다는 뜻이면서, "지금 필요한가"(`YAGNI`)를 되묻게 한다.
그럼에도 고치는 쪽으로 정한 근거는 §3.7 에 적는다.

### 2.2 동기 스트리밍 클라이언트가 **이미 있다**

이 설계의 방향을 바꾼 발견이다. `handler_client` 에는 `httpx.Client`(진짜 동기) 기반
`SyncClient` 가 있고, `stream()` 이 제너레이터로 SSE 를 증분 파싱한다.

| 위치 | 내용 |
|---|---|
| [`_sync_client.py:238`](../llm_manager/_internal/handler_client/_sync_client.py#L238) | `with self._http.stream("POST", "/v1/stream", ...)` |
| [`_sync_client.py:85-97`](../llm_manager/_internal/handler_client/_sync_client.py#L85) | `_parse_sse` 가 `response.iter_lines()` 로 한 줄씩 `yield` |
| [`handler_client/__init__.py:213`](../llm_manager/_internal/handler_client/__init__.py#L213) | 모듈 레벨 `stream()` 으로 공개 |

즉 **HTTP 계층에는 동기 증분 스트리밍이 이미 갖춰져 있다.** 문제는 그 위의 매니저 로직이다.

### 2.3 동기 구현을 따로 쓸 수 없는 이유 — 오케스트레이션이 async 쪽에만 있다

§2.2 대로 HTTP 계층에는 동기 스트리밍이 이미 있다. 그런데도 "그냥 동기로 다시 쓰면 되지" 가
안 되는 이유가 여기 있다. 흐름을 단계별로 보면 sync/async 가 섞여 있다.

| 단계 | 위치 | sync/async |
|---|---|---|
| `prepare()` — 캐시 조회·키 생성 | [runner.py:72](../llm_manager/_internal/runner.py#L72) | sync |
| `_prepare_files` — stored_files 해석 | [runner.py:240](../llm_manager/_internal/runner.py#L240) | async |
| `_build_server_call_input` → `resolve_files` | [runner.py:429](../llm_manager/_internal/runner.py#L429) | async |
| **`agent_llm` standby 선점·대기 (스트림 경로)** | [runner.py:693-716](../llm_manager/_internal/runner.py#L693) | **async 전용** |
| SSE 스트림 소비 | [runner.py:623](../llm_manager/_internal/runner.py#L623) | async |
| **404 자동 복구** | [runner.py:629-646](../llm_manager/_internal/runner.py#L629) | **async 전용** |
| **리더 토큰 해제 (`finally`)** | [runner.py:734-735](../llm_manager/_internal/runner.py#L734) | **async 전용** |
| `_finalize_stream` — MDB 저장 | [runner.py:320](../llm_manager/_internal/runner.py#L320) | sync |

> **오해 주의 — "sync 에서는 dedup 을 못 쓴다" 는 뜻이 아니다.**
> 동기 호출자도 dedup 을 정상으로 쓴다. 실제로 `llm_request`(논스트림 sync)는 `asyncio.run` 으로
> async 흐름을 통째로 돌려 standby·404 복구·저장을 전부 정상 수행한다. 아래 표가 말하는 것은
> **"동기 구현을 *따로 하나 더* 만들면 이 셋을 복제해야 한다"** 는 것뿐이다.

`prepare` 와 `_finalize_stream` 은 sync 라 동기 경로에서도 그대로 쓸 수 있다. **문제는 그 사이의
굵은 글씨 셋 — standby 리더/대기자 처리·404 자동 복구·`_StreamMeta` 누적**이다. 이들은 async
구현 안에만 있고 짝이 되는 동기 판이 없다. 동기 경로를 만들면 **두 벌로 복제**해야 하고,
한쪽만 고치는 드리프트가 시작된다(§3.3 에서 이 근거로 하이브리드를 기각한다).

**그리고 어떤 안을 택하든 지켜야 할 제약이 하나 나온다.** standby 리더 토큰은 스트림이 끝날
때까지 쥐고 있다가 `finally` 에서 놓는다([runner.py:734-735](../llm_manager/_internal/runner.py#L734)).
따라서 **async 제너레이터의 `finally` 가 반드시 실행되게 해야 한다.** 안 그러면 락이 TTL 만료까지
남는다. 이것이 §4 의 핵심 방어선이다.

> **곁길로 빠졌다가 접은 것 — `prepare` 가 루프를 막는 문제.**
> `prepare()` 는 async 흐름 안에서 동기 MDB 조회를 하므로 그 동안 이벤트 루프가 멈춘다.
> 초안은 이것을 "async 가 껍데기다" 라고까지 썼으나 **과장이었다.** 실측해 보니 `cache_get`
> 왕복은 **중앙값 3.9ms**(최초 1회만 67.6ms — 커넥션 수립)로, 초 단위인 LLM 호출 옆에서 0.1%
> 미만이다. `mdb_manager.aio`·`redis_manager.aio` 로 전환하는 안도 검토했으나
> **`AsyncMongoDBManager` 는 싱글턴이 아니고 `aclose()` 를 요구해** 클라이언트 수명을 새로
> 설계해야 한다 — 4ms 를 없애려고 커넥션 누수 위험을 지는 셈이라 기각했다.
> **이 문서는 기존 함수를 바꾸지 않는다.** (참고: `store.py` 는 2026-03-25 작성,
> MDB async 도입은 2026-04-15 — 당시엔 동기 API 밖에 없었다. 실수가 아니라 유일한 선택이었다.)

### 2.4 같은 sync 래퍼가 두 곳에 있고, 하나는 죽어 있다

전량 grep 결과 "전부 모은 뒤 `iter()`" 패턴이 **두 곳**이다.

| 위치 | 반환 | 소비자 |
|---|---|---|
| [`llm_manager/__init__.py:305`](../llm_manager/__init__.py#L305) | 이벤트 `dict` | **공개 API** — 이 문서가 고칠 대상 |
| [`runner.py:739`](../llm_manager/_internal/runner.py#L739) | `StreamChunk` | **0건** — 패키지·테스트 통틀어 부르는 곳이 없다 |

공개 래퍼는 `runner` 의 sync 판을 거치지 않고 **async 판을 직접** 부른다. 즉 `runner.py:739` 는
도달 불가능한 죽은 코드다. 같은 사정이 `runner.llm_request`(논스트림 sync)에도 있다.

**고칠 곳은 공개 API 한 곳이다.** 죽은 둘은 이 변경으로 불필요해진 것이 아니므로 지우지 않고
표시만 한다(`SURGICAL`, §7).

### 2.5 이벤트 루프 수명 — 새로 만드는 위험이 아니다

`llm_request`(sync, 논스트림)는 이미 `asyncio.run` 으로 매 호출 루프를 만들고 닫는다
([__init__.py:239](../llm_manager/__init__.py#L239)). 그런데 `handler_client.aio._get_client()`
는 모듈 전역 `AsyncClient` **싱글턴**이라, 두 번째 sync 호출은 이미 닫힌 루프에서 만들어진
커넥션 풀을 재사용하게 된다.

**이 설계는 그 구조를 바꾸지 않는다.** 아래 어떤 안을 택하든 "sync 호출 1회 = 루프 1회" 는
그대로다. 즉 **선재 위험이고 이 문서의 범위 밖**이다(docs/35 §7 에 이미 기록).

## 3. 설계

### 3.1 채택 — 루프를 살려 두고 chunk 마다 한 걸음 (+ `_events()` 정리 고정)

> **이 절은 디시플린 리뷰(2026-08-29) 후 다시 썼다.** 초안은 `agen.aclose()` 가 standby 락을
> 푼다고 세 곳에 적었는데 **틀렸다.** 실제 구조와 정정 내용은 §4.1 에 있다. 아래는 정정 후 설계다.

두 조각이다. **(가) async 쪽 정리를 결정적으로 만들고, (나) sync 래퍼가 루프를 소유·회수한다.**

#### (가) `_events()` 에 `try/finally` — async 경로도 함께 개선된다

지금 [`__init__.py:291`](../llm_manager/__init__.py#L291) 의 `_events()` 는 `try/finally` 가 없다.

```python
async def _events():
    async for chunk in chunk_stream:     # ← 빠져나가도 chunk_stream 을 안 닫는다
        ...
        yield event
```

`async for` 는 이터레이터를 닫지 않으므로, 바깥을 닫아도 **안쪽 `_leader_stream` 의 `finally`
(= standby 락 해제, [runner.py:734-735](../llm_manager/_internal/runner.py#L734))가 실행되지 않는다.**
지금은 이벤트 루프의 asyncgen 파이널라이저가 나중에 대신 닫아 준다 — 즉 **정리가 GC 타이밍에 달려
있다.** (`Kiwoom-ETF/backend/llm/streaming.py:57-60` 이 그 동작을 실측으로 확인해 두고 의존한다.)

```python
async def _events():
    try:
        async for chunk in chunk_stream:
            ...
            yield event
    finally:
        await chunk_stream.aclose()      # ← 3줄 추가: 닫으면 안쪽까지 닫힌다
```

**이것은 sync 를 위한 양보가 아니라 async 경로의 개선이다.** 실사용 소비자(ETF·PF)가 `break`·취소·
예외로 순회를 놓을 때, 정리가 "운 좋게 도는 것" 에서 **계약**으로 바뀐다.

#### (나) sync 래퍼 — 루프를 소유하는 이터레이터

정리를 제너레이터의 `finally` 에만 두면 **소비자가 `next()` 를 한 번도 안 부를 때 아무것도 안 돈다**
(§4.2). 그래서 반환값을 작은 클래스로 만들어 **닫기를 멱등으로** 하고 `__del__` 까지 건다.

```python
class _SyncStream:
    """async 스트림을 sync 이터레이터로. 루프를 소유하고 반드시 회수한다."""

    def __init__(self, loop, agen):
        self._loop, self._agen, self._closed = loop, agen, False

    def __iter__(self):
        return self

    def __next__(self):
        try:
            return self._loop.run_until_complete(self._agen.__anext__())
        except StopAsyncIteration:
            self.close()
            raise StopIteration from None
        except BaseException:            # mid-stream 예외도 정리하고 그대로 올린다
            self.close()
            raise

    def close(self):
        if self._closed:                 # 멱등 — __del__ 과 명시 close 가 겹쳐도 안전
            return
        self._closed = True
        try:
            self._loop.run_until_complete(self._agen.aclose())
        except Exception:
            logger.warning("sync 스트림 정리 중 aclose 실패", exc_info=True)
        finally:
            try:
                self._loop.run_until_complete(self._loop.shutdown_asyncgens())
                self._loop.run_until_complete(self._loop.shutdown_default_executor())
            finally:
                self._loop.close()       # ← 앞이 무엇을 던지든 루프는 반드시 닫는다

    def __del__(self):
        self.close()
```

```python
def llm_request_stream(...):
    loop = asyncio.new_event_loop()
    try:
        agen, meta = loop.run_until_complete(_setup())   # 준비 + standby 선점까지
    except BaseException:
        loop.close()                     # 준비 단계에서 실패해도 루프를 흘리지 않는다
        raise
    return _SyncStream(loop, agen), meta
```

#### 왜 이 모양인가 — 리뷰가 잡은 것 넷을 각각 막는다

| 리뷰 지적 | 어디서 막나 |
|---|---|
| `aclose()` 가 안쪽까지 안 닫아 락이 안 풀린다 | **(가)** `_events()` 의 `finally` |
| `next()` 0회면 정리가 통째로 안 돈다 | `__del__` + 멱등 `close()` |
| `aclose()` 가 던지면 뒤 3줄이 날아간다 | 중첩 `try/finally` — `loop.close()` 는 무조건 |
| 준비 단계 예외 시 루프가 남는다 | 진입부 `try/except BaseException: loop.close()` |

**여전히 못 막는 것 하나** — 인터프리터 종료 중 `__del__` 은 신뢰할 수 없다(§4.3). 이건 async 판도
같으므로 **계약으로 명시**한다(§3.2).

#### 실측 — 프로토타입 (2026-08-29)

chunk 사이 0.3초짜리 가짜 async 스트림으로 확인했다.

| 확인 항목 | 결과 |
|---|---|
| meta 가 이터레이션 전에 오는가 | **0.10s 에 반환** (첫 chunk 는 0.40s) |
| 증분성 | chunk 가 0.40 → 0.70 → 1.00 → 1.30s 에 하나씩 |
| 중간에 버릴 때 정리 | 실행됨 |

> 그 프로토타입에는 dedup 이 없어 스레드가 1(메인뿐)이었다. **실경로에서는 dedup 의
> `asyncio.to_thread` 때문에 executor 스레드가 뜬다** — 그래서 `shutdown_default_executor()` 가
> 필요하다. "스레드를 안 만든다" 는 **우리가 직접 만들지 않는다**는 뜻으로만 읽어야 한다.

#### 바꾸는 범위

`llm_manager/__init__.py` **한 파일**이다 — `_events()` 3줄 + sync 래퍼 본문.
`prepare`·`dedup`·`store`·`runner.py` 는 건드리지 않는다.

### 3.2 함께 하는 것 — 스트림 소비 계약을 명시한다

`llm_request_stream_async` 는 **standby 락을 이미 잡은 상태로** `(stream, meta)` 를 돌려준다.
그런데 "이것을 반드시 소비하거나 닫아야 한다" 는 계약이 **어디에도 적혀 있지 않다.** 타입만 보면
평범한 이터레이터다.

받아 놓고 순회하지 않으면 락이 `standby_ttl`(기본 600초) 만료까지 남고, 그동안 같은 cache_key 의
다른 요청은 **리더가 죽었는지 일하는 중인지 구분할 수 없어** TTL 을 다 기다린다. 이는
`guide-doc/user-guide/dedup.md` 가 **`SIGKILL` 용 실패 모드**로 이미 적어 둔 상태와 같다 —
문제는 **크래시 없이 평범한 코드 경로로 그 상태에 도달**할 수 있다는 것이다.

**이 결함은 sync 판이 아니라 async API 에 원래 있다**(실측으로 확인: 순회하지 않고 버리면 해제 안 됨).
그래서 코드로 막지 않고 — standby 획득 시점을 옮기는 일은 이 패키지에서 가장 조심스러운 영역이라
별건이다(§7) — **계약을 문서에 박는다.**

| 대상 | 넣을 문장 |
|---|---|
| `llm_request_stream_async` / `llm_request_stream` docstring | 반환된 스트림은 **끝까지 소비하거나 `aclose()`(sync 는 `close()`) 해야 한다.** 방치하면 같은 입력의 다른 요청이 최대 `standby_ttl` 만큼 대기한다 |
| `README` 스트리밍 절 | 같은 취지 한 줄 |
| `guide-doc/user-guide/dedup.md` 한계 절 | `SIGKILL` 옆에 "스트림 방치" 를 같은 실패 모드로 추가 — 다만 `guide-doc/` 은 버전 관리 대상이 아니므로(docs/35) **로컬 갱신 몫**이다 |

### 3.3 기각 — 백그라운드 스레드 + 큐 브리지

초안의 채택안이었다. 워커 스레드에서 `asyncio.run` 으로 async 흐름을 통째로 돌리고 chunk 를
큐로 넘겨받는 구조다. **§3.1 이 같은 목적을 스레드 없이 달성하므로 기각한다.**

기각 근거는 **직접 관리해야 할 것의 수**다. 스레드 안이면 큐 역압·예외 마샬링·중단 플래그·
스레드 join 을 전부 손으로 다뤄야 하고, 각각이 틀릴 수 있는 자리다. §3.1 은 그 넷을 `finally`
한 블록으로 대신한다 — 게다가 §4 가 반드시 지켜야 한다고 못박은 "async 제너레이터의 `finally`
실행" 이 그 블록에서 자연스럽게 보장된다.

덧붙여, dedup 이 내부에서 `asyncio.to_thread` 를 쓰므로(§2.3 표) 워커 스레드 안의 루프가 다시
스레드를 띄운다. 동작에 문제는 없지만 층이 하나 늘어 디버깅이 어려워진다.

### 3.4 기각 — 하이브리드(async 준비 + sync 스트리밍)

`SyncClient.stream()`(§2.2)이 이미 있으니, 준비만 `asyncio.run` 으로 끝내고 SSE 는 동기로 받는
길도 있다. **기각한다.**

`prepare` 와 `_finalize_stream` 은 sync 라 그대로 쓸 수 있으나, 그 사이의
**standby 리더/대기자 처리·404 자동 복구·`_StreamMeta` 누적**이 전부 async 구현 안에 있다(§2.3).
동기 경로를 만들면 그 셋을 **두 벌로 복제**하게 되고, 한쪽만 고치는 드리프트가 시작된다.
지금 이 레포에서 고치고 있는 문제(같은 규칙이 세 곳에 복붙돼 어긋난 것 — docs/35)와 같은 종류의
빚을 새로 만드는 셈이다.

**복제해야 할 양을 실측했다.** SSE 를 받는 부분은 `SyncClient.stream()` 덕에 공짜지만, 그 앞뒤가 남는다.

| 동기 판을 새로 써야 할 계층 | 줄 수 | async 함수 |
|---|---:|---:|
| `file_processing/resolver.py` (분류·업로드·context cache) | 952 | 10 |
| `file_processing/dedup.py` (standby 선점·대기·실패기록) | 418 | 8 |
| `file_processing/uploader.py` | 143 | 2 |
| `stored_file_resolver.py` | 126 | 2 |
| **합계** | **~1,640** | **22** |

즉 **어댑터 약 15줄을 피하는 값이 1,640줄 이중 유지**다.

덧붙여 방향도 어긋난다. `resolver.py` 의 async 는 진짜 async 라
[`asyncio.gather`](../llm_manager/_internal/file_processing/resolver.py#L930) 로 inline·files_api 를
병렬 처리한다. 동기로 다시 쓰면 그 병렬성을 잃거나, 지키려면 결국 스레드를 쓰게 된다 —
**어댑터를 피하려다 다른 자리에서 스레드를 만난다.**

### 3.5 기각 — 그대로 두고 문서에만 명시

가장 싸지만 코드 동작과 문서가 `SSOT` 를 나눠 갖게 된다. 문서를 안 읽은 사람은 계속 같은 함정을
밟고, "sync 스트림" 이라는 이름이 계속 거짓말을 한다. 기각.

### 3.6 기각 — sync 함수 제거

소비자가 0이니(§2.1) 이름값 못 하는 공개 API 를 없애는 것도 선택지다. 그러나 배포된 SDK 의 공개
표면을 깨는 결정이라 되돌리기 어렵고(`REVERSIBLE`), sync 함수의 쓰임새(async 를 못 쓰는 스크립트·
노트북)에서 스트리밍이 필요한 것이 바로 그 상황이다. 기각.

### 3.7 왜 지금 하는가 (`YAGNI` 반론)

소비자가 0인데 왜 고치나 — 세 가지다.

- **소비자가 0이라 지금이 가장 싸다.** 깨질 코드가 없어 회귀 위험이 없다.
- **이름이 거짓말하는 API 는 유지비가 0이 아니다.** 언젠가 누군가 "sync 스트림이 있네" 하고 쓰다가
  지연이 안 줄어드는 이유를 찾느라 시간을 쓴다.
- **async 가 이미 진짜다.** 없던 기능을 새로 만드는 게 아니라 **한쪽만 어긋난 것을 맞추는** 일이다.

## 4. 안전성 검증

디시플린 리뷰(2026-08-29)가 프로토타입으로 초안을 깨뜨렸다. 아래는 그 결과와 대응이다.

### 4.1 초안이 틀렸던 것 — `aclose()` 는 락을 풀지 않았다

초안은 `agen.aclose()` 를 "핵심 방어선" 이라 세 곳에 적었다. **틀렸다.**

async 제너레이터가 두 겹이다 — sync 래퍼가 잡는 것은 [`_events()`](../llm_manager/__init__.py#L291)
이고, 락을 푸는 `finally` 는 안쪽 [`_leader_stream`](../llm_manager/_internal/runner.py#L734) 에 있다.
`_events()` 에 `try/finally` 가 없어 바깥을 닫아도 안쪽이 안 닫힌다. 리뷰 프로토타입 출력:

```
aclose() 직후             released=False    ← 초안이 여기서 풀린다고 주장
shutdown_asyncgens() 후   released=True     ← 실제로는 여기서 풀렸다
```

초안대로 구현했다면 **부차적 정리라고 적어 둔 세 번째 줄이 유일한 방어선**이었을 것이다.
§3.1(가)가 `_events()` 에 `finally` 를 넣어 이것을 제자리로 돌린다.

> **구현 중 한 번 더 틀렸다.** §4.2 표에 "`next()` 0회는 `__del__` 이 막는다" 고 적었는데, 테스트를 쓰자마자 `assert [] == ['inner']` 로 깨졌다. 시작 안 된 async 제너레이터에는 실행할 `finally` 가 없다(PEP 525). **정리 계층을 글로 추론하면 두 번 다 틀렸고, 테스트가 두 번 다 잡았다** — 그래서 §5-8 처럼 "실제 해제 함수가 불렸는지" 로 단언하는 것이 중요하다.

### 4.2 위험별 대응

| 위험 | 대응 |
|---|---|
| `aclose()` 가 안쪽까지 안 닫아 **락 미해제** | §3.1(가) `_events()` 의 `finally` |
| **`next()` 0회**로 버려짐 | `__del__` 이 **루프는** 회수한다. **안쪽 정리(standby 해제)는 못 한다** — 시작 안 된 async 제너레이터엔 실행할 `finally` 가 없고(PEP 525), 락은 제너레이터 **바깥**에서 잡기 때문이다. **async 판과 동일**하며 테스트로 그 동등성을 고정했다(§5-3). 해소는 §7 |
| `aclose()` 가 던져 **뒤 정리가 날아감** (httpx teardown 등) | 중첩 `try/finally` — `loop.close()` 는 무조건 실행 |
| **준비 단계 예외**로 루프가 남음 | 진입부 `try/except BaseException: loop.close(); raise` |
| 일부 소비 후 방치 → 루프·executor 누적 | `__del__` 이 GC 시점에 회수 + 명시적 `close()` 를 계약으로 권장(§3.2) |
| mid-stream 예외 | `__next__` 가 `close()` 후 그대로 raise (리뷰 실측: 안전) |
| 캐시 히트 | chunk 1개짜리 스트림 — standby 토큰이 없어 누수 대상 아님 |
| executor 스레드 잔존 | `shutdown_default_executor()` — dedup 의 `to_thread` 때문에 필요 |

### 4.3 막지 못하는 것 — 정직하게 적는다

**인터프리터 종료 중에는 정리가 실패한다.** `release_standby` 가
[`await asyncio.to_thread(...)`](../llm_manager/_internal/file_processing/dedup.py#L405) 라
종료 시점에는 그 await 를 완료시킬 루프가 없다. 리뷰 실측에서 `RuntimeError: no running event loop`
가 `Exception ignored in:` 으로 삼켜졌다 — **로그에도 안 남아 운영에서 관측이 안 된다.**

**이것은 async 판도 같다.** 그래서 코드로 막지 않고 §3.2 의 계약과 §7 의 후속 항목으로 넘긴다.

### 4.4 재진입 — "동일한 제약" 이 아니다 (초안 정정)

초안은 "이미 돌고 있는 루프 안에서 호출하는 것은 지금 `asyncio.run` 판과 동일한 제약" 이라 했다.
리뷰가 두 차이를 실측했다.

- **에러 메시지가 다르다.** 현행 `asyncio.run() cannot be called from a running event loop`
  (함수명이 있어 진단이 쉽다) → 새 판 `Cannot run the event loop while another loop is running`.
- **현행은 루프를 만들기 전에 실패하지만, 새 판은 만든 뒤 실패한다.**

후자는 §3.1 진입부의 `try/except BaseException: loop.close()` 가 막는다. 전자는 남으므로
**docstring 에 "async 컨텍스트에서는 `_async` 판을 쓰라" 를 명시**한다.

## 7. 범위 밖

- **standby 획득 시점** — 락을 `_setup()` 이 아니라 **제너레이터 시작 시점**에 잡으면 §3.2 의 결함이
  코드로 해소된다. 다만 리더/대기자 판정·실패 기록·승격 순서가 모두 현재 시점 가정 위에 서 있고
  (`docs/31` 에 불변식이 정리돼 있다), 소비자 0인 경로를 위해 그 코드를 흔들 이유가 없다. **별건.**
- **인터프리터 종료 중 정리 실패** — §4.3. async 판도 같으므로 이 문서에서 코드로 막지 않는다.
- **`aio._get_client()` 싱글턴과 이벤트 루프 수명** — §2.5. 선재 위험이고 `llm_request`(논스트림
  sync)에도 똑같이 있다. 고치려면 프로세스 전역 워커 루프가 필요해 별건.
  단, 이 설계는 루프를 연 채 이터레이터를 돌려주므로 **살아 있는 두 루프에 싱글턴이 동시에 노출되는
  경우**(이터레이터 둘을 번갈아 소비)가 새로 가능해진다 — 리뷰 실측에서 파손은 재현되지 않았다(이론적).
- **`llm_request`(논스트림 sync)** — 전부 모으는 게 정상인 API 라 이 문서와 무관.
- **`runner.py` 의 죽은 sync 래퍼 둘** — `runner.llm_request_stream`(:740)·`runner.llm_request` 는
  소비자가 0이다(§2.4). 원래 죽어 있던 것이므로 **이 문서에 기록만 하고 코드는 건드리지 않는다.**
  공개 래퍼를 고치고 나면 "전부 모으는 sync 스트림" 이라는 잘못된 본보기가 남으므로 별건으로 정리 가치가 있다.
