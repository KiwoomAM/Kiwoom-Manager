> **완료**. Redis standby 레코드 방식 — files_api / context_cache / agent_llm 3계층 dedup. 후속으로 redis-handler v2.0.0 으로 정리 (메모리 폴백 동반).
> 본 문서는 2개 문서 (`08.cache-stampede-dedup` 설계, `15.redis-handler-v2-migration` 구현체 정리) 의 통합 기록본.

## Part A — 설계 (08)

### 1. 배경 / 문제

llm-request 는 비동기 서비스. agent 가 동일 요청을 동시 N건 보낼 수 있음 (`asyncio.gather`).

**시나리오**: cache miss 시 N 개 follower 가 동시에 같은 비싼 작업 (Files API 업로드 / Context Cache 생성 / LLM 호출) 을 N 회 실행 → 비용 + 시간 + Rate Limit 손실.

| 계층 | 피해 |
|---|---|
| Files API 업로드 | 같은 PDF N 회 업로드 → URI 캐시도 N 개 (Redis 충돌은 `cache_set` 가 막지만 작업 자체는 N 회) |
| Context Cache | N 회 cache 생성 → Gemini 측 N 개 cache 객체 생성, TTL 만료 시점 분산 |
| LLM 호출 | N 회 호출 → 토큰 비용 N 배 |

**현재 코드 dedup 상태**:

| 자리 | 메커니즘 | dedup |
|---|---|---|
| `cache_get/cache_set` | MongoDB upsert | ✅ 덮어쓰기는 방지 (작업 자체는 막지 못함) |

### 2. 해결 — Redis standby 레코드

**핵심 아이디어**:

- Leader: 첫 요청이 `SETNX` 로 standby 레코드 획득 → 비싼 작업 수행 → 본 캐시 저장 + standby 삭제
- Follower: standby 감지 시 exponential backoff 폴링 → 본 캐시 완료 시 결과 사용
- 적용: Files API 업로드 / context_cache / agent_llm (3 계층)

**standby 키 구조** (별도 prefix 블록):

| 키 | 용도 |
|---|---|
| `standby:files_api:{hash_key}` | Files API 업로드 dedup |
| `standby:context_cache:{hash_key}` | Context Cache 생성 dedup |
| `standby:agent_llm:{cache_key}` | LLM 호출 dedup |

### 3. standby 생명주기

```
SETNX standby_key TTL=10min      ← leader 만 성공
  ├─ 비싼 작업 수행
  ├─ 본 캐시 저장 (Files API URI / context_cache hash / MDB cache_key)
  └─ DEL standby_key              ← 정상 완료

예외 발생 시:
  └─ DEL standby_key (finally)    ← follower 가 stale 대기 안 하도록
```

### 4. 대기 방식 — Exponential Backoff 폴링

| 파라미터 | 디폴트 |
|---|---|
| `standby_ttl_seconds` | 600 (10분) |
| 초기 backoff | 0.5s |
| 최대 backoff | 5s |
| 폴링 timeout | `standby_ttl_seconds` 와 일치 |

**timeout 도달 시 (Y' Hybrid)**: leader 가 `standby_ttl` 내에 완료 못 함 → follower 가 자체 비싼 작업 진행. LLM 비결정성으로 두 호출자가 다른 응답 받을 수 있음 — README 안내.

### 5. 입력 인자

| 인자 | 위치 | 효과 |
|---|---|---|
| `standby_ttl_seconds` | 호출자 input (default 600) | dedup 보호 윈도우 |
| `cache_mode` | 기존 인자 | False 면 dedup 없음 (재실행 모드) |

### 6. 모듈 구조

| 파일 | 역할 |
|---|---|
| `service/app/logic/file_processing/dedup.py` (신규) | `try_acquire_standby`, `wait_for_result`, `release_standby` 등 standby API |
| `service/app/logic/file_processing/uploader.py` | Files API 업로드 dedup 진입점 |
| `service/app/logic/file_processing/context_cache.py` | Context Cache 생성 dedup |
| `service/app/logic/runner.py` | LLM 호출 dedup (`_run_with_dedup`) |

### 7. 에러 처리

| 시나리오 | 처리 |
|---|---|
| 작업 도중 예외 | `finally` 에서 `DEL standby_key` |
| `SETNX` 실패 (Redis 장애) | dedup 우회 — agent 직접 실행 (안전 fallback) |
| timeout 도달 (Y' Hybrid) | follower 가 자체 작업 진행, LLM 비결정성 README 안내 |

### 8. 동시성 한계 (README 안내)

- 첫 요청이 `standby_ttl_seconds` 내 완료 → follower 들 결과 공유 ✅
- 첫 요청이 `standby_ttl_seconds` 초과 → follower 들도 자체 호출 → 같은 입력에 다른 응답 가능 (LLM 비결정성)

## Part B — redis-handler v2.0.0 마이그레이션 (15)

### 1. 배경

**현재 상태**: `dedup.py` 가 redis-handler v1 의 raw `SETNX` / `GET` / `DEL` 직접 호출. v2.0.0 출시로 **메모리 폴백** 정책 도입 — Redis 장애 시 자동으로 in-memory dict 로 폴백.

**변화**:

| 메서드 | v1 | v2 |
|---|---|---|
| `RedisHandler().setnx(standby_key, ttl)` | Redis 만 | ✅ 메모리 폴백 |
| `RedisHandler().get(standby_key)` | Redis 만 | ✅ 메모리 폴백 |
| `RedisHandler().delete(standby_key)` | Redis 만 | ✅ 메모리 폴백 |

### 2. 의미론 변화 — "메모리 폴백" 의 함의

**시나리오 비교**:

| 시나리오 | v1 (Redis only) | v2 (Redis + 메모리 폴백) |
|---|---|---|
| Redis 정상 | ✅ 정상 dedup | ✅ 정상 dedup (동일) |
| Redis 장애 (단일 프로세스) | ❌ dedup 실패 → 모두 직접 실행 | ✅ in-memory dict 로 dedup 유지 |
| Redis 장애 (멀티 프로세스) | ❌ 동일 | ⚠️ 프로세스별 dedup — 다른 프로세스끼리는 dedup 안 됨 (차선) |

→ Redis 장애 시 동일 프로세스 내 동시 요청 보호는 유지됨.

### 3. 결정 — 하이브리드 마이그레이션

`dedup.py` 의 3 메서드 호출을 redis-handler v2 메서드로 교체. 의미론은 자연스럽게 메모리 폴백 흡수. 호출자 코드 변경 없음.

### 4. 변경 파일

| 파일 | 변경 |
|---|---|
| `service/app/logic/file_processing/dedup.py` | redis-handler v1 raw 호출 → v2 메서드 (`setnx` / `get` / `delete`) |
| `service/tests/logic/conftest.py` | 픽스처 재작성 (메모리 폴백 인지) |
| `service/tests/logic/test_dedup.py` | 영향 확인 (시그니처 동일, 동작 동일 — 폴백 시나리오 추가) |
| `service/pyproject.toml` | redis-handler 의존성 v2.0.0+ |

### 5. 운영 시나리오별 동작

| 시나리오 | dedup 동작 |
|---|---|
| Redis 정상, 단일 프로세스 N 동시 | ✅ leader 1 + follower N-1 |
| Redis 정상, 멀티 프로세스 | ✅ Redis 가 분산 leader 결정 |
| Redis 장애, 단일 프로세스 | ✅ in-memory dict 가 leader 결정 |
| Redis 장애, 멀티 프로세스 | ⚠️ 프로세스별 leader (차선 — 동일 프로세스 내는 보호) |

### 6. Task 결과 (Phase 1~4 모두 완료)

| Phase | 내용 | 결과 |
|---|---|---|
| 1 | redis-handler 의존성 버전 갱신 | ✅ |
| 2 | `dedup.py` 본체 정리 (하이브리드) | ✅ |
| 3 | 테스트 픽스처 재작성 | ✅ |
| 4 | 통합 검증 | ✅ |

호출자 코드 (`runner.py`, `uploader.py`, `context_cache.py`) 변경 없음 — dedup API 시그니처 그대로.
