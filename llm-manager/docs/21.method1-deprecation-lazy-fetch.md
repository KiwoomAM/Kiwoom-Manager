# 21. Method 1 폐기 + Lazy Fetch with Standby Dedup (Phase 3)

> Method 1 (data-mode `files=[FileInput(bytes)]`) 을 폐기한다. agent 가 file-manager 에 직접 등록 (`register_or_get` 헬퍼) 후 `file_path + 5 메타` 만 llm-request 에 전달. llm-request 는 lazy fetch — 실제 bytes 는 4·5단계 standby leader 만 가져온다 (기존 dedup 로직이 fetch 까지 자동 흡수).

---

## 1. 배경 / 문제 정의

### 1.1 Phase 1+2 의 한계

Phase 1+2 후 두 입력 모드 공존:
- **Method 1 (data-mode):** `files=[FileInput(bytes)]` — 호출자가 매 요청마다 bytes 전송
- **Method 2 (path-mode):** `stored_files=[StoredFile(file_path, 5 메타)]` — Phase 2 신설

운영 정책이 Method 1 위주였음. 다음 문제 발생:

1. **Agent 메모리 부족** — 같은 PDF 에 70 개 질문 시 70 × bytes 가 agent 메모리에 동시 적재 → 평가 진행 불가
2. **llm-request 메모리 폭발** — 70 동시 HTTP 요청이 70 × bytes 를 받음
3. **Phase 2 가 해결책이지만 미사용** — `stored_files` 가 있어도 agent 정책상 사용 안 함

### 1.2 Method 1 의 본질적 문제

Method 1 에서 llm-request 는 **HTTP 요청 받는 시점에 bytes 를 메모리에 적재** 해야 함. 후속 dedup (URI 캐시 / MDB 캐시) 가 hit 이어도 시점이 늦음.

→ **bytes 가 들어오는 그 순간이 병목.** Method 1 자체를 폐기해야 해결.

### 1.3 새 정책 — Agent 가 file-manager 직접 등록

```
[전 — Method 1]                          [후 — Phase 3]
Agent (bytes 70 회 메모리 적재)           Agent (bytes 1 회만 처리 후 release)
   │ 70 × bytes 전송                          │ file_manager.register_or_get(bytes, meta) 1 회
   │                                          │     → 6 필드 dict 받음 (file_path 포함)
   │                                          │ bytes release. file_path 만 자기 DB 보관
   ▼                                          │
llm-request                                   │ 70 × llm-request 호출 (file_path 만)
   │ register_files (매번 호출)                ▼
   │ bytes 70 × 적재                       llm-request
                                              │ resolve_stored_files (lazy, fetch X)
                                              │ 4·5단계 standby leader 만 fm.get_file (1 회)
```

→ **agent 메모리 0, llm-request fetch 1 회.**

## 2. 사전 정보

### 2.1 file-manager SDK API

기존 (Phase 1+2 사용):
- `check_cache(meta_hashing_3)` → `{hit, file_path}`
- `upload_file(bytes, meta_5)` → file_path
- `get_file(file_path)` → `(bytes, metadata_6)`
- `build_metadata(local_path)` → metadata_5

**Phase 3 신설:**
- `register_or_get(bytes, meta_5) → metadata_6 dict` — `check_cache` → miss 면 `upload_file` 합성 헬퍼

### 2.2 기존 dedup 메커니즘 — fetch 까지 자동 흡수

[dedup.py](packages/llm-request/service/app/logic/file_processing/dedup.py) 의 `try_acquire_standby` 가 Redis SETNX 기반 leader 1 명 / waiter N-1 명 분리. `resolver.py::_upload_and_cache_file` 이 이 패턴 사용 중.

Phase 3 변경: leader 분기에 fetch 한 줄 추가.

```python
# Phase 3 변경 (한 줄)
if acquired:  # leader (단 1 명)
    if not fi.data:
        fi.data, _ = await fm.get_file(fi.file_path)  # ← 추가
    upload_to_gemini(fi.data) → URI 캐시
```

→ 70 동시 요청에서 leader 1 명만 fetch + upload, waiter 69 명은 wait + URI 받아 사용. **fetch 1 회만 발생.**

### 2.3 inline / Files API 분기

[validators.py](packages/llm-request/service/app/logic/file_processing/validators.py) 의 mime/size 한도가 분류:
- inline: image/audio 합 ≤20MB 또는 PDF/text 합 ≤50MB
- Files API: 위 한도 초과

Phase 3 의 lazy fetch:
- inline 분기 (`_process_inline`): `Part.from_bytes` 가 bytes 직접 사용 → 시점에 lazy fetch
- Files API 분기 (`_upload_and_cache_file`): standby leader 만 lazy fetch

inline 가는 작은 파일은 동시 fetch 발생 가능하지만 작은 파일 (수 MB) 이라 메모리 부담 작음. dedup 추가는 YAGNI.

### 3.2 file-manager SDK 신설 — `register_or_get`

```python
# packages/file-manager/sdk/file_manager/handler.py
async def register_or_get(
    self,
    bytes_data: bytes,
    metadata: dict,  # 5 필드: file_name, file_size, file_mtime, mime_type, extension
) -> dict:
    """check_cache → miss 면 upload_file → 6 필드 dict 반환.

    Returns:
        {file_name, file_size, file_mtime, mime_type, extension, file_path}
        — agent 가 그대로 StoredFile(**result) 로 변환해 llm-request 호출 가능.
    """
    hash_meta = {k: metadata[k] for k in ("file_name", "file_size", "file_mtime")}
    result = await self.check_cache(hash_meta)
    if result["hit"]:
        file_path = result["file_path"]
    else:
        file_path = await self.upload_file(bytes_data, metadata)
    return {**metadata, "file_path": file_path}
```

별도 PR (file-manager 패키지) 로 진행. llm-request Phase 3 와 병행 가능.

### 3.3 결정 사항

| # | 결정 | 결과 | 근거 |
|---|------|------|------|
| D1 | Method 1 vs Method 2 | **Method 1 폐기, Method 2 만 유지** | agent 메모리 / llm-request 메모리 동시 해결 |

### 5.4 `file_resolver.py::resolve_stored_files` lazy 화

```python
# Phase 3
async def resolve_stored_files(refs: list[StoredFile]) -> list[FileInput]:
    """validators 진입 즉시 + FileInput(data=b"") 만 생성 (fetch X)."""
    placeholder_inputs = [
        FileInput(
            file_name=ref.file_name,
            file_size=ref.file_size,
            file_mtime=ref.file_mtime,
            mime_type=ref.mime_type,
            extension=ref.extension,
            data=b"",
            file_path=ref.file_path,

    validate_file_sizes(placeholder_inputs)
```

### 5.5 `resolver.py::_process_inline` lazy fetch 추가

```python
# Phase 3 변경 — bytes 비었으면 fetch
async def _process_inline(...):
    fm = FileManagerHandler()
    for fi in inline_files:
        if not fi.data:                # 정상 흐름에선 항상 빈 상태. 가드 의도는 §5.5 주석 참고
            try:
                fi.data, _ = await fm.get_file(fi.file_path)
            except FMServiceError as e:
                if e.status_code == 404:
                    fi.data, _ = await _fetch_with_check_cache_fallback(fm, fi)
                else:
                    raise
        part = Part.from_bytes(data=fi.data, mime_type=fi.mime_type)
        ...
```

> **`if not fi.data:` 가드의 의도:** 정상 흐름은 항상 fi.data 빈 상태로 진입 (file_resolver 가 `data=b""` 로 placeholder 만 만들기 때문). 다만 **404 자동 복구 경로** (`resolve_files_after_404` → `resolve_files` 재호출) 에서 첫 호출 시 fetch 한 bytes 가 fi.data 에 남아있음 → 가드가 두 번째 호출의 재fetch 방지. 한 줄짜리 안전망이라 유지.

### 5.6 `resolver.py::_upload_and_cache_file` lazy fetch 추가

```python

async def _upload_and_cache_file(fi, checksum, ...):
    fm = FileManagerHandler()
    acquired = await dedup.try_acquire_standby("files_api", checksum, ttl)
    if acquired:
```

### 5.7 404 fallback 헬퍼

Phase 2 의 `_resolve_one` 안 fallback 로직을 공통 헬퍼로:

```python
# file_resolver.py 또는 별도 위치
async def _fetch_with_check_cache_fallback(fm, fi: FileInput) -> tuple[bytes, dict]:
    """get_file 404 → check_cache 로 새 path 찾기 → 재 fetch.

    miss 시 FileResolveError raise. resolved_via 를 'fallback' 으로 갱신.
    """
    cache = await fm.check_cache({
        "file_name": fi.file_name,
        "file_size": fi.file_size,
        "file_mtime": fi.file_mtime,
    })
    if not cache["hit"]:
        raise FileResolveError(
            f"file_path '{fi.file_path}' not found, check_cache miss"
        )
    new_path = cache["file_path"]
    logger.warning("[Phase3] stale file_path: input=%s, resolved=%s", fi.file_path, new_path)
    fi.file_path = new_path
    fi.resolved_via = "fallback"
    return await fm.get_file(new_path)
```

## 6. 에러 처리

### 6.1 Lazy fetch 의 404 처리

`_process_inline` / `_upload_and_cache_file` 에서 `fm.get_file` 호출 시 404:
- `_fetch_with_check_cache_fallback` 헬퍼로 분기 (§5.7)
- check_cache hit → 새 file_path 로 재시도 + WARN log + `resolved_via="fallback"`
- check_cache miss → `FileResolveError` raise (502, 'file_resolve')

### 6.2 호환성 매트릭스

| | 옛 SDK (`files` 사용) | 새 SDK (`stored_files` 만) |
|---|---|---|
| **옛 Service** (`LLMRequestBody.files` 살아있음) | ✅ 정상 (Phase 2 그대로) | ✅ 정상 |
| **새 Service** (`files` 제거 + extra="forbid") | ❌ ValidationError (silent drop 방지) | ✅ 의도된 동작 |

→ **옛 SDK + 새 Service 는 깨짐.** 이건 의도된 — Method 1 폐기 명시. agent 측이 `register_or_get` + `stored_files` 로 마이그레이션 필수.

→ 운영: SDK + Service + agent 코드 **3 측 동시 배포** 필요. agent 마이그레이션 미완료 시 전환 시점 문제 발생.

## 8. 사용 예시

### Agent 측 코드 (ESG)

```python
from file_manager import FileManagerHandler
from llm_request import StoredFile, llm_request_async

fm = FileManagerHandler()

# 1. 첫 호출: bytes + meta → register_or_get → 6 필드 dict
with open("report.pdf", "rb") as f:
    bytes_data = f.read()
meta = fm.build_metadata("report.pdf")
sf_dict = await fm.register_or_get(bytes_data, meta)
del bytes_data  # bytes release — agent 메모리 회수

# 2. agent DB 에 sf_dict 저장 (이후 70 회 질문에 재사용)
db.evaluations.insert_one({"file_meta": sf_dict})

# 3. llm-request 70 회 호출 (file_path + 5 메타만 전송)
ref = StoredFile(**sf_dict)
for question in QUESTIONS_70:
    response, _ = await llm_request_async(
        {"contents": question, "model": "gemini-2.5-flash"},
        stored_files=[ref],
    )
    print(response.text)
```

### 동시 호출 (asyncio.gather)

```python
ref = StoredFile(**sf_dict)
tasks = [
    llm_request_async(
        {"contents": q, "model": "gemini-2.5-flash"},
        stored_files=[ref],
    )
    for q in QUESTIONS_70
]
results = await asyncio.gather(*tasks)
# llm-request 측: leader 1 명만 fm.get_file → upload, 69 명은 wait → URI 공유
```

## Appendix — 결정 근거 요약

### 왜 lazy fetch 가 자연스러운가

기존 `_upload_and_cache_file` 의 standby 가 Files API upload dedup. Phase 3 는 **그 leader 분기에 fetch 한 줄만 추가**. dedup 메커니즘 재설계 X — 70 동시 요청에서 leader 1 명만 fetch 하는 게 자동 보장.

### 왜 inline 분기는 dedup 추가 안 하는가

inline 가는 파일은 mime/size 한도상 작음 (개별 ≤ 20MB / ≤ 50MB). 70 동시 fetch 해도 메모리 부담 작음. dedup 추가 시 복잡도 증가 대비 이득 작음. **YAGNI.**

### 왜 Method 1 즉시 폐기인가 (deprecate 안 하고)

사용자 요구: "Method 1 파기" 명시. deprecate 후 일정 기간 유지 시 운영 정책상 Method 1 계속 사용됨 → 메모리 문제 안 풀림. **즉시 제거 + agent 마이그레이션 필수** 가 효과적.
