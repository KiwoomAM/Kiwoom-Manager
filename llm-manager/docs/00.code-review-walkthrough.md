# Code Review Walkthrough

llm-manager 패키지 전체 코드 리뷰 요약. 파일별 역할 + 설계 의도 + 핵심 개념.

---

## 전체 흐름도

### 요청 → 응답 (단일 요청)

```
[Agent]
  llm_request_async(llm_input, file_paths=[...])
      │
      ├─ checksum 계산 (로컬, SHA-256)
      ├─ ≤20MB → inline (base64)
      │  >20MB → Redis 조회 → miss면 /v1/files 업로드
      └─ POST /v1/request
           │
[Service: routers/request.py]  ← JSON → Python 변환만
           │
[runner.py: llm_request_async()]
           │
           ├─ register_files()          file-manager에 등록 (check_cache → aupload_file)
           ├─ validate_mime_types()   Gemini 지원 타입 화이트리스트
           ├─ validate_file_sizes()   2GB 초과 차단
           │
           ├─ prepare()
           │     ├─ make_file_checksum() × N   file_name+size+mtime → SHA-256
           │     ├─ canonicalize_input()        volatile 키 제거 + 정규화
           │     ├─ make_cache_key()            SHA-256 → cache_key
           │     └─ done_check() → MDB 조회
           │           HIT → cached_output 반환 (즉시 종료)
           │           MISS → _Prepared(cached_output=None)
           │
           ├─ [cache HIT] → return cached_output
           │
           ├─ dedup.try_acquire_standby("agent_llm", cache_key)
           │     acquired=True  (leader)  → _do_llm_call()
           │     acquired=False (waiter)  → wait_for_standby_release()
           │                                    HIT  → return cached
           │                                    MISS/timeout → _do_llm_call()
           │
           └─ _do_llm_call()
                 │
                 ├─ _build_server_call_input()
                 │     └─ resolve_files()
                 │           ├─ classify_files()      video/inline/files_api 분류
                 │           ├─ _process_inline()     bytes → Part 변환
                 │           └─ _process_files_api()
                 │                 A. context_cache HIT (Redis)
                 │                 B. files_api HIT (Redis)
                 │                 C. MISS → dedup → 업로드 → Redis 저장
                 │                 ④ context_cache 생성
                 │
                 ├─ _apply_resolved()
                 │     inline_parts + uri_parts + text → contents 재조립
                 │     file_checksums 제거
                 │
                 ├─ aio_call(**call_input)   LLM 호출
                 │     Gemini 404 → resolve_files_after_404() → 1회 재시도
                 │
                 └─ finalize()
                       save_result() → MDB 저장
                       return (LLMResponse, meta)
```

## 파일별 역할 + 설계 의도

---

### SDK

---

#### `__init__.py` — Public API + Singleton

외부에서 `from llm_manager import llm_request_async` 로 쓸 수 있는 진입점.

**Singleton 패턴** (`_instance`):
```python
_instance: AsyncClient | None = None

def _get_client() -> AsyncClient:
    global _instance
    if _instance is None:
        _instance = AsyncClient(base_url=_resolve_base_url())
    return _instance
```
HTTP 클라이언트를 한 번만 만들고 재사용한다. 매 요청마다 새로 만들면 TCP 연결 비용이 반복 발생하므로, 모듈 레벨에 `_instance`로 보관하고 처음 호출 시에만 생성한다. `global` 키워드는 함수 안에서 모듈 레벨 변수를 수정할 때 필요하다 — 없으면 Python이 지역 변수로 착각해서 `UnboundLocalError`가 난다.

**`__all__`**: `from llm_manager import *` 했을 때 노출할 이름 목록. 명시하지 않으면 `_`로 시작하지 않는 것이 전부 노출된다.

---

#### `_client.py` — HTTP 클라이언트

두 함수의 역할 구분:
- `_request()` — 서버 연결 자체를 다룬다. 연결 실패(`ConnectError`) → `ServiceConnectionError`, HTTP 4xx/5xx → `ServiceError`. 모든 엔드포인트가 공통으로 거치는 레이어.
- `request()` — 엔드포인트별 body 조립. 어느 URL에 무엇을 보낼지 결정하고 `_request()`를 호출한다.

**엔드포인트**: 서버가 열어놓은 "출입구". `/v1/request`, `/v1/done-check` 등. 서버가 정의하고 클라이언트(SDK)가 찾아간다.

**body**: HTTP 요청의 "편지 내용". URL + method + body가 HTTP 요청의 3요소. 서버 간 통신은 body를 JSON으로 직렬화해서 보내는 게 사실상 표준 — `httpx`에서 `json=body`로 넘기면 자동 변환 + `Content-Type: application/json` 헤더도 붙는다.

---

#### `exceptions.py` — 예외 계층

```
SDKError(Exception)
    ├── ServiceConnectionError   # 서버에 연결조차 못 한 경우 (status=0)
    └── ServiceError             # 연결은 됐지만 서버가 에러 반환 (status 필수)
```

`ServiceConnectionError`는 `status=0`이 기본값 — 연결 실패는 HTTP status 코드 자체가 없으므로. `ServiceError`는 `status`가 필수 파라미터 — 서버가 응답을 줬으니 반드시 있다.

---

#### `models.py` — SDK 타입

`ResponseResult`, `DoneCheckResult`는 **TypedDict**. Pydantic `BaseModel`과 다르게 런타임 검증을 하지 않고 타입 힌트만 제공한다. SDK 내부 반환 타입이라 외부에서 직접 쓰는 용도가 아니다 — `__init__.py`의 `__all__`에 포함되지 않은 이유.

---

#### `aio.py` — Re-export

`llm_handler.aio`의 함수들을 `llm_manager.aio`로 그대로 내보내는 파일. 로직이 전혀 없다.
```python
from llm_handler.aio import create_cache, upload_file  # noqa: F401
```
`# noqa: F401` — "imported but unused" 린터 경고 억제. re-export가 목적이라 함수를 직접 쓰지 않아도 의도적으로 import한 것임을 표시.

---

### Service

---

#### `config.py` — 환경변수 설정

`pydantic-settings`의 `BaseSettings` 상속. 코드에 기본값이 있고, `.env` 파일이나 환경변수로 덮어쓸 수 있다. 운영 환경에서는 환경변수로 주입하고, 로컬에서는 기본값(`192.7.9.45`)으로 동작.

---

#### `main.py` — FastAPI 앱

**lifespan**: 서버 시작/종료 시 실행되는 코드. `configure_handlers()`를 여기서 호출해서 MDB/Redis/LLM-handler 연결을 초기화한다.

**미들웨어**: 모든 요청이 통과하는 레이어. 웹 프레임워크 미들웨어(request_id 부여, 로깅)로, 기업 시스템의 "미들웨어 서버"와는 다른 개념.

**에러 핸들러**: `LLMManagerError` 잡아서 JSON 에러 응답으로 변환. FastAPI가 자동으로 잡지 못하는 커스텀 예외를 처리.

---

#### `routers/request.py` — 얇은 라우터

라우터는 JSON↔Python 변환 + runner 위임만 한다. 비즈니스 로직이 없는 이유: 테스트/재사용성. runner.py는 HTTP 없이도 직접 호출할 수 있어서 테스트가 쉽다.

HTTP body가 JSON인 이유: API 서버끼리 통신할 때 JSON이 사실상 표준. FastAPI는 Pydantic 모델을 선언하면 자동으로 JSON 파싱 + 검증을 해준다.

---

#### `core/errors.py` — 서비스 에러 계층

```
LLMManagerError
    ├── CacheError(502)              # MDB/Redis 장애
    ├── FileUploadError(502)         # file-manager 업로드 실패
    ├── ValidationError(422)         # 일반 입력 오류
    ├── UnsupportedFileTypeError(422) # 지원 안 하는 MIME
    └── FileTooLargeError(422)       # 2GB 초과
```

502는 "상류 서버 문제" — llm-manager 자체 문제가 아니라 의존 서비스(MDB, file-manager) 장애임을 클라이언트에게 알린다.

---

#### `core/providers.py` — 연결 초기화

`configure_handlers()`가 환경변수를 세팅하고 MDB/Redis/LLM-handler 연결을 초기화한다. 서버 시작 시 `lifespan`에서 1회만 호출. stale standby 키도 여기서 정리한다.

---

#### `logic/types.py` — 중립 타입

`FileChecksum` TypedDict 하나만 있는 파일. 존재 이유: **순환 import 방지**. `resolver.py`와 `runner.py`가 서로를 import하면 순환이 생기는데, 공유 타입을 중립 파일에 두면 둘 다 `types.py`만 import하면 된다.

---

#### `logic/keying.py` — 캐시 키 생성

**캐시 키 구성 원칙**:
- `file_checksums` → 포함 (파일 동일성의 핵심)
- `cached_content`, `file_uri` → 제외 (매 호출마다 달라지는 volatile 값)

`canonicalize_input()`: volatile 키 제거 → 키 정렬 → float 반올림 → JSON 직렬화. 같은 입력이 항상 같은 문자열이 되도록 결정론적으로 만든다.

`make_file_checksum()`: `file_name + file_size + file_mtime`으로 계산 — 파일 내용 bytes 없이도 동일성 판단 가능.

---

#### `logic/done_check.py` — MDB 캐시 조회

`canonicalize → SHA-256 → MDB 조회` 를 묶은 함수. `lookup_cache=False`면 키만 생성하고 조회는 생략 (save_mode=True인데 cache_mode=False일 때).

MDB 조회 실패 시 `cache_error=True`만 세팅하고 LLM 직접 호출로 fallback — 캐시 장애가 서비스 장애로 이어지면 안 되기 때문.

---

#### `logic/store.py` — MDB CRUD

`save_result()`: `_id=cache_key`로 저장. TTL이 있으면 `expires_at`도 계산해서 저장.

`cache_get()`: `_id`로 find_one. None이면 MISS.

---

#### `logic/file_register.py` — file-manager 등록

file-manager에 파일을 등록하는 **side-effect 전용** 함수. `return inputs`로 입력 그대로 반환 — file-manager에서 새로운 식별자를 받아서 FileInput을 변경하지 않는다. 파이프라인은 이후에도 원래 `FileInput`으로 계속 흐른다.

hashing 3필드(`file_name`, `file_size`, `file_mtime`)로 존재 확인 → 없으면 bytes + 5필드로 업로드.

---

#### `logic/runner.py` — 전체 흐름 조율

**`prepare()`** (sync 함수):
LLM 호출 전까지의 준비. sync인 이유: mdb-handler가 내부적으로 sync 클라이언트를 사용. 실제 병목은 이후 `_do_llm_call`(파일 업로드 + LLM 호출)이고 MDB 조회는 수십ms 수준.

prepare의 4가지 분기:
1. `cache_mode=F, save_mode=F` → MDB 조회 불필요, 바로 반환
2. `cache_mode=F, save_mode=T` → 저장용 키만 생성 (`lookup_cache=False`)
3. `cache_mode=T, HIT` → `cached_output` 채워서 반환
4. `cache_mode=T, MISS` → `cached_output=None`으로 반환

**`_apply_resolved()`**:
`contents = resolved.inline_parts + resolved.uri_parts + text_contents` — **파일 파트 먼저, 텍스트 나중**. Gemini 권장 순서. `file_checksums`는 캐시 키 계산용이었으니 Gemini에 넘기기 전에 반드시 제거.

**`finalize()`**:
MDB 저장 실패해도 예외를 삼키고 `(LLMResponse, meta)` 정상 반환 — 저장 실패가 응답 실패로 이어지면 안 된다.

**`_do_llm_call()`**:
Gemini 404 → `_is_gemini_404()`로 메시지 기반 판정 (llm-handler가 정확한 예외 타입을 노출 안 해서 보수적 방법) → Redis 무효화 + 재업로드 + 1회만 재시도.

**`agent_llm` dedup**:
```python
acquired = await dedup.try_acquire_standby("agent_llm", cache_key, standby_ttl_seconds)
if acquired:  # leader
    try:
        return await _do_llm_call(prep, database)
    finally:
        await dedup.release_standby("agent_llm", cache_key)  # 성공/실패 무관 제거

# waiter
cached = await dedup.wait_for_standby_release(
    "agent_llm", cache_key, standby_ttl_seconds,
    find_cache_fn=lambda: _recheck_agent_llm_cache(prep, database),  # MDB 재조회
)
```

#### `logic/file_handler/validators.py` — Fail-fast 검증

runner 진입 직후 실행 — prepare/MDB 조회 이전에 명백히 잘못된 입력을 차단.
- `SUPPORTED_MIME_TYPES`: `frozenset` — 불변 집합, `in` 검사가 O(1)
- 2GB 초과: Files API 제한 (inline/Files API 어느 경로로도 처리 불가)

---

#### `logic/file_handler/resolver.py` — 파일 처리 조율

**`classify_files()`**: 비디오는 무조건 Files API. 나머지는 크기순 정렬 후 20MB 누적까지 inline, 초과분은 Files API.

**`_process_inline()`**: `FileInput.data`(bytes)를 그대로 Part로 변환. file-manager 거치지 않고 bytes 직접 사용.

**`_process_files_api()`** 분기:
- A: context_cache Redis HIT → `cached_content` name 반환
- B: files_api Redis HIT → URI 반환
- C: MISS → `dedup.try_acquire_standby` → leader면 업로드 + Redis 저장, waiter면 대기
- ④: context_cache 대상 파일들로 `create_context_cache()` 호출

**`resolve_files()`**:
`context_cache_ttl`이 있고 파일이 전부 inline 크기면 Files API로 업그레이드 — context cache는 Files API URI가 필요하기 때문.
`asyncio.gather`로 파일들을 병렬 처리.

**`resolve_files_after_404()`**:
Gemini 404 발생 시 Redis 캐시 무효화 후 `resolve_files` 재호출. 강제로 재업로드하도록 Redis 삭제 먼저.

---

#### `logic/file_handler/cache_store.py` — Redis CRUD

```
BaseJsonStore (redis-handler 제공)
    └── FileCacheStore (prefix="file_cache")
```

`_make_key("files_api", checksum)` → `"file_cache:files_api:{checksum}"`.
prefix는 **네임스페이스** — 다른 패키지와 Redis 키 충돌 방지.

**본 캐시 vs standby 키 구조**:
- 본 캐시: `file_cache:files_api:{checksum}`
- standby: `file_cache:files_api_standby:{checksum}`
같은 `file_cache:` 네임스페이스를 공유하되 `_standby` suffix로 구분.

**`compute_files_api_ttl()`**: Gemini가 반환하는 실제 만료 시각 기반으로 Redis TTL 동적 계산. 1시간 buffer를 빼서 Redis가 Gemini보다 먼저 만료되도록 — stale URI 반환 방지.

---

#### `logic/file_handler/dedup.py` — Cache Stampede 방지

**Exponential Backoff 파라미터**:
```python
_BACKOFF_INITIAL = 0.5    # 첫 대기 0.5초
_BACKOFF_MULTIPLIER = 2.0 # 매 루프마다 2배
_BACKOFF_CAP = 10.0       # 최대 10초
# 실제 시퀀스: 0.5 → 1 → 2 → 4 → 8 → 10 → 10 → ...
```
처음엔 빠르게 확인(업로드가 금방 끝날 수도 있으니까), 오래 걸리면 점점 느리게(Redis poll 비용 감소).

**`try_acquire_standby()`**:
`client.set(standby_key, value, nx=True, ex=ttl_seconds)` — `nx=True`가 SETNX. Redis 레벨에서 atomic하게 처리되어 동시에 N개 요청이 와도 하나만 `True`를 받는다.
value에 `{"started_at": "..."}` 저장 — 언제 꽂았는지 디버깅용.

**`wait_for_standby_release()`** 루프 순서:
1. `asyncio.sleep(delay)` 대기
2. `find_cache_fn()` 호출 → HIT이면 즉시 반환 (이미 앞사람 성공)
3. `client.get(standby_key)` → None이면 `return None` (앞사람 실패 → 내가 시작)
4. delay 증가

standby 키가 사라졌을 때 `None` 반환하는 이유: 직전 루프에서 캐시 MISS를 확인했으니 "캐시도 없고 standby도 없다" = 앞사람이 실패했다는 의미 → 내가 다시 시작.

**`release_standby()`**: `finally` 블록에서 호출. 성공/실패 무관하게 항상 깃발 제거. 예외 삼킴 — Redis 장애 시에도 TTL로 자연 정리되므로 호출자 흐름을 막으면 안 된다.

#### `logic/file_handler/uploader.py` — Gemini 업로드

**`upload_pdf_parts()`**:
`split_pdf()` 후 각 파트 순차 업로드. `finally`에서 임시 파일 삭제 — 성공/실패 무관하게 보장. `part_path != path` 조건으로 원본 파일은 건드리지 않는다.

**`create_context_cache()`**:
재시도 대상 키워드: `("500", "503", "429", "RESOURCE_EXHAUSTED")` — 서버 일시 오류나 rate limit만 재시도. 400, 422 등은 재시도해봤자 의미 없으므로 바로 raise. 최대 3번 시도, 재시도 간격 5초.

계층 정리:
```
resolver.py          ← 전체 흐름 조율
    └── uploader.py
            ├── upload_pdf_parts()      ← Gemini에 파일 올리기
            └── create_context_cache() ← 올린 파일로 cache 생성 (가장 작은 단위)
                    └── llm_handler.aio.create_cache() ← Gemini API 직접 호출
```

#### `logic/file_handler/splitter.py` — PDF 분할

**왜 분할 후 다시 병합하나?**

`_estimate_page_sizes()`의 추정이 실제보다 작게 나오는 경향이 있다. PDF에는 페이지 콘텐츠 외에 문서 전체에 공유되는 데이터(폰트 임베딩, cross-reference 테이블, 문서 카탈로그)가 있는데, 이를 페이지별로 나눠 추정하면 실제 분할 후 파트 크기가 추정보다 작아진다. 결과적으로 28MB, 19MB, 22MB처럼 과하게 쪼개지는 경우가 생기고, 병합 후처리로 45MB 범위 내에서 합쳐서 업로드 횟수를 줄인다.

**`split_pdf()`**:
- `_depth` 파라미터: `*` 뒤 키워드 전용 + `_` prefix → "외부에서 쓰면 안 된다"는 의미
- 분할 후 실제 크기(`os.path.getsize`) 재확인 → 여전히 초과면 재귀 재분할 (최대 3회)
- `garbage=4, deflate=True` — 불필요 객체 제거 + 압축 저장
- `delete=False` — 임시 파일을 닫아도 삭제하지 않음. 호출자(uploader)가 업로드 후 직접 삭제할 책임.
- 병합 상한을 50이 아닌 45MB로 설정한 이유: `insert_pdf` 후 크기가 약간 늘어날 수 있어서 여유를 둠.

## 핵심 설계 원칙

### 에러 처리 일관성
| 상황 | 처리 |
|------|------|
| MDB 저장 실패 | 예외 삼킴, 응답은 정상 반환 |
| MDB 조회 실패 | `cache_error=True`, LLM 직접 호출 fallback |
| Redis standby release 실패 | 예외 삼킴, TTL로 자연 정리 |
| Gemini 404 | Redis 무효화 + 재업로드 + 1회 재시도 |
| create_cache 500/503/429 | 5초 대기 후 최대 3회 재시도 |

원칙: **캐시/저장 장애가 서비스 장애로 이어지면 안 된다.**

### Dedup 3계층 공통 패턴
```
layer       저장소   standby 키
files_api   Redis    file_cache:files_api_standby:{checksum}
context_cache Redis  file_cache:context_cache_standby:{hash_key}
agent_llm   MDB      agent_llm_standby:{cache_key}
```
저장소만 다르고 패턴(SETNX → leader/waiter → exponential backoff → Y' Hybrid)은 동일.

### Context Cache 조건
- `context_cache_ttl` 명시 시에만 생성 (opt-in)
- 캐시 키: `file_checksums + model + system_instruction`
- tools를 키에서 제외하는 이유: Gemini 설계상 tools는 context cache에 포함할 수 없고, call 시점에 별도로 전달된다
- 같은 파일 시간당 4회 이상 호출 시 권장
