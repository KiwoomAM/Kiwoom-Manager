# Files API 보관 vs Context Cache 수명 — 사실 정리

> 제3자 관점 · 사실 기반 기록. §1–7은 사실·두 입장·미확인 항목을 정리하고, §8에 현 시점
> 잠정 방향을 덧붙인다(확정 아님). 코드 변경은 아직 없다. (상태: 미결정, 잠정 방향 = 단순성 우선)

---

## 1. 쟁점

1. **Files API 파일을 context cache 생성 직후 즉시 삭제할지, 48h 두고 재사용할지.**
2. (1과 얽힘) **Context Cache TTL을 길게 연장(renew)할지, 짧게 두고 필요 시 재빌드할지.**

(2)는 (1)의 상위 항목이다 — context cache 수명 정책에 따라 Files API 보관 가치가 달라진다.

---

## 2. 사실 — Gemini 동작·과금

### 2.1 Files API

- 저장 자체는 **무과금**. 48h 후 자동 삭제. 프로젝트당 **20GB**, 파일당 2GB 한도.
- 20GB는 **하드 캡 + fail-closed** — 초과 시 새 업로드가 실패한다(그 시점 업로드가 필요한 요청이 깨짐).
- 업로드에 드는 것은 돈이 아니라 latency/대역폭이며, 최초 1회 발생한다.

### 2.2 Context Cache 독립성

- Context Cache는 생성 시점에 파일 내용의 토큰화 결과를 자기 복사본으로 보유한다.
  → 생성 후 원본 Files API 파일을 삭제해도 캐시는 유효하다.
- 코드도 이 전제로 동작한다: context_cache HIT이면 `uri_parts=[]`로 반환하고 LLM 호출에 Files API URI를 넣지 않는다 (`resolver.py` 분기 A, `runner._apply_resolved`).

### 2.3 Context Cache 과금

[공식 문서](https://ai.google.dev/gemini-api/docs/caching) · [pricing](https://ai.google.dev/gemini-api/docs/pricing):

- Gemini Developer API에는 **별도 생성 수수료가 없다.** 과금은 두 가지다:
  1. 사용 시 캐시 토큰 할인 요금 — 캐시를 낀 호출마다 그 토큰을 할인가로 과금.
  2. 저장료 = TTL 시간 × 캐시 토큰 수 × 시간당 단가.
- 단가 (Standard):
  | 모델 | 캐시 input | 저장료 |
  |---|---|---|
  | 2.5 Flash | $0.03 / 1M (text/img/video), $0.1 (audio) | $1.00 / 1M tokens / hour |
  | 2.5 Pro | $0.125 / 1M (≤200k), $0.25 (>200k) | $4.50 / 1M tokens / hour |
  - 캐시 input은 표준 input 대비 큰 할인이다(Flash 기준 약 1/10 수준).
- Default TTL = 1시간. `"300s"` 등 sub-hour 설정이 가능하다.
- 저장료는 **"설정한 TTL" 기준**이다(wall-clock 실사용 시간이 아님). thread #81267 (Google staff Pannaga_J), docs/20.context-cache-expire.md §2:
  | 동작 | 청구 |
  |---|---|
  | `caches.delete` | 원래 TTL 그대로 청구 — 조기 삭제해도 절감 0 |
  | `caches.update(ttl=짧게)` | 줄인 TTL로 재청구 — 절감됨 |
  - 1시간 floor는 없다. sub-hour TTL은 sub-hour로 청구된다.
  - 절감은 처음부터 짧게 set 하거나 세션 끝에 `update`로 단축해야 실현된다(`delete`로는 안 됨). 후자가 기존 `delete_cache` / `/v1/context-cache/expire`에 해당한다.
  - granularity(초 vs 분)는 thread #81267에 명시가 없다. docs/20은 "분 단위 prorate"로 기술하나 출처 미확정 추정이다. 어느 쪽이든 sub-hour다.

### 2.4 과금에서 따라오는 산술적 함의

- 생성비가 0이므로, renew(연장)와 rebuild(재빌드)의 금전 차이는 **설정 저장 시간**에서만 발생한다.
  - renew: idle 구간 포함 저장료 발생.
  - rebuild(짧은 TTL): 활성 구간만 저장료 발생.
  - 따라서 idle이 있으면 rebuild의 저장료가 renew보다 작거나 같다.
  - 단 청구가 *설정 TTL* 기준이므로, 절감은 짧게 set 하거나 세션 끝에 `update`로 단축할 때만 실현된다.
- rebuild의 비-금전 비용은 latency다 — 만료 후 첫 호출에서 cache 재생성 stall. Files API가 살아 있으면 재업로드는 면제된다(무과금).
- Files API는 무과금이므로 즉시 삭제해도 금전 절약은 0이다. 삭제로 얻는 것은 ① 20GB 캡 회피, ② 운영 상태 단순화(§5)다.

## 3. 사실 — 현 시스템 동작 (코드)

- 존재 확인 순서: MDB(LLM 응답) → Redis context_cache → Redis files_api. 생성 순서(files_api 업로드 → context cache 생성 → LLM call)의 역순.
- MDB 키 vs context_cache 키: MDB는 질문(contents)+파일 checksum까지 포함 → "같은 질문+같은 파일"이어야 HIT. context_cache는 파일 checksum+model+system+tools만 → 질문 무관. ∴ "같은 파일, 다른 질문"은 MDB miss / context_cache HIT.
- checksum dedup: 같은 파일은 1회만 업로드, Redis HIT(~47h)으로 재사용. 저장량은 유저 수가 아니라 유니크 파일 수에 비례.
- 분기 B: context_cache 만료 + files_api URI 생존 시 재업로드 없이 cache 재빌드.
- too-small fail-soft: 1024 토큰 미달 파일은 context cache skip → Files API URI 직접 사용.
- 404 자동복구: Gemini 404 시 Redis 무효화 + 재업로드 1회 재시도.
- 불변식: Redis files_api TTL(~47h) < Gemini Files API(48h) — Redis가 먼저 만료돼 stale URI 방지.
- 19GB watermark eviction (`capacity.py`; `_upload_and_cache_file`이 업로드 직전 `ensure_files_api_capacity` 호출): 매 업로드 직전 **`files_api:*` 키를 SCAN해 각 `file_size`를 합산**한다(유지되는 카운터가 아니라 매번 재계산). `합산 + 이번 파일 > 19GB`면 잔여 TTL 짧은 순으로 evict(연쇄: context_cache → Gemini 파일 → Redis 키). Gemini에 직접 질의하지 않는 이유 — Redis SCAN이 `files.list` 페이지네이션보다 빠르고(로컬), 캐시용 records가 이미 존재. SCAN은 `strict`(폴백 차단)라 Redis 장애 시 under-count 대신 에러.
  - 단일 카운터가 아니라 SCAN-합산이므로 **48h 자동만료가 자동 반영**(TTL로 사라진 키는 합산에서 빠짐, stale-counter 문제 없음). 단 여전히 O(N) SCAN+GET이다(O(1) 아님).
  - Redis files_api TTL(~47h) < Gemini(48h)라 합산은 Gemini 실제보다 약간 **under-count**될 수 있다(47–48h 구간 파일·저장 실패분). 이 방향을 **1GB 여유(19/20)**로 흡수.
  - 업로드량이 48h 창에 20GB를 넘기면 포화 후 매 업로드가 evict를 유발(잔여 TTL 짧은 순 → 곧 죽을 파일부터). 20GB 미만이면 eviction은 휴면(SCAN 후 return).
  - 또한 19GB에 한참 못 미쳐도 매 업로드마다 SCAN하는 건 낭비라, 이를 피하려면 별도 게이트 코드를 또 짜야 한다 — 코드가 계속 늘어나는(과다) 느낌.
- `delete_cache` 네이밍: 이름은 delete지만 실제는 `caches.update(ttl=grace)`이다(청구 절감 목적).

## 4. 사실 — 비용·성능 비교 (조건부)

> §4는 비용·성능 축의 비교다. 운영 단순성 축은 §5에서 별도로 다룬다.

### 4.1 Files API: 즉시 삭제 vs 유지

| 항목 | 즉시 삭제 | 48h 유지 |
|---|---|---|
| 돈 (저장) | 절약 0 (무과금) | 0 (무과금) |
| 재빌드 시 재업로드 | 매번 발생 (latency) | 면제 (URI 재사용) |
| 20GB 캡 | proactive 회피 (footprint 항상 낮음) | reactive — eviction/자연만료에 의존 |
| 운영 상태 | orphan 없음 (단순 불변식) | orphan 존재 (stale Redis·404 경로·LRU 로직 상존) |
| 추가 구현 | 삭제 + Redis 정리 필요 | 약간 수정 필요 (전면 무변경 아님) |
| 전제 | 재사용 ≈ 0 일 때 손해 없음 | 전제 없음 (재사용 있으면 이득) |

- 재사용이 있으면 유지가 재업로드를 면제한다. 재사용이 없으면 두 안의 비용·성능 차이는 거의 없다.
- 운영 상태/단순성 축에서는 즉시 삭제 쪽 상태가 단순하다(§5).

### 4.2 Context Cache: 연장(renew) vs 짧은 TTL + 재빌드

| 항목 | 연장 | 짧은 TTL + 재빌드 |
|---|---|---|
| 저장료 | idle 포함 | 활성만 |
| 재생성 stall | 없음 | 만료 후 첫 호출에 1회 |
| 연속 사용 매끄러움 | 연속 | TTL이 턴 간격보다 짧으면 턴 사이 만료 |
| Files API 의존 | 불필요 | 필요 (재빌드 소스) |

- 저장료는 짧은 TTL이 작다(§2.4). TTL이 대화 턴 간격보다 짧으면 매 턴 재생성 stall이 발생한다.

### 4.3 두 결정의 결합 (비용·성능 축)

- 비용·성능상 저장료가 가장 작은 조합: 짧은 TTL + Files API 유지.
- 가장 큰 조합: 연장 + 즉시 삭제(idle 저장료 + 무과금 파일 삭제로 절약 0 + 재빌드 경로 제거).
- 이는 비용·성능 한정 비교다.

## 5. 두 입장과 근거

> 두 입장은 우선하는 축이 다르다 — A는 비용·성능·자원활용, B는 운영 단순성·예측가능성.
> 비용·성능 축은 (실가동 후) 측정으로 비교 가능하고(§6), 단순성 축은 측정으로 비교되지 않는다.

### 입장 A — Files API 48h 유지 + 짧은 context cache TTL
- 근거: Files API 무과금. 생성비 0이라 짧은 TTL이 저장료를 줄임. 48h 내 재방문 시 재업로드 면제. 분기 B가 큰 틀을 지원(소폭 수정 필요).
- 약점: 재방문이 거의 없으면 유지 이득이 거의 0(중립). **유지의 운영 비용 자체가 eviction machinery**(매 업로드 SCAN·연쇄삭제·드리프트 1GB 마진·strict 폴백)이며, SCAN 낭비를 줄이려면 또 게이트 코드가 필요해 코드가 계속 늘어난다. orphan·stale·404 경로 등 상태도 복잡.

### 입장 B — context cache 연장 + Files API 즉시 삭제
- 근거:
  - 운영 단순성: orphan(고아) Files API 파일 보관 자체가 관리 부담. 여유 공간이 남아도(예: 10GB 여유) 즉시 삭제해 "context cache가 있으면 대응 Files API가 없다"는 단순 불변식을 유지.
  - eviction을 해결책으로 보지 않음: 19GB reactive eviction은 캡 근처에서만 동작하며, 그 전까지 orphan/stale 상태와 LRU 로직 복잡성이 상존. proactive 삭제가 상태를 단순화.
  - (초기 제기) dangling 우려, 응답속도 변동.
- 비용·성능 관점의 사실:
  - dangling은 무과금 + 48h 자동소멸이라 금전·버그 사안은 아니다. 운영 단순성 사안과는 구분된다.
  - 응답속도 변동은 캐시 일반의 특성이며, Files API를 삭제해도 변동의 한 원인(context cache TTL 만료)은 남는다. route_reason 로그로 경로 식별 가능.
  - 연장은 idle 저장료를 발생시키고, Files API 삭제는 무과금이라 금전 절약이 0이다.
- 요지: B의 정당화는 20GB 캡과 운영 단순성이다. 전자는 (실가동 후) 측정 가능 변수, 후자는 측정으로 갈리지 않는 우선순위 선택이다.

## 6. 결정에 필요한 입력

### 6.1 비용·성능 축의 핵심 변수 — 재사용률
> "48h 안에 같은 파일(checksum)이 두 번 이상 쓰이는 비율."

- 높으면: 비용·성능상 유지가 재업로드를 면제(이득 실재). 200명이라도 *유니크 파일* 기준이다.
- 0에 수렴하면: 비용·성능상 두 안이 거의 동률 → 차이는 §6.2 축에서만 발생.

이상적 측정법: resolver가 `[route] ... mode=files_api source=cached/live`를 기록하므로
`재사용률 = count(source=cached) / (count(cached)+count(live))`를 로그에서 산출 가능.

현 시점 측정 불가:
- ① 챗봇이 실가동 전(미사용).
- ② 현재 로그는 챗봇 대화가 아니라 정해진 agent 로직 트래픽이라 재사용 패턴이 실제 챗봇과 다르게 편향됨.
- → 현재 산출값은 대표성이 없다.

대안 입력: 실가동 후 측정, 또는 챗봇 설계상 예상 패턴(공용 corpus = 높은 재사용 / 각자 다른 파일 업로드 = 낮은 재사용).

### 6.2 측정으로 갈리지 않는 축 — 운영 단순성 vs 자원 활용
비용·성능이 동률(또는 미측정)인 구간에서 두 안의 차이는 우선순위 선택에서만 발생한다:
- 운영 단순성 우선 → 즉시 삭제(orphan 없는 단순 불변식).
- 자원 활용/무변경 우선 → 유지(무과금 자원, 추가 구현 최소).

### 6.3 미확인 / 검증 필요 항목
- context cache 저장료 proration granularity(초 vs 분). prorate 여부·1h floor 없음은 확정(§2.3). 분 이하 정밀도가 필요하면 실제 청구서로 검증.
- 20GB 사용량 산출 방식. Gemini에는 storage 총 사용량을 직접 주는 엔드포인트가 **없다**(확인됨) — `files.list`로 각 File의 `sizeBytes`를 합산해야 하며 페이지네이션이 필요하다(다중 호출, 느림). 현재 19GB 체크는 이를 피해 **Redis `files_api:*` SCAN+합산**을 쓴다(로컬이라 빠름, §3). 둘 다 enumerate+sum O(N)이며, 차이는 로컬(Redis) vs 네트워크 페이지네이션(Gemini). 검증 필요: Redis 합산의 systematic under-count(TTL 격차)가 실제로 1GB 여유 안에 들어오는지 — 대량 동시 업로드로 47–48h 구간 사망지대 파일이 1GB를 넘으면 여유 부족 가능.

## 7. 구현 제약 (안 선택과 무관하게 성립하는 사실)

- 즉시 삭제를 구현하는 경우:
  - context cache가 실제 생성된 경우에만 삭제해야 한다. too-small로 skip된 파일은 Files API URI가 유일 경로이므로, 무조건 삭제 시 매 턴 재업로드가 발생한다.
  - Gemini 파일 삭제와 Redis files_api 레코드를 함께 삭제해야 한다. 한쪽만 삭제하면 stale URI → 404 churn이 발생한다.
  - 19GB eviction과 역할이 겹친다 — 즉시 삭제 시 eviction은 거의 동작하지 않는 코드가 된다(유지/제거를 명시 결정 필요).
- 48h 유지를 선택해도 코드 소폭 수정이 필요하다(완전 무변경 아님 — 구체 변경분은 구현 시 별도 정리).
- Context Cache 저장료 최소화는 두 입장과 무관하게 동일하다: 연장 대신 짧은 TTL + 세션 종료 시 `update` 단축(§2.3 — delete 아님).

## 8. 잠정 방향 (현 시점) — 단순성 우선

확정 아님. 현 시점 정보로는 **유지보수 단순성을 우선해 입장 B(즉시 삭제 + context cache 중심) 쪽**으로 기운다. 근거:

- Files API 유지(A)의 가격표 = **eviction machinery 자체**(매 업로드 SCAN·연쇄삭제·드리프트 마진·strict 폴백). 게다가 SCAN 낭비를 줄이려면 게이트 코드를 또 더해야 하는 등 **코드가 계속 늘어난다.** "이 코드를 유지·확장할 바에"라는 판단은 곧 운영·유지보수 단순성을 이유로 B를 택하는 것이다.
- 이 코드의 존재·증식 자체가 입장 B의 "복잡성" 주장에 대한 구체 증거다.
- 비용 절감 동기가 약하면(과금 주체가 개인이 아님) A의 이점(무과금 재사용)의 가치가 낮아져 단순성 쪽 가중치가 커진다.

**트레이드(명시):** 이는 비용·성능 축에선 불리한 선택이다(§4.3 — Files API는 무과금, context cache는 과금; 재빌드 latency 발생). 즉 *회사 비용·약간의 latency를 받아들이고 코드 단순성을 사는* 것 — 비용·성능이 아니라 **운영 단순성 우선**이라는 가치판단으로만 정당화된다.

**재검토 조건:** 실가동 후 재사용률(§6.1)이 높게 나오면 A의 재사용 이점이 단순성 손실을 상쇄할 수 있으므로 다시 본다.

|---|---|
| "Files API를 지우면 비용 절약" | ✗ 무과금이라 금전 절약 0. (운영 단순성 사안은 별개) |
| "재빌드가 연장보다 비싸다" | ✗ 생성비 0이라 idle 없는 만큼 오히려 작다. 재빌드 비용은 latency. |
| "200명이면 20GB 찬다" | △ 저장량은 유저 수가 아니라 유니크 파일 수 × 크기. 공용 corpus면 무관, 각자 다른 파일이면 사실일 수 있음. |
| "dangling = 비용/버그 위험" | ✗ 무과금 + 48h 자동소멸이라 금전·버그 사안 아님. 운영 단순성 우려는 별개로 성립. |
