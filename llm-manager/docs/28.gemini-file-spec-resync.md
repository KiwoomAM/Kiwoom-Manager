# Gemini 파일 스펙 재확인 — 비디오 포맷 / 인라인 비디오 / PDF 1000p 분할

> 2026-06-24 Google 공식 문서를 모달리티별로 재확인한 결과, 현재 구현이 공식
> 스펙과 어긋나는 3개 지점을 발견해 정정한다. 파일 전달 전략의 큰 그림은
> [07.inline-vs-files-api-strategy.md](07.inline-vs-files-api-strategy.md)가 SSOT이며,
> 이 문서는 그 중 **§2.1 / §2.4 / §4.1 / §6.1** 을 갱신하는 변경분만 다룬다.
> PDF 분할의 큰 그림은 [25.pdf-split-shared-pool-and-unsplittable-reject.md](25.pdf-split-shared-pool-and-unsplittable-reject.md).

## 1. 배경 / 문제 정의

[07 §2.1·§2.4](07.inline-vs-files-api-strategy.md)는 초기 설계 시점의 공식 문서 확인에
기반한다. 이번에 Files API·이미지·오디오·비디오·문서 문서를 다시 확인하니, 그 사이
스펙이 갱신됐거나 당시 "보수적"으로 적었던 부분이 실제와 어긋났다. 어긋남은 두 종류다:

1. **잘못된 거부** — Gemini는 지원하는데 우리가 막아 사용자 파일이 거부됨 (비디오 포맷, 인라인 비디오).
2. **잘못된 통과** — Gemini가 거부할 입력을 우리가 막지 않아 런타임에 터짐 (1000p 초과 PDF).

`FAIL-LOUD`·`MEASURE-FIRST` 관점에서 둘 다 정정 대상이다.

## 3. 변경 A — 비디오 MIME 화이트리스트 보강

[validators.py](../llm_manager/_internal/file_processing/validators.py) `SUPPORTED_MIME_TYPES`
비디오 항목에 누락된 포맷을 추가한다.

- 공식 누락분: `video/mpg`, `video/wmv`
- 실탐지 보강: `video/x-ms-wmv`

**`video/x-ms-wmv` 추가 근거**: `.wmv` 파일은 `Part.from_bytes`의 매직바이트 기반
탐지(`filetype`)나 OS mime 매핑에서 공식 표기 `video/wmv`가 아니라 `video/x-ms-wmv`로
잡히는 경우가 흔하다. 공식 표기만 넣으면 실제 `.wmv` 업로드가 여전히
`UnsupportedFileTypeError`로 거부될 수 있어, 둘 다 화이트리스트에 둔다. (`EXPLICIT`:
실제 들어오는 식별자를 기준으로 막지 않게.)

변경 후 비디오 목록(10종):

```
video/mp4, video/mpeg, video/mov, video/avi, video/x-flv,
video/mpg, video/webm, video/3gpp, video/wmv, video/x-ms-wmv
```

> 07 §2.4 비디오 행을 이 목록으로 갱신한다.

## 4. 변경 B — 인라인 비디오 허용 (선분리 제거)

### 4.1 현재 동작과 잘못된 전제

[resolver.py `classify_files`](../llm_manager/_internal/file_processing/resolver.py)의
Step 1은 `video/*`를 **무조건** `files_api_pool`로 선분리한다. 주석 근거는
"Gemini inline 자체 불가"인데, 공식 문서상 **20MB 미만 비디오는 인라인 전송이
지원**된다. 전제가 틀렸다.

### 4.2 결정 — 선분리 자체를 제거 (greedy 합계가 자연 처리)

비디오를 image/audio와 동등한 인라인 후보로 취급하면, 기존 합계(greedy) 로직이
크기에 따라 자동 라우팅한다. **별도 분기가 필요 없어진다.**

- **선분리 루프 삭제** → 모든 파일이 인라인 후보로 풀에 들어간다.
- [`_inline_total_limit`](../llm_manager/_internal/file_processing/resolver.py)의 미디어
  판정에 `video/` 추가 → 비디오가 있으면 20MB 적용
  (공식: 인라인 비디오는 요청 총 20MB 미만).
- greedy 단일 순회가 처리: 합계 20MB에 들어오는 비디오는 인라인, 넘치는
  비디오는 자연히 `files_api_pool`로 밀린다. 대형 비디오는 항상 합계를 초과하므로
  종전처럼 Files API로 간다 — 동작 회귀 없음.

변경 전후 (의사코드):

```python
# 전: 비디오 강제 분리
for fi in files:
    if fi.mime_type.startswith("video/"):
        files_api_pool.append(fi)
    else:
        inline_pool.append(fi)

# 후: 전부 인라인 후보, greedy가 크기로 라우팅
inline_pool = list(files)
files_api_pool = []
```

```python
# _inline_total_limit
has_media = any(
    fi.mime_type.startswith(("image/", "audio/", "video/")) for fi in pool
)
return _INLINE_LIMIT_WITH_IMAGE_AUDIO if has_media else _INLINE_LIMIT_PDF_OR_TEXT_ONLY
```

### 4.3 짚어둘 엣지케이스 — 혼합 모달리티 라우팅 변화

`[PDF 45MB + 소형 비디오 10MB]`처럼 섞이면, 비디오가 후보에 끼어 한도가
50MB→20MB로 내려간다. 결과적으로 **소형 비디오가 인라인, 큰 PDF가 Files API**로
라우팅된다.

- **정합성**: 구글 스펙상 유효하다 — 인라인 미디어가 하나라도 있으면 요청 총합은
  20MB 규칙을 따라야 하므로, 큰 PDF를 같은 요청에 인라인할 수 없다.
- **비용**: 오히려 유리한 쪽일 때가 많다 — 큰 PDF가 Files API + Redis HIT로
  캐시되어 멀티턴/병렬 재호출에서 매번 재전송을 피한다([07 §4.1.1](07.inline-vs-files-api-strategy.md) 반복 호출 최적화 근거와 일치).
- **결론**: 이 라우팅 변화를 **수용**한다. 별도 우선순위 로직(큰 PDF를 인라인에
  남기기)은 `YAGNI` — 현 수요에 근거 없음.

> 07 §2.1(비디오 행), §4.1 Step 1, §4.1 Step 2의 `has_image_or_audio` 설명을 갱신한다.

## 5. 변경 C — 1000페이지 초과 PDF 페이지 분할 (거부 아님)

### 5.1 정책

공식 한도는 PDF당 **1000페이지**. 초과 PDF는 거부하지 않고 **한도 이하 파트로 페이지
분할해 전송**한다(사용자 결정). 분할 우선순위는 **크기(50MB) 먼저 → 그 다음
페이지(1000p)**: 50MB 크기 분할을 끝낸 뒤 결과 파트가 여전히 1000p를 넘으면 페이지로
더 쪼갠다.

- 분할 수: 파트당 ≤1000p가 되도록 `ceil(pages / 1000)` 등분 (1000~2000→2등분,
  2000~3000→3등분 …). 정확히 1000p는 분할하지 않음.
- 단일 페이지가 50MB를 넘는 진짜 분할불가 케이스만 기존 `PdfPageTooLargeError`로
  거부(유지). **`PdfTooManyPagesError`는 도입하지 않는다**(거부 폐기).

### 5.2 splitter 확장 — `split_pdf(path, target_mb=50, max_pages=1000)`

[splitter.py](../llm_manager/_internal/file_processing/splitter.py) `split_pdf`에
`max_pages` 파라미터를 추가해 **각 파트가 ≤target_mb AND ≤max_pages**를 만족하게 한다.

- 조기 반환을 `file_size ≤ target AND n_pages ≤ max_pages`일 때만 `[path]`로 좁힌다
  (현재는 크기만 봄).
- 기존 크기 분할(`_estimate_page_sizes`→`_group_pages`→`_split_group`→`_merge_adjacent`)로
  ≤50MB 파트를 만든 뒤, **페이지 캡 패스**를 덧붙인다: 파트가 >max_pages면
  `ceil(pages/max_pages)` 등분해 각 등분 페이지 범위를 `_split_group`으로 저장한다
  (`_split_group`이 크기도 함께 보장).
- 페이지만 초과(≤50MB)하는 PDF는 크기 분할을 건너뛰고 페이지 캡만 적용.
- 공유 리소스 복제(§5.6)로 페이지 파트가 50MB를 넘으면 `_split_group` 재귀가 크기로
  더 쪼갠다(페이지 부분집합이라 ≤max_pages는 유지).
- [`upload_pdf_parts`](../llm_manager/_internal/file_processing/uploader.py)도
  `max_pages`를 받아 `split_pdf`에 전달.

### 5.3 Files API 경로 — 분할 게이트 확장

[`_upload_and_cache_file`](../llm_manager/_internal/file_processing/resolver.py)의 분할
분기 조건을 **`size > 50MB` → `size > 50MB OR page_count > 1000`**으로 넓힌다.
page_count는 이미 업로드 직전에 stash(현 L210-211)하므로 그 값을 게이트에 쓴다.
≤50MB지만 >1000p인 PDF도 이제 `upload_pdf_parts`(분할 경로)로 들어간다.

### 5.4 인라인 경로 — 페이지 전개 + Files API 폴백

인라인으로 분류된 PDF가 >1000p면 **메모리에서 페이지 분할** 후 파트를 인라인으로
보낸다. 단, 분할 파트 합계가 인라인 한도를 넘으면(공유 리소스 복제로 커질 수 있음 —
§5.6) 그 PDF는 **Files API로 폴백**한다(사용자 결정).

`resolve_files`가 classify(+승급) 직후, `_process_inline` 전에 전개 단계를 둔다:

```python
inline_pool, files_api_pool = classify_files(files, llm_input)
# (§4.4 승급 정책 — 기존)
...
# 인라인 PDF 페이지 전개 → 재분류로 budget·폴백 처리
expanded = await _expand_pdfs_over_page_limit(inline_pool)
inline_pool, spilled = classify_files(expanded, llm_input)
files_api_pool = spilled + files_api_pool
```

- `_expand_pdfs_over_page_limit(pool)`: 각 PDF의 bytes 확보 → `_count_pdf_pages`.
  ≤1000p(또는 None)면 그대로 둔다. >1000p면 tempfile에 써서 `split_pdf(tmp, 50, 1000)`로
  쪼개 part bytes를 읽어 **part FileInput들로 치환**(`file_name`에 `#partN`, `data` 채움,
  `page_count` 세팅). 비-PDF는 그대로.
- 재분류는 기존 greedy(20/50MB 한도, §4.1)를 그대로 써 **예산 초과분을 files_api로
  자연 폴백**시킨다 — 새 예산 로직 불필요.
- 폴백된 part FileInput은 이미 ≤50MB·≤1000p라 Files API 경로(§5.3 게이트)에서 재분할
  없이 단건 업로드된다.
- 전개가 bytes를 미리 채우므로(`data` 보유), 이후 `_process_inline` /
  `_upload_and_cache_file`은 재fetch하지 않는다(기존 lazy 계약과 일치).

### 5.5 측정 불가(None) → 분할 안 함 (fail-soft)

`_count_pdf_pages`가 깨진/비-PDF에 `None`을 반환하면 페이지 분할을 시도하지 않고 그대로
진행(fail-soft). 페이지 수를 못 세는 입력을 분할하는 것은 근거가 약하고, 실제 문제라면
Gemini가 거부해 전파된다. [07 §4.4.1](07.inline-vs-files-api-strategy.md) fail-soft 철학과 일관.

### 5.6 용량 증가 주의 (공유 리소스 복제)

PyMuPDF 페이지 분할은 여러 페이지가 공유하는 폰트·이미지 풀을 각 파트에 복제할 수 있어
**파트 합계가 원본보다 커질 수 있다**([25](25.pdf-split-shared-pool-and-unsplittable-reject.md)
공유 풀 현상). 텍스트 위주 PDF(>1000p의 통상 케이스)는 증가폭이 작지만, §5.4의 인라인
폴백이 이 증가로 한도를 넘는 경우를 받친다.

**변경 A**
- `video/mpg`, `video/wmv`, `video/x-ms-wmv` → `validate_mime_types` 통과 (예외 없음)

**변경 B**
- 소형 비디오(≤20MB) → `inline_pool`; 대형 비디오(>20MB) → `files_api_pool`
- `[PDF 45MB + 비디오 10MB]` → 비디오 inline, PDF files_api (§4.3)

**변경 C — splitter**
- 1500p·소형 PDF → 2파트, 각 ≤1000p (페이지 캡)
- 2500p·소형 PDF → 3파트, 각 ≤1000p (`ceil(pages/1000)`)
- 1000p·소형 → 분할 안 함 (`[path]` 반환)
- 단일 페이지>50MB → `PdfPageTooLargeError` (회귀)

**변경 C — Files API 게이트**
- ≤50MB·1500p PDF → `_upload_and_cache_file`이 `upload_pdf_parts`(분할) 호출 (단건 upload 아님)

**변경 C — 인라인 전개/폴백**
- ≤50MB·1500p PDF, 파트 합계 인라인 한도 내 → 전개 후 `inline_pool`에 파트 N개
- 파트 합계가 한도 초과 → 해당 PDF가 `files_api_pool`로 폴백
- ≤1000p PDF → 전개 무영향 (그대로)
- 깨진 PDF(`_count_pdf_pages` None) → 분할 안 함, 통과 (fail-soft)
