# 38. 챗봇용 대화 함수 신설 — `llm_chat_async` · `llm_chat_stream_async`

관련: [docs/37](37.streaming-function-calls-and-messages.md) §4를 대체한다 · [KiwoomAM/Kiwoom-Manager#99](https://github.com/KiwoomAM/Kiwoom-Manager/issues/99)(머지됨, PR #104) · [KiwoomAM/Kiwoom-Rag#875](https://github.com/KiwoomAM/Kiwoom-Rag/issues/875)

기준: llm-manager `f86e89d`(main), Kiwoom-Rag `71cb713e`(main), Kiwoom-ESG `f0fabc4c`(main). 이 문서의 줄 번호는 그 커밋 기준이다.

## 1. 배경 / 문제 정의

도구를 쓰는 챗봇이 매니저를 우회한다. Kiwoom-Rag 챗봇은 `llm_manager.aio.stream` 을 두 곳에서 직접 부른다([llm_node.py:51](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/graph/nodes/llm_node.py#L51), [response_generator.py:71](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/graph/nodes/response_generator.py#L71)). 그 대가로 셋을 잃는다.

만료된 Files API 주소로 Gemini가 지면 복구가 없다. 매니저는 Redis 주소 기록을 지우고 다시 올려 한 번 재시도하는데([resolver.py:816](../llm_manager/_internal/file_processing/resolver.py#L816)), 챗봇은 LLM 노드에서만 타임아웃·연결 오류·과부하·요청 한도를 다시 시도하고([llm_node.py:61](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/graph/nodes/llm_node.py#L61) · [:72](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/graph/nodes/llm_node.py#L72)) 최종 답변 노드는 재시도하지 않아 그대로 턴 실패가 된다. Gemini에서 지워진 Files API 주소가 Redis에 남아 있으면 그 기록이 만료될 때까지 그 파일이 든 대화가 매 호출 실패한다.

첨부를 Files API 주소로 푸는 코드가 소비자에 있다. 챗봇이 파일마다 `file_preprocessing_async` 를 부르고 상한·기억·실패 격리를 직접 관리한다([client.py:102](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/utils/client.py#L102)). 다른 서비스가 같은 대화 기능을 만들면 같은 코드를 다시 쓴다.

밑단 타입을 내부 경로로 가져온다. 챗봇이 `from llm_manager._internal.handler_client import Content` 로 가져오고, 테스트는 그 내부 모듈을 흉내 내는 코드까지 둔다.

**docs/37 §4가 세운 설계는 전제가 바뀌었다.** 그 문서는 첨부가 바이트로 채널에 앉아 있는 상태에서 표찰(§4.3의 ④)과 `stored_files` 인자를 설계했다. 그 뒤 챗봇이 첨부를 파일매니저 주소 블록으로 바꿔 두어, 이 문서는 "챗봇이 이미 하는 것을 SDK로 옮긴다"로 방향을 다시 잡는다.

### 2.2 매니저가 이미 가진 것

`file_preprocessing_async` 는 `StoredFile` 을 받아 체크섬을 만들고, Redis에 그 체크섬의 Files API 주소가 있으면 재사용하고 없으면 파일매니저에서 바이트를 받아 Gemini Files API로 올린다([preprocess.py:30](../llm_manager/_internal/file_processing/preprocess.py#L30) → [resolver.py:398](../llm_manager/_internal/file_processing/resolver.py#L398) → [stored_file_resolver.py:73](../llm_manager/_internal/stored_file_resolver.py#L73)). 크기 분류를 하지 않아 작은 파일도 Files API 주소를 받는다. 기존 404 복구 함수([resolver.py:816](../llm_manager/_internal/file_processing/resolver.py#L816))는 이 흐름에 그대로 쓸 수 없다. 크기 분류와 Context Cache 흐름을 다시 거치고, 결과도 파일별이 아니라 한데 모은 목록이다. 가져다 쓸 수 있는 것은 Redis 주소 기록을 지우는 `cache_store.delete_files_api`([cache_store.py:217](../llm_manager/_internal/file_processing/cache_store.py#L217))이며, 다시 해소하는 것은 이 함수의 파일별 반복문을 한 번 더 도는 것이다.

### 2.3 바이트로 남는 경로 둘 — 둘 다 폴백이다

사용자 첨부는 파일매니저 등록이 실패하거나 브라우저가 수정시각을 주지 않을 때만 그 파일이 바이트로 인라인된다([file_processors.py:184](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/utils/file_processors.py#L184)). 사규 PDF도 같다. 파일매니저 주소 등록이 원칙이고 등록이 실패할 때만 바이트가 되며, 그 판단을 코드가 주석에 적어 두었다([loader.py:72](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/rag/regulations/loader.py#L72)의 `_block_for`, 도구 결과 뒤 별도 발화로 붙는 곳은 [execute_workers.py:258](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/graph/nodes/execute_workers.py#L258)).

사규 PDF는 이 설계의 범위 밖이다. 사규를 이 대화 함수에 태울지는 함수를 만든 뒤 그 기능 담당자와 논의하며, 이 문서는 사용자 첨부에만 적용된다(§6).

### 2.4 캐시와 저장이 이 흐름에 맞지 않는 이유

Context Cache는 둘에서 막힌다. `file_preprocessing_async` 가 캐시 모드에서 Files API 주소 목록 대신 캐시 식별자를 돌려주고([preprocess.py:64](../llm_manager/_internal/file_processing/preprocess.py#L64)), Gemini가 캐시 호출에 도구 정의를 함께 받지 않아 도구가 바뀔 때마다 캐시를 새로 만들게 된다. 대신 Gemini 2.5 이상은 요청 앞쪽이 겹치면 설정 없이 자동으로 할인하므로(암묵 캐싱) 반복 비용은 줄어든다.

응답 캐시는 대화에서 적중이 없다. 대화는 매 턴 이력이 늘어 같은 요청이 되풀이되지 않는다. 저장도 챗봇이 이미 하고 있고, 매니저가 저장하는 `agent_llm` 기록을 읽는 코드는 사내에 없다. 저장을 끄면 동시 요청 대기(standby)도 걸리지 않아([runner.py:557](../llm_manager/_internal/runner.py#L557) · [:700](../llm_manager/_internal/runner.py#L700)) 이슈 #102(스트림을 안 쓰고 버리면 다른 요청이 막힌다)와 무관해진다.

### 2.5 meta 후보

기존 `ResponseMeta` 여덟 칸 중 캐시에 딸린 여섯은 이 함수에서 늘 빈다([models.py:94](../llm_manager/models.py#L94)). `metadata` 는 넘긴 값을 되돌려 준다. 남는 것은 `file_meta` 하나인데, Kiwoom-ESG 평가가 이 칸의 `pdf_part_ranges` 로 분할 PDF 인용을 원본 쪽수로 바꿔 출처를 검증한다(`Kiwoom-ESG backend/LLM/evaluator.py:137`·`:315`). 챗봇 대화 경로는 이 칸을 읽지 않는다.

## 3. 설계

### 3.1 만들 것

async 두 함수를 만든다. 이름은 기존 공개 함수 `llm_request_async`·`llm_request_stream_async` 와 나란히 읽히도록 `llm_chat_async`·`llm_chat_stream_async` 로 확정했다.

```python
async def llm_chat_stream_async(
    messages: list[ChatMessage], *, system=None, model=None, tools=None,
    tool_config=None, temperature=None, max_tokens=None, ...
) -> AsyncGenerator[StreamChunk, None]: ...

async def llm_chat_async(messages: list[ChatMessage], *, ...) -> LLMResponse: ...
```

입력은 밑단 [`aio.stream`](../llm_manager/_internal/handler_client/aio.py#L180)처럼 인자를 펼쳐 받는다. 받는 인자는 밑단 `stream()` 에서 `contents`·`history`·`cached_content`·`service_name` 을 뺀 것이며, 이 대응을 테스트가 확인한다(§4). `service_name` 은 기존 함수처럼 환경변수 `SERVICE_NAME` 에서 넣고, 없으면 요청 전에 실패한다([runner.py:102](../llm_manager/_internal/runner.py#L102)). `cache_mode`·`save_mode`·`context_cache_ttl` 은 두지 않는다(§2.4).

돌려주는 것은 결과뿐이다. 스트림은 `StreamChunk` 객체를 그대로 내보내고 논스트림은 `LLMResponse` 를 돌려준다. meta는 담을 칸이 없어 두지 않는다(§2.5). 첨부 해소와 404 복구는 첫 청크가 나오기 전 제너레이터 안에서 일어나므로, 소비자가 호출을 감싼 시간 상한이 해소 시간까지 잡는다.

### 3.2 첨부 — `ChatMessage` 와 `StoredFile`

매니저 전용 메시지 타입을 새로 만든다. 밑단 전송 모델 [`Content`](../llm_manager/_internal/handler_client/models.py#L441)는 건드리지 않고, 매니저가 받은 `ChatMessage` 를 치환한 뒤 `Content` 로 바꿔 보낸다.

```python
ChatMessage(role="user", content=[
    StoredFile(file_path=..., file_name=..., file_size=..., file_mtime=..., mime_type=..., extension=...),
    Part(type="text", text="이 보고서 요약해줘"),
])
```

`content` 는 `StoredFile` 과 파일이 아닌 `Part`(글·함수 호출·함수 결과 등)만 허용한다. 바이트를 담은 `inline` 조각과 Files API 주소를 담은 `file` 조각은 타입 검사가 거부한다. 첨부는 `StoredFile` 한 가지로 고정하고, 파일매니저 주소를 만드는 것은 소비자, Files API로 올리는 것은 매니저가 맡는다는 경계를 타입으로 지킨다. `stored_files` 인자는 두지 않는다 — 파일이 어느 발화에 딸렸는지는 `messages` 가 이미 담고 있다.

`role` 은 Gemini가 쓰는 `user`·`model` 둘만 받고 매니저는 변환하지 않는다. 챗봇은 대화 기록의 `assistant` 를 보내기 직전에 `model` 로 이미 바꾼다([client.py:200](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/utils/client.py#L200)).

### 3.3 해소 흐름

첨부는 호출마다 파일 단위로 풀고, 실패한 파일만 안내 문구로 바꾼다.

```
messages 안의 StoredFile 마다
  ├ 체크섬 계산 → Redis에 Files API 주소 있으면 재사용, 없으면 파일매니저에서 받아 Files API 업로드
  ├ 분할된 PDF는 조각 여러 개가 그 StoredFile 위치에 차례로 들어간다
  ├ 60초를 넘기면 그 파일만 안내 문구로 바꾸고 로그에 남긴다
  └ 그 밖의 실패도 그 파일만 안내 문구로 바꾸고 로그에 남긴다
치환된 messages → Content 로 변환 → Gemini 호출
  ├ 스트림: 첫 청크 전 첨부 실패 → 그 호출 파일들의 Redis 주소 기록 삭제 → 다시 해소 → 1회 재시도
  └ 논스트림: 호출이 첨부 실패로 지면 → 같은 복구 → 1회 재시도
```

파일별 상한은 매니저 안에 60초로 둔다. 매니저 안쪽 상한이 600초라 상한이 없으면 한 파일이 호출 전체를 오래 붙잡는다. 실패를 파일 단위로 격리하는 이유는 오래전 첨부 하나 때문에 지금 대화가 멈추지 않게 하는 것이며, 챗봇이 같은 판단을 코드 주석에 적어 두었다. 실패 목록은 로그에만 남긴다. 안내 문구는 챗봇과 같은 `[{file_name}: 첨부를 불러오지 못했습니다]` 이다([client.py:177](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/utils/client.py#L177)).

**첨부 실패는 404만이 아니다.** 지워지거나 만료된 Files API 파일을 참조하면 Gemini는 403을 주고, llm-handler가 401·403을 자기 운영 문제로 분류해 `handler_ops`(502)로 바꿔 올린다(Kiwoom-Handler `llm-handler/service/app/core/errors.py` 의 `classify_api_error`). 2026-09-17에 실제 챗봇으로 확인한 메시지는 "Gemini stream 권한/인증 실패 (gemini_status=403)" 였고, 404만 보는 판정으로는 복구가 서지 않아 그 대화가 매 호출 실패했다. 그래서 복구 판정을 `is_gemini_file_unavailable`([gemini_errors.py:26](../llm_manager/_internal/gemini_errors.py#L26))로 따로 두고 404와 `gemini_status=403` 을 함께 본다. API 키·쿼터 문제도 같은 모양이라 함께 걸리는데, 그때는 재업로드가 같은 이유로 실패해 원래 예외가 올라간다. Context Cache 만료 처리는 이 판정을 쓰지 않는다 — 거기서 403을 "이미 없음"으로 보면 인증 실패가 조용한 성공이 된다.

재시도는 Files API 주소로 보낸 파일이 있을 때만 한다. 첨부가 없거나 모두 안내 문구로 바뀐 호출은 다시 풀 것이 없어 같은 요청을 한 번 더 보낼 뿐이며, 기존 `llm_request` 도 파일이 있을 때만 복구한다([runner.py:506](../llm_manager/_internal/runner.py#L506)).

해소 전체에는 매니저가 상한을 두지 않는다. 해소는 소비자가 호출을 감싼 시간 상한 안에서 세어지므로(§3.1), 소비자가 그 상한을 해소 시간까지 덮게 잡는다(§5).

턴 기억은 이 단계에 넣지 않는다. 호출 단위로만 해소하며, 두 번째 호출부터는 Redis 주소 재사용이 업로드를 막는다. 느린 첨부가 실제로 생기면 같은 반복문에 기억을 얹는다(§6).

### 3.4 공개 export

`ChatMessage` 와 함께 `Content`·`FunctionResponse` 를 [`llm_manager`](../llm_manager/__init__.py#L130)와 [`llm_manager.aio`](../llm_manager/aio.py#L40) 양쪽에 내보낸다. 공개 함수 `aio.stream` 이 `messages: list[Content]` 를 받는데 그 타입을 공개로 가져올 수 없던 빈틈을 함께 닫는다.

### 3.5 기각한 대안

**`stored_files` 인자로 파일을 따로 받기**(docs/37 §4.3의 ④ 포함) — 그 인자는 평평한 목록이라 파일이 어느 발화에 딸렸는지를 버린다. 대화에서는 매니저가 위치를 추측해야 하고, 파일을 앞으로 몰면 여러 턴 첨부에서 "이건 어때?" 가 무엇을 가리키는지 잃는다. 표찰을 따로 두는 안도 `StoredFile` 을 그 위치에 놓으면 필요가 없어진다.

**바이트 조각도 받기** — 챗봇의 인라인 폴백이 그대로 동작하지만 첨부 형태가 두 가지가 된다. 매니저는 첨부를 `StoredFile` 한 가지로 고정한다. 파일매니저 주소를 못 만든 첨부를 기존 `aio.stream` 경로로 보낼지 안내 문구로 바꿀지는 소비자가 고른다(§5).

**청크를 dict로 내보내기** — 기존 `llm_request_stream_async` 와 형식이 같아지지만 소비자가 청크 읽기를 모두 고쳐야 하고, `getattr` 로 읽는 코드는 dict에서 예외 없이 빈 값을 낸다. 그 dict 자체가 서버 시절 형식의 잔재다(별건, §6).

**`(결과, meta)` 로 돌려주기** — 기존 함수와 모양이 같아지고 나중에 칸을 더하기 쉽지만, 지금 담을 칸이 없다. meta가 필요해지면 그때 반환 모양을 바꾸고 소비자를 함께 고친다(§6).

**설정 dict 하나로 입력 받기** — 매니저 기존 함수와 쓰는 법이 같아지지만, 소비자의 기존 호출이 인자를 펼친 모양이라 이관이 커지고 타입 검사도 못 받는다.

**Context Cache·응답 캐시 옵션 두기** — §2.4의 이유로 쓸 흐름이 없다. 쓸 수 없는 옵션을 두면 잘못 켤 길만 남는다.

**해소 전체 상한 두기** — 답 없이 턴이 끊기는 것은 막지만, 늦은 파일 하나가 뒤에 선 파일을 모두 안내 문구로 밀어내고 값을 정할 실측이 없다. 매니저는 파일별 상한만 두고 전체 시간은 소비자 상한에 맡긴다.

**턴 기억을 지금 넣기** — 기억이 막는 것은 60초를 넘겨 끊긴 파일을 같은 턴의 다음 호출에서 다시 기다리는 것이다. 제대로 푼 파일은 두 번째 호출부터 Redis 주소를 재사용해 기억 없이도 빠르다. 60초를 넘기는 첨부가 보고된 적이 없고, 기억은 같은 반복문에 얹는 층이라 나중에 더해도 이 단계 코드를 다시 쓰지 않는다.

## 5. 소비자 이관

챗봇이 고칠 것과 그대로 두는 것이 갈린다.

**그대로 둔다.** 대화 저장, 청크 읽기 여섯 곳, 그래프 노드 구조, 재시도와 시간 상한으로 감싸는 구조, 도구 호출·결과를 조각으로 바꾸는 코드.

**고친다.** LLM 호출 두 곳을 새 함수로 바꾸고, `to_llm_messages` 가 파일매니저 주소 블록을 Files API 주소로 풀지 않고 `StoredFile` 을 `ChatMessage` 에 그대로 넣게 하며, `Content` 를 공개 export에서 가져온다. 시간 상한 두 곳([llm_node.py:50](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/graph/nodes/llm_node.py#L50)의 60초, [response_generator.py:70](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/graph/nodes/response_generator.py#L70)의 90초)은 해소 시간까지 덮게 늘린다. 지금은 해소가 그 상한 밖([llm_node.py:45](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/core/graph/nodes/llm_node.py#L45))에서 일어나지만 새 함수에서는 안으로 들어온다.

**챗봇이 고를 것.** 파일매니저 등록이 실패해 파일매니저 주소 없이 바이트로 남은 첨부를 어떻게 할지다.

| | 폴백 유지 | 폴백 제거 |
|---|---|---|
| 파일매니저 주소가 없는 첨부 | 기존 `aio.stream` 경로로 보낸다 | 안내 문구로 바꾼다 |
| 경로 판정 | 이력에 바이트 블록이 하나라도 있으면 기존 경로로 간다 | 판정이 없다 |
| 지속 시간 | 한 번 폴백이 난 대화는 체크포인트가 남아 있는 동안 기존 경로로 간다 | 해당 없다 |
| 첨부 해소 코드 | 기존 경로가 앞선 턴의 파일매니저 주소 블록을 Files API 주소로 풀어야 해서 남는다 | 지울 수 있다. 사규 경로는 이 설계의 범위 밖이라 그대로 둔다 |

이관하면 챗봇이 지금 가진 턴 기억 보호가 사라진다. 60초를 넘겨 끊긴 첨부를 같은 턴의 다음 호출에서 다시 기다리게 되며, 한 턴에 호출이 최대 네 번이라([client.py:40](https://github.com/KiwoomAM/Kiwoom-Rag/blob/71cb713e/src/backend/utils/client.py#L40)) 그런 파일 하나가 최대 240초를 쓴다. 그런 첨부가 보고된 적은 없어, 기억을 더한 뒤 옮길지는 챗봇이 판단한다.

## 6. 범위 밖 (별건으로 분리)

**턴 기억 2단계.** 느린 첨부가 생기면 같은 반복문에 기억을 얹는다. 전달 방식은 기억 객체를 인자로 받는 안과 매니저가 턴 기억 장치를 공개하는 안 둘이며, 그때 고른다.

**meta 추가.** 필요해지면 첫 후보는 `file_meta` 다(§2.5). 반환 모양이 바뀌므로 소비자를 함께 고친다.

**사규 PDF.** 사규도 파일매니저 주소 등록이 원칙이고 등록이 실패할 때만 바이트다(§2.3). 사규를 이 대화 함수에 태울지는 함수를 만든 뒤 그 기능 담당자와 논의한다.

**기존 스트림 함수의 dict.** 서버 시절 형식의 잔재라 객체로 바꾸는 것이 맞으나 소비자가 있어 별도 논의 대상이다.

**`llm_request` 를 파일·호출 두 함수로 나누기.** 검토했으나 지금 할 이유가 없다. 챗봇용 함수가 쓸 파일 처리는 `file_preprocessing_async` 로 이미 떼어져 있고, Context Cache가 파일 분류 규칙을 바꾸고 업로드를 자기 흐름에 품어 독립 함수로 떼기 어렵다.
