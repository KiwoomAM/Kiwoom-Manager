## 1. 배경 / 문제 정의

### 1.1 두 가지 요구

**(A) 파일 전처리만 떼어 쓰고 싶다 — `file_preprocessing`**

사용자가 `llm_request` 전체(LLM 캐시 조회 → 파일 처리 → LLM 호출 조립 → 저장)가
아니라, **그중 "파일 처리(업로드/캐시 생성)" 단계만** 독립적으로 호출하고 싶다.
LLM 응답 캐시 조회·LLM 호출 조립은 빼고, stored_files 를 받아 다음만 수행한다:

- Files API 업로드 (필요 시 PDF 분할 포함) → URI 확보
- (opt-in) Context Cache 생성

반환은 "잘 처리됐다"는 확인 + 재사용 핸들이다.

**(B) Context Cache 수명을 사용자가 연장하고 싶다 — `update_context_cache`**

현재 `delete_cache(cache_ids, *, grace_seconds=5)` 는 이름은 delete 지만 실제로는
Gemini `caches.update(ttl=grace_seconds)` 로 TTL 을 **단축**해 만료시킨다. grace_seconds
는 1~3600 으로 받을 수 있다(기본 5).

문제: "만료(delete)"와 "연장(keep-alive)"이 한 함수에 섞여 있다. 의도가 반대인데
같은 인자(grace_seconds)로 표현돼, 호출자가 `delete_cache(id, grace_seconds=3600)` 으로
"연장"을 흉내 내야 한다 — 이름과 동작이 어긋난다.

→ 두 의도를 **이름으로 분리**한다(구 `delete_cache` 는 제거하고 새 이름으로 교체):
- `delete_context_cache(cache_ids)` — **무조건 5초 뒤 만료** (시간 인자 없음, 고정)
- `update_context_cache(cache_ids, *, ttl)` — 사용자가 **TTL 을 선택해 연장**

> 이름: 둘 다 `_context_cache` 접미사로 통일. handler_client 내부의 `update_cache(name, ttl)`
> 와도 이름이 달라 혼동 없음. 구 `delete_cache` 는 deprecated 별칭 없이 제거 — llm-manager
> 와 ESG 를 **둘 다 완료 후 함께 배포**하므로 과도기 별칭이 불필요(§7).

### 1.2 범위

- 영향 코드는 **전부 `llm-manager` 패키지 내부** (형제 매니저 무변경).
- 운영 핫패스(`runner.llm_request*`, `resolve_files`)의 동작은 **불변**. 새 기능은
  기존 헬퍼를 재사용하되, 공유 헬퍼 추출 시 기존 로직이 깨지지 않도록 한다.

## 2. 사전 정보 (코드로 확정한 사실)

설계 결정의 근거가 된 현재 동작. 모두 코드 확인 완료.

### 2.1 파일 분류(inline vs files_api)는 `classify_files` 한 함수에 묶여 있다

`resolver.classify_files` (resolver.py:86) 가 크기·모달리티 기준으로 inline/files_api 를
나눈다. 이 함수는 **runner 핫패스가 그대로 사용**하므로 수정하지 않는다.
→ `file_preprocessing` 은 **classify_files 를 호출하지 않고** 전 파일을 files_api 로
직행시켜 "작은 파일도 강제 업로드"를 달성한다(기존 함수 무변경).

### 2.2 URI 는 호출 payload 에선 평탄, Redis 에선 파일별로 묶인다

파일 3개가 각각 1/3/2 개로 분할된 경우:

```
resolve_files 반환 uri_parts (= LLM 호출 contents):
  [A1, B1, B2, B3, C1, C2]          ← 6개 평탄화

Redis (files_api:{checksum} 키, 파일별):
  {A체크섬} → {uris: [A1],        split: false}
  {B체크섬} → {uris: [B1,B2,B3],  split: true}
  {C체크섬} → {uris: [C1,C2],     split: true}     ← 파일별 그룹 (3개 키)
```

근거: `_upload_and_cache_file` (resolver.py:227) — 한 파일의 모든 part 를 그 파일
체크섬 키 하나에 `uris:[...]` 로 저장한 뒤, `uri_parts` 에는 평탄하게 append.
→ `file_preprocessing` 의 파일별 출력 `(n, ?)` 은 **Redis 가 이미 가진 그룹을 복원**하는
것뿐이다(파일 단위 루프 + 파일별 수집).

### 2.3 `delete_cache` 는 현재 grace_seconds(1~3600)를 받고, 호출처가 있다

- 시그니처: `delete_cache(cache_ids, *, grace_seconds=5)` (__init__.py:419).
- grace_seconds 를 넘기는 기존 호출처(전부 llm-manager 내부):
  - `tests/integration/test_expire_e2e.py:79, 98` → `grace_seconds=60`
  - `quickstarts/llm_manager/quickstart_sdk.ipynb`, `verify_all.ipynb` → `grace_seconds=5`
- → delete_cache 에서 인자를 제거하면 위 호출처도 함께 고쳐야 한다(미수정 시 TypeError).
- 주의: `quickstarts/handler_client/06_context_cache.ipynb` 의 `delete_cache(cache.name)` 은
  **다른 함수**(handler_client 내부의 Gemini 직삭제)다 — 매니저 공개 API 아님.

**크로스 repo 호출처 (확인 완료):**
- **Kiwoom-ESG** — live 호출처. `backend/LLM/evaluator.py:198` 가 `delete_cache_async(cache_id,
  grace_seconds=5)` 로 직접 호출, `backend/tests/unit/test_evaluator.py:172` 가
  `assert_called_once_with("abc", grace_seconds=5)` 로 시그니처를 못박음. → 인자 제거 시
  **ESG 코드 1 + 테스트 1 동반 수정 필요**(다른 repo).
- **Kiwoom-GM** — 무관. `notebooks/holdings_schema_poc.ipynb:132` 는 SDK 호출이 아니라
  **제거된 옛 FastAPI 서버에 HTTP body**(`json={"cache_ids":..., "grace_seconds":1}`)로 쏨.
  서버가 이미 없어 stale — Python 레벨 영향 없음.
- 관측: 두 곳 다 작은 값(1, 5)만 사용 → "긴 ttl 연장" 호출자 없음(분리 안전). ESG 의 5 는
  새 고정 기본값과 동일 → 인자만 떼면 동작 불변.
- 처리 방안(가/나/다)은 §6 에서 확정.

### 2.4 만료(delete)와 연장(refresh)은 Gemini API 는 같고 Redis 동작이 다르다

| | delete (만료) | update (연장) |
|---|---|---|
| Gemini | `caches.update(ttl=5)` | `caches.update(ttl=사용자값)` |
| Redis TTL | 단축(`shrink_context_cache_ttl`) | 새 값으로 연장 |
| Redis 키 부재 시 | **성공**(이미 만료 = idempotent) | **실패**(연장 대상 없음 + cached_content 이름 못 찾음) |

근거: `context_cache_lifecycle._expire_one` (context_cache_lifecycle.py:45) 은 Redis 에서
`cached_content_name` 을 찾아 Gemini update 를 호출한다. 키가 없으면 이름 자체를 못
얻으므로, 연장은 부재를 성공으로 칠 수 없다(FAIL-LOUD).

## 3. 공개 API 계약

### 3.1 `file_preprocessing`

```python
def file_preprocessing(
    llm_input: dict,
    *,
    stored_files: list[StoredFile],
    timings: Timings | None = None,
) -> dict[str, str] | list[list[str]]: ...

async def file_preprocessing_async(...) -> dict[str, str] | list[list[str]]: ...   # 동일 인자
```

- **입력**
  - `llm_input` — `llm_request` 와 동일 dict. `model`/`system`/`tools`/`tool_config` 는
    여기서 꺼내 쓴다(context cache 재료). LLM 호출은 하지 않으므로 `contents` 는 안 봄.
  - `stored_files` — file-manager 에 등록된 파일 참조. 여러 개 허용.
  - `timings` — `context_cache_ttl`(opt-in) + `standby_ttl`(dedup) 만 의미 있음.
    나머지 키(http_timeout/mdb_ttl)는 무시(일관성 위해 기존 `Timings` 재사용).
- **동작**: classify 건너뛰고 전 파일을 files_api 로 강제 처리. `context_cache_ttl`
  지정 시 전체 파일에 대해 Context Cache 1개 생성.
- **출력**
  - context cache 모드(`context_cache_ttl` 지정 + 생성 성공) → **dict 두 키**:
    ```python
    {"context_cache_id": "<hash_key>", "cached_content_name": "cachedContents/xxxx"}
    ```
    - `context_cache_id`(= hash_key): `update_context_cache`/`delete_context_cache` 에 그대로
      넘기는 값(둘 다 hash_key 로 Redis 조회). `llm_request` 응답 `meta.context_cache_id` 와 동일.
    - `cached_content_name`: Gemini 의 cache id. **사용자가 Gemini 를 직접 호출**(genai SDK 등)
      할 때 쓰는 값. (이 값으로는 우리 도구의 Redis 조회 불가 — §2.4. 그래서 둘 다 내보냄.)
  - files_api-only 모드(또는 too-small 로 캐시 skip) → `(n, ?)` 파일별 URI 리스트.
    `result[i]` = i 번째 stored_file 의 URI 들(분할 시 여러 개).

> 출력 엣지: context cache 모드라도 토큰 미달(too-small, fail-soft)로 캐시가 안 만들어지면
> 파일은 이미 업로드됐으므로 `(n, ?)` URI 리스트로 떨어진다(runner 의 fail-soft 와 동일 철학).

### 3.2 `delete_context_cache` (신설 — 구 `delete_cache` 대체)

```python
def delete_context_cache(cache_ids: str | list[str]) -> ExpireResult: ...
async def delete_context_cache_async(cache_ids: str | list[str]) -> ExpireResult: ...
```

- **무조건 5초 뒤 만료**(내부 상수 고정). 시간 인자 없음.
- 동작/반환은 구 `delete_cache` 와 동일(`ExpireResult`, partial failure, 부재 = idempotent 성공).
- breaking: 구 `delete_cache`(+`_async`) **제거** → §2.3 호출처 동반 수정(이름·인자 둘 다).
- **입력 가드**: `cache_ids` 에 `cachedContents/...`(Gemini cache id)가 오면 `ValueError`.
  이 함수는 `context_cache_id`(hash_key)만 받는다 — Gemini 이름은 Redis 키 매칭이 안 돼
  **조용한 no-op(만료 안 됐는데 success 보고)** 이 되므로 즉시 막는다(FAIL-LOUD). 상세 §4.5.

### 3.3 `update_context_cache` (신설)

```python
def update_context_cache(cache_ids: str | list[str], *, ttl: int) -> ExpireResult: ...
async def update_context_cache_async(cache_ids: str | list[str], *, ttl: int) -> ExpireResult: ...
```

- Gemini `caches.update(ttl=ttl)` + Redis TTL 을 `ttl` 로 연장.
- Redis 키 부재 → 해당 id 는 `failed`(연장 대상 없음). delete 의 "부재=성공"과 반대(§2.4).
- 반환은 `ExpireResult` 재사용(`expired`=연장 성공 / `failed`). 필드명이 expire 향이지만
  의미("처리 성공한 id / 실패한 id")는 그대로 들어맞아 새 결과형은 만들지 않는다(SIMPLE).
- **ttl 범위: 1~3600초** (확정). delete 와 동일 범위. 범위 밖이면 `ValueError`.
- **입력 가드**: delete 와 동일 — `cachedContents/...` 입력 시 `ValueError`(hash_key 만 받음, §4.5).

## 4. 모듈 설계 (내부 "어떻게")

### 4.0 결정 요약 (§3 까지 확정분)

- 파일 처리는 **files_api-first 유지** — 작은 파일도 강제 업로드 후 (opt-in) context cache.
  inline-direct cache 는 도입 안 함(URI 백업·404 복구·검증된 경로 재사용 우선, docs/26 §3 논의).
- `delete_context_cache` 는 5초 고정, `update_context_cache` 는 ttl 선택. 둘 다 `context_cache_lifecycle` 에.
- `_process_files_api` 의 "한 파일 처리" 부분을 **공유 헬퍼로 추출**하되, 기존 동작 불변.

### 4.1 공유 헬퍼 추출 — `_resolve_one_files_api`

현재 `_process_files_api` (resolver.py:335) 의 for 루프 몸통(파일 1개에 대한
Redis 조회 → standby dedup → 업로드/재사용)을 **함수로 추출**한다. 추출 목적은
`file_preprocessing` 이 같은 파일단위 로직을 재사용하기 위함(SSOT).

```python
async def _resolve_one_files_api(
    fi: FileInput, checksum: str, *, standby_ttl_seconds: int,
) -> tuple[list[Part], list[FileRef]]:
    """파일 1개를 files_api 경로로 처리 → (uri_parts, file_refs).

    기존 _process_files_api 루프 몸통과 동일: Redis HIT 재사용 / MISS standby 선점
    업로드 / waiter 대기 / timeout Y' Hybrid. 호출자별로 빈 리스트를 새로 만들어
    받으므로 파일별 그룹이 자연히 분리된다.
    """
```

- **불변 보장**: `_process_files_api` 는 이 헬퍼를 루프에서 호출하도록 바꾸되, 각 파일의
  반환 part/ref 를 기존처럼 단일 `uri_parts`/`file_refs` 에 `extend` 한다 → 평탄화 결과 동일.
  context cache 생성(분기 ④)·분기 A 조회는 `_process_files_api` 에 그대로 남긴다.
- 회귀 방지: 추출 전후로 `tests/_internal/file_processing/test_resolver*.py` 그대로 통과해야 함.

### 4.2 `file_preprocessing` 내부 흐름

위치: `_internal/file_processing/` 에 신설 모듈 `preprocess.py` (resolver.py 비대화 방지,
FOCUSED). 공개 래퍼는 `__init__.py` 에 `file_preprocessing`/`_async` (llm_request 와 동형).

```
file_preprocessing_async(llm_input, *, stored_files, timings):
  ensure_configured (to_thread)
  t = _resolve_timings(timings)                      # context_cache_ttl, standby_ttl 만 사용
  files = await resolve_stored_files(stored_files)   # validators(mime/size) fail-fast
  checksums = [make_file_checksum(fi) for fi in files]

  # ── 전 파일 강제 files_api (classify 안 씀) ──
  per_file_uris: list[list[str]] = []
  file_refs_all: list[FileRef] = []
  for fi, cs in zip(files, checksums):
      _uri_parts, refs = await _resolve_one_files_api(fi, cs, standby_ttl_seconds=t["standby_ttl"])
      per_file_uris.append([r.uri for r in refs])   # 파일별 그룹 (FileRef.uri — resolver.py:224 와 동일)
      file_refs_all.extend(refs)

  ctx_ttl = t["context_cache_ttl"]
  if ctx_ttl and ctx_ttl > 0:
      if not llm_input.get("model"):
          raise ValueError("context cache 생성에는 model 필요")
      hash_key = cache_store.make_context_cache_key(checksums, model=..., system=..., tools=..., tool_config=...)
      name = await _create_and_save_context_cache(   # standby dedup 포함은 4.2.1 참조
          hash_key, checksums, file_refs_all, model=..., ttl=ctx_ttl, ...)
      if name:                                       # name(=cached_content 이름) 은 생성 성공 증거일 뿐
          return hash_key                            # ← 반환은 context_cache_id(=hash_key, Redis 키)
      # too-small fail-soft (name is None) → uri 폴백
  return per_file_uris                               # ← files_api 모드: (n, ?) 파일별 uri
```

#### 4.2.1 context cache 생성 시 dedup

`_process_files_api` 분기 ④ 와 동일하게, context cache 생성도 `dedup` standby 로
보호한다(중복 생성 방지). 이 부분도 분기 ④ 의 try_acquire/wait/timeout 블록을
**그대로 재사용**할 수 있게 작은 헬퍼(`_resolve_or_create_context_cache(hash_key, ...)`)로
추출할지, 복제할지는 4.1 추출과 함께 결정한다(같은 SSOT 판단). → 추출 권장.

### 4.3 `delete_context_cache` (구 `delete_cache` 대체, 5초 고정)

- `__init__.py`: 구 `delete_cache`/`_async` 제거, `delete_context_cache(cache_ids)`/`_async` 신설
  — `grace_seconds` 없음. 내부 상수 `_DELETE_GRACE_SECONDS = 5` 로 `expire_caches(ids, 5)` 호출.
- `context_cache_lifecycle.expire_caches`/`_expire_one` 은 grace 파라미터 유지(내부 호출용).

### 4.4 `update_context_cache` — `_extend_one`

`context_cache_lifecycle.py` 에 `extend_caches`/`_extend_one` 신설. `_expire_one` 의 거울:

```
_extend_one(cache_id, ttl):
  doc = find_context_cache(cache_id)          # ① Redis 조회
  if not doc:
      return failed("연장할 캐시 없음")         #   ← 부재=실패 (delete 와 반대)
  name = doc["cached_content_name"]
  await llm_aio.update_cache(name, ttl)        # ② Gemini update (404 → failed: 캐시 사라짐)
  cache_store.set_context_cache_ttl(cache_id, ttl)  # ③ Redis TTL 연장 (실패해도 Gemini 는 연장됨 → expired)
  return expired
```

- cache_store 에 `set_context_cache_ttl(hash_key, ttl)` 추가 — 기존 `shrink_context_cache_ttl`
  과 같은 `_expire`(Redis EXPIRE) 래퍼지만 **의도가 연장**이라 이름을 분리(EXPLICIT).
  (EXPIRE 는 늘리기/줄이기 둘 다 가능하나, 키 부재 시 no-op 이므로 ②에서 Redis 부재를
  먼저 걸러야 ③이 의미 있음.)
- 404 처리: `_expire_one` 은 404 를 expired(이미 사라짐=목적 달성)로 보지만, `_extend_one`
  은 **연장 대상이 사라진 것이므로 failed**. → 의미 반대(§2.4).

### 4.5 입력 가드 — `cachedContents/` 거부 (delete·update 공통)

`__init__.py` 의 `delete_context_cache`/`update_context_cache`(+`_async`) 래퍼에서, 기존
빈 ids / ttl 범위 가드와 **같은 자리**에 한 줄 추가한다:

```python
def _reject_cached_content_name(ids: list[str]) -> None:
    """Gemini cache id(cached_content_name)를 hash_key 자리에 넣은 실수를 fail-fast.

    두 식별자는 형태가 확연히 다름 — context_cache_id 는 64-hex(sha256),
    cached_content_name 은 'cachedContents/...'. 후자는 Redis 키 매칭이 안 돼
    조용한 no-op(만료/연장 안 됐는데 success)이 되므로 즉시 막는다(FAIL-LOUD).
    file_preprocessing 이 dict 로 둘 다 노출하므로 혼동 가능 → 가드 필요.
    """
    bad = [i for i in ids if i.startswith("cachedContents/")]
    if bad:
        raise ValueError(
            f"context_cache_id(hash_key)를 넣으세요 — cached_content_name 은 받지 않습니다: {bad}"
        )
```

- 위치: 인자 정규화(str→list) 직후, `expire_caches`/`extend_caches` 호출 **전**.
- delete·update 양쪽 동일 적용(SSOT — 헬퍼 1개 공유).

## 5. 에러 처리

| 상황 | file_preprocessing | update_context_cache |
|---|---|---|
| validators(mime/size) 위반 | 진입 즉시 raise(기존 fail-fast) | — |
| context cache too-small(1024 미만) | fail-soft → `(n,?)` uri 폴백 | — |
| Gemini 404 (files_api) | `_resolve_one_files_api` 내 업로드 단계라 404 자동복구 범위 밖(아직 호출 전). 업로드 실패는 그대로 raise | — |
| Redis 조회/저장 실패 | `CacheError` raise (기존 resolver 와 동일) | id 별 `failed` |
| Redis 키 부재 | 해당 없음(업로드하면 생김) | id 별 `failed`("연장 대상 없음") |
| Gemini update 5xx | — | id 별 `failed` |
| 빈 cache_ids / ttl 범위밖 | — | `ValueError`(delete 와 동일 가드) |
| `cachedContents/...` 입력 | — | `ValueError`(hash_key 만 받음, §4.5 — delete 도 동일) |

- **partial failure**: `update_context_cache` 는 `delete_context_cache` 처럼 id 별 독립 처리 →
  `ExpireResult(expired=[...], failed=[ExpireFailure...])`. 일부 실패해도 raise 안 함.

## 8. 사용 예시

### 8.1 `file_preprocessing` — files_api 모드 (context cache 안 함)

```python
from llm_manager import file_preprocessing_async, StoredFile

# 파일만 미리 업로드해 URI 확보 (context_cache_ttl 미지정)
uris = await file_preprocessing_async(
    {"model": "gemini-2.5-flash"},          # contents 불필요 (LLM 호출 안 함)
    stored_files=[StoredFile(**sf_a), StoredFile(**sf_b)],
)
# uris == [["files/aaa"], ["files/bbb1", "files/bbb2"]]   # (n, ?) — b 는 분할되어 2개
```

### 8.2 `file_preprocessing` — context cache 모드

```python
cache_id = await file_preprocessing_async(
    {"model": "gemini-2.5-flash", "system": "너는 ESG 분석가다"},
    stored_files=[StoredFile(**sf_a), StoredFile(**sf_b)],
    timings={"context_cache_ttl": 1800},     # opt-in → 전체에 대해 cache 1개
)
# cache_id == "<hash_key 64-hex>"  (생성 성공 — context_cache_id, update/delete 에 그대로 사용)
#   또는      [["files/aaa"], ["files/bbb"]]  (too-small fail-soft → uri 폴백)
```

### 8.3 캐시 만료 / 연장

```python
from llm_manager import delete_context_cache_async, update_context_cache_async

# 만료 — 무조건 5초 뒤 (시간 인자 없음)
await delete_context_cache_async(cache_id)

# 연장 — 사용자가 TTL 선택 (1~3600초)
res = await update_context_cache_async(cache_id, ttl=3600)
# res.expired == [cache_id]              (연장 성공)
# res.failed  == [ExpireFailure(...)]    (Redis 부재/404 등)
```

> `cache_id` 는 `file_preprocessing`(context cache 모드)이 반환한 값을 그대로 쓰거나,
> `llm_request` 응답 `meta.context_cache_id` 로 얻는다 — 둘 다 같은 `context_cache_id`(hash_key).
