## 1. 변경 배경

### 근본 문제: Files API URI가 캐시를 깬다

ESG Agent는 분석 보고서 PDF 등 파일을 Gemini에 전송할 때 **Gemini Files API**를 사용합니다.
Files API는 파일을 업로드하면 `files/abc123` 형태의 URI를 반환하는데,
**같은 파일이라도 업로드할 때마다 URI가 바뀝니다.**

기존 `llm-request`는 이 URI를 LLM 입력 그대로 캐시 키에 포함시켰기 때문에,
같은 파일로 같은 질문을 해도 URI가 달라진 순간 **항상 cache miss**가 발생했습니다.

```
1차 호출: llm_input = {contents: "분석해줘", file_uri: "files/abc123"} → cache miss → LLM 호출
2차 호출: llm_input = {contents: "분석해줘", file_uri: "files/xyz789"} → cache miss → LLM 호출  ← 같은 파일인데!
```

이 문제를 해결하려면 **"파일의 동일성"을 URI가 아닌 파일 자체의 정보로 판단**해야 했습니다.
파일명 + 수정시각 + 크기로 구성한 checksum을 캐시 키에 넣고,
URI 등 매번 바뀌는 volatile 값은 캐시 키에서 제외하는 방식으로 해결했습니다.

### 파일 처리가 에이전트 책임이었던 문제

기존에는 파일을 Gemini에 전송하는 방식(inline / Files API / context cache)을 **에이전트 개발자가 직접 결정하고 구현**해야 했습니다.

- 20MB 이하 → inline(base64)으로 보낼지
- 20MB 초과 → Files API로 업로드할지
- 자주 쓰는 파일 → context cache를 만들어 토큰 비용을 아낄지
- 50MB 초과 PDF → 어떻게 분할해서 올릴지

이 판단과 처리가 에이전트마다 중복 구현되거나, 아예 구현되지 않은 채로 방치되었습니다.
**파일 처리의 일반화**가 필요했습니다.

### 목표

1. **파일 동일성 = checksum 기반**: 같은 파일이면 URI가 달라도 cache hit
2. **파일 처리 자동화**: inline/Files API/split 분기를 llm-request가 책임지고, 에이전트는 파일 메타정보만 넘기면 됨
3. **Files API URI 재사용**: 한 번 업로드한 파일의 URI를 Redis에 저장해 중복 업로드 방지
4. **서버화**: 에이전트마다 DB에 직접 연결하지 않고, 중앙 Service가 처리

이 과정에서 파일 저장 자체는 llm-request의 범위를 벗어난다는 판단 하에
**file_manager** 서비스를 별도 아이디어로 분리했습니다.
llm-request Service는 파일 바이트를 직접 보관하지 않고, file_manager에 HTTP 요청으로 가져오는 구조입니다.

### 변경 요약

| 문제 | 해결 |
|------|------|
| Files API URI가 캐시 키에 포함 → 항상 miss | checksum 기반 캐시 키, URI는 volatile로 제외 |
| 파일 처리 방식을 에이전트가 직접 구현 | file_handler가 크기/타입별 자동 분기 |
| 같은 파일 매번 재업로드 | Redis에 URI 캐시 (47h), 재사용 |
| PDF 50MB 초과 업로드 불가 | 자동 분할 후 병렬 업로드 |
| 에이전트마다 DB 직접 연결 | Service(port 8101)로 중앙화 |
| 파일 저장 책임 불명확 | file_manager 서비스로 분리 |

## 2. 변경 흐름 (시간순)

이 PR의 커밋들은 크게 **6단계**로 나뉩니다.

### Stage 1: 라이브러리 기반 다듬기

| 커밋 | 내용 |
|------|------|
| `8c14231` | `llm_worker` → `llm_request` 패키지명 변경 + 함수명 통일 |
| `89b0793` | 에러 핸들링 개선 — silent failure 방지 |
| `c433606` | MongoDB 문서 키를 `cache_key` → `_id`로 변경 (중복 방지) |
| `fc13f2a` | `meta` → `metadata` 필드명 통일 |
| `68fdc54` | LLM 호출 실패 시 에러 결과도 MongoDB에 저장 |
| `657533d` | error-saving 로직 재검토 후 제거 (불필요 판단) |
| `a99b888` | 캐시 키 생성 시 빈 문자열 처리 통일 |

**왜?** 서버화 전에 기존 라이브러리의 동작을 안정화. 캐시 키 결정성(determinism)을 확보해야
서버화 후에도 같은 입력 → 같은 캐시 키가 보장됨.

### Stage 2: Checksum 기반 파일 캐시 키

| 커밋 | 내용 |
|------|------|
| `d3fb1ee` | 파일 포함 요청의 checksum 저장 로직 설계 (docs) |
| `f07a572` | `checksum.py` 구현 — SHA-256(file_name + mtime + size) |
| `b46efc6` | `fetch_by_cache_key()` 함수 구현 — 캐시 키로 직접 조회 |

**왜?** 파일의 동일성을 판단하는 핵심. `file_uri`나 `cached_content`는 업로드할 때마다 바뀌므로
캐시 키에서 제외하고, 파일 내용 기반의 checksum만 포함시켜야 cache hit 가능.

**핵심 결정**: 파일 전체를 SHA-256 해싱하면 2GB 파일에 ~4초 소요.
→ `(file_name, file_mtime, file_size)` 튜플로 대체. mtime touch 시 false miss 감수.

### Stage 3: File Handler 구현 (라이브러리 단계)

| 커밋 | 내용 |
|------|------|
| `61e5b39` | file_handler 핵심 모듈 구현 (resolver, cache_store, uploader, splitter) |
| `bc53b1a` | validators 추가 (MIME 검증, 2GB 제한) |
| `fd35eb0` | 파일 분류 로직 개선 (partial mixing 전략) |
| `805f2c8` | 버그 수정 |

**왜?** 서버화 전에 **라이브러리로 먼저 동작 검증**. 이 단계에서 파일 처리 로직의 정확성을 확인한 뒤
서버로 옮기는 전략. ("로직 검증 먼저, 구조 변환은 나중에")

**file_handler 핵심 로직:**

```
파일 입력
  ↓
classify_files()  ← 파일 크기/타입별 분류
  ├── inline_pool (≤20MB, 이미지/오디오 포함 시)
  │                (≤50MB, PDF/텍스트만 있을 때)
  └── files_api_pool (나머지)
  ↓
process_inline()  ← 바이트 → base64 Part
  ↓
process_files_api()  ← 3단계 폴백
  ├── A. Redis context_cache HIT → cached_content 반환
  ├── B. Redis files_api HIT → URI 재사용
  └── C. MISS → 업로드 → Redis 저장
        └── PDF >50MB → split_pdf() → 파트별 업로드
  ↓
(opt) D. context_cache 생성 (context_cache_ttl 지정 시)
```

### Stage 4: 서버화 (SDK + Service 분리)

| 커밋 | 내용 |
|------|------|
| `03dd9c0` | **핵심 커밋** — 전체 구조를 `sdk/` + `service/`로 분리 |

**왜?** 에이전트 머신에서 MongoDB/Redis/LLM-handler에 직접 연결하지 않고,
Service가 중앙에서 모든 백엔드 로직을 처리.

**변경 내용:**

```
변경 전 (라이브러리):
  llm_request/
    ├── __init__.py     ← 직접 MDB/Redis/LLM 호출
    ├── runner.py
    ├── keying.py
    └── ...

변경 후 (SDK + Service):
  sdk/llm_request/
    ├── __init__.py     ← HTTP 클라이언트만 (httpx)
    ├── _client.py      ← AsyncClient (base_url → Service)
    ├── models.py       ← RequestResult, DoneCheckResult
    └── exceptions.py   ← SDKError, ServiceError

  service/app/
    ├── main.py         ← FastAPI 앱 (port 8101)
    ├── config.py       ← 환경변수 설정
    ├── core/
    │   ├── providers.py     ← MDB/Redis/LLM 핸들러 초기화
    │   ├── errors.py        ← 에러 계층구조
    │   └── file_manager_client.py  ← file_manager HTTP 클라이언트
    ├── logic/
    │   ├── runner.py        ← prepare → 파일처리 → call → finalize
    │   ├── keying.py        ← 캐시 키 생성
    │   ├── done_check.py    ← MDB 조회
    │   ├── store.py         ← MDB 저장
    │   └── file_handler/    ← (Stage 3에서 구현한 로직 이관)
    ├── models/              ← Request/Response DTO
    └── routers/
        └── request.py       ← API 엔드포인트
```

**Service API 엔드포인트:**

| Method | Path | 용도 |
|--------|------|------|
| POST | `/v1/request` | LLM 요청 (비스트리밍) |
| POST | `/v1/request/stream` | LLM 요청 (SSE 스트리밍) |
| POST | `/v1/done-check` | 캐시 조회만 (LLM 호출 X) |
| POST | `/v1/fetch` | cache_key로 직접 조회 |
| GET | `/health` | 헬스체크 |

### Stage 5: File Manager 분리

| 커밋 | 내용 |
|------|------|
| `73a3311` | file_manager 분리 + SDK에서 파일 업로드 로직 제거 |
| `d81b804` | file_manager 완전 분리 |

**왜?** llm-request가 "LLM 캐싱 서비스"와 "파일 관리"를 동시에 담당하면 책임이 과중.
파일 저장/조회는 별도 `file_manager` 패키지로 분리.

**변경 사항:**
- SDK: 파일 바이트를 직접 전송하지 않음. `FileMeta`(메타정보만) 전달
- Service: 파일 바이트가 필요할 때 `file_manager` 서비스에 HTTP 요청으로 가져옴 (lazy fetch)
- `file_manager_client.py` 추가 — file_manager 서비스와의 HTTP 통신 담당

### Stage 6: Cache Stampede Dedup + Observability + 버그 수정

| 변경 | 내용 |
|------|------|
| `dedup.py` 신설 | Redis SETNX standby 패턴 — 3계층(files_api/context_cache/agent_llm) 동시 적용 |
| runner.py 통합 | leader/waiter 분기, exponential backoff 대기, Y' Hybrid timeout 정책 |
| `[route]`/`[dedup]` 로깅 | resolver.py + runner.py에 `logger.info` 추가 — meta 스키마 변경 없이 분기 추적 |
| `meta.route_reason` | debug=True 시 응답에 라우팅 이유 포함 |
| SDK `Timings` TypedDict | 흩어진 ttl 인자 4종을 단일 `timings=` 인자로 통합. private `_configure` 삭제 |
| `create_cache` 인자명 수정 | llm-handler v0.1.1 Breaking Change 대응 — `system_instruction=` → `system=` |

**왜?** Phase A 구현 후 운영 관점에서 드러난 문제 해결.
- 동시성으로 인한 비용 폭증(stampede) → SETNX standby로 해결
- 분기/캐시 동작이 meta로 안 보이는 문제 → grep 가능한 `key=value` 로그로 노출
- ttl 인자가 함수마다 흩어져 사용 어려움 → 단일 dict로 통합

### Stage 7: File-manager bytes passthrough — 왕복 제거

| 변경 | 내용 |
|------|------|
| 에이전트 DTO 교체 | `file_metas: list[FileMeta]` → `files: list[FileInput]` (meta + bytes) |
| `ingest.py` 신설 | 서비스 진입점에서 file-manager 호출 흡수 (`acheck_cache` + `aupload_file`) |
| `aget_file` 제거 | resolver가 에이전트가 준 bytes를 그대로 LLM payload에 사용. file-manager 왕복 삭제 |
| file-manager SDK 단순화 | `acheck_cache` → `bool`, `aupload_file` → `None`. `CacheCheckResult` 타입 제거 |
| file-manager 엔드포인트 축소 | `/files/check-cache` → `{hit: bool}`, `/files/upload` → `{ok: true}` |
| `UploadRequest` 확장 | `mime_type`, `extension` 필드 추가 (agent 제공, 없으면 서버 추론 fallback) |
| `FileInput`/`FileKeyingMeta` 신규 | 파이프라인은 FileInput이 그대로 관통. 별도 내부 타입 없음 |
| `/v1/done-check` 경량화 | `FileKeyingMeta`(hashing 3필드만) 수신 |

**왜?** Stage 5에서 file-manager를 분리한 뒤 운영해 보니 왕복 I/O 문제가 드러남 — 에이전트는 이미 파일 bytes를 갖고 있는데, 에이전트가 file-manager에 업로드하고 받은 `file_path`로 llm-request가 다시 bytes를 `aget_file()` 한다. 매 요청마다 왕복이 한 번씩 끼는 구조.

**근본 판단**:
- file-manager의 목적은 **사후 로깅 저장소** (문제 발생 시 감사용). LLM 응답 경로에 끼어들 이유가 없음.
- 에이전트 개발자가 file-manager SDK까지 숙지해야 하는 부담 → 책임 축소 필요.

**권한 경계 재정의**:

| 주체 | 제공/소유 |
|---|---|
| 에이전트 | `file_name`, `file_size`, `file_mtime`, `mime_type`, `extension`, `data(bytes)` |
| file-manager | `file_path` 등 내부 식별자 (외부 비노출) |

hashing 3필드 (name + size + mtime)만 cache key 계산에 사용. 나머지 meta는 LLM payload/로깅에 사용.

**명시적 비-목표**:
- 파일 무결성 검증 (checksum 대조) 안 함 — 방침 결정 사항
- mime_type/extension 내용 검증 안 함 — 에이전트 값 신뢰

상세 설계: [file-manager-bytes-passthrough.md](10.file-manager-bytes-passthrough.md)

### 3-Layer 캐시 구조

```
요청 도착
  │
  ├─ Layer 1: MongoDB (agent_llm)
  │   키 = SHA-256(llm_input + file_checksums)
  │   "같은 질문 + 같은 파일 → 같은 응답"
  │   HIT → LLM 호출 없이 즉시 반환
  │
  ├─ Layer 2A: Redis files_api (TTL 47h)
  │   키 = file_cache:files_api:{checksum}
  │   "이 파일 이미 Gemini에 업로드됨?"
  │   HIT → URI 재사용, 재업로드 불필요
  │
  └─ Layer 2B: Redis context_cache (TTL 사용자 지정)
      키 = file_cache:context_cache:{hash}
      "이 파일+모델 조합의 context cache 있음?"
      HIT → cached_content 이름 재사용 (토큰 90% 할인)
```

## 4. 주요 변경 상세

### 4.1 캐시 키 결정성 (keying.py)

**문제**: LLM 입력에는 `timestamp`, `request_id`, `file_uri` 등 매번 바뀌는 값이 포함됨.
이 값들이 캐시 키에 들어가면 동일 요청도 매번 cache miss.

**해결**:
```python
# canonicalize_input()이 하는 일:
# 1. 허용 필드만 추출 (contents, model, temperature, file_checksums 등)
# 2. volatile 키 제거 (timestamp, request_id, cached_content, file_uri 등)
# 3. None → "", float → 소수점 4자리, 중첩 정렬
# 4. JSON 직렬화 → SHA-256
```

**핵심 규칙**:
- `file_checksums` → 캐시 키에 **포함** (파일 동일성 핵심)
- `cached_content` → 캐시 키에서 **제외** (업로드마다 달라짐)
- `file_uri` → 캐시 키에서 **제외** (업로드마다 달라짐)

### 4.2 파일 분류 전략 (resolver.py — classify_files)

단순한 "전부 inline" 또는 "전부 Files API"가 아닌, **partial mixing** 전략:

```
파일 목록: [3MB img, 15MB pdf, 25MB pdf, 100MB video]

1. video → 무조건 Files API (inline 불가)
2. 나머지를 크기순 정렬: [3MB img, 15MB pdf, 25MB pdf]
3. 이미지/오디오 포함 → 임계값 20MB
   → 3MB img (누적 3MB, ≤20MB ✓) → inline
   → 15MB pdf (누적 18MB, ≤20MB ✓) → inline
   → 25MB pdf (누적 43MB, >20MB ✗) → Files API

결과: inline=[3MB img, 15MB pdf], files_api=[25MB pdf, 100MB video]
```

**왜 partial mixing?**
- 작은 파일을 Files API로 보내면 업로드 오버헤드만 증가
- 큰 파일을 inline으로 보내면 요청 body가 거대해짐
- 적절히 섞어서 비용과 성능의 균형

### 4.3 PDF 분할 (splitter.py)

Gemini Files API 단일 파일 제한: 50MB.

```
100MB PDF (200페이지)
  ↓
split_pdf(target_mb=50)
  ↓
페이지별 바이트 추정 (이미지 + 텍스트/벡터)
  ↓
그리디 패킹: 청크 ≤50MB까지 페이지 누적
  ↓
[청크1: 1-95페이지, 48MB] [청크2: 96-200페이지, 52MB]
  ↓
52MB 청크 → 재귀 분할 (최대 depth 3)
  ↓
후처리: 인접한 작은 청크 병합 (≤45MB)
  ↓
최종: [part1.pdf, part2.pdf, part3.pdf]
  ↓
각각 Files API 업로드 (병렬)
```

### 4.4 SDK 설계 (_client.py, __init__.py)

SDK는 의도적으로 **최소한의 역할**만 수행:

```python
# SDK가 하는 것:
# - llm_input과 files(FileInput list)를 JSON으로 Service에 POST
# - 응답 파싱 (result, meta 튜플)
# - 에러 변환 (HTTP 4xx/5xx → SDKError/ServiceError)

# SDK가 하지 않는 것:
# - MongoDB 직접 접근 ✗
# - Redis 직접 접근 ✗
# - LLM 호출 ✗
# - 파일 바이트 처리 ✗
```

**에러 계층**:
```
SDKError (base)
├── ServiceConnectionError  ← Service 연결 실패/타임아웃
└── ServiceError            ← Service가 4xx/5xx 반환
    └── error_type: "validation" | "cache" | "file" | "handler"
```

### 4.5 Service 에러 처리 (core/errors.py)

```
LLMRequestServiceError (base, 500)
├── CacheError (502)              ← Redis/MDB 장애
├── FileUploadError (502)         ← Gemini 업로드 실패
├── ValidationError (422)         ← 입력 검증 실패
├── UnsupportedFileTypeError (422) ← 지원하지 않는 MIME
└── FileTooLargeError (422)       ← 2GB 초과
```

**fail-fast 원칙**: MIME 타입과 파일 크기는 `prepare()` 진입 전에 검증.
비싼 MDB 조회나 LLM 호출 전에 빨리 거부.

### 4.6 Gemini 404 자동 복구

```
LLM 호출 → Gemini 404 (파일 만료/삭제)
  ↓
resolve_files_after_404()
  ↓
1. Redis files_api:{checksum} 삭제
2. Redis context_cache:{hash} 삭제
3. resolve_files() 재실행 → 재업로드
4. LLM 재호출 (1회만)
5. 또 404 → 에러 raise
```

### 4.7 Cache Stampede Dedup (dedup.py)

**문제**: 동시 요청 N개가 동일한 cache miss를 만나면 N번 중복으로 업로드/context_cache 생성/LLM 호출이 발생.

```
t=0ms   req A, B, C 동시 도착
t=1ms   각자 done_check → MDB miss
t=2ms   각자 Redis files_api 조회 → miss
t=3ms   각자 upload_file() → Gemini 업로드 3회  ⚠️
t=11s   각자 LLM 호출 3회 → 토큰 비용 3배  ⚠️
```

**해결**: Redis SETNX로 "처리 중" standby 레코드를 먼저 선점.

```python
# service/app/logic/file_handler/dedup.py
async def try_acquire_standby(prefix, key, ttl_seconds) -> bool:
    # SETNX: 한 명만 성공, 나머지는 False
    return client.set(standby_key, value, nx=True, ex=ttl_seconds) is not None
```

**3계층 적용** — files_api, context_cache, agent_llm 모두 동일 패턴:

```
요청 도착
  ├── leader (SETNX 성공)  → 작업 수행 → finally: release_standby()
  └── waiter (SETNX 실패)  → wait_for_standby_release()
                              ├── 본 캐시 polling (HIT → 즉시 종료)
                              ├── standby 사라짐 → 자기가 작업 시작
                              └── timeout(기본 600s) → 자기가 작업 시작 (Y' Hybrid)
```

**Exponential backoff**: 0.5 → 1 → 2 → 4 → 8 → 10s (cap), 전체 timeout = `standby_ttl_seconds`.

**Y' Hybrid 정책**: timeout 시 에러 raise 대신 자기가 작업 시작 (caller에 영향 없음, warning 로그만).

**구현 노트**: `redis_handler`에 SETNX 미노출 → `redis_handler.get_client()`로 raw redis-py 클라이언트 직접 사용.

**레디스 standby 키 구조**:
```
file_cache:files_api_standby:{checksum}
file_cache:context_cache_standby:{hash_key}
agent_llm_standby:{cache_key}
```

상세 설계: [cache-stampede-dedup.md](08.cache-stampede-dedup.md)

### 4.8 Observability 로깅

`meta` 응답 스키마는 고정한 채, 서비스 로그(uvicorn stdout)만 보고 내부 분기를 추적할 수 있도록 `logger.info` 추가.

**통일 원칙**: `source=live` (신규 처리) / `source=cached` (Redis 재사용) / `source=none` (조건 미충족)

**[route] — 파일별 경로 결정** (resolver.py)
```
[route] file=image.png mode=inline
[route] file=medium.pdf mode=files_api source=cached uris=1
[route] file=large.pdf mode=files_api source=live parts=2 duration_ms=12000
[route] mode=context_cache source=cached name=cachedContents/abc
[route] mode=context_cache source=live name=cachedContents/abc
[route] mode=context_cache source=none reason=no_files_api_files
```

**[dedup] — Standby 역할** (runner.py)
```
[dedup] role=leader key=abc12345
[dedup] role=waiter wait_ms=2134 leader_completed=true
[dedup] role=standby_timeout wait_ms=10000
```

**meta.route_reason** (debug=True 시 응답에 포함)
- `cache_miss`, `cache_hit`, `cache_off_save_off`, `cache_off_save_on`
- `cache_error_fallback`, `cache_deserialize_error`, `standby_wait_hit`

상세: [observability-backlog.md](14.observability-backlog.md)

### 4.9 SDK Timings TypedDict

기존: `mdb_ttl`, `context_cache_ttl`, `standby_ttl_seconds`, HTTP timeout이 공개 함수 시그니처에 흩어져 있고
HTTP timeout은 private `_configure(timeout=...)`로만 설정 가능했음.

변경: `Timings` TypedDict로 4개 키를 단일 인자로 통합. 기본 `http_timeout=600`으로 상향.

```python
# sdk/llm_request/__init__.py
class Timings(TypedDict, total=False):
    http_timeout: float          # SDK → Service HTTP 응답 대기 (기본 600)
    mdb_ttl: int | None          # MDB 응답 캐시 수명 (None=무기한, 기본 None)
    context_cache_ttl: int | None  # Gemini Context Cache 수명 (None=opt-out, 기본 None)
    standby_ttl: int             # Cache stampede dedup standby TTL (기본 600)

# 사용
result, meta = await llm_request_async(
    llm_input,
    files=[...],
    timings={"http_timeout": 1200, "context_cache_ttl": 3600},
)
```

`_configure()` private 함수는 삭제됨.

| `LLM_HANDLER_URL` | `http://192.7.9.45:8100` | Service → Gemini |

**에이전트 측**: `LLM_REQUEST_URL`만 필요. `FILE_MANAGER_URL`은 llm-request 서비스 측에서만 설정.

### Docker

Service는 `service/Dockerfile`로 컨테이너화 가능. port 8101 expose.

### Redis 필수 의존성

**Redis가 없으면 Service가 시작되지 않습니다.** Redis는 선택적 최적화가 아니라,
Files API URI 캐시(47h)와 context_cache 재사용에 필수적인 인프라입니다.
startup 시 `_ensure_redis_connected()`로 연결을 확인하며, 연결 실패 시 에러를 raise하고 서비스가 종료됩니다.

```
REDIS_URL 미설정 또는 연결 불가 → Service startup 실패
```

### Startup standby flush

Service 재기동 시 이전 세션이 남긴 stale standby 키를 일괄 정리합니다.
**전제**: llm-request는 단일 docker 인스턴스로 운영 → 재기동 시 점유 중인 leader가 없음.

```
대상 패턴:
  file_cache:*_standby:*    (files_api / context_cache standby)
  agent_llm_standby:*       (agent_llm standby)
```

[providers.py](../service/app/core/providers.py)의 `_flush_stale_standbys()`가 lifespan 시작 시 SCAN+DEL로 처리.
정리된 키 개수는 `startup standby flush: N stale keys 정리` 로그로 노출됨.

## 9. 이슈 대응

### Issue #441: re-export 목록에서 async 함수 누락 + llm_handler 직접 import 강제

**이슈 내용**: `llm_request`의 re-export 목록에서 `create_cache`, `configure` 등이 async로 노출되지 않음. `llm_handler.aio`에 이미 async 구현이 있으니 이를 참조해서 연결 필요.

#### main 기준 문제 진단 (이슈 raise 시점)

main의 `packages/llm-request/llm_request/__init__.py`는 sync 버전만 flat re-export하고 있었음:

```python
# main: packages/llm-request/llm_request/__init__.py
import llm_handler
import llm_handler.aio              # 모듈만 import, 함수 노출 X
from llm_handler import (
    ...
    configure,
    create_cache,
    delete_cache,
    list_caches,
    upload_file,                    # ← sync 버전만 flat re-export
    ...
)
```

→ async 함수를 쓰려면 `llm_request.llm_handler.aio.create_cache()`처럼 긴 경로로 접근해야 했음. 이

#### 이 PR에서 해결된 방식

**1) async re-export — SDK 분리 과정에서 해결됨**

SDK/Service 분리(Stage 4)에서 `llm_request.aio` 서브모듈을 신설:

```python
# sdk/llm_request/aio.py (이 PR에서 신설)
from llm_handler.aio import (
    call, configure, create_cache, delete_cache,
    embed, list_caches, session, stream, upload_file,
    AsyncSession, CacheRef, ..., FileRef, ...,
)
```

이제 외부는 `from llm_request.aio import create_cache` 식으로 async 함수를 그대로 사용 가능. 별도 경로(`llm_request.llm_handler.aio.*`) 불필요.

**2) sync 쪽 configure 이름 충돌 — 추가 수정**

이슈 검토 중 발견: sync 쪽 `llm_request.configure`가 llm-request 자체의 base_url 설정 함수를 가리키고 있어 **llm_handler.configure가 덮어씌워져 노출 불가**했음.

[sdk/llm_request/__init__.py](../sdk/llm_request/__init__.py) 수정:

- `from llm_handler import (...)` 목록에 `configure` 추가 → flat re-export
- 기존 `def configure(...)` (llm-request 자체 함수) → `def _configure(...)`로 private 처리
- `__all__`의 `"configure"` 위치를 llm_handler flat re-export 섹션으로 이동

llm-request 자체 서비스 URL은 `LLM_REQUEST_URL` 환경변수로 제어하므로 public 함수가 불필요했고, 테스트/내부 오버라이드용으로만 `_configure`를 남김.

**참고**: `configure`는 싱글톤 클라이언트 인스턴스를 설정하는 함수로 네트워크 I/O가 없어 sync로 구현됨. llm_handler 원본도 sync(`def`)이며, async 전환은 불필요.

#### 결과

```python
# 외부 사용 (llm_handler 직접 import 없이, sync/async 모두 지원)
from llm_request import configure, create_cache           # sync
from llm_request.aio import configure, create_cache       # async (create_cache만 async def)

# sync
configure(base_url="http://handler:8100")
cache = create_cache(...)

# async
configure(base_url="http://handler:8100")                 # configure는 sync 동일
cache = await create_cache(...)
```

| 항목 | main 기준 | 이 PR 기준 |
|------|-----------|------------|
| `llm_request.create_cache` (sync) | O | O |
| `llm_request.aio.create_cache` (async) | ✗ 없음 | **O 신설** |
| `llm_request.configure` → llm_handler.configure | ✗ llm-request 자체 함수가 덮어씀 | **O 수정** |
| `llm_request.aio.configure` → llm_handler.aio.configure | ✗ 없음 | **O 신설** |
