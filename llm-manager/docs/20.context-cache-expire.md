# 20. Context Cache Expire API

agent 가 task 종료 시점에 Context Cache 의 storage 비용을 prorate 단축할 수 있도록 expire API 를 추가한다.

---

## 1. 배경/문제 정의

### 현재 상태

`timings={"context_cache_ttl": N}` 을 지정하면 Service 가 Gemini Context Cache 를 생성하고 Redis 에 매핑을 저장한다. TTL 동안 같은 hash_key 요청은 이 cache 를 재사용한다. **TTL 만료 시점은 cache 생성 시점에 결정되며, 그 이후 변경 수단이 없다.**

### 문제

agent 가 처음에 TTL 을 정확히 추정하기 어렵다. 안전하게 길게 잡으면 task 가 끝난 후에도 storage 비용이 계속 누적되고, 너무 짧게 잡으면 cache 가 자주 재생성되어 cache write 비용 + 레이턴시 손해를 본다. **task 종료 시점을 agent 가 알지만 서버는 모르므로, agent 가 능동적으로 cache 수명을 단축할 수 있는 수단이 필요하다.**

### 목표

- agent 가 cache 가 더 이상 필요 없을 때 명시적으로 단축 요청할 수 있는 SDK/HTTP 인터페이스 제공
- 단축 후 Gemini storage 비용을 grace period 까지로 prorate 청구하도록 보장
- in-flight 요청을 끊지 않는 grace 안전장치 내장
- 기존 cache 동작 (자연 만료, 자동 생성) 은 변경 없음

### 비목표 (scope 밖)

- TTL 연장 (extend) — 처음 TTL 보다 길게 늘리는 기능. YAGNI.
- shared cache 충돌 방지 — 같은 hash_key 를 쓰는 다른 agent 보호. cache 재생성 비용이 작아서 (write 1회 < storage 1h) 그대로 수용.
- 자동 refcount — 서버가 reference 추적해서 자동 단축. 분산 환경에서 추적 비용 큼.

## 2. 사전 정보 — Gemini Context Cache 청구 동작

공식 forum 답변 ([thread #81267](https://discuss.ai.google.dev/t/clarification-on-context-cache-storage-billing-ttl-vs-actual-time/81267)) 기준 청구 동작:

| 동작 | 청구 |
| --- | --- |
| `caches.delete(name)` | **원래 설정한 TTL 그대로 청구**. delete 는 비용 절감 효과 없음. |
| `caches.update(name, ttl=...)` | **새 TTL 기준으로 prorate 청구**. 분 단위 (minute-level prorate). |

→ **반드시 update API 사용.** delete 는 의미 명확하지만 비용 절감 X.

### 비용 영향 예시 (gemini-2.5-flash, 100K 토큰 PDF)

| 시나리오 | Storage 비용 |
| --- | --- |
| TTL 1h 자연 만료 (현재) | $0.10 |
| TTL 1h 잡고 30분 후 update(ttl=60s) | ~$0.052 (약 48% 절감) |
| Grace 60s 추가 storage 비용 | ~$0.017 (무시 가능) |

storage 가격: $1.00 / 1M tokens / hour (gemini-2.5-flash 기준).

## 3. 저장소/스키마 설계

### 3.1 Redis 키 구조 — 변경 없음

기존 키 그대로:

```
file_cache:context_cache:{hash_key}        → {file_checksums, model, ..., cached_content_name, files_api_uris}
```

→ 새 키 (reverse index 등) **신설하지 않음**. 응답에 `hash_key` 자체를 opaque 식별자로 노출하여, expire 시 agent 가 그걸 전달하면 서버가 한 번의 GET 으로 doc 을 찾는다.

근거: `cached_content_name → hash_key` 역방향이 필요한 유일한 시점은 expire 인데, 그 시점 agent 가 식별자를 들고 있으므로 응답 노출이 reverse index 보다 단순하다.

### 3.2 RequestMeta 응답 스키마 변경

기존 `RequestMeta` 에 단일 필드 추가:

```python
class RequestMeta(BaseModel):
    source: str
    cache_hit: bool
    cache_key: str | None = None
    ...
    context_cache_id: str | None = None   # 신규
```

- Context Cache 가 생성/재사용되었을 때만 값. 그 외 `None`
- 응답 dict 에서는 `None` 일 때 키 자체 부재 (`file_meta` 와 동일 패턴)
- 값은 내부 `hash_key` (64-char hex) 와 동일하지만, SDK 사용자에겐 **opaque token** 으로 문서화 — expire 용도 외 의미 없음

> **명명 근거**: `cached_content_name` 은 Gemini 가 발급한 cache 의 내부 식별자라 SDK 노출이 어색. `hash_key` 도 내부 구현 노출이라 같음. → 추상화된 `context_cache_id` 채택.

### 3.3 신규 Request/Response 모델

```python
# models/requests.py
class ExpireContextCacheRequest(BaseModel):
    cache_ids: list[str] = Field(min_length=1)
    grace_seconds: int = Field(default=60, ge=1, le=3600)

# models/responses.py
class ExpireContextCacheResponse(BaseModel):
    expired: list[str]
    failed: list[ExpireFailure]

class ExpireFailure(BaseModel):
    cache_id: str
    error: str
```

## 4. 전체 파이프라인

### 4.1 Cache 생성 경로

기존 로직 그대로. 응답 합성 시점에 [routers/request.py](../service/app/routers/request.py) 에서 `hash_key` 를 `meta.context_cache_id` 로 매핑하는 한 줄만 추가.

```
resolver._process_files_api()
  ↓ hash_key 계산 (기존)
  ↓ cache_store.save_context_cache(hash_key, doc, ttl)  (기존)
  ↓ resolved.context_cache_id = hash_key  (신규: ResolvedResult 에 필드 추가)
  ↓ runner 가 LLM 호출 + 응답 + meta 합성
  ↓ routers/request.py: meta.context_cache_id = resolved.context_cache_id  (신규)
```

cache hit 경로에서도 동일 — `hash_key` 가 이미 계산된 상태이므로 그대로 노출.

### 4.2 Expire 경로 (신규)

```
agent: expire_context_cache_async([id1, id2], grace_seconds=60)
  ↓ SDK: POST /v1/context-cache/expire
       {"cache_ids": [id1, id2], "grace_seconds": 60}
  ↓ Service: routers/context_cache.expire
       asyncio.gather(_expire_one(cid) for cid in cache_ids)
            ↓ 각 cache_id (= hash_key) 별:
            ① cache_store.find_context_cache(hash_key) → doc
                 (없음 → "expired" 분류; 이미 정리됨 / TTL 만료)
            ② name = doc["cached_content_name"]
            ③ Gemini caches.update(name, ttl=f"{grace_seconds}s")
                 (404 NotFound → "expired" 분류)
                 (5xx → "failed" 분류, 다음 cache_id 계속)
            ④ Redis TTL 단축
                 EXPIRE file_cache:context_cache:{hash_key} grace_seconds
  ↓ 응답
       {"expired": [...], "failed": [{"cache_id": "...", "error": "..."}]}
```

**Race window 동작**: grace 60s 동안 같은 hash_key 로 새 요청이 들어오면:
- Redis 키는 grace 동안 살아있음 → HIT → 같은 cached_content_name 으로 generate 시도
- Gemini cache 도 grace 동안 살아있음 → 성공
- grace 후엔 양쪽 다 만료 → 새 요청은 cache miss 로 새로 생성

→ grace 내 in-flight 요청 + 새 요청 모두 안전.

```python
def shrink_context_cache_ttl(self, hash_key: str, ttl: int) -> None:

    self._expire(self._make_key("context_cache", hash_key), ttl)
```

### 5.5 logic/context_cache_lifecycle.py (신규)

expire 로직 모듈 — resolver 의 생성 로직과 분리.

```python
async def expire_caches(cache_ids: list[str], grace_seconds: int) -> ExpireContextCacheResponse:
    results = await asyncio.gather(
        *[_expire_one(cid, grace_seconds) for cid in cache_ids],
        return_exceptions=False,  # 각 _expire_one 안에서 예외 흡수
    )
    expired = [r["cache_id"] for r in results if r["status"] == "expired"]
    failed = [
        ExpireFailure(cache_id=r["cache_id"], error=r["error"])
        for r in results if r["status"] == "failed"
    ]
    return ExpireContextCacheResponse(expired=expired, failed=failed)


async def _expire_one(cache_id: str, grace_seconds: int) -> dict:
    # ① Redis 조회 (cache_id = hash_key)
    doc = cache_store.find_context_cache(cache_id)
    if not doc:
        # 이미 만료 / 정리됨 → idempotent success
        return {"cache_id": cache_id, "status": "expired"}

    name = doc["cached_content_name"]

    # ② Gemini update
    try:
        await llm_handler.aio.update_cache(name, ttl=f"{grace_seconds}s")
    except NotFoundError:
        # 이미 만료 → success
        return {"cache_id": cache_id, "status": "expired"}
    except Exception as e:
        logger.exception("Gemini update_cache 실패: cache_id=%s", cache_id[:16])
        return {"cache_id": cache_id, "status": "failed", "error": str(e)}

    # ③ Redis TTL 단축
    try:
        cache_store.shrink_context_cache_ttl(cache_id, grace_seconds)
    except Exception as e:
        logger.exception(
            "Redis TTL 단축 실패 (Gemini는 단축됨): cache_id=%s", cache_id[:16]
        )
        # Gemini 는 단축됐으니 expired 로 분류 (Redis 는 자연 만료)
        return {"cache_id": cache_id, "status": "expired"}

    return {"cache_id": cache_id, "status": "expired"}
```

## 6. 에러 처리

### 6.1 정상 응답 (200) 내 분류

| 상황 | 분류 |
| --- | --- |
| Redis 키 없음 (이미 정리됨) | `expired` |
| Gemini 404 NotFound | `expired` |
| Gemini update 성공 + Redis 단축 성공 | `expired` |
| Gemini update 성공 + Redis 단축 실패 | `expired` (Gemini 비용 단축됐고 Redis 는 자연 만료) |
| Gemini update 5xx / 네트워크 오류 | `failed` |

→ 호출자는 `failed` 항목 있으면 재시도 또는 무시 결정. 모든 항목 `expired` 면 부담 없음.

### 6.2 422 검증 실패

- `cache_ids` 빈 리스트
- `grace_seconds` 범위 밖 (1 ≤ x ≤ 3600)

### 6.3 SDK 예외

기존 패턴 유지:

- `ServiceConnectionError` — Service 연결 실패
- `ServiceError(error_type=...)` — Service 가 4xx/5xx 응답

새 `error_type` 은 추가 안 함 — expire 자체가 실패해도 다음 호출에 영향 없고, 응답 안 partial failure 가 충분히 표현력 있음.

## 8. 사용 예시

### 기본 — 70개 질문 후 cleanup

```python
from llm_request import llm_request_async, expire_context_cache_async, StoredFile

cache_ids: set[str] = set()

for q in questions:  # 70번
    response, meta = await llm_request_async(
        {"contents": q, "model": "gemini-2.5-flash"},
        stored_files=[StoredFile(**sf_dict)],
        timings={"context_cache_ttl": 3600},
    )
    if meta.context_cache_id:
        cache_ids.add(meta.context_cache_id)

result = await expire_context_cache_async(list(cache_ids))
print(result.expired)   # ["..."]
print(result.failed)     # []
```

### 즉시 만료 원할 때 (race 무시)

```python
await expire_context_cache_async(cache_ids, grace_seconds=1)
```
