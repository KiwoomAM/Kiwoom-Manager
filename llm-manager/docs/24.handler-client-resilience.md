# 24. handler_client 네트워크 복원력 보강 설계

> 장애보고서 「Handler 서비스 연결 오류 (Remote Protocol Error)」 §3-3 의 SDK 구조적
> 취약점을, `llm_manager` 내부 `handler_client` 에 적용하기 위한 설계.

## 1. 배경 / 문제 정의

### 1-1. 장애 맥락
RAG·RM 등에서 `httpx.RemoteProtocolError: Server disconnected without sending a
response` 가 발생, 서버 재부팅으로만 해소된 장애가 있었다. **직접 원인은 WSL2/Docker
네트워크 레벨**(좀비 네트워크 등)로 SDK 코드와 무관하다.

다만 장애 분석 중 발견된 §3-3 의 **SDK 구조적 취약점**이 `api-handler`/`mdb-handler` SDK 와
동일하게 `handler_client` 에도 존재함을 확인했다. 네트워크가 불안정해지는 동일 상황에서
`llm_manager` 소비자(RAG/RM 등)도 똑같이 raw `RemoteProtocolError` 로 터질 수 있다.

### 1-2. handler_client 현 상태 (대조 결과)

| §3-3 항목 | handler_client 현황 | 위치 |
| --- | --- | --- |
| ① Singleton httpx 영구 재사용 | 동일 — 모듈 전역 `_instance` | `__init__.py:107`, `aio.py:74` |
| ② keep-alive race (expiry 5s == server 5s) | 동일 — `Limits` 미설정 | `_sync_client.py:26`, `_client.py:26` |
| ③ RemoteProtocolError 미처리 | 동일 — `ConnectError` 만 catch | `_sync_client.py:46`, `_client.py:46` |

- 서버(llm-handler) uvicorn 은 `--timeout-keep-alive` 미지정 → **기본 5초**
  (`Kiwoom-Handler/llm-handler/service/Dockerfile:15`). client httpx 기본 `keepalive_expiry`
  도 5초 → **동률이라 race 창이 넓다.**
- `RemoteProtocolError` 는 `httpx.ProtocolError → TransportError` 계열로
  `ConnectError` 의 하위가 **아니다** → 기존 except 로 안 잡힘.

### 1-3. 이 설계의 범위
- **①은 유지** — 커넥션 풀 재사용 자체는 정상/바람직. 문제는 *죽은 소켓 재사용*이고
  그건 ②·③ 으로 해결한다. 싱글톤 구조 변경 없음.
- **②·③ 만 보강.** sync(`_sync_client.py`) / async(`_client.py`) 양쪽 동일 적용.

## 2. 사전 정보 (기술 사실)

1. **httpx `HTTPTransport(retries=N)` 는 RemoteProtocolError 를 재시도하지 않는다.**
   연결 *수립* 단계의 `ConnectError`/`ConnectTimeout` 만 대상. 죽은 keep-alive 소켓
   재사용 실패(RemoteProtocolError)는 커버 못 함 → **retries 옵션 미채택.**
2. **"Server disconnected without sending a response" = 요청 미처리.**
   서버가 응답 1바이트도 안 보내고 끊었으므로 그 요청은 처리되지 않았을 가능성이 높다.
   → 비스트리밍 요청 **1회 재시도는 이중 실행 위험이 낮다.**
3. **keep-alive race 해결 원리는 "client 가 server 보다 먼저 idle 소켓을 폐기"** 하게
   만드는 것. client `keepalive_expiry < server timeout-keep-alive(5s)` 면 client 가
   server 마감 전에 소켓을 버려 stale 재사용이 사라진다.

## 3. 결정사항 (확정)

각 항목은 후보 선택지를 비교한 뒤 **굵게** 표시한 안을 택했다.

### ③ RemoteProtocolError 처리 전략
| 선택지 | 내용 | 채택 |
| --- | --- | --- |
| **wrap + call 1회 재시도** | RemoteProtocolError 를 `HandlerConnectionError` 로 wrap, 비스트림 `call` 은 새 소켓으로 1회 재시도. stream 은 wrap-only | ✅ **선택** |
| wrap 만 (재시도 없음) | wrap 만 하고 재시도는 caller 책임 | — |
| TransportError 전체로 확대 | RemoteProtocolError 외 ReadError/WriteError 등 `httpx.TransportError` 계열 전부 흡수 | — |

> **근거**: "응답 없이 끊김 = 요청 미처리"라 비스트림 1회 재시도가 안전하면서도 caller 부담을
> 없앤다. TransportError 전체 확대는 의도치 않은 예외까지 삼킬 위험이 있어 제외.

> **[알려진 한계] (리뷰 #jyoh14)** `httpx.RemoteProtocolError` 는 두 경우에 발생한다 —
> ① 서버가 응답을 **시작하기 전** 끊김(`"Server disconnected without sending a response"`,
> = 미처리, 재시도 안전), ② **본문 수신 도중** 끊김(`"peer closed connection without sending
> complete message body"`, = 서버가 이미 처리·응답 시작). 현재 except 는 메시지를 구분하지 않아
> ②도 재시도한다. 영향: `generate`/`embed` 는 중복 생성(응답 1개라 비용만 낭비),
> `create_cache`(POST `/v1/caches`)는 중복 캐시 생성 가능성. **빈도·영향이 낮아(SIMPLE 기조)
> 동작 변경 없이 한계로만 명시**한다. 더 엄밀히 가려면 ②를 메시지로 식별해 재시도에서
> 제외하거나, 비-idempotent POST(`/v1/caches`)를 path 기반으로 제외하는 방법이 있다 (후속 선택지).

### ② keep-alive race 해결 위치
| 선택지 | 내용 | 채택 |
| --- | --- | --- |
| **A. client 쪽만** | llm-manager SDK 에 `Limits(keepalive_expiry=2.0)` (서버 5s 보다 짧게). 단일 repo, 한 줄 | ✅ **선택** |
| B. server 쪽만 | Kiwoom-Handler uvicorn `--timeout-keep-alive` 를 120s 등으로 상향 | — |
| C. 양쪽 다 | client 짧게 + server 길게 (가장 견고하나 두 repo) | — |
| D. 이번엔 제외 | ② 미변경, ③ 재시도로만 대응 | — |

> **근거**: ③ 재시도가 잔여 race 를 흡수하므로 ②는 "정확성"이 아니라 "발생 빈도 축소"로
> 격하 → cross-repo 조율(B/C)까지 갈 필요 없이 단일 repo A 로 충분. server-side 상향은
> §8 후속 과제로 남김.

### ①·② 관련 — HTTPTransport(retries=)
| 선택지 | 내용 | 채택 |
| --- | --- | --- |
| 추가 (retries=1) | 연결 수립 단계 ConnectError/ConnectTimeout 1회 재시도 | — |
| **미추가** | transport 옵션 미설정, 재시도는 ③(call 1회 재시도)으로 일원화 | ✅ **선택** |

> **근거**: `retries=` 는 RemoteProtocolError 를 못 막는데 "재시도가 된다"는 혼동만 유발.
> 재시도 책임을 ③ 한 곳으로 모은다.

### ① Singleton 구조
| 선택지 | 내용 | 채택 |
| --- | --- | --- |
| **유지** | 모듈 전역 `_instance` 싱글톤 그대로 | ✅ **선택** |
| 변경 | 요청별/주기적 클라이언트 재생성 등 | — |

> **근거**: 커넥션 풀 재사용 자체는 정상/바람직. 문제는 *죽은 소켓 재사용*이고 그건
> ②·③ 으로 해결되므로 싱글톤은 손대지 않는다.

## 4. 모듈별 상세 설계

### 4-1. 클라이언트 생성 (② keepalive)

`SyncClient.__init__` / `AsyncClient.__init__` 의 httpx 생성에 `limits` 추가:

```python
# _common.py — 상수 1곳 (SSOT)
KEEPALIVE_EXPIRY = 2.0   # 서버 timeout-keep-alive(5s) 보다 짧게 → stale 소켓 재사용 차단

# _sync_client.py / _client.py 공통 (from ._common import KEEPALIVE_EXPIRY)
self._http = httpx.Client(           # _client.py 는 httpx.AsyncClient
    base_url=base_url,
    timeout=timeout,
    limits=httpx.Limits(keepalive_expiry=KEEPALIVE_EXPIRY),
)
```

- `KEEPALIVE_EXPIRY = 2.0` (서버 5s 대비 충분한 margin) 은 **`_common.py` 단일 상수**로 둔다.
  두 클라이언트 파일에 같은 값을 박으면 SSOT 위반(수동 동기화) → 한 곳에서 import.
- `max_connections` / `max_keepalive_connections` 는 **현행 유지**(미지정 = httpx 기본).
  이번 범위 밖.

### 4-2. 비스트리밍 `_request` (③ wrap + 1회 재시도)

sync/async `_request` 를 다음 로직으로:

```python
def _request(self, method, path, **kwargs):
    try:
        response = self._http.request(method, path, **kwargs)
    except httpx.RemoteProtocolError as e:
        # stale keep-alive 소켓: 서버가 응답 없이 끊음 = 요청 미처리 → 1회 재시도.
        # 단, multipart 파일 업로드는 파일 핸들이 소진되어 재전송 불가 → 재시도 제외.
        if "files" in kwargs:
            raise HandlerConnectionError(f"Handler 연결 실패: {e}") from e
        try:
            response = self._http.request(method, path, **kwargs)
        except (httpx.RemoteProtocolError, httpx.ConnectError) as e2:
            raise HandlerConnectionError(f"Handler 연결 실패 (재시도 후): {e2}") from e2
    except httpx.ConnectError as e:
        raise HandlerConnectionError(f"Handler 연결 실패: {e}") from e

    # (이하 status_code >= 400 처리 동일)
```

- **재시도 1회 한정.** 두 번째도 실패하면 `HandlerConnectionError` 로 wrap.
- **파일 업로드 예외**: `upload_file` 은 열린 파일 핸들(`files={"file": (name, f, ...)}`)을
  넘기는데, 재시도 시 핸들이 EOF 라 빈 body 전송 위험 → `"files" in kwargs` 면 재시도하지
  않고 즉시 wrap. (멀티파트 업로드는 빈도 낮고, 재시도는 caller 책임으로 위임)
- `_request` 경유 메서드: `call`/`embed`/`create_cache`/`delete_cache`/`list_caches`/
  `get_cache`/`update_cache`/`delete_file`/`get_file`/`list_files`/`upload_file`.
  GET/DELETE/PATCH 는 본래 idempotent 라 재시도 무해. POST `/v1/generate`·`/v1/embed` 는
  "미처리" 전제로 안전.

### 4-3. 스트리밍 `stream` (③ wrap-only, 재시도 없음)

sync `stream` / async `stream` 의 `except httpx.ConnectError` 를 확장:

```python
except (httpx.ConnectError, httpx.RemoteProtocolError) as e:
    raise HandlerConnectionError(f"Handler 연결 실패: {e}") from e
```

- 스트림은 중간까지 받다 끊기면 부분 출력이 생겨 단순 재시도가 위험 → **wrap 만.**
- 적용 지점: 스트림 **시작 시**(`self._http.stream(...)` 진입)와 **본문 수신 중**
  (`aiter_lines`/`iter_lines` 루프) 모두 바깥 `try` 가 감싸므로 한 곳 수정으로 커버.

## 5. 에러 처리 매트릭스

| 상황 | 기존 | 변경 후 |
| --- | --- | --- |
| 비스트림, 첫 시도 RemoteProtocolError | raw 예외 전파 | 1회 재시도 → 성공 시 정상 반환 |
| 비스트림, 재시도도 실패 | — | `HandlerConnectionError` |
| 파일 업로드, RemoteProtocolError | raw 전파 | 재시도 없이 `HandlerConnectionError` |
| 스트림, RemoteProtocolError | raw 전파 | `HandlerConnectionError` (재시도 없음) |
| ConnectError (기존) | `HandlerConnectionError` | 동일 |

## 8. 범위 밖 / 후속 과제

- 서버 uvicorn `--timeout-keep-alive` 상향 (②의 server-side 보강) — 별도 repo.
- `HTTPTransport(retries=)` — 본 설계에서 의도적으로 제외.
- 커넥션 풀 크기 튜닝(`max_connections` 등) — 별도 검토.

## 9. 영향 / 호환성

- 공개 API 표면 변화 없음 (`llm_manager.call` 등 시그니처 불변).
- caller 가 받는 예외 타입이 raw `httpx.RemoteProtocolError` → `HandlerConnectionError`
  로 **개선**(타입 일관성↑). 기존 `except HandlerConnectionError` 가 더 많은 케이스를 흡수.
- 정상 경로 성능 영향 없음. 재시도는 오류 경로에서만 1회.
