## 배경

Phase 3 (서버화) 직후 식별된 한계:

- llm-request SDK 가 파일 책임을 과다 보유 — checksum / Redis 조회 / 업로드 분기 / 캐시 관리 등
- 파일 실체 관리는 LLM 응답 캐싱과 직교하는 책임 → 분리 가치 명확
- 다른 서비스도 같은 file-manager 를 쓸 수 있도록 외부 패키지로 추출

## Part A — file_manager 외부 분리 설계 (09)

### 설계 범위

- 파일 실체 관리 (`packages/file-manager/`) → 별도 패키지
- llm-request 는 LLM 응답 캐싱/호출에만 집중

### 외부 의존 인터페이스

| 인터페이스 | 원산지 | 비고 |
|---|---|---|
| `FileMeta` 모델 | `file_manager.sdk.models` | file-manager SDK 가 권위 |
| **checksum 계산** | llm-request 자체 — 메타 해시 `sha256(file_name + file_mtime + file_size)` | 현업 패턴상 충돌 희귀 (메타 3 필드로 결정적 키) |
| bytes 조회 API | file-manager Service `get_file(file_path)` | llm-request 가 필요 시 호출 |

### 새 아키텍처 (분리 후)

```
agent
  ├─ file-manager SDK ── (등록 / 조회) ──→ file-manager Service
  └─ llm-request SDK  ── (LLM 호출) ────→ llm-request Service
                                                │
                                                └─ (bytes 필요 시) ──→ file-manager Service
```

### 입력 DTO 변경

| Phase 3 (분리 전) | 분리 후 |
|---|---|
| `FileInput(bytes, name, size, mtime)` | `FileInput(file_path?, bytes?, name, size, mtime)` — file_path 또는 bytes 둘 다 수용 |
| caller 가 bytes 직접 보냄 | caller 가 file-manager 등록 후 file_path 보내거나, 첫 호출 시엔 bytes 보냄 (Method 1, 후속 Phase 3 에서 폐기) |

## Part B — bytes passthrough 구현 (10)

### 권한 경계

| 책임 | 담당 |
|---|---|
| 파일 등록 / 조회 / 캐시 | file-manager Service (별 패키지) |
| LLM 응답 캐싱 / 호출 / 재시도 | llm-request Service |
| caller 의 진입점 | llm-request SDK 만 (file-manager 직접 호출 X — 분리 첫 단계 시점) |

### 옵션 비교 (왕복 vs passthrough)

| 옵션 | 흐름 | 선택 |
|---|---|---|
| 왕복 | SDK → file-manager (bytes) → llm-request | ❌ — SDK ↔ file-manager ↔ llm-request 3 hop, agent 메모리 부담 |
| **passthrough** | SDK → llm-request → (bytes 필요 시) file-manager | ✅ — agent 는 llm-request 만 알면 됨, llm-request Service 가 fetch |

### 새 구조

- agent → llm-request SDK 로 `FileInput(bytes)` 또는 `FileInput(file_path)` 전송
- llm-request Service 가 file-manager 를 통해 등록/조회 자동화
- `file_register.py` 신규 — data-mode (`bytes` 동봉) 입력을 받아 file-manager 에 등록 후 `file_path` 확보

### 변경 파일

| 파일 | 변경 |
|---|---|
| `sdk/llm_request/` | checksum 계산만 유지, 업로드 책임 → file-manager 로 위임 |
| `service/app/models/requests.py` | `FileInput` 모델 (`file_path` + 5 메타 또는 `bytes` 동봉) |
| `service/app/routers/request.py` | `/v1/request`, `/v1/done-check` 핸들러 갱신 |
| `service/app/logic/file_register.py` (신규) | data-mode 등록 책임 — bytes 받으면 file-manager `register_or_get` 호출 |
| `service/app/logic/runner.py` | `_prepare_files` 단순화 |
| `service/app/logic/file_handler/resolver.py` | `file_register` 통합 |
| `validators`, `keying` | 메타 해시 기반 cache_key |

### 에러 처리

| 시나리오 | 응답 |
|---|---|
| file-manager 호출 실패 | `ServiceError(error_type="file_register" or "file_resolve")` |
| base64 디코드 실패 | 400 ValidationError |
| 메타와 실제 bytes 불일치 (file_size 다름) | 400 ValidationError |
| 대용량 파일 HTTP body 한도 초과 | 413 — caller 측에서 청크/스트리밍 검토 |

### 명시적 비-목표 (non-goals)

- file-manager 의 클러스터 구조 / replication
- file-manager Service 의 LLM-aware 분기 (예: PDF 페이지 분할) — file-manager 는 모름
- agent 가 file-manager 를 직접 호출하는 것 (이 시점에는 llm-request 가 단일 진입점. **Phase 3 의 Method 1 폐기에서 변경됨** — agent 가 file-manager 직접 호출하게 됨)

### Task 결과 (모두 완료)

- Phase 3 의 file 관련 코드를 file-manager 외부 패키지로 분리
- llm-request 의 SDK + Service 가 `file_path` 기반 인터페이스로 단일화
- `file_register.py` 가 data-mode 입력 처리를 담당 (이후 Method 1 폐기로 다시 삭제됨 — `18.file-meta-stored-files-history.md` Phase 3)
