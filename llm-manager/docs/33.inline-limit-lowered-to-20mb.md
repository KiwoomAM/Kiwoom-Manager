# 33. inline 한도 20MB 인하 (메모리 정책)

## 1. 배경 / 문제 정의

inline 경로는 파일 bytes를 base64로 바꿔 JSON body에 실어 보낸다. 실측 결과 **요청당 메모리 피크가 원본 크기의 약 4배**다([docs/32](32.inline-bytes-release.md) §2·§6).

```
44.52 MiB PDF → 힙 peak 192.9MB, RSS 248.0MB   (docs/32 회수 적용 후)
```

LLM Handler의 동시 처리 상한이 40건이므로, 최악의 경우 **7.7GB**가 필요하다. 운영에서 메모리 이슈가 반복 보고되고 있다.

[docs/07](07.inline-vs-files-api-strategy.md) §7이 inline을 선호한 근거는 "**inline = 비용 0** (Files API 업로드·저장비 없음)"인데, **그 계산에 메모리가 빠져 있었다.** 이 문서는 그 트레이드오프를 다시 정한다.

## 2. 결정

`_INLINE_LIMIT_PDF_OR_TEXT_ONLY` 를 **50MB → 20MB** 로 낮춘다.

```python
_INLINE_LIMIT_WITH_IMAGE_AUDIO = 20 * 1024 * 1024  # Gemini 강제 상한 — 못 올림
_INLINE_LIMIT_PDF_OR_TEXT_ONLY = 20 * 1024 * 1024  # 정책(메모리) — 50MB에서 인하 (docs/33)
```

### 2.1 모달리티 분기는 유지한다

두 값이 같아져 `_inline_total_limit()` 의 분기가 항상 같은 수를 돌려주게 된다. 그럼에도 **상수 2개와 분기를 남긴다** — **값은 같지만 근거가 다르기 때문이다.**

| 상수 | 근거 | 되돌릴 수 있나 |
|---|---|---|
| `_INLINE_LIMIT_WITH_IMAGE_AUDIO` | Gemini가 문서화한 **강제 상한** ("Inline image data limits your total request size ... to 20MB") | **못 올림** |
| `_INLINE_LIMIT_PDF_OR_TEXT_ONLY` | **우리 메모리 정책** | 올릴 수 있음 (`REVERSIBLE`) |

하나로 합치면 이 구분이 사라져, 나중에 PDF 한도만 되돌리려는 사람이 근거를 다시 도출해야 한다. 주석으로 구분을 명시한다.

### 2.2 건드리지 않는 것 — 이름이 같은 다른 50MB

코드에 `50MB`가 둘 있고 **하나만** 바꾼다. 혼동 주의.

| 어떤 50MB | 뜻 | 이번에 |
|---|---|---|
| `_INLINE_LIMIT_PDF_OR_TEXT_ONLY` | inline 총합 한도 (우리 정책) | **20MB로 인하** |
| `splitter.split_pdf(target_mb=50)` | Gemini **PDF per-file 상한** (스펙 강제) | **안 건드림** |

## 3. 효과 (실측 — 2026-07-14)

**A. 44.52 MiB PDF (`2022_CJ제일제당_지속가능보고서.pdf`) — 재라우팅 확인**

```
분류 결과: inline=0, files_api=1
```

inline 경로를 완전히 벗어났다. base64 팽창(+33%)도 JSON 직렬화 복사도 발생하지 않는다 —
Files API 경로는 bytes를 tempfile로 내리고 `fi.data = b""` 로 즉시 회수한다([resolver.py:388](../llm_manager/_internal/file_processing/resolver.py#L388)).
종전 이 파일의 inline 피크가 192.9MB 였다([32](32.inline-bytes-release.md) §6).

**B. 18.5 MiB PDF (`2022_SK하이닉스_지속가능경영보고서.pdf`) — 새 한도 아래, inline 최악 피크**

| 단계 | 힙 current | 힙 peak | RSS 최대 |
|---|---:|---:|---:|
| 0. 시작 | 0.0MB | 0.0MB | 70.8MB |
| 3. classify_files (inline=1) | 18.5MB | 18.5MB | 89.4MB |
| 4. _process_inline (base64) | 24.7MB | 67.9MB | 138.6MB |
| **6. json.dumps + encode** | 49.4MB | **80.2MB** | **144.8MB** |

**요청당 힙 피크 80.2MB.** peak ≈ raw × 4 라는 어림이 실측으로 확인된다(18.5 × 4 = 74 ≈ 80.2).

**C. 종합**

| | 변경 전 | 변경 후 |
|---|---:|---:|
| 44.5MB PDF 요청당 피크 | 192.9MB (inline) | **Files API 경로** (base64·JSON 안 거침) |
| inline 최악 피크 | 192.9MB (한도 50MB) | **80.2MB** (한도 20MB, 실측) |
| **40 동시 최악** | **≈ 7.7 GB** | **≈ 3.2 GB** |

> 40 동시 수치는 실측 80.2MB × 40 의 **산술 외삽**이다(동시 실행을 실제로 재지 않았다).
> 한도 상한인 정확히 20MB 파일이라면 약 87MB → 약 3.5GB 로 조금 더 높다.

## 4. 대가

20~50MB 파일이 Files API로 밀려 **최초 1회 업로드 지연·비용**이 생긴다. 단 Redis에 URI가 **47h 캐시**되므로 같은 문서를 반복 조회하면 업로드는 최초 1회뿐이다(상각된다).

## 5. 테스트 파급

기존 테스트가 **50MB 정책을 계약으로 고정**하고 있다. 의도(합계 초과 시 files_api로 spill)는 유지하고, **파일 크기 숫자만 새 한도에 맞게 스케일**한다. 단언을 지우지 않는다.

| 테스트 | 종전 기대 | 조치 |
|---|---|---|
| `test_pdf_text_only_uses_50mb_limit` | 합계 40MB → 둘 다 inline | **이름·크기 스케일** (8+8=16MB ≤ 20MB) |
| `test_no_promotion_when_ttl_none` | 30+30MB → 작은 것 inline / 큰 것 files_api | **스케일** (5+18=23MB → 혼합 유지) |
| `test_overflow_parts_spill_to_files_api` | 40+40MB → 하나만 inline | **스케일** (5+18MB) |
| `test_recovery_invalidates_spilled_part_checksum` | 40+40MB → part2 만 spill | **스케일** — 안 깨졌지만 20MB 에선 *둘 다* spill 해 "spilled 것만 무효화"의 변별력이 사라진다 |
| `test_total_over_limit_pushes_largest_to_files_api` | 10MB inline + 45MB spill | 통과 (주석의 한도 숫자만 정정) |

신규 테스트 `test_pdf_over_20mb_goes_to_files_api` — **한도가 20MB임을 직접 고정**한다(25MB PDF 단건 → files_api). 상수를 되돌리면 실패한다.

### 6.0 도커 실행 시 함정 (재현하려는 사람 주의)

**레포 디렉터리를 그대로 컨테이너에 마운트하면 안 된다.** 레포에 남은 `.venv`·`__pycache__`
아티팩트가 테스트를 오염시켜, 변경과 무관한 `test_dedup`·`test_runner_standby` 가 비결정적으로
실패한다(실행마다 실패 개수가 11/14/16 로 바뀜, 21s 타임아웃). 이 아티팩트를 제외한 사본을
마운트하면 안정적으로 통과한다.

또한 형제 매니저 레포(`file-manager` 등)를 통째로 `PYTHONPATH` 에 넣으면, 그쪽 `tests/`(정규
패키지 — `__init__.py` 있음)가 llm-manager 의 namespace `tests` 를 가려 conftest import 가 깨진다.
**패키지 모듈 디렉터리만** 노출해야 한다.

### 6.1 남은 불확실성 (정직하게)

OOM이 **어디서** 나는지 아직 특정되지 않았다. inline 경로는 `context_cache_ttl=None` 일 때만 타므로([resolver.py:785](../llm_manager/_internal/file_processing/resolver.py#L785)), 컨텍스트 캐시를 켜고 쓰는 서비스는 이 변경의 영향을 받지 않는다.

`_process_inline` 은 파일마다 `[route] file=... mode=inline` 을 로그로 남긴다. **운영 로그에서 이 줄을 세면 inline이 실제로 쓰이는지·어느 서비스인지 실증할 수 있다.** 이 변경이 실제로 OOM을 줄였는지는 그 데이터로만 확인 가능하다.
