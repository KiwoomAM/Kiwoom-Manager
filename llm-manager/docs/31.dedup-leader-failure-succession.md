# 31. dedup — leader 실패가 herd로 번지는 문제 (실패 전파 + SETNX 폴백)

> 상태: **구현 완료** (§5 로드맵 참고). adversarial 리뷰에서 나온 C1·C2 회귀(§3-5),
> fencing(§3-6), Redis 정책(§3-7), 재획득 후 캐시 재확인(§3-8), timeout 소진 fail-fast(§3-9)를 반영했다.
> 관련: `docs/08.dedup-design-and-impl.md`(dedup SSOT), `docs/25`(PDF 분할)

## §1. 배경 / 문제 정의

ESG 평가(한 회사 28개 항목, 같은 PDF 1개)를 동시 실행했더니 **28건 전부 실패**했다.
로그의 `expected 101282537`은 현대글로비스 보고서(101,282,537바이트)의 정확한 크기다.
즉 **여러 요청이 동시에 101MB 원본을 각자 내려받다가** 죽었다.

```
❌ A0000010 예외: peer closed connection (received 22347280 bytes, expected 101282537)
❌ A0000050 예외: peer closed connection (received 20521616 bytes, expected 101282537)
❌ A0000009 예외: peer closed connection (received  8199584 bytes, expected 101282537)
❌ A0000066 예외: peer closed connection (received 89292660 bytes, expected 101282537)
...
```

받은 바이트가 제각각인 동시 다발 부분 다운로드 — 한 파일을 여러 요청이 **동시에** 받고 있었다는
직접 증거다. dedup이 정확히 이걸 막으라고 있는데, 막지 못했다.

### 왜 dedup이 뚫렸나

정상 경로는 설계대로 동작한다. leader가 `SETNX`로 standby를 선점해 혼자 받고, **본 캐시를 저장한
뒤** standby를 지우므로(`resolver.py`: `save_files_api` → `finally: release_standby`), 깨어난
follower들은 캐시 HIT으로 **URI 메타만** 재사용한다. 바이트를 다시 받지 않는다.

깨지는 건 **leader가 실패할 때**다.

```
leader   : SETNX 성공 → fetch 실패 → (캐시 저장 없음) → finally: DEL standby → raise
follower : 폴링 → 캐시 MISS → standby 없음 → return None   (dedup.py:130)
           → 호출자가 곧장 자기가 작업 시작                  (resolver.py:437)
```

follower는 깨어날 때 **standby를 다시 잡지 않는다.** 27개가 같은 폴링 주기에 동시에 깨어나므로
**27개가 동시에 101MB를 받으러 간다.** 실패 1건이 27배로 증폭된다.

이 결함은 **4개 호출부 전부**에 동일하게 있다.

| 계층 | 호출부 | leader 실패 시 |
|---|---|---|
| files_api | `resolver.py:437` | follower 전원이 각자 fetch+업로드 |
| context_cache | `resolver.py:612` | follower 전원이 각자 캐시 생성 |
| agent_llm | `runner.py:576` | follower 전원이 각자 LLM 호출 |
| agent_llm(stream) | `runner.py:705` | 〃 |

덤으로 **로그가 오해를 부른다.** `wait_for_standby_release`는 timeout일 때도, leader 실패로
standby가 사라졌을 때도 똑같이 `None`을 돌려준다. 그래서 호출부는 후자에도
`standby timeout → 자기가 업로드`라고 찍는다. 실제로는 timeout이 아니라 leader 실패였다.

## §2. 목표 (불변식)

1. **어느 순간에도 같은 key에 대한 비싼 작업은 최대 1개.** leader가 실패해도, 실패 기록이 만료돼도
   이 불변식이 깨지지 않는다.
2. **leader가 실패하면 재시도 없이 곧장 실패를 전파한다.** 대기 중인 나머지는 재시도 없이 즉시 실패한다.
3. **실패 원인이 호출자에게 그대로 닿는다.** 28건의 로그가 모두 같은 원인을 가리켜야 진단이 된다.

### 왜 "승계 없이 즉시 전파"인가 (결정 변경)

처음엔 "승계 1회"를 검토했으나 폐기했다. 이 herd를 촉발한 실패는 파일·서버 문제(101MB fetch 단절)라
승계해봐야 **101MB를 한 번 더 받아보고 또 죽을** 뿐이다. 일시적 딸꾹질을 흡수하는 이득보다, 승계
leader가 다시 101MB를 끌어오는 비용이 크다. leader가 실패하면 그 원인을 그대로 전파하고, 재시도는
**사용자가 문제를 고친 뒤 다시 돌리는 것**으로 맡긴다(실패 기록 TTL이 그 재시도 시점을 연다).

## §3. 설계

### §3-1. 새 Redis 키 — 실패 기록 (negative cache)

| 키 | 값 | TTL |
|---|---|---|
| `standby:{prefix}:{key}` | (기존) leader 선점 마커 | `standby_ttl_seconds` |
| `failed:{prefix}:{key}` | `{"class", "message", "status_code", "error_type"}` (§3-3) | **계층별 (아래)** |

| 계층 | TTL | 근거 |
|---|---|---|
| files_api / context_cache | 60초 | 101MB 재다운로드·캐시 재생성이 비싸고, 원인이 서버·파일이면 1분 안엔 안 고쳐진다 |
| agent_llm | **15초** | LLM 실패는 rate limit·5xx처럼 일시적인 경우가 많아 짧게. 단 폴링 cap(§3-2)보다는 커야 안전 |

**폴링 cap과의 관계 (중요).** waiter 폴링은 exponential backoff로 간격이 늘어 최대 `_BACKOFF_CAP`
(현재 **10초**, `dedup.py:37`)까지 잔다. 실패 기록 TTL이 이 cap보다 짧으면 **기록이 만료된 뒤에
깨어나는 waiter**가 생겨, 그 waiter가 기록을 못 보고 herd가 되살아난다. 그래서 최소 TTL > cap 이어야
하고, agent_llm 15초는 이 여유(10초 + 5초)를 둔 값이다. **단, 이 조건이 깨져도(§3-2의 SETNX
폴백이) herd를 막는다** — TTL은 "빠른 실패"를 위한 최적화이고, 정확성은 SETNX 폴백이 보장한다.

### §3-2. 흐름

```
leader (SETNX 성공):
    작업 수행
    성공 → 본 캐시 저장 → DEL standby            (기존과 동일)
    실패 → SET failed{error} TTL                 (신규)
           → DEL standby → raise

follower (SETNX 실패 → 폴링):
    캐시 HIT              → 재사용 (기존과 동일)
    standby 사라짐        → failed 기록 확인      (신규)
        ├ 있음            → 재시도 없이 leader의 원본 에러로 즉시 raise
        └ 없음(만료/eviction) → SETNX 재시도       ← 폴백도 안전하게
              ├ 획득 → 자기가 leader (기존 Y' Hybrid 와 동일 경로)
              └ 실패 → 다른 애가 잡음 → 계속 대기
    timeout               → SETNX 재시도 (동일). 획득 시 자기가 작업, 실패 시 재대기
```

두 개의 안전장치가 겹친다.

1. **실패 기록** — 정상 경로. leader 실패 후 깨어난 waiter들이 기록을 보고 즉시 같은 에러로 실패한다.
   101MB 재다운로드는 0번, 28건이 같은 원인으로 빠르게 끝난다.
2. **SETNX 폴백** — 안전망. 실패 기록이 (TTL 만료·Redis eviction으로) 없더라도, waiter는 곧장
   일하지 않고 `SETNX`부터 다시 시도한다. 여러 개가 동시에 깨어나도 **하나만** 잡아 작업하고 나머지는
   재대기 → 불변식 1이 TTL과 무관하게 유지된다.

기존 코드의 구멍은 정확히 2번이 없다는 것이었다. waiter가 깨어나면 `SETNX` 없이 곧장 자기가
작업을 시작해, 27개가 동시에 일했다. 이제 timeout(Y' Hybrid) 경로까지 포함해 **"깨어나면 항상
SETNX부터"**로 통일한다.

### §3-3. 에러 전파

실패 기록에 원본 예외의 **관찰 가능한 계약**을 저장하고, 대기자들은 같은 내용으로 실패한다.
전용 예외 하나로 뭉개면(`DedupLeaderFailedError("선행 요청 실패")`) 원인이 가려져, 지금처럼
로그만 보고는 왜 죽었는지 알 수 없다.

**무엇을 저장하나.** `message`(verbatim), `status_code`, `error_type`, 그리고 원본 클래스명
(디버깅용). 소비자는 **예외의 Python 타입(isinstance)이 아니라 `status_code`·`error_type`
속성으로 분기**하고 ESG는 `message`를 로깅한다(`exceptions.py` 계약: "내부 코드는 클래스를
읽지 않음"). 그래서 이 세 값만 보존하면 관찰 가능한 동작이 원본과 동일하다.

**왜 클래스 생성자로 재구성하지 않나.** `llm_manager.exceptions`의 생성자가 제각각이다 —
대부분 `__init__(message)`지만 `PdfPageTooLargeError(page, size_mb)`처럼 다른 것이 있어,
`error_type`→클래스 매핑 후 생성자 호출은 취약하다. 대신 `LLMManagerError(message,
status_code, error_type)`로 재구성하면 **모든 하위 타입을 거치지 않고** 계약을 그대로 싣는다.
- 원본이 `LLMManagerError` 하위: `status_code`·`error_type`를 그대로 실어 소비자 분기가 동일.
- 원본이 라이브러리 예외(httpx `RemoteProtocolError` 등): `status_code`=502,
  `error_type`="leader_failed", `message`는 verbatim(=원본 로그와 같은 텍스트). 클래스명은
  기록에 남겨 진단 시 참조.
- 어느 경우도 **message를 가공·마스킹하지 않는다** — 28건 로그가 같은 원문을 가리키게.

### §3-4. 모듈 — dedup.py가 SSOT

4개 호출부가 같은 결함을 복제하고 있으므로, 판단을 `dedup.py`로 모은다.
`wait_for_standby_release`가 `None`/dict 대신 **판정(verdict)**을 돌려주고, 호출부는 그에 따라 분기한다.

`WaitResult.kind` 는 **3종**이다. "재획득 실패 → 계속 대기"는 호출부로 새어 나가지 않고
`wait_for_standby_release` 안에서 재폴링으로 흡수되므로 verdict 가 아니다.

| 판정 | 의미 | 호출부 동작 |
|---|---|---|
| `cached` | leader 성공, 캐시 HIT | 재사용 (기존) |
| `failed` | leader 실패 기록 발견 | 재시도 없이 즉시 raise (원본 에러) |
| `lead` | standby 사라짐/timeout → SETNX 재획득 성공 | 자기가 작업 |

이러면 호출부 4곳의 diff가 작고(분기), 실패·재획득 판단 로직은 한 곳에만 존재한다(`SSOT`).
기존 호출부의 `None → 곧장 자기가 작업` 및 오해를 부르던 `standby timeout` 로그는 사라진다.

호출부는 `cached`/`failed` 를 **명시적으로** 분기하고 나머지를 `lead` 로 떨어뜨린다. verdict 를
나중에 늘린다면 이 else 가 조용히 herd 로 오작동할 수 있으니, 늘릴 때 호출부 4곳을 함께 봐야 한다.

## §3-5. 리뷰에서 잡힌 두 회귀 (C1·C2)

첫 구현을 adversarial 리뷰에 걸어 **직접 재현되는 회귀 두 건**을 찾았다. 둘 다 고쳤다.

### C1 — 낡은 실패 기록이 재실행을 오염시킨다

실패 기록을 **아무도 지우지 않았다.** leader 가 standby 를 잡을 때 확인도, 삭제도 안 했다.
그래서 실패 후 TTL(60초) 안에 재실행하면:

```
t=0    leader 실패 → failed 기록 → standby 해제 → 27개 즉시 실패   ✅ 의도대로
t=+20s 재실행 (파일·서버는 이제 정상)
       항목1  → SETNX 성공 → 정상적으로 101MB 받는 중
       항목2~ → 폴링 → 캐시 MISS → **t=0의 낡은 기록** → 즉시 실패  ❌ 회귀
```

**실패한 배치를 곧바로 다시 돌리는 것은 ESG 의 정상 패턴**이다. 수정 전이라면 (느리게나마)
28건이 다 성공했을 상황이 27건 실패로 바뀐다 — 고치기 전의 코드보다 나쁘다.

**수정.** `try_acquire_standby` 가 **선점에 성공하면 그 key 의 실패 기록을 지운다**(`_clear_failure`).
실패 기록은 "그 시도가 실패했다"이지 "이 key 는 영영 안 된다"가 아니다. 새 leader 가 섰다는 건
새 시도가 시작됐다는 뜻이므로 이전 실패는 무효다.

이래도 원래 목표(즉시 전파)는 지켜진다. waiter 의 폴링은 **실패 기록 확인(2)이 standby 확인(3)보다
먼저**라, leader 실패 직후 깨어난 27개는 재획득을 시도하기 전에 기록을 보고 `failed` 로 끝난다.

### C2 — timeout 경로가 재획득 결과를 버렸다

`_try_reacquire` 를 부르고 **반환값을 쓰지 않은 채** 무조건 `lead` 를 돌려줬다. 그래서 leader 가
*실패*하지 않고 **느리게 매달리면**(실패 기록이 안 생긴다) 대기자들이 같은 시각에 timeout 에 도달해
**전원 `lead`** → herd 가 그대로 살아났다. 문서(§3-2)는 "timeout 진입도 SETNX 를 거친다"고 적었는데
코드가 그렇지 않았다 — 문서·코드 드리프트.

**수정.** timeout 에서도 재획득 성공 시에만 `lead` 를 주고, 실패하면(= 다른 대기자가 방금 leader 가
된 것) 다음 라운드로 **계속 기다린다**. `_MAX_TIMEOUT_ROUNDS`(3) 를 소진하면 그때만 중복을 감수하고
자기가 작업한다(구 Y' Hybrid 의 liveness 탈출구).

**계약 변경.** 기존 Y' Hybrid 는 "leader 가 느리면 timeout 즉시 내가 한다(중복 감수)"였다. 이제는
"재획득에 성공할 때만 내가 하고, 아니면 그 leader 를 기다린다"이다. 기존 테스트 3건
(`test_timeout_falls_back_to_own_*`)이 옛 계약(`upload_count == 2` = herd 의 N=2 판)을 고정하고
있어 새 계약(`== 1`, 중복 0)으로 갱신했다.

### 남은 한계 — timeout 경로의 동시 작업은 ≤2 (≤1 아님)

실제 Redis 에서 standby 키의 TTL 은 대기 timeout 과 같다. 그래서 대기자가 timeout 에 도달할 땐
leader 의 키가 **이미 만료**돼 있고, 재획득은 대기자 중 하나만 성공한다. 그런데 원래의 느린 leader 는
자기가 락을 잃은 줄 모르고 **계속 작업 중**이다. 즉 이 경로의 동시 작업은 최대 2개(원래 leader +
승격된 leader)가 될 수 있다 — 28개가 1~2개로 줄었을 뿐, §2 불변식 1을 엄밀히는 만족하지 않는다.

이걸 0 으로 만들려면 leader 가 작업 중 주기적으로 TTL 을 갱신(lease 연장)해야 하는데, 백그라운드
갱신 태스크가 필요해 복잡도가 확 오른다. **지금은 하지 않는다** — 실제로 "느린 leader + 승격" 조합이
로그에 잡히면 그때 한다(YAGNI). 다만 그 상태에서 **옛 leader 가 새 leader 의 락을 지우는** 2차 피해는
막아야 한다 → §3-6.

## §3-6. 락 소유권 (fencing) — M5

**문제.** `release_standby` 가 소유권 검사 없이 무조건 DEL 했고, standby 값에는 누가 잡았는지
식별자가 없었다(`{"started_at": ...}` 뿐). 그래서 TTL 만료로 락이 넘어간 뒤 이렇게 된다.

```
A(느린 leader)  standby 잡음 → 작업 중... (TTL 만료)
B(대기자)       timeout → 재획득 성공 → 새 leader → 작업 시작
A               뒤늦게 끝남 → finally: release_standby → **B 의 락을 지움**   ❌
C, D, E...      standby 없네? → 각자 재획득 → 추가 leader 등장 → herd 자기증식
```

**수정.** standby 값에 소유자 토큰(`{"owner": <uuid>, "started_at": ...}`)을 넣고,
`try_acquire_standby` 가 그 **값 문자열 전체를 토큰으로 반환**한다. 해제는
`RedisManager.compare_and_delete(key, token)` 으로 **내 토큰일 때만** 지운다.

- 반환 타입 변경: `try_acquire_standby` 는 `bool` → `str | None` (토큰 / 못 잡음).
- `WaitResult` 에 `token` 필드 추가 — `lead` 판정과 함께 승격한 waiter 의 토큰을 싣는다.
- 호출부 4곳은 받은 토큰을 `finally` 의 `release_standby(prefix, key, token)` 로 넘긴다.
- `token=None` 이면 해제는 **no-op** — Redis 장애로 락 없이 진행한 요청은 지울 락이 없다.
- `compare_and_delete` 의 `False` 는 "해제 실패"가 아니라 "이미 내 소유가 아님"(TTL 만료 후
  승계됨 / 이미 해제됨)이다. 정상 상황이므로 에러로 다루지 않고 `info` 로만 남긴다.

토큰을 **값 전체**로 두는 이유: `compare_and_delete` 는 값 전체를 비교하므로, 우리가 SET 한 문자열을
그대로 들고 있다가 돌려줘야 한다. `owner` 만 저장하고 재직렬화하면 키 순서·공백 차이로 어긋날 수 있다.

사내 redis-manager 규칙("분산 락을 delete 로 해제하지 말 것")과도 이제 맞는다.

## §3-7. Redis 장애 시 정책 — 진입 경로에 맞춘다 (M3)

**문제.** 대기 경로가 Redis 장애를 삼키고 "락 없이 자기가 작업"으로 강등했다. 그래서
leader 가 락을 잡고 작업하는 도중 Redis 가 끊기면:

```
get(standby)   → Redis 죽음 → None (v3 는 read 를 메모리 폴백, strict-read 미지원)
               → 코드는 "leader 가 사라졌네?" 로 오해 → 재획득 시도
SETNX          → 폴백 차단이라 RuntimeError
(구) _try_reacquire → 이걸 삼키고 (True, None) = "락 없이 그냥 일해"
결과           → 대기자 27명 전원이 leader → **없애려던 herd 가 그대로 부활**
```

**핵심 관찰.** Redis 가 죽어 있으면 **새로 들어온 요청은 진입 단계에서 이미 실패한다** —
`try_acquire_standby` 가 RuntimeError 를 그대로 올린다. 즉 "Redis 가 없으면 llm-manager 는
못 쓴다"가 **이미 현재의 계약**이다. 그런데 **대기 중이던 요청만** 예외적으로 봐주고 있었고,
그 봐주는 대가가 herd 였다.

| | Redis 죽었을 때 (수정 전) |
|---|---|
| 새 요청 (진입) | 이미 실패 (RuntimeError) |
| 대기 중 요청 | 락 없이 전원 작업 → **herd** |

**결정.** 대기 경로도 진입 경로와 같이 **RuntimeError 로 실패**시킨다. 없던 실패를 만드는 게
아니라, 이미 실패하는 상황에서 예외를 없애는 것이다. `_try_reacquire` 의 `except RuntimeError`
강등 분기를 제거하니 코드도 단순해졌다(반환도 `tuple[bool, str|None]` → `str | None`).

**대가.** Redis 블립 시 leader 는 살아남아도 대기자들은 에러로 끝난다. 받아들인다 —
Redis 없이는 dedup 이 성립하지 않고, 대안(전원 herd)의 대가가 훨씬 크다(파일 서버 붕괴,
LLM 중복 과금).

**기각한 대안.** Redis 가 없을 때 `asyncio.Lock` 으로 프로세스 내부만이라도 잠그는 안.
ESG 28건은 한 프로세스에서 `gather` 로 돌므로 실제 사고를 완전히 커버하지만, 잠금 장치가
둘이 되어 복잡도가 는다. Redis 장애가 잦다는 증거가 쌓이면 그때 한다(YAGNI).

## §3-8. 재획득 후 캐시 재확인 (double-checked locking)

**앞선 이슈 문서(#dedup-cache-recheck)가 잡아낸 결함.** herd 수정 뒤 standby 계열 테스트가
전량 실행 시 무작위로 하나씩 실패했다. 처음엔 이를 **flaky 테스트**로 오진하고 `patient_waiter`
fixture(라운드 상한을 크게)로 증상만 가렸다. 실제로는 **테스트가 아니라 코드가 틀렸다.**

**문제 — leader 성공 경로의 herd.** §1의 herd 수정은 "leader 성공 시 캐시 저장이 락 해제보다
먼저이므로 정상 경로는 안전하다"를 근거로 삼았다. 그 순서는 leader 쪽 필요조건일 뿐이고,
대기자 쪽 확인 순서 때문에 보장이 깨진다. 폴링 1회는 캐시(경로 1)와 standby(경로 3)를 **다른
시점에** 본다. 그 사이에 leader 가 완주하면:

```
대기자  캐시 확인(경로 1) → 없음        ← leader 아직 작업 중
                                         leader: 캐시 저장
                                         leader: 락 해제
대기자  락 확인(경로 3) → 없음 → 재획득 성공 → "lead"   ← 방금 채워진 캐시를 못 봄 → 중복 작업
```

herd 수정 **전**엔 대기자 전원(27명)이 중복했고, 수정 **후**엔 1명이 중복한다. 규모는 줄었지만
불변식(동시 작업 ≤1)은 여전히 **leader 성공 경로에서** 깨져 있었다. files_api 면 중복 업로드,
agent_llm 이면 LLM 중복 과금이다.

**수정.** 경로 3·4에서 재획득에 성공하면, **락을 잡은 직후 캐시를 한 번 더 본다**(`_reacquire_or_cached`).
HIT 이면 방금 잡은 락을 반납하고 `cached` 를 반환한다 — 고전적 double-checked locking 의 두 번째
확인이다. M5 덕에 `release_standby` 가 토큰 기반이라 "안 쓸 락 반납"도 안전하다.

**"flaky"의 정체.** 이 재확인이 없던 탓에, 레이스 창(대기자의 캐시확인~락확인 사이)이 부하로
벌어지면 대기자 1명이 `lead` 를 집었다. 그래서 전량 실행(느림)에서만 무작위로 깨졌고 단독
실행에선 통과했다 — flaky 의 외양이었지만 결정론적 재현이 가능한 코드 버그다(테스트
`TestReacquireRechecksCache` 가 leader 완주를 대기자 캐시 읽기 직후로 고정해 100% 재현).

증상만 가리던 `patient_waiter` fixture 는 근본 수정 후 제거했다.

## §3-9. timeout 라운드 소진 — 자기 작업 대신 fail-fast (PR #79 리뷰)

**리뷰 지적(비블로킹).** `_MAX_TIMEOUT_ROUNDS`(3) × `standby_ttl_seconds`(기본 600초) = 최악
대기 **30분**. 상위 요청 타임아웃 예산과 맞는지 확인 권고. + 자체 발견: 소진 terminal 이
"자기 작업(lead)"이라 **여러 대기자가 함께 소진하면 herd**가 났다(드문 꼬리).

**먼저 규모를 바로잡음.** "30분"은 오해를 부른다. 정상 흐름의 승격은 **1회**다.

```
리더1 조용히 죽음 → (TTL 600초 만료) → 대기자A 승격 → A 정상 완료
                                        → 나머지 대기자는 A 의 캐시 결과 재사용(즉시)
```

즉 **한 번 죽으면 최악 ≈ TTL 1회 ≈ 10분**이고, 나머지는 A 의 결과를 받는다. 30분은 **A 마저,
그다음도 연달아 조용히 죽는** 3연속 크래시에서만 나온다(극히 드문 꼬리). 게다가 이번 ESG 사고의
리더는 "알리고" 죽어(예외→실패 기록) 이 timeout 경로를 **아예 밟지 않았다** — TTL 대기는 오직
프로세스가 **조용히 크래시**할 때만이다.

- **TTL 이란?** standby 락의 수명이자 대기자의 한 라운드 timeout(둘이 같은 값). 리더가 조용히
  죽으면 락을 지울 사람이 없으므로, TTL 이 만료돼야 대기자가 넘겨받는다 — "락이 이만큼 살았으면
  리더가 죽은 것으로 보고 넘겨받는다"는 안전장치다. 대기자는 죽음을 스스로 판정하지 않는다;
  Redis 가 TTL 로 키를 지우고 대기자는 "키 없음"만 관측한다.

**결정 — 소진 terminal 을 `raise` 로.** 라운드를 줄이는 대신(1로 줄이면 §3-8 처럼 herd 재발),
**라운드 소진 시 자기 작업(lead) 대신 `CacheError` 를 raise** 한다.

- 정상 경우(승격 1회 후 성공): 라운드 2에서 대기자가 A 의 캐시를 잡아 `cached` — 지금과 동일.
- 극단(연속 크래시로 소진): 자기 작업(herd) 대신 **전원 fail-fast** → 사용자가 재시도.
- **herd 는 어떤 경로에서도 0** 이 된다. M3·"승계 없음"의 fail-fast 철학과 일관.

**TTL 은 안 건드림.** TTL 을 줄이면 tail 이 짧아지지만, **가장 오래 걸리는 정상 작업보다 길어야**
한다(짧으면 멀쩡히 일하는 리더의 락이 먼저 만료돼 대기자가 끼어들어 중복). 정상 작업 최대
소요를 확정하기 전엔 손대지 않는다 — 필요해지면 그때(YAGNI).

**남긴 것.** 상위 요청 타임아웃 예산과의 정합은 호출자(ESG 등) 몫이다. 소진이 raise 로 바뀌어
"30분 매달리다 상위 타임아웃으로 실패"가 "라운드 소진 시 명시적 CacheError"로 바뀌었다 —
끊김이 조용하지 않고 이유가 남는다.

## §4. 결정 사항 (확정)

1. **승계 없음 — leader 실패는 즉시 전파.** 결정론적이든(`PdfPageTooLargeError`) 일시적이든
   구분하지 않는다. 승계하면 101MB를 한 번 더 받아야 하는데, 이 herd의 원인은 서버·파일이라
   재시도해도 같은 결과다. 재시도는 사용자가 고친 뒤 다시 돌리는 것으로 맡긴다(§2).
   → 설계가 단순해진다: `attempts` 카운터·승계 leader 개념이 통째로 빠진다.
2. **실패 기록 TTL은 계층별.** files_api·context_cache 60초, agent_llm 15초(§3-1).
   agent_llm이 짧은 이유는 LLM 실패가 일시적인 경우가 많아 정상 재시도를 오래 막지 않기 위해서다.
   단 어느 쪽도 폴링 cap(10초)보다는 크게 두어 herd 재발을 막고, 그마저 깨져도 SETNX 폴백이 보장한다.

별도로 확인한다.
