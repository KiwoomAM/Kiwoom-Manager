> 본 문서는 그 구현체 `dedup.py` 를 redis-handler v2.0.0 새 API 로 정리하는 작업의 설계서다.

## 1. 배경 / 문제 정의

### 현재 상태

`service/app/logic/file_processing/dedup.py` 는 cache stampede 방지용 standby 메커니즘을 구현한다 ([설계: §08](08.cache-stampede-dedup.md)). 핵심 동작 3 개:

- `try_acquire_standby` — Redis `SET NX EX` 로 standby 키 선점 시도
- `wait_for_standby_release` — standby 가 사라질 때까지 exponential backoff 대기
- `release_standby` — finally 블록에서 standby DEL

이 셋 모두 **redis-handler v1.x 시점에 `setnx` API 가 미구현이었기 때문에** raw Redis 클라이언트(`redis_handler.get_client()`)를 직접 끌어 쓰는 우회 패턴을 사용해왔다. 모듈 docstring 8행에 그 이유가 명시되어 있다.

```python
# 현재
from redis_handler import get_client

client = get_client()
if client is None:
    raise RuntimeError("Redis 미연결 — standby 불가")
result = await asyncio.to_thread(
    client.set, standby_key, value, nx=True, ex=ttl_seconds,
)
return result is not None
```

### 변화

redis-handler v2.0.0 (`refactor/redis-handler` 브랜치 → main 머지) 가 다음을 추가했다:

- `RedisHandler.setnx(key, value, *, ttl)` — 전용 SETNX 메서드
- `RedisHandler.set(key, value, ex=, nx=True)` — 일반 set 에 NX 옵션
- `RedisUnavailableError` — Redis 미연결 시 NX/XX 호출에서 raise (분산 의미론 보호)
- `BaseJsonStore` 가 raw client → `RedisHandler` 인스턴스 사용으로 내부 정리 (외부 시그니처는 backward compatible)

→ raw 클라이언트 우회 패턴이 **더 이상 필요 없다**. 정리할 시점.

### 문제

raw 우회 패턴 자체가 동작은 하지만:

1. **추상화 누수** — `dedup.py` 가 `redis_handler` 의 *내부* 함수(`get_client`)에 의존. 라이브러리가 권장하는 고수준 API 가 있는데 일부러 우회.
2. **분산 의미론 보호 미적용** — 새 `RedisHandler.setnx` 는 Redis 미연결 시 메모리 폴백 대신 `RedisUnavailableError` 를 raise (§2.2 참조). raw 클라이언트는 이 보호 장치가 없어 잘못 사용하면 의미론 깨질 위험.
3. **코드 가독성** — 매 함수마다 `client = get_client(); if client is None: raise ...` 보일러플레이트 4 줄 반복.

### 목표

- `dedup.py` 의 raw 우회 제거 → `RedisHandler` 고수준 API 사용.
- 모듈 docstring 의 "redis-handler에 setnx 미구현 → ..." 주석 제거.
- 분산 의미론 보호를 의도된 방식(`RedisUnavailableError` → `RuntimeError` 변환) 으로 적용.
- 의미론 변화의 영향과 트레이드오프를 본 문서에 기록.

### 비목표

- dedup 알고리즘 변경 (backoff, TTL, key naming 등 §08 설계 그대로).
- `providers.py` 의 `_flush_stale_standbys` 의 `scan_iter()` 변경 (handler 고수준 API 에 없으므로 raw 정당).
- `cache_store.py` 의 `BaseJsonStore` 상속 코드 변경 (자동으로 새 BaseJsonStore 사용).
- redis-handler 자체 추가 기능 요구.

## 2. 사전 정보

### 2.1 Cache Stampede 와 dedup — 매우 짧은 복습

같은 작업(예: 같은 PDF 의 Files API 업로드) 을 여러 요청이 동시에 시작하면 중복 작업·외부 API 부담·결과 충돌이 발생할 수 있다.

해결: 작업을 시작하기 전에 Redis 에 "standby 키" 를 SETNX 로 선점.

- 첫 요청: SETNX 성공 → 작업 진행
- 동시에 들어온 후속 요청: SETNX 실패 → 첫 요청이 끝날 때까지 backoff 대기 → 본 캐시 HIT 보면 즉시 반환

→ Redis 단일 진실 원천(single source of truth) 이 핵심. 모든 인스턴스가 같은 Redis 를 보고 있어야 의미가 있다.

### 2.2 redis-handler v2.0.0 의 폴백 정책

redis-handler 는 이중 백엔드 구조다:

```
사용자 코드
    ↓
RedisHandler  ─── (Redis 가용) ───→ RedisBackend  ─→ 진짜 Redis 서버
    │
    └─── (Redis 다운) ─→ MemoryBackend  ─→ 프로세스 안의 dict
```

- 일반 명령(`get`, `set` ttl, `delete`, `expire`, ...): Redis 다운 시 **메모리 폴백** — 프로세스 안 dict 에서 읽고 쓴다.
- NX/XX 명령(`setnx`, `set(nx=True)`, `set(xx=True)`): **폴백 차단** — Redis 미연결이면 `RedisUnavailableError` raise.

NX 가 폴백을 차단하는 이유: NX 는 "이 키가 아직 없을 때만 쓴다" 라는 분산 의미론을 가진다. 메모리 폴백을 허용하면 인스턴스 A 의 메모리는 NX 통과, 인스턴스 B 의 메모리는 NX 실패 — 두 인스턴스가 서로 다른 결과를 내서 dedup 이 깨진다. **분산 환경에서 NX 는 진짜 Redis 가 아니면 의미가 없다.**

### 2.3 dedup 이 redis-handler v2 에서 사용하는 3 메서드

| 호출 | 의미 | 폴백? |
|---|---|---|
| `RedisHandler().setnx(key, value, ttl=ttl)` | NX 로 standby 선점 | ❌ 차단 (RedisUnavailableError) |
| `RedisHandler().get(standby_key)` | standby 살아있는지 조회 | ✅ 메모리 폴백 |
| `RedisHandler().delete(standby_key)` | standby 해제 | ✅ 메모리 폴백 |

`get` / `delete` 는 분산 의미론을 가지지 않는 일반 명령이라 폴백 가능. 하지만 dedup 패턴 *전체* 의 의미가 분산 보장에 의존하므로 본 모듈은 진입 시점에 한 번 `is_redis_connected()` 를 명시 체크하는 안전 장치를 둔다 (§5.3).

## 3. 의미론 변화 분석 — "메모리 폴백" 이 무엇인지

> 본인이 이해하기 어려웠던 부분. 이 섹션 단독으로 읽어도 이해되도록 풀어 설명한다.

### 3.1 시나리오 비유

큰 도서관에 책 한 권이 있고, 동시에 여러 사람이 빌리려 한다고 가정하자.

- **Redis = 도서관 카운터의 공식 대출 장부** — 모든 사람이 같은 장부를 보고, "이 책 누가 빌렸는지" 한 곳에서 확인.
- **Memory = 각자 손에 들고 있는 메모지** — 자기만 보는 메모. 다른 사람의 메모와는 무관.

dedup 의 의미는 "공식 장부에 내 이름을 적자(SETNX) → 다른 사람은 못 적음 → 내가 끝낼 때까지 다른 사람은 대기" 다.

만약 카운터(=Redis) 가 갑자기 닫혀서 쓸 수 없게 됐다면?
- (가) "각자 메모지에 적자" 로 규칙을 바꾸면 → A 도 자기 메모에 적고, B 도 자기 메모에 적음 → **둘 다 동시에 빌리려 함** = dedup 깨짐.
- (나) "카운터 닫혔으니 빌리기 못 함" 으로 명시 거부 → 적어도 잘못된 결과는 안 남음 = 안전.

→ NX 명령의 메모리 폴백 차단은 (나) 의 정책이다. v2.0.0 의 `setnx` 가 `RedisUnavailableError` 를 raise 하는 이유.

### 3.2 일반 `get` 의 폴백은 다른 문제

같은 도서관 비유에서 "이 책 지금 누가 빌렸나" 를 *조회만* 하는 행위는?

- 카운터 닫혀있을 때 (가) 의 "각자 메모 보기" 로 폴백 — A 의 메모엔 빌린 사람 없음 → "비어있음" 답함.
- 실제론 다른 인스턴스 B 가 진짜 Redis 에 standby 키를 박아둔 상태. 하지만 A 는 그걸 모름 → "standby 사라졌다" 로 잘못 판정 → 작업 시작.

→ 이게 본 마이그레이션의 미묘한 의미론 변화. 옛날엔 raw `client.get()` 이라 Redis 다운 시 connection error 로 깨졌는데, 새 `handler.get()` 은 메모리 폴백으로 *조용히* 잘못된 답을 내놓을 수 있다.

### 3.3 시나리오 비교 표

| 시나리오 | 옛 raw client | 새 RedisHandler |
|---|---|---|
| Redis 정상 가동 — 정상 흐름 | ✅ 정상 | ✅ 정상 (동일) |
| Redis 처음부터 미연결 (init 실패) | `get_client() == None` → `RuntimeError` | `setnx` → `RedisUnavailableError` → `RuntimeError` (변환). `is_redis_connected() == False` → `RuntimeError` (wait 진입 시) |
| **dedup 진행 중 Redis 단절** (드문 상황) | `client.get/delete` 호출 중 connection error → 예외 전파 → 호출자 실패 처리 | **`handler.get` 메모리 폴백 → 빈 dict → "standby 없음" 잘못 판정 → 호출자 작업 시작 → 중복 작업 가능** |

### 3.4 보호 유지 결정 — 하이브리드 마이그레이션

이 트레이드오프는 **수용하지 않는다**. 옛 raw client 의 "단절 시 즉시 예외" 동작을 의도적으로 유지한다.

**근거**:
- 빈도: dedup 진행 중 Redis 단절은 드물지만 0 은 아니다 (HA 페일오버, 네트워크 글리치, 컨테이너 재시작 등).
- silent dedup bypass 는 디버깅이 어렵다 — 로그에 명확한 신호 없이 중복 작업이 일어나서 "왜 같은 파일을 두 번 업로드했지?" 같은 추적이 어려움.
- 옛 raw 동작은 "단절이면 명확히 실패" 라 운영자에게 즉각적인 신호를 줌.

**채택 방법 — 하이브리드**:
- `setnx` (NX 명령): handler API 사용. 폴백 차단이 명시적이라 옛 raw 와 동등 보호 (§5.1).
- `wait_for_standby_release.get`: **raw `get_client()` 유지**. handler 의 메모리 폴백을 의도적으로 우회. 단절 시 ConnectionError → 호출자에 명확 전파 (§5.1).
- `delete` (release): handler API 사용. 폴백되어도 영향 미미 (이미 try/except 로 삼킴, TTL 자연 정리).

→ raw 클라이언트 사용은 "wait 의 get 한 곳" 으로 축소 (옛 3 곳 → 새 1 곳). 추상화 일관성 손해는 미미하지만 분산 의미론 보호는 옛날과 동등.

**한 가지 미해결 한계**:
v2.0.0 의 `is_redis_connected()` 가 runtime 단절을 자동 감지하지 않음 (`init_redis()` / `close_redis()` 시점에만 갱신). 즉 wait 진입 시 `is_redis_connected()` 만 봐도 mid-flight 단절은 못 잡는다. 그래서 **raw client.get 의 ConnectionError 전파**가 유일한 실시간 감지 수단이다.

향후 redis-handler 가 `RedisHandler.get(strict=True)` 같은 폴백 차단 옵션을 제공하면 이 raw 사용도 정리 가능 (§9 추후 정리).

## 4. 전체 파이프라인

dedup 호출 흐름 (변경 전후 동일, 내부 구현만 교체).

```
호출자 (logic/runner.py 등)
    │
    ├─ try_acquire_standby(prefix, key, ttl) ──┐
    │                                            │
    │  ┌─ True ─────────────── 자기가 선점 ──→ 작업 진행
    │  │
    │  └─ False ─→ wait_for_standby_release(...)
    │              │
    │              ├─ HIT (find_cache_fn)  → 즉시 반환
    │              ├─ standby 사라짐         → None (호출자 작업 시작)
    │              └─ timeout                → None (Y' Hybrid, 호출자 작업 시작)
    │
    └─ finally: release_standby(prefix, key)

내부 — 변경 전:                   내부 — 변경 후:
  redis_handler.get_client()        redis_handler.RedisHandler() (싱글톤)
  client.set(nx=True, ex=ttl)       handler.setnx(key, value, ttl=ttl)
  client.get(key)                   handler.get(key)
  client.delete(key)                handler.delete(key)
                                    + setnx 시 RedisUnavailableError 변환
                                    + wait 진입 시 is_redis_connected() 체크
```

#### `try_acquire_standby` (line 54-77)

`RedisHandler.setnx` 직접 호출 + `RedisUnavailableError` → `RuntimeError` 변환으로 기존 호출자 인터페이스(`RuntimeError`) 보존.

```python
async def try_acquire_standby(
    prefix: str,
    key: str,
    ttl_seconds: int,
) -> bool:
    """Redis SETNX 로 standby 선점 시도.

    Returns:
        True  — 자기가 선점 (작업 시작)
        False — 다른 요청이 이미 작업 중 (호출자는 wait_for_standby_release)

    Raises:
        RuntimeError: Redis 미연결 (RedisHandler 가 RedisUnavailableError raise).
    """
    standby_key = _make_standby_key(prefix, key)
    value = json.dumps({"started_at": datetime.now(UTC).isoformat()})
    try:
        return await asyncio.to_thread(
            RedisHandler().setnx, standby_key, value, ttl=ttl_seconds,
        )
    except RedisUnavailableError as e:
        raise RuntimeError("Redis 미연결 — standby 불가") from e
```

#### `wait_for_standby_release` (line 80-137) — **raw `get_client()` 의도적 유지** (§3.4)

handler.get 은 단절 시 메모리 폴백이라 dedup 의 "엄격" 의미론에 부적합. raw 클라이언트의 ConnectionError 전파 동작을 그대로 유지한다.

```python
async def wait_for_standby_release(
    prefix: str,
    key: str,
    timeout: int,
    find_cache_fn: Callable[[], Any] | None = None,
) -> dict | None:
    """standby 사라질 때까지 exponential backoff 대기.

    엄격 의미론 채택 (§3.4): raw client.get 사용. Redis 단절 시 ConnectionError
    전파로 silent dedup bypass 차단. RedisHandler.get 의 메모리 폴백 우회.
    redis-handler 가 strict 옵션을 제공하면 그때 마이그레이션 (§9 추후 정리).
    """
    client = get_client()
    if client is None:
        raise RuntimeError("Redis 미연결 — standby 불가")

    standby_key = _make_standby_key(prefix, key)
    delay = _BACKOFF_INITIAL
    elapsed = 0.0

    while elapsed < timeout:
        await asyncio.sleep(delay)
        elapsed += delay

        if find_cache_fn is not None:
            result = find_cache_fn()
            if inspect.isawaitable(result):
                result = await result
            if result:
                return result

        # raw client.get — 단절 시 ConnectionError raise (handler 폴백 차단 의도)
        if await asyncio.to_thread(client.get, standby_key) is None:
            return None

        delay = min(delay * _BACKOFF_MULTIPLIER, _BACKOFF_CAP)

    logger.warning(
        "standby 대기 timeout(%d초) 초과 — 호출자가 작업 시작. "
        "standby_key=%s, 중복 발생 가능. 빈도 높으면 standby_ttl_seconds 늘리세요.",
        timeout, standby_key,
    )
    return None
```

#### `release_standby` (line 140-156)

```python
async def release_standby(prefix: str, key: str) -> None:
    """standby DEL. finally 블록용.

    Redis 미연결/장애 시 예외는 삼킴 — 호출자 흐름 방해 방지.
    남은 standby는 TTL로 자연 정리됨.
    """
    try:
        standby_key = _make_standby_key(prefix, key)
        await asyncio.to_thread(RedisHandler().delete, standby_key)
    except Exception:
        logger.exception(
            "standby release 실패 (무시, TTL로 자연 정리): prefix=%s, key=%s",
            prefix, key[:16] if key else "",
        )
```

### 5.2 `service/tests/logic/conftest.py` — 픽스처 재작성

dedup 가 **raw client (wait 함수) + RedisHandler (setnx/delete)** 두 가지를 사용하므로 픽스처도 둘 다 다뤄야 한다.

#### Fake 클래스 — 단일 backing store 공유

raw 클라이언트와 RedisHandler 가 **같은 데이터를 보아야** 테스트가 정확하다 (예: setnx 로 박은 키를 get 으로 조회). 두 fake 가 같은 `dict` 를 공유하도록 설계.

```python
class _SharedStore:
    """raw client mock 과 handler mock 이 공유하는 in-memory 저장소."""

    def __init__(self) -> None:
        self.data: dict[str, str] = {}


class FakeRawClient:
    """raw redis-py client 의 .get / .delete 만 흉내내는 fake.

    dedup.wait_for_standby_release 가 raw `get_client()` 로 호출하는 메서드만 커버.
    """

    def __init__(self, store: _SharedStore) -> None:
        self._store = store

    def get(self, key: str) -> str | None:
        return self._store.data.get(key)

    def delete(self, *keys: str) -> int:
        count = 0
        for k in keys:
            if k in self._store.data:
                del self._store.data[k]
                count += 1
        return count


class FakeRedisHandler:
    """RedisHandler 의 setnx/delete 만 흉내내는 fake.

    dedup.try_acquire_standby / release_standby 가 호출하는 메서드만 커버.
    분산 의미론 시뮬레이션 위해 메모리 폴백 동작 안 함 — 항상 Redis 가용 상태.
    """

    def __init__(self, store: _SharedStore) -> None:
        self._store = store

    def setnx(self, key: str, value: str, *, ttl: int | None = None) -> bool:
        if key in self._store.data:
            return False
        self._store.data[key] = value
        return True

    def delete(self, key: str) -> int:
        return 1 if self._store.data.pop(key, None) is not None else 0
```

## 6. 에러 처리

### 6.1 예외 매핑

| 호출 | 발생 가능 예외 | 처리 |
|---|---|---|
| `RedisHandler().setnx(...)` | `RedisUnavailableError` (Redis 미연결) | `try_acquire_standby` 가 `RuntimeError("Redis 미연결 — standby 불가")` 로 변환. 기존 호출자 인터페이스 유지 |
| `RedisHandler().setnx(...)` | `RedisRetryExhausted` (재시도 소진) | 별도 처리 안 함 — 호출자에게 전파. 매우 드문 케이스 (Redis 일시 장애 + 재시도 한도 초과) |
| `RedisHandler().get(...)` | (대부분 폴백) | wait 루프 진입 시점의 `is_redis_connected()` 체크로 1차 방어. 진행 중 단절은 §3.4 수용 |
| `RedisHandler().delete(...)` | `Exception` 광범위 | `release_standby` 가 `try/except Exception` 으로 삼킴. TTL 자연 정리 의존 |

### 6.2 호출자 영향

dedup 함수들의 **외부 인터페이스** (시그니처, raise 하는 예외 타입) 는 변경 없음. 호출 코드는 수정 불필요.

- `try_acquire_standby` 가 raise 하는 `RuntimeError` — 동일.
- `wait_for_standby_release` 가 raise 하는 `RuntimeError` — 동일 (진입 시점 체크에서만, 더 빠름).
- `release_standby` 는 예외 안 raise — 동일.

### 6.3 운영 시나리오별 동작

| 운영 상황 | 동작 |
|---|---|
| Redis 정상 | 변경 없음 (동일 동작) |
| Redis 처음부터 미연결 | `try_acquire_standby` 즉시 `RuntimeError`. `wait_for_standby_release` 즉시 `RuntimeError`. dedup 비활성 — 호출자가 직접 작업 진행 (Y' Hybrid) |
| dedup 진행 중 Redis 단절 | §3.4 분석대로 메모리 폴백 → 잘못된 standby 판정 가능 → 중복 작업 가능. 빈도 낮고 영향 미미 |

## 8. 사용 예시

### 8.1 호출자 코드 — 변경 없음

dedup 호출 패턴은 그대로:

```python
# logic/runner.py 등 호출자
from app.logic.file_processing import dedup

acquired = await dedup.try_acquire_standby("files_api", checksum, ttl_seconds=600)
if acquired:
    try:
        # 본 작업 (예: Files API 업로드)
        result = await upload_to_files_api(...)
    finally:
        await dedup.release_standby("files_api", checksum)
else:
    # 다른 요청이 이미 작업 중 — 대기
    cached = await dedup.wait_for_standby_release(
        "files_api", checksum,
        timeout=600,
        find_cache_fn=lambda: load_cache(checksum),
    )
    if cached:
        return cached
    # standby 풀림 + 캐시 미스 → 직접 작업
```
